# ADR-002 — PostgreSQL, неизменяемость и миграции

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Нужны транзакционные переходы, неизменяемая история выпусков и доказательств, аудит и очередь (спецификация §3, I03, I15, I19). Правила каталога: `pg`-Pool без ORM, миграции — пронумерованные SQL-файлы в `docs/migrations/`.

## Решение

1. **СУБД:** PostgreSQL не ниже 16. На машине разработки — 18.3; версия на целевом ПК фиксируется на этапе 17 (U-03). Функции только из PostgreSQL 16: `gen_random_uuid()`, частичные уникальные индексы, `FOR UPDATE SKIP LOCKED`, `jsonb`, полнотекстовый поиск с конфигурацией `russian`. Специфика PostgreSQL 18 (например, `uuidv7()`) не используется.

**Расширения (D-015, этап 05).** Список закрыт: `pg_trgm` (поставляется с СУБД) и `vector` версии не ниже 0.8. Оба ставятся при развёртывании (ADR-011), `CREATE EXTENSION` выполняет административное подключение в `packages/db/src/setup.ts`, а миграция только проверяет наличие и падает с внятной причиной. `server` и `worker` не стартуют без расширения так же, как при несовпадении версии схемы. В таблицах классов `immutable` и `append-only` расширения не используются.

**Локаль базы (D-015, этап 05).** База создаётся с `LOCALE_PROVIDER = builtin`, `BUILTIN_LOCALE = 'C.UTF-8'`, `ENCODING 'UTF8'`. Причина: при libc-локали `C` приведение регистра кириллицы не выполняется — `lower('ДОГОВОР')` возвращает исходную строку, а `to_tsvector('russian','Договор')` не равен `to_tsvector('russian','договор')`. До этапа 05 это ни на что не влияло, потому что регистр приводится в JavaScript; русский полнотекстовый поиск сломался бы тихо. Кластер разработки пересоздавать не требуется — локаль задаётся при создании базы. Требование к кластеру целевого ПК проверяется на этапе 17.
2. **Схема** — по `docs/architecture/data-model.md`. Каждая таблица относится к классу `immutable`, `append-only`, `frozen-after`, `mutable` или `derived`.
3. **Неизменяемость — две линии:**
   - роль приложения `kontur_app` не получает `UPDATE`/`DELETE` на таблицы классов `immutable` и `append-only`;
   - триггер `forbid_mutation` запрещает изменение таких строк; для `frozen-after` триггер разрешает изменение только до замораживающего состояния.
   Администратор ОС или владелец БД может обойти обе линии; это ограничение явно (I19).
4. **Роли БД:**

| Роль | Права |
|---|---|
| `kontur_migrator` | DDL; только команда миграций |
| `kontur_app` | DML по классам изменяемости; без DDL |
| `kontur_backup` | чтение для `pg_dump` |

5. **Миграции:** файлы `docs/migrations/NNNN_описание.sql`, только вперёд. Раннер в `packages/db` применяет каждый файл в транзакции и пишет в `schema_migration` номер, имя, SHA-256 файла и время. Изменённый уже применённый файл — ошибка запуска. Отката миграций в production нет; откат — восстановление из резервной копии (ADR-011).
6. **Запуск миграций:** в разработке и тестах — автоматически при старте тестовой БД; в production — отдельной командой `migrate` перед стартом служб. `server` и `worker` при несовпадении версии схемы не стартуют и сообщают причину.
7. **Тестовая БД:** отдельный кластер или база, имя содержит `test`; раннер отказывается мигрировать в тестовом режиме базу без `test` в имени.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| ORM с автогенерацией миграций | противоречит правилам каталога; скрывает SQL-ограничения, на которых держатся инварианты |
| Row-Level Security как основной механизм изоляции | сложность с пулом соединений и `SET LOCAL` при одной роли приложения; изоляция обеспечивается слоем данных (ADR-006), RLS не вводится в первой версии |
| Down-миграции в production | риск потери данных; для прод-отката надёжнее резервная копия |
| Отдельная графовая БД для связей требований | спецификация допускает реляционное хранение связей (§3) |

## Последствия

- Инварианты неизменяемости проверяются интеграционными тестами: попытка `UPDATE` выпуска ролью приложения отклоняется.
- Любая правка «задним числом» реализуется новой строкой (ревизией, событием), а не изменением старой.
- Сопровождение триггеров — часть каждой миграции, создающей таблицу.

## Проверка

Этап 02: миграция пустой БД, повторный запуск без изменений, отказ при изменённом файле миграции, отказ `UPDATE` неизменяемой таблицы.
