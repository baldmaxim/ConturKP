# ADR-004 — Долговечная очередь заданий в PostgreSQL

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Импорт, распознавание, выгрузки TenderHub, синхронизация почты, проверки, генерация файлов и размещение выполняются в фоне. Задания не должны теряться при перезапуске, повторы не должны создавать дубли, параллельные GPU-задачи ограничены (спецификация §12, I14, A15).

## Решение

1. **Очередь — таблица `job` в той же БД.** Постановка задания происходит в транзакции доменной команды: доменная запись и задание фиксируются вместе или не фиксируются вовсе.
2. **Захват:** `SELECT … FOR UPDATE SKIP LOCKED` с условием `status = 'queued' AND run_after <= now()`, затем `status = 'running'`, новый случайный `lease_token`, `locked_by`, `locked_until = now() + lease`, `attempts + 1`.
3. **Аренда и восстановление:** worker продлевает `locked_until` (heartbeat). Recovery-проход возвращает в `queued` задания с истёкшей арендой и обнуляет `lease_token` — так восстанавливаются задания после падения процесса.
3a. **Ограждение по токену аренды (R01-06).** Heartbeat, успех, ошибка, повтор и подтверждение отмены — условные обновления `WHERE id = $1 AND lease_token = $2 AND status = 'running'`. Доменный результат пишется в той же транзакции, которая под блокировкой задания проверяет токен. Обработчик, получивший 0 строк, потерял аренду: он прекращает работу и ничего не записывает. Протокол — `docs/architecture/state-machines.md` §2.
4. **Повторы:** экспоненциальная задержка с ограничением; `max_attempts` по виду задания. Ошибки классифицируются как повторяемые и неповторяемые; текст ошибки без секретов.
5. **Дедупликация:** частичный уникальный индекс на `dedupe_key` для незавершённых статусов. Формат ключей описан в `docs/architecture/state-machines.md`.
6. **Идемпотентность обработчиков:** токен аренды не отменяет уже начатый внешний запрос. Поэтому каждое внешнее действие имеет собственный ключ идемпотентности или естественную уникальность, а новая попытка после перехвата сначала сверяет внешнее состояние (A29). Проверка «результата ещё нет» перед действием — не защита от двух обработчиков: защита — условная запись по токену.
7. **Классы ресурсов:** `default`, `network`, `gpu`. Лимит `gpu` = 1 одновременно в портале через `resource_slot('gpu')`, захватываемый тем же токеном аренды, что и задание. Обработчик, потерявший аренду, прерывает вызов модели и освобождает исполнитель. Новый захват слота — только после `locked_until + gpu_takeover_grace`, где защитный интервал больше максимального шага GPU-задания. Чужие процессы (LM Studio, агент MailHub) портал не контролирует; конкуренция за GPU — U-05.
7a. **Приоритет интерактивной работы (этап 05, AR05-07).** Захват уже идёт в порядке `priority DESC, run_after, created_at`; значения закрепляются так:

| Вид задания | Класс | `priority` | Вид появился на этапе |
|---|---|---|---|
| `search.semantic` — смысловая ветка прогона поиска | `gpu` | 100 | 05 |
| ответ ответного ядра | `gpu` | 90 | 08a |
| импорт, разбор, приём распознавания, сканы каналов | `default` / `network` | 50 | 03–04 |
| `index.build` — пачка чанков и полнотекстового индекса версии | `default` | 10 | 05 |
| `index.embed` — пачка векторов версии | `gpu` | 10 | 05 |
| `local_ocr` — распознавание вне охвата RDWeb | `default` | 5 | 05a |
| `index.purge` — удаление данных выведенной версии индекса | `default` | 0 | 05 |

   Значения выставляет код этапа 05 при постановке; до него все задания ставились с приоритетом 0.

   - **Не более одной незавершённой пачки каждого вида на версию индекса:** `dedupe_key = index-build:<search_index_version_id>` и `index-embed:<search_index_version_id>`; существующий частичный уникальный индекс по `dedupe_key` для незавершённых статусов делает второе задание того же вида невозможным. Следующая пачка ставится с тем же низким приоритетом в той же транзакции, которая фиксирует результат предыдущей, — очередь никогда не содержит сотен пачек, обгоняющих интерактивный запрос.
   - **Размер пачки ограничен временем:** шаг `index.embed` не должен держать слот `gpu` дольше `index_embed_budget` (цель — 2 с на целевом ПК, значение в настройке); шаг `index.build` так же ограничен числом страниц, чтобы не занимать фоновую полосу надолго. Так ожидание интерактивного запроса за чужой пачкой ограничено одним шагом.
   - **Интерактивная полоса worker.** Worker выполняет задания последовательно, поэтому одного приоритета мало: смысловой запрос ждал бы окончания любого долгого задания — импорта большого архива или распознавания. С этапа 05 процесс worker ведёт две полосы захвата с одним и тем же протоколом аренды: фоновую (все виды заданий) и интерактивную (только `search.semantic`, с этапа 08a — ответ). Обе полосы подчиняются `resource_slot('gpu')`, поэтому интерактивная ждёт только текущую пачку `index.embed`, а не импорт.
   - **Срок интерактивного запроса.** Прогон поиска, чья смысловая ветка не завершилась к `deadline_at`, терминализуется как `degraded` с причиной `semantic_timeout` (`state-machines.md` §21); задание получает `cancel_requested`. Голодание превращается в явную деградацию, а не в бесконечное ожидание.
7b. **Локальное распознавание (D-014, этап 05a; уточнено ревью 05-pre-1, AR05-08).** Отдельного класса `ocr` нет. Извлечение текстового слоя PDF, `.docx`, `.xlsx`, `.csv` — класс `default`. Распознавание сканов движком на CPU (как в Locus: Tesseract) — тоже `default`, с приоритетом 5 из таблицы 7a, чтобы не обгонять импорт; между страницами обработчик шлёт heartbeat и проверяет отмену, а прогон терминализуется одной транзакцией по протоколу этапа 04. Если на этапе 05a выбран движок на GPU, он использует класс `gpu` и слот `resource_slot('gpu')` по существующему протоколу. Если замеры 05a покажут, что CPU-распознавание вытесняет импорт из фоновой полосы, вводится отдельный слот поправкой к этому ADR и только с полной семантикой `resource_slot`: захват тем же `lease_token`, защитный интервал перехвата, порядок блокировок `resource_slot` → `job`, условные записи. Имя класса без такого протокола не допускается.
8. **Отмена:** `queued` отменяется сразу; для `running` команда ставит `cancel_requested`. Действующий обработчик видит флаг при heartbeat и подтверждает отмену условной записью; устаревший обработчик подтвердить не может; новый владелец видит флаг при захвате и завершает задание как `cancelled`.
9. **Наблюдаемость:** состояние задания видно в статусе объекта, к которому оно относится (распознавание, размещение и т. д.), и на экране состояния интеграций.

## Реализация (этап 03)

- `packages/db/src/jobs.ts` — постановка (`ON CONFLICT` по частичному уникальному индексу `dedupe_key`), захват (`FOR UPDATE SKIP LOCKED`, новый `lease_token`, для `gpu` — слот `resource_slot` тем же токеном после защитного интервала), heartbeat, условные успех/ошибка/отмена, recovery-проход.
- `apps/worker/src/runtime.ts` — цикл worker: heartbeat каждые `lease/3`, потеря аренды или флаг отмены останавливают обработчик; доменный результат и `succeeded` пишутся в одной транзакции после блокировки задания с проверкой токена (`complete`).
- Повторы: задержка `2 с · 2^(attempts−1)`, не больше 10 мин; неизвестная ошибка считается повторяемой (`internal`); исчерпание попыток — `failed`.
- Виды заданий этапа 03: `import.expand`, `import.register`, `intake.scan`; сканы планирует сам worker по `scan_interval_seconds` активных каналов.
- **Терминальная ошибка** (попытки исчерпаны или ошибка неповторяемая): доменный отказ обработчика (`onTerminalFailure`) и перевод задания в `failed` пишутся в одной транзакции после блокировки задания с проверкой аренды. Если эта транзакция не удалась, задание **не** объявляется `failed`: оно возвращается в очередь с задержкой и кодом `terminal_fixation_failed` (R03-05). Правило: обе записи или ни одной; несогласованного состояния «задание failed, партия running» быть не может, ценой видимого незавершённого задания.
- **GPU и аренда — формальный порядок блокировок: `resource_slot` → `job`.** Любой переход, затрагивающий обе строки, берёт их только в этом порядке; обратный порядок давал цикл ожидания между heartbeat и доменной транзакцией (R03-10). Порядок соблюдают: захват (`claimJob`), продление (`heartbeatJob`), блокировка перед доменной записью (`lockOwnedJob`, `withLease`, `complete`), успех, отмена, ошибка с повтором, терминальная ошибка и возврат в очередь (`succeedJob`, `confirmCancel`, `failJob`, `requeueJob`) — освобождение слота и перевод задания выполняются в одной короткой транзакции после блокировки и проверки `resource_slot` → `job`; ни одна запись не выполняется до подтверждения владения обеими строками (N03-01 ревью 03-5).
- **Владение подтверждается до любой записи (R03-13).** Успех, отмена, ошибка с повтором, терминальная ошибка и возврат в очередь выполняются короткой транзакцией: сначала блокируется и проверяется слот (для `gpu`), затем задание (`id`, `lease_token`, `status = 'running'`), и только после обеих проверок пишутся изменения — сперва освобождение слота, затем перевод задания. Если любая проверка не прошла, не меняются ни слот, ни задание: устаревший обработчик не может освободить слот и тем обойти защитный интервал перехвата. Изменяющие CTE, которые трогали слот до подтверждения владения заданием, не используются.
- **Продление аренды — «обе или ни одной» (R03-11).** Heartbeat выполняется короткой транзакцией: блокировка и проверка слота, затем блокировка и проверка задания, и только после этого обе аренды получают один и тот же новый срок. Если задание уже не принадлежит этому токену, слот не меняется; если слот уже чужой, не меняется задание. После первой подтверждённой потери аренды worker прекращает слать heartbeat этого задания, даже если обработчик ещё не завершился по сигналу отмены.

## Реализация (этап 05)

- Приоритет по умолчанию `enqueueJob` — 50 (`DEFAULT_JOB_PRIORITY`): импорт, разбор, приём распознавания и сканы каналов стоят выше пачек индексации (10) и удаления (0), ниже смыслового запроса (100) — таблица §7a.
- Интерактивная полоса: `WorkerRuntime.loop` запускает рядом с фоновым циклом `laneLoop` с видами `INTERACTIVE_KINDS` (`search.semantic`); обе полосы — тот же `claimJob` с тем же протоколом аренды и слота `gpu`.
- `IJobContext.complete(fn, then)`: `then` выполняется в той же транзакции после перевода задания в `succeeded`; так пачка индексации ставит следующую пачку того же вида без конфликта частичного уникального индекса `dedupe_key` с самой собой.
- Проход обслуживания поиска (`apps/worker/src/maintenance.ts`, раз в `maintenanceIntervalMs` = 5 с): просроченные прогоны поиска, проверка модели, версии индекса, постановка пачек, активация, удаление выведенных версий. Он же страхует от потерянной постановки: следующая итерация восстанавливает ход индексации без внешнего события.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| pg-boss / graphile-worker | рабочие варианты на PostgreSQL, но добавляют зависимость и собственную схему; транзакционная постановка вместе с доменной записью требует дополнительной проверки их API. Можно пересмотреть на этапе 03 по актуальной документации без изменения доменной модели |
| Redis + BullMQ | отдельный сервис на Windows; очередь вне транзакции домена |
| Выполнение в процессе HTTP-сервера | задания теряются при перезапуске; блокирует ответы |

## Последствия

- Одна точка резервного копирования: очередь в дампе БД.
- Нагрузка очереди на PostgreSQL мала для двух инженеров.
- Нужны тесты на гонку захвата, истечение аренды и повтор после неизвестного исхода.

## Проверка

Этап 03: перезапуск worker во время задания, два worker на одном задании, повтор с тем же `dedupe_key`, ограничение `gpu`, возобновление приостановленного обработчика после перехвата задания (условные записи возвращают 0 строк, доменный результат не пишется), отмена во время перехвата. Бумажный сценарий — `docs/architecture/walkthroughs.md` §10.

Этап 05: при очереди из пачки `index.embed` и смыслового запроса следующим захватывается запрос; вторую незавершённую пачку того же вида одной версии поставить нельзя; интерактивная полоса захватывает запрос, пока фоновая выполняет долгое задание класса `default`; просроченный прогон поиска терминализуется `degraded`, а позднее завершение задания его не перезаписывает.
