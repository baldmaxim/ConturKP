# ADR-004 — Долговечная очередь заданий в PostgreSQL

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Импорт, распознавание, выгрузки TenderHub, синхронизация почты, проверки, генерация файлов и размещение выполняются в фоне. Задания не должны теряться при перезапуске, повторы не должны создавать дубли, параллельные GPU-задачи ограничены (спецификация §12, I14, A15).

## Решение

1. **Очередь — таблица `job` в той же БД.** Постановка задания происходит в транзакции доменной команды: доменная запись и задание фиксируются вместе или не фиксируются вовсе.
2. **Захват:** `SELECT … FOR UPDATE SKIP LOCKED` с условием `status = 'queued' AND run_after <= now()`, затем `status = 'running'`, новый случайный `lease_token`, `locked_by`, `locked_until = now() + lease`, `attempts + 1`.
3. **Аренда и восстановление:** worker продлевает `locked_until` (heartbeat). Recovery-проход возвращает в `queued` задания с истёкшей арендой и обнуляет `lease_token` — так восстанавливаются задания после падения процесса.
3a. **Ограждение по токену аренды (R01-06).** Heartbeat, успех, ошибка, повтор и подтверждение отмены — условные обновления `WHERE id = $1 AND lease_token = $2 AND status = 'running'`. Доменный результат пишется в той же транзакции, которая под блокировкой задания проверяет токен. Обработчик, получивший 0 строк, потерял аренду: он прекращает работу и ничего не записывает. Протокол — `docs/architecture/state-machines.md` §2.
4. **Повторы:** экспоненциальная задержка с ограничением; `max_attempts` по виду задания. Ошибки классифицируются как повторяемые и неповторяемые; текст ошибки без секретов.
5. **Дедупликация:** частичный уникальный индекс на `dedupe_key` для незавершённых статусов. Формат ключей описан в `docs/architecture/state-machines.md`.
6. **Идемпотентность обработчиков:** токен аренды не отменяет уже начатый внешний запрос. Поэтому каждое внешнее действие имеет собственный ключ идемпотентности или естественную уникальность, а новая попытка после перехвата сначала сверяет внешнее состояние (A29). Проверка «результата ещё нет» перед действием — не защита от двух обработчиков: защита — условная запись по токену.
7. **Классы ресурсов:** `default`, `network`, `gpu`. Лимит `gpu` = 1 одновременно в портале через `resource_slot('gpu')`, захватываемый тем же токеном аренды, что и задание. Обработчик, потерявший аренду, прерывает вызов модели и освобождает исполнитель. Новый захват слота — только после `locked_until + gpu_takeover_grace`, где защитный интервал больше максимального шага GPU-задания. Чужие процессы (LM Studio, агент MailHub) портал не контролирует; конкуренция за GPU — U-05.
8. **Отмена:** `queued` отменяется сразу; для `running` команда ставит `cancel_requested`. Действующий обработчик видит флаг при heartbeat и подтверждает отмену условной записью; устаревший обработчик подтвердить не может; новый владелец видит флаг при захвате и завершает задание как `cancelled`.
9. **Наблюдаемость:** состояние задания видно в статусе объекта, к которому оно относится (распознавание, размещение и т. д.), и на экране состояния интеграций.

## Реализация (этап 03)

- `packages/db/src/jobs.ts` — постановка (`ON CONFLICT` по частичному уникальному индексу `dedupe_key`), захват (`FOR UPDATE SKIP LOCKED`, новый `lease_token`, для `gpu` — слот `resource_slot` тем же токеном после защитного интервала), heartbeat, условные успех/ошибка/отмена, recovery-проход.
- `apps/worker/src/runtime.ts` — цикл worker: heartbeat каждые `lease/3`, потеря аренды или флаг отмены останавливают обработчик; доменный результат и `succeeded` пишутся в одной транзакции после блокировки задания с проверкой токена (`complete`).
- Повторы: задержка `2 с · 2^(attempts−1)`, не больше 10 мин; неизвестная ошибка считается повторяемой (`internal`); исчерпание попыток — `failed`.
- Виды заданий этапа 03: `import.expand`, `import.register`, `intake.scan`; сканы планирует сам worker по `scan_interval_seconds` активных каналов.
- **Терминальная ошибка** (попытки исчерпаны или ошибка неповторяемая): доменный отказ обработчика (`onTerminalFailure`) и перевод задания в `failed` пишутся в одной транзакции после блокировки задания с проверкой аренды. Если эта транзакция не удалась, задание **не** объявляется `failed`: оно возвращается в очередь с задержкой и кодом `terminal_fixation_failed` (R03-05). Правило: обе записи или ни одной; несогласованного состояния «задание failed, партия running» быть не может, ценой видимого незавершённого задания.
- **GPU и аренда — формальный порядок блокировок: `resource_slot` → `job`.** Любой переход, затрагивающий обе строки, берёт их только в этом порядке; обратный порядок давал цикл ожидания между heartbeat и доменной транзакцией (R03-10). Порядок соблюдают: захват (`claimJob`), продление (`heartbeatJob`), блокировка перед доменной записью (`lockOwnedJob`, `withLease`, `complete`), успех, отмена, ошибка с повтором, терминальная ошибка и возврат в очередь (`succeedJob`, `confirmCancel`, `failJob`, `requeueJob`) — освобождение слота и перевод задания выполняются одним оператором, где слот идёт первым.
- **Продление аренды — «обе или ни одной» (R03-11).** Heartbeat выполняется короткой транзакцией: блокировка и проверка слота, затем блокировка и проверка задания, и только после этого обе аренды получают один и тот же новый срок. Если задание уже не принадлежит этому токену, слот не меняется; если слот уже чужой, не меняется задание. После первой подтверждённой потери аренды worker прекращает слать heartbeat этого задания, даже если обработчик ещё не завершился по сигналу отмены.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| pg-boss / graphile-worker | рабочие варианты на PostgreSQL, но добавляют зависимость и собственную схему; транзакционная постановка вместе с доменной записью требует дополнительной проверки их API. Можно пересмотреть на этапе 03 по актуальной документации без изменения доменной модели |
| Redis + BullMQ | отдельный сервис на Windows; очередь вне транзакции домена |
| Выполнение в процессе HTTP-сервера | задания теряются при перезапуске; блокирует ответы |

## Последствия

- Одна точка резервного копирования: очередь в дампе БД.
- Нагрузка очереди на PostgreSQL мала для двух инженеров.
- Нужны тесты на гонку захвата, истечение аренды и повтор после неизвестного исхода.

## Проверка

Этап 03: перезапуск worker во время задания, два worker на одном задании, повтор с тем же `dedupe_key`, ограничение `gpu`, возобновление приостановленного обработчика после перехвата задания (условные записи возвращают 0 строк, доменный результат не пишется), отмена во время перехвата. Бумажный сценарий — `docs/architecture/walkthroughs.md` §10.
