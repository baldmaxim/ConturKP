# ADR-006 — Пользователи, роли, изоляция тендеров и почтовых ящиков

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Пользователи: до двух назначенных инженеров и руководитель; модель не согласует и не выпускает (спецификация §1, I12). Права проверяются сервером, а не только UI или MCP (I13). Нет утечек между тендерами (I05, A12). Доступ к письмам и вложениям ограничен доступными ящиками даже при известном ID (A35). MailHub использует cookie-сессию и AllowedAccounts (`docs/discovery.md` §6). Руководитель будет согласовывать со смартфона (D-004).

## Решение

### Субъекты

| Субъект | `app_user.kind` | Как аутентифицируется | Что может |
|---|---|---|---|
| Инженер | `human` + роль `engineer` | пароль → серверная сессия | работа с назначенными тендерами; выпуск согласованного кандидата |
| Руководитель | `human` + роль `manager` | пароль → серверная сессия | всё по назначенным тендерам; согласование, возврат, решения по удержаниям, принятие бизнес-риска |
| Администратор | `human` + роль `admin` | пароль → серверная сессия | пользователи, доступ к ящикам, назначения, интеграции, настройки. Без членства в тендере не видит его данных и не согласует |
| Модель через MCP | токен `api_token` пользователя | Bearer-токен MCP | чтение в правах пользователя + только предложения (`propose`) |
| Модель внутри портала | `service` / `model` | внутренний вызов worker | создаёт только `model_suggestion` |
| Интеграции | `service` / `integration` | внутренний вызов worker | пишет данные своей интеграции через обработчики заданий, не через публичный API |

### Права — возможности, а не экраны

1. Каждый обработчик команды объявляет требуемую возможность: `tender.read`, `stage.write`, `stage.manage`, `audit.read`, `source.write`, `finding.write`, `candidate.create`, `candidate.approve`, `candidate.release`, `send.register`, `hold.resolve`, `risk.accept`, `admin.*`, `mcp.propose`.
2. Возможность вычисляется сервером из роли, назначения на тендер (`tender_member`) и вида субъекта. Для MCP-токена — пересечение прав пользователя с областями токена (`read`, `propose`).
3. `candidate.approve`, `candidate.release`, `send.register`, `hold.resolve`, `risk.accept` и `finding.accept_risk` доступны только `human`. Сервисная учётная запись модели и MCP-токен их не получают ни при какой конфигурации.
4. **Вторая линия в БД:** триггеры на `approval`, `release`, `risk_acceptance`, `decision`, `send_event` проверяют, что автор — `human` с нужной ролью и назначением на тендер в момент вставки. Области `api_token` ограничены CHECK-ограничением `read`/`propose`.
5. Каждый отказ пишет `audit_event` с `outcome = denied` (A25).

### Изоляция тендеров

6. Весь доступ к данным — через репозитории `packages/db`, которые принимают `AccessContext` (субъект, возможности, список тендеров) и добавляют условие тендера в каждый запрос. Запрос без `AccessContext` не компилируется.
7. Ресурс чужого тендера возвращает `404`, а не `403`: отказ не раскрывает существование, названия и счётчики (A12). Поиск и MCP получают область из `AccessContext` до выполнения запроса (ADR-008).
8. Инженеров на тендере не больше двух: проверка в транзакции назначения с блокировкой строки тендера.

### Изоляция почтовых ящиков

9. `mailbox_access` отражает доступ пользователя к ящикам MailHub. До X-03 доступ ведёт администратор вручную по согласованию владельца; после X-03 — синхронизация с AllowedAccounts плюс ручная корректировка.
10. Письмо видно, если у пользователя есть доступ хотя бы к одному ящику из `communication_occurrence` и, для писем, связанных с тендером, — членство в этом тендере. Вложения, текст, превью и скачивание проверяются так же (A35). Цитаты из писем в поиске фильтруются тем же правилом до ранжирования.

### Сессии и транспорт

11. Пароли — argon2id; библиотека выбирается на этапе 02. Открытой регистрации в LAN нет: первый администратор и руководитель создаются одноразовой командой на сервере.
12. Сессия — случайный токен в cookie `HttpOnly`, `Secure`, `SameSite=Strict`; в БД только хэш. Изменяющие запросы требуют CSRF-токен, связанный с сессией, и проверку `Origin`. Неактивная сессия истекает; абсолютный срок ограничен.
13. Доступ по HTTPS внутри LAN/VPN. Способ выпуска сертификата и сетевое имя — U-02. Без TLS портал запускается только на `127.0.0.1` для разработки.
14. Секреты интеграций (ключ TenderHub, OAuth Яндекс Диска, учётная запись SMB, токены MailHub и LocalAI) — в переменных окружения или хранилище учётных данных Windows, не в БД, не в логах и не в ответах API/MCP (I17). Интерфейс показывает только признак «задано / не задано».

### Смартфон

15. Все проверки выполняются сервером одинаково для десктопа и смартфона. Согласование со смартфона — та же команда `candidate.approve` с тем же диалогом состава (BRAND.md §9.1, ветка `design/brand`).

## Реализация (этап 02)

- Пароли — argon2id встроенным `node:crypto.argon2` (Node ≥ 24.7), параметры OWASP m = 19 МиБ, t = 2, p = 1; формат PHC-строки (соль и ключ — стандартный base64 без `=`) хранит параметры, поэтому замена реализации не требует миграции; совместимость с пакетом `argon2` в обе стороны проверяется тестом (R02-04). API помечен в Node как экспериментальный: ограничение записано в отчёте этапа 02; при изменении API — переход на пакет argon2 без изменения формата.
- Сессия: cookie `kkp_session` (HttpOnly, SameSite=Strict, Secure при TLS); CSRF — cookie `kkp_csrf` (читаемая) + заголовок `X-CSRF-Token`, в сессии хранится SHA-256 токена; для изменяющих запросов обязателен `Origin` из `ALLOWED_ORIGINS`. Неактивность — 720 мин, абсолютный срок — 168 ч по умолчанию.
- Перебор паролей: 5 неудач на логин и 20 на адрес за 15 минут → `429`; счётчики в памяти процесса server.
- Контекст доступа читается из БД на каждый запрос: снятие роли, назначения или отключение пользователя действует сразу. Назначение действует, только пока у пользователя есть та же глобальная роль.
- Администратор без назначения видит карточку тендера и участников (для администрирования), но не этапы и дальнейшее содержимое. Это действует и для производных представлений: из журнала тендера ему выдаются только административные действия с карточкой и участниками (R02-02).
- Права проверяются и перед выдачей сохранённого ответа по `Idempotency-Key`: повтор не обходит отзыв назначения или роли (R02-01).
- Изменения, способные убрать последнего администратора, сериализуются общей транзакционной блокировкой (R02-03).
- Возможности этапа 02: `tender.read` и `stage.write` — участник; `stage.manage` (создание этапов) и `audit.read` — руководитель тендера; `audit.read` также у администратора; `admin.users`, `admin.tender`, `admin.audit` — администратор.

## Реализация (этап 06)

- Новая возможность `calculation.capture` — у участника тендера (инженер и руководитель по назначению): запрос выгрузки расчёта и решения по сопоставлению позиций. Связь этапа с тендером TenderHub меняет `admin.tender` при назначении на тендер. Чтение выгрузок, ревизий, позиций, строк и сопоставлений — `tender.read`; чужой тендер — `404`.
- Ключ TenderHub — только переменная окружения `TENDERHUB_API_KEY` (I17): в БД, журналах, ответах API, сырых ответах и манифесте выгрузки его нет (проверяется тестами и smoke); `config:check` показывает только «задано / не задано».

## Реализация (этап 06a)

Договорной контур — новая ось изоляции рядом с тендером (D-017, D-022, D-023), по образцу `mailbox_access` (§9–10): явная выдача, строки ведёт администратор.

- Возможности договора выдаются строками `contract_access`, а не ролью: `contract.create` — глобально, `contract.read`, `contract.link`, `contract.manage` — по договору. Выдача действует, пока у пользователя есть роль инженера или руководителя, как назначение на тендер: одной системной роли администратора для содержимого мало.
- `admin.contract` — у роли `admin`: видит карточки всех договоров (номер, предмет, статус, автор) и ведёт строки доступа, но содержимого не открывает. Выдать себе чтение он может, только если у него есть и роль инженера или руководителя; выдача видна в журнале.
- Создатель договора получает строки `source = creator`: `contract.read` и `contract.manage` (документы, карточка, архив). Подтверждение связи с тендером — отдельная возможность `contract.link`, только явной выдачей (fail-closed). БД держит это сама: строка создателя — только у автора, только по договору и только чтение или ведение (FK и CHECK, миграция 0013, R06a-01); глобальная `contract.create` — только административной выдачей.
- Невидимый договор — `404`, видимый без нужной возможности — `403`. Без `contract.read` — только административные метаданные: текста, файла, фрагментов, результатов анализа, цитат и поисковой выдачи нет.
- Связь договора с тендером подтверждает пользователь с `contract.link` по договору и `source.write` по тендеру. Связь не даёт доступа ни в одну сторону: участник тендера без выдачи не видит связанный договор, читатель договора не видит тендер без назначения.
- Единица договора в области тендера (состав этапа или снимок) ищется и читается только при `contract.read` (D-022 OD-3): фильтр прав до ранжирования исключает её, выдача показывает лишь число исключённых единиц; права перепроверяются при чтении прогона, цитаты и оригинала.
- Вторая линия в БД: владелец каждой строки цепочки — тендер или договор (CHECK и составные FK, матрица `docs/architecture/06a-ownership-chain.md` §7); охранники прогона поиска и его результатов принимают единицу договора в тендерном прогоне только от связанного договора.

## Реализация (этап 07)

Почтовая ось изоляции (D-025, OD-07-3), по образцу договоров 06a: `mailbox` — контекст доступа, `mail_access` — строка на тройку «ящик, пользователь, возможность» (`mail.read`, `mail.import`, `mail.link`, `mail.manage`); выдача действует только при роли инженера или руководителя (`effectiveMailCapabilities`). Ящики и выдачи ведёт глобальная `admin.mailbox`, содержимого она не открывает: без собственной `mail.read` администратор видит только служебные сведения ящика.

- Письмо, ревизия, тело, адреса, вложения, фрагменты и цитата — только с `mail.read` на ящик письма; невидимое — `404`, известный ID вложения не помогает (A35).
- §10 уточнён решениями D-025: связь письма с тендером доступа к письму не даёт (OD-07-3). В контексте тендера письмо видно при `mail.read`, действующей связи и доступе к тендеру; вне тендера — в контексте ящика по одной `mail.read`. Одна логическая коммуникация в двух ящиках — две копии (`mail_message`), доступ к копии не распространяется на другую (И-07-1).
- Документ вложения наследует права письма: редакция, прогон, фрагменты и байты — только с `mail.read`; команда распознавания — с `mail.import`.
- Журнал: события почты пишутся без темы, тела, адресов и имени файла; события связи — без `tender_id`.
- `AllowedAccounts` MailHub не синхронизируется: машинного доступа нет (X-03), выдачи ведёт администратор ящиков.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Роли только в интерфейсе | нарушает I13 |
| Общий сервисный токен LocalAI или MailHub для всех | нарушает изоляцию ящиков и тендеров (`docs/discovery.md` §6.2) |
| Keycloak/OIDC | лишний сервис для трёх пользователей в LAN; можно добавить позже без изменения модели прав |
| Row-Level Security как единственная защита | см. ADR-002 |

## Последствия

- Интеграционные тесты прав обязательны на этапах 02, 07, 13, 16: подмена роли в запросе, чужой тендер, чужой ящик, модель вызывает approve.
- Администратор не является «суперпользователем данных»: для работы с тендером нужно назначение, и оно видно в аудите.

## Проверка

Этап 02: отказ неаутентифицированному, инженер не получает прав руководителя подменой запроса, чужой тендер недоступен, аудит фиксирует автора. Этапы 13 и 16: A25, A36, A37.

## Связанные требования

I05, I12, I13, I16, I17; A12, A24, A25, A35, A36, A37; F10.
