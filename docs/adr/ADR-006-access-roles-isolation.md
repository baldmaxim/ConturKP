# ADR-006 — Пользователи, роли, изоляция тендеров и почтовых ящиков

Статус: proposed
Дата: 2026-09-17

## Контекст

Пользователи: до двух назначенных инженеров и руководитель; модель не согласует и не выпускает (спецификация §1, I12). Права проверяются сервером, а не только UI или MCP (I13). Нет утечек между тендерами (I05, A12). Доступ к письмам и вложениям ограничен доступными ящиками даже при известном ID (A35). MailHub использует cookie-сессию и AllowedAccounts (`docs/discovery.md` §6). Руководитель будет согласовывать со смартфона (D-004).

## Решение

### Субъекты

| Субъект | `app_user.kind` | Как аутентифицируется | Что может |
|---|---|---|---|
| Инженер | `human` + роль `engineer` | пароль → серверная сессия | работа с назначенными тендерами; выпуск согласованного кандидата |
| Руководитель | `human` + роль `manager` | пароль → серверная сессия | всё по назначенным тендерам; согласование, возврат, решения по удержаниям, принятие бизнес-риска |
| Администратор | `human` + роль `admin` | пароль → серверная сессия | пользователи, доступ к ящикам, назначения, интеграции, настройки. Без членства в тендере не видит его данных и не согласует |
| Модель через MCP | токен `api_token` пользователя | Bearer-токен MCP | чтение в правах пользователя + только предложения (`propose`) |
| Модель внутри портала | `service` / `model` | внутренний вызов worker | создаёт только `model_suggestion` |
| Интеграции | `service` / `integration` | внутренний вызов worker | пишет данные своей интеграции через обработчики заданий, не через публичный API |

### Права — возможности, а не экраны

1. Каждый обработчик команды объявляет требуемую возможность: `tender.read`, `source.write`, `finding.write`, `candidate.create`, `candidate.approve`, `candidate.release`, `send.register`, `hold.resolve`, `risk.accept`, `admin.*`, `mcp.propose`.
2. Возможность вычисляется сервером из роли, назначения на тендер (`tender_member`) и вида субъекта. Для MCP-токена — пересечение прав пользователя с областями токена (`read`, `propose`).
3. `candidate.approve`, `candidate.release`, `send.register`, `hold.resolve`, `risk.accept` и `finding.accept_risk` доступны только `human`. Сервисная учётная запись модели и MCP-токен их не получают ни при какой конфигурации.
4. **Вторая линия в БД:** триггеры на `approval`, `release`, `risk_acceptance`, `decision`, `send_event` проверяют, что автор — `human` с нужной ролью и назначением на тендер в момент вставки. Области `api_token` ограничены CHECK-ограничением `read`/`propose`.
5. Каждый отказ пишет `audit_event` с `outcome = denied` (A25).

### Изоляция тендеров

6. Весь доступ к данным — через репозитории `packages/db`, которые принимают `AccessContext` (субъект, возможности, список тендеров) и добавляют условие тендера в каждый запрос. Запрос без `AccessContext` не компилируется.
7. Ресурс чужого тендера возвращает `404`, а не `403`: отказ не раскрывает существование, названия и счётчики (A12). Поиск и MCP получают область из `AccessContext` до выполнения запроса (ADR-008).
8. Инженеров на тендере не больше двух: проверка в транзакции назначения с блокировкой строки тендера.

### Изоляция почтовых ящиков

9. `mailbox_access` отражает доступ пользователя к ящикам MailHub. До X-03 доступ ведёт администратор вручную по согласованию владельца; после X-03 — синхронизация с AllowedAccounts плюс ручная корректировка.
10. Письмо видно, если у пользователя есть доступ хотя бы к одному ящику из `communication_occurrence` и, для писем, связанных с тендером, — членство в этом тендере. Вложения, текст, превью и скачивание проверяются так же (A35). Цитаты из писем в поиске фильтруются тем же правилом до ранжирования.

### Сессии и транспорт

11. Пароли — argon2id; библиотека выбирается на этапе 02. Открытой регистрации в LAN нет: первый администратор и руководитель создаются одноразовой командой на сервере.
12. Сессия — случайный токен в cookie `HttpOnly`, `Secure`, `SameSite=Strict`; в БД только хэш. Изменяющие запросы требуют CSRF-токен, связанный с сессией, и проверку `Origin`. Неактивная сессия истекает; абсолютный срок ограничен.
13. Доступ по HTTPS внутри LAN/VPN. Способ выпуска сертификата и сетевое имя — U-02. Без TLS портал запускается только на `127.0.0.1` для разработки.
14. Секреты интеграций (ключ TenderHub, OAuth Яндекс Диска, учётная запись SMB, токены MailHub и LocalAI) — в переменных окружения или хранилище учётных данных Windows, не в БД, не в логах и не в ответах API/MCP (I17). Интерфейс показывает только признак «задано / не задано».

### Смартфон

15. Все проверки выполняются сервером одинаково для десктопа и смартфона. Согласование со смартфона — та же команда `candidate.approve` с тем же диалогом состава (BRAND.md §9.1, ветка `design/brand`).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Роли только в интерфейсе | нарушает I13 |
| Общий сервисный токен LocalAI или MailHub для всех | нарушает изоляцию ящиков и тендеров (`docs/discovery.md` §6.2) |
| Keycloak/OIDC | лишний сервис для трёх пользователей в LAN; можно добавить позже без изменения модели прав |
| Row-Level Security как единственная защита | см. ADR-002 |

## Последствия

- Интеграционные тесты прав обязательны на этапах 02, 07, 13, 16: подмена роли в запросе, чужой тендер, чужой ящик, модель вызывает approve.
- Администратор не является «суперпользователем данных»: для работы с тендером нужно назначение, и оно видно в аудите.

## Проверка

Этап 02: отказ неаутентифицированному, инженер не получает прав руководителя подменой запроса, чужой тендер недоступен, аудит фиксирует автора. Этапы 13 и 16: A25, A36, A37.

## Связанные требования

I05, I12, I13, I16, I17; A12, A24, A25, A35, A36, A37; F10.
