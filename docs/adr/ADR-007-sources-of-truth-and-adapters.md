# ADR-007 — Источники истины и адаптеры интеграций

Статус: proposed
Дата: 2026-09-17

## Контекст

Спецификация фиксирует источники истины: TenderHub — расчёт; портал — решения и выпуски; LocalAI и RDWeb — обработка и доказательства; индекс не заменяет журнал (02 §4, спецификация §2–3). Инвентаризация показала разрывы: у TenderHub нет неизменяемого снимка расчёта (X-01), у LocalAI — фильтра по редакциям (X-04), у MailHub — машинного доступа (X-03), у RDWeb подтверждён только формат экспорта (X-05), сервис переговоров не определён (Q-06).

## Решение

### Владение данными

| Данные | Источник истины | Что хранит портал | Правило |
|---|---|---|---|
| Расчёт (позиции, строки, коммерческие стоимости, итог) | TenderHub | неизменяемые `calculation_revision` со сырыми ответами | портал не меняет расчёт и не считает свою смету |
| Оригиналы документов | портал (получение) | `blob` + `document_revision` | оригинал — основа превью и доказательств |
| Распознавание | RDWeb (основное), текстовый слой/локальный OCR (явно помеченный) | неизменяемые `recognition_run` и `evidence_fragment` | новый прогон — новая запись; локальный OCR не выдаётся за RDWeb (A43) |
| Поисковый индекс | LocalAI | состояние индексации `fragment_index_state` | производные данные; удаление индекса не трогает доказательства (A42) |
| Письма | MailHub | копии писем как `communication` + фрагменты | чтение без побочных эффектов |
| Переговоры | сервис переговоров | сессии, редакции транскрипции, сегменты | подсказки отдельно от речи |
| Требования, покрытие, замечания, решения, приложения, кандидаты, согласования, выпуски, размещения, отправки | портал | всё | транзакционные переходы и аудит |

### Адаптеры

1. Каждая интеграция — адаптер в `packages/adapters` с контрактом из `docs/contracts/adapters.md`. Ядро (`packages/core`, `packages/db`) не знает форматов внешних систем: адаптер переводит ответы в доменные объекты.
2. Всё, что взято из внешнего ответа и используется как доказательство или снимок, хранит сырой ответ (`blob`), версию контракта адаптера и время получения.
3. Предположения о внешних API помечаются в контракте как «проект» и изолируются в адаптере. Отсутствие API не меняет ядро: доменная сущность одна, источники её заполнения разные (API, импорт файла, ручной ввод с основанием).
4. Статус каждой интеграции ведётся в `integration_status`: `NOT_IMPLEMENTED`, `VERIFIED_FIXTURE`, `VERIFIED_LIVE`, `BLOCKED_EXTERNAL`. Фикстурный тест не даёт `VERIFIED_LIVE` (state-machines §19).

### TenderHub до и после X-01

5. **До X-01** портал делает `calculation_capture` вида `portal_capture`: чтение `overview`, всех страниц `positions`, `positions/with-costs` без кэша, `boq-items-full`; до и после чтения сверяются `updated_at`, итог и счётчики. Результат — `calculation_revision` вида `provisional`. Выпуск в production-назначения с такой ревизией блокируется (`CALCULATION_PROVISIONAL`, state-machines §11.1); тестовые и пилотные выпуски допускаются с явной пометкой.
6. **После X-01** адаптер получает ревизию по ID TenderHub; ревизия вида `verified`. Доменная модель не меняется.
7. Закрытие расчёта: портал не строит собственный таймер закрытия. `submission_deadline` из TenderHub — сигнал для выгрузки; факт закрытия фиксируется как свойство ревизии из источника (`closed_at_source`), когда TenderHub его отдаст (X-01, Q-01).
8. Связь «этап КП ↔ версия тендера TenderHub» задаётся в `stage_calculation_source` (Q-03). Какая сумма считается итогом КП — правило `tender_stage.kp_total_rule` (Q-05).

### Остальные интеграции

9. **RDWeb:** полноценный импорт экспортного архива (PDF + `_results.md` + `_results.html` + `_blocks.json`, schema_version 1). Автоматическая постановка задач — только после контракта X-05; до этого `BLOCKED_EXTERNAL`.
10. **LocalAI:** индексирует фрагменты портала с ID портала и выполняет поиск с фильтром по разрешённым редакциям до top-k — после X-04. До этого смысловой поиск недоступен и честно помечен (ADR-008).
11. **MailHub:** до X-03 — импорт EML/экспорта на синтетических данных и по разрешению владельца; после X-03 — сервисное чтение по курсору изменений. Вызовы с побочными эффектами (`opened`, `draft`, перемещение) адаптер не использует.
12. **Переговоры:** импорт manifest (JSON или текст + manifest) по схеме из контракта. API — после Q-06.
13. **Яндекс Диск и SMB:** независимые адаптеры размещения с тестовыми корнями; авторизация и проверка содержимого Яндекс Диска сверяются с официальной документацией на этапе 14.
14. **Модель:** шлюз модели (ADR-009); провайдер задаётся настройкой, облачный fallback не включается сам.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Прямое чтение БД TenderHub, как в LocalAI | обходит официальный API и права; спецификация предпочитает API (§2) |
| Хранить расчёт только ссылкой на TenderHub | нарушает воспроизводимость исторического выпуска (I02) |
| Повторный OCR в портале вместо RDWeb | нарушает C01 и роль RDWeb |
| Ждать доработок соседних систем до начала реализации | блокирует независимые этапы; спецификация требует продолжать их (README пакета) |

## Последствия

- Внешние форматы меняют только адаптеры и contract-тесты.
- Production-выпуск зависит от X-01 или решения владельца по Q-01; до этого реализация и пилот на тестовых назначениях возможны.

## Проверка

Этап 06: сверка выгрузки до/после, изменение в ходе импорта, 401/403/429, повторное событие закрытия, новая ревизия после открытия. Этапы 04, 05, 07, 14: contract-тесты адаптеров и отдельные live-smoke.

## Связанные требования

I02, I06, I10, I15, I16, I18; C01, C02; F04–F08, F11, F12; этапы 04–07, 14.
