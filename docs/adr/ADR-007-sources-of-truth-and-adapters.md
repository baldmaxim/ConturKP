# ADR-007 — Источники истины и адаптеры интеграций

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Спецификация фиксирует источники истины: TenderHub — расчёт; портал — решения и выпуски; LocalAI и RDWeb — обработка и доказательства; индекс не заменяет журнал (02 §4, спецификация §2–3). Инвентаризация показала разрывы: у TenderHub нет неизменяемого снимка расчёта (X-01), у LocalAI — фильтра по редакциям (X-04), у MailHub — машинного доступа (X-03), у RDWeb подтверждён только формат экспорта (X-05), сервис переговоров не определён (Q-06).

## Решение

### Владение данными

| Данные | Источник истины | Что хранит портал | Правило |
|---|---|---|---|
| Расчёт (позиции, строки, коммерческие стоимости, итог) | TenderHub | неизменяемые `calculation_revision` со сырыми ответами | портал не меняет расчёт и не считает свою смету |
| Оригиналы документов | портал (получение) | `blob` + `document_revision` | оригинал — основа превью и доказательств |
| Распознавание | RDWeb (основное), текстовый слой/локальный OCR (явно помеченный) | неизменяемые `recognition_run` и `evidence_fragment` | новый прогон — новая запись; локальный OCR не выдаётся за RDWeb (A43) |
| Поисковый индекс | портал (D-013, ADR-012) | чанки, векторы и состояние индексации `fragment_index_state` | производные данные; удаление индекса не трогает доказательства (A42) |
| Письма | MailHub | копии писем как `communication` + фрагменты | чтение без побочных эффектов |
| Переговоры | сервис переговоров | сессии, редакции транскрипции, сегменты | подсказки отдельно от речи |
| Требования, покрытие, замечания, решения, приложения, кандидаты, согласования, выпуски, размещения, отправки | портал | всё | транзакционные переходы и аудит |

### Адаптеры

1. Каждая интеграция — адаптер в `packages/adapters` с контрактом из `docs/contracts/adapters.md`. Ядро (`packages/core`, `packages/db`) не знает форматов внешних систем: адаптер переводит ответы в доменные объекты.
2. Всё, что взято из внешнего ответа и используется как доказательство или снимок, хранит сырой ответ (`blob`), версию контракта адаптера и время получения.
3. Предположения о внешних API помечаются в контракте как «проект» и изолируются в адаптере. Отсутствие API не меняет ядро: доменная сущность одна, источники её заполнения разные (API, импорт файла, ручной ввод с основанием).
4. Статус каждой интеграции ведётся в `integration_status`: `NOT_IMPLEMENTED`, `VERIFIED_FIXTURE`, `VERIFIED_LIVE`, `BLOCKED_EXTERNAL`. Фикстурный тест не даёт `VERIFIED_LIVE` (state-machines §19).

### TenderHub до и после X-01

5. **До X-01** портал делает `calculation_capture` вида `portal_capture`: чтение `overview`, всех страниц `positions`, `positions/with-costs` без кэша, `boq-items-full`; до и после чтения сверяются `updated_at`, итог и счётчики. Результат — `calculation_revision` вида `provisional`. Боевой выпуск (`mode = production`) с такой ревизией блокируется (`CALCULATION_PROVISIONAL`, state-machines §11.1) независимо от набора назначений доставки; тестовый выпуск (`mode = test`) допускается, но не может стать отправкой (R01-05).
6. **После X-01** адаптер получает ревизию по ID TenderHub; ревизия вида `verified`. Доменная модель не меняется.
6a. **Идентичность расчёта (R01-04).** Содержимое (`calculation_content`) и наблюдение источника (`calculation_revision`) разделены. Хэш содержимого покрывает позиции, строки, итог КП с валютой и семантикой, составляющие итога и курсы с датами. Повтор той же выгрузки идемпотентен только относительно последней ревизии этапа: возврат A → B → A создаёт новую ревизию со ссылкой на прежнее содержимое (R01-08); повтор той же внешней ревизии идемпотентен; `verified`-ревизия с тем же содержимым, что и `provisional`, — новая запись, ссылающаяся на то же содержимое. Закрытие у источника — событие, а не изменение записи (state-machines §6).
7. Закрытие расчёта: портал не строит собственный таймер закрытия. `submission_deadline` из TenderHub — сигнал для выгрузки; факт закрытия фиксируется как свойство ревизии из источника (`closed_at_source`), когда TenderHub его отдаст (X-01, Q-01).
8. Связь «этап КП ↔ версия тендера TenderHub» задаётся в `stage_calculation_source` (Q-03). Какая сумма считается итогом КП — правило `tender_stage.kp_total_rule` (Q-05).

   **Реализация (этап 06).** Реализован транспорт официального API (`X-API-Key`, область `tenders:read`, только `GET`) и `PortalCaptureStrategy`; адаптер один (`packages/adapters/src/tenderhub/`), транспорт подменяемый — второй транспорт прямого чтения (D-016) не реализован: доступ владельцем не подтверждён, отсутствие транспорта дефектом не является, D-016 не отменён. Выгрузку выполняет только worker (задание `calculation.capture`); сервер в TenderHub не обращается. Результат согласованной выгрузки — ревизия `provisional`; `verified`, `closed_at_source` и события источника продукт не создаёт — `TenderHubRevisionReader` остаётся интерфейсом проекта со статусом `BLOCKED_EXTERNAL` (X-01), доменные правила `verified` и событий закрытия проверены контрактными тестами на фикстурах. Срок подачи (`submission_deadline` из `tenders/brief`) — только сигнал выгрузки по сроку (`trigger = deadline`): собственного таймера закрытия нет, ревизия после срока остаётся `provisional`. Итог КП не выводится и `kp_total_rule` не заполняется (Q-05): сохраняются все доступные составляющие и значения источника, недоступность правила видна в данных, API и интерфейсе. Номер тендера TenderHub закрепляется за одним тендером портала (`external_ref`). Сопоставление позиций между ревизиями — хранение и API решений человека; автоматического сопоставления нет (этап 10). Подробности — `docs/contracts/adapters.md` §2, `docs/architecture/state-machines.md` §6, `docs/architecture/data-model.md` §4.5.

### Остальные интеграции

9. **RDWeb:** полноценный импорт экспортного архива (PDF + `_results.md` + `_results.html` + `_blocks.json`, schema_version 1). Автоматическая постановка задач — только после контракта X-05; до этого `BLOCKED_EXTERNAL`.

   **Реализация (этап 04).** Источник истины для распознанного текста — прогон `recognition_run`, а не документ: новая версия OCR того же PDF создаёт новый прогон со ссылкой `supersedes_run_id`, прежние фрагменты и ссылки на них остаются (A10). Архив принимается только к уже зарегистрированной редакции, и соответствие подтверждается SHA-256 PDF из архива: результат чужого или старого файла не принимается. Портал не считает себя источником истины для распознавания — он хранит ровно то, что прислал RDWeb, отделяя распознанный текст от описаний модели (I06) и сохраняя сам архив в `blob` как доказательство происхождения. Клиент API RDWeb на этапе 04 не писался (D-010): автоматическая постановка задач остаётся `BLOCKED_EXTERNAL` по X-05.
10. **Индекс и поиск — портал (D-013, D-015, ADR-012).** Locus (LocalAI) закрыт, внешнего поставщика индекса нет. Портал сам строит индекс поверх своих фрагментов и ищет с фильтром по разрешённым единицам источника до ранжирования. X-04 и Q-13 сняты как неприменимые. Индекс остаётся производными данными: его потеря не трогает доказательства и выпуски (I15).

10a. **Локальное распознавание — портал (D-014).** Движок `local_ocr` покрывает форматы вне охвата RDWeb (текстовый слой PDF, `.docx`, `.xlsx`, `.csv`, сканы). RDWeb остаётся источником истины для распознавания проектной документации; локальный прогон никогда не выигрывает у прогона RDWeb при автоподборе в снимок области.

    **Реализация (этап 05a, D-024).** Маршрут PDF — явная политика документа `recognition_route` (`auto` / `local` / `rdweb`), без эвристики «PDF — значит RDWeb»: PDF с прогоном RDWeb (идущим или успешным) относится к `rdweb`, локальный прогон на него не ставится; при `auto` PDF распознаётся локально только явной командой человека, при `local` — и автоматически. DOCX, XLSX и CSV RDWeb не обрабатывает — их маршрут `local`, постановка автоматическая. Иной формат — отказ `unsupported_format`, разборщик не угадывается (OD-4). Источник локального прогона — неизменяемая редакция: SHA-256 оригинала, распознаватель, его версия, хэш конфигурации, формат, языки и способ обработки образуют отпечаток, который считает БД; путь и имя файла в идентичность не входят (AD-05a-2). Выбор прогона — функция БД `recognition_preferred_run`: успешный RDWeb выше локального, внутри класса — глубже по линейной истории; время создания и порядок очереди не участвуют, ручного переопределения нет (AD-05a-3). Функцию используют автоподбор снимка и текущей области, охранники снимка и прогона поиска — выбор нельзя обойти прямым вызовом приложения. Проверенные части Locus перенесены с указанием происхождения (метрики качества, нормализация текста), зависимости от Locus во время работы нет (OD-7). OCR — tesseract.js с моделями `rus` и `eng` из npm, без сети и облака (OD-5); контракт `LocalOcrEngine` — `docs/contracts/adapters.md` §3a.
11. **MailHub:** до X-03 — импорт EML/экспорта на синтетических данных и по разрешению владельца; после X-03 — сервисное чтение по курсору изменений. Вызовы с побочными эффектами (`opened`, `draft`, перемещение) адаптер не использует.
12. **Переговоры:** импорт manifest (JSON или текст + manifest) по схеме из контракта. API — после Q-06.
13. **Яндекс Диск и SMB:** независимые адаптеры размещения; среда назначения (`test`/`production`) задаётся при создании и не меняется, корень и политика версионируются (`delivery_destination_version`), доставка закрепляет версию и среду, равную режиму выпуска (R01-05). Авторизация и проверка содержимого Яндекс Диска сверяются с официальной документацией на этапе 14.
14. **Модель:** шлюз модели (ADR-009); провайдер задаётся настройкой, облачный fallback не включается сам.

## Реализация (этап 07)

- MailHub (п. 11): X-03 не закрыт — автоматического чтения, разбора интерфейса и автоматизации браузера нет; строка `integration_status` `mailhub/MailHubMailboxReader` = `BLOCKED_EXTERNAL`. Штатный путь — ручной импорт EML в зарегистрированный ящик (D-025, OD-07-4, AD-07-3); отправленные импортируются с направлением `outbound`. Побочных эффектов чтения нет: письма не помечаются прочитанными и не перемещаются.
- Письмо хранится копией в ящике с неизменяемыми ревизиями: исходный EML — `blob`, нормализованная шапка и фрагменты тела — ревизия. Импорт EML в общий набор источников этапа (этап 03) с этапа 07 — отказ элемента с пояснением; ранее принятые файлы не меняются.
- Переговоры и вопросы–ответы — файловый manifest (`kontur.negotiation.v1`, `kontur.qa.v1`); сервис переговоров — `BLOCKED_EXTERNAL` (Q-06). Подсказка участнику — отдельный вид сегмента, в доказательный корпус не входит (I08, A03).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Прямое чтение БД TenderHub вместо API | обходит официальный API и права; спецификация предпочитает API (§2) |
| Прямое чтение БД TenderHub как второй транспорт одного адаптера | **принято условно (D-016)**: только read-only роль или реплика, только из worker, одна транзакция `REPEATABLE READ`, сырые строки сохраняются как снимок, использованный транспорт виден в состоянии интеграций. Закрывает атомарность снимка, но не идентичность согласованной ревизии — production-блокер остаётся |
| Хранить расчёт только ссылкой на TenderHub | нарушает воспроизводимость исторического выпуска (I02) |
| Повторный OCR в портале вместо RDWeb для проектной документации | нарушает C01 и роль RDWeb |
| Локальное распознавание в портале для форматов вне охвата RDWeb | **принято (D-014)**: RDWeb эти форматы не обрабатывает, а после закрытия Locus второго OCR не возникает — C01 соблюдается |
| Собственный индекс и смысловой поиск в портале | **принято (D-013, D-015)**: внешнего поставщика больше нет, второго RAG не возникает |
| Ждать доработок соседних систем до начала реализации | блокирует независимые этапы; спецификация требует продолжать их (README пакета) |

## Последствия

- Внешние форматы меняют только адаптеры и contract-тесты.
- Production-выпуск зависит от X-01 или решения владельца по Q-01; до этого реализация и пилот на тестовых назначениях возможны.

## Проверка

Этап 06: сверка выгрузки до/после, изменение в ходе импорта, 401/403/429, повторное событие закрытия, новая ревизия после открытия. Этапы 04, 05, 07, 14: contract-тесты адаптеров и отдельные live-smoke. Этап 05a: разборщики на настоящих фикстурах (XLSX, DOCX, CSV в UTF-8 и Windows-1251, PDF с текстовым слоем, сканы и смешанный), повреждённые и небезопасные пакеты, пределы, настоящий OCR tesseract.js; маршрут, идентичность и выбор прогона — второй линией БД (`tests/localParsers.test.ts`, `localPdf.test.ts`, `localRecognitionSchema.test.ts`, `localRecognition.test.ts`).
