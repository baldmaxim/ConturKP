# ADR-008 — Область поиска: явные ID разрешённых единиц источника

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17 (исправлено по ревью 01-1: R01-01, R01-02); уточнено D-013/D-015 (2026-09-22) и ревью 05-pre-1 (2026-09-28: AR05-02, AR05-05, AR05-06)

## Контекст

Поиск ограничен тендером, правами и выбранным набором источников; поздний документ не появляется в режиме исторического выпуска (I05, A11, A12). Нельзя искать по всему текущему индексу и потом фильтровать top-k (спецификация §3). LocalAI фильтрует только по источнику до ранжирования, строит ID фрагмента из пути и номера чанка и расширяет поиск по договору на связанные тендеры (`docs/discovery.md` §5). Второй OCR/RAG без доказанной необходимости создавать нельзя (C01). «Не найдено» не равно «не предусмотрено» (I07).

Ревью 01-1 показало: фильтр по редакциям документов недостаточен. У одного PDF может быть несколько прогонов распознавания (R1, R2), а письма и транскрипции — отдельные сущности. Область должна называть конкретные единицы источника и совпадать с входами проверки.

## Решение

1. **Единица источника** — то, из чего получены фрагменты: прогон распознавания (`recognition_run`), письмо (`communication`), редакция транскрипции (`transcript_revision`). У каждого фрагмента записаны `source_unit_type` и `source_unit_id`.
2. **Снимок области** — неизменяемый `evidence_scope` с типизированными элементами: редакция документа + выбранный прогон, письмо, редакция транскрипции (`docs/architecture/state-machines.md` §5.1). Проверка, кандидат, манифест, исторический поиск и MCP по выпуску используют один и тот же снимок.
3. **`SearchScope` строит сервер** из контекста запроса. Контекст — расширяемое объединение по виду (AR05-06, ADR-012 §24): `{ kind: 'tender', tenderId, mode, … }` реализуется на этапе 05; `{ kind: 'contract', contractId }` реализован на этапе 06a (возможность `contract.read`, текущий корпус договора; ADR-012 §24). Поля ниже — для вида `tender`; вид `contract` модель прогона поиска не менял.

| Поле | Откуда |
|---|---|
| `context.kind` | `tender` (этап 05); `contract` (этап 06a) |
| `tenderId` | запрос; проверяется `AccessContext` |
| `mode` | `working` (текущий черновой состав), `review` (снимок проверки), `release` (снимок выпуска), `comparison` (два снимка) |
| `evidenceScopeId` | для `review`, `release`, `comparison` — сохранённый снимок; для `working` — временный снимок из `draft`-ревизии набора и последних прогонов, его хэш пишется в результат |
| `allowedSourceUnits` | единицы снимка минус письма из ящиков, недоступных пользователю сейчас, и минус единицы договоров без `contract.read` (этап 06a, D-022 OD-3); в рабочем составе — ещё и договоров без действующей связи с тендером |
| `scopeHash` | хэш снимка + хэш применённого фильтра прав; пишется в результат и аудит |

   Клиент не передаёт ID единиц сам: он выбирает этап, проверку или выпуск, сервер разворачивает область. Развёрнутая область закрепляется в прогоне поиска `search_run` (`allowed_source_unit_ids`, `scope_hash`, ссылка на снимок) и не пересчитывается для его смысловой ветки (ADR-012 §14).
4. **Права поверх снимка.** Снимок не даёт вечного разрешения: доступ к ящикам проверяется при каждом запросе, письма без доступа исключаются из `allowedSourceUnits` до ранжирования (A35).
5. **Фильтр до ранжирования.** Любая ветка поиска — точная, полнотекстовая или смысловая — отбирает кандидатов только среди фрагментов с `source_unit_id ∈ allowedSourceUnits`. Постфильтрация результатов top-k запрещена. Это требование определяет реализацию смыслового поиска: ANN-индекс не создаётся, потому что он применяет фильтр после обхода (D-015).
6. **Исторический режим** использует только снимок выпуска. Более поздние прогоны того же PDF, новые письма и редакции транскрипций в область не входят (A10, A11).
7. **Точный и полнотекстовый поиск — в PostgreSQL портала** по неизменяемым `evidence_fragment`: точные обозначения (коды листов, марки, номера позиций) и полнотекстовый поиск с конфигурацией `russian`. Это поиск по собственному реестру доказательств, который нужен для полноты прохода (спецификация §12), изоляции и стабильных цитат. **Уточнение D-015:** сюда же добавляются эмбеддинги и смысловая ветка. Вторым RAG это не становится — после закрытия Locus (D-013) портальный индекс единственный, а генерация ответа остаётся отдельной обязанностью ответного ядра (ADR-009), не поиска.
8. **Смысловой поиск — в портале** (D-013, D-015, ADR-012). Внешнего поставщика индекса нет: чанки строятся из фрагментов портала и несут единицу источника и тендер, а принадлежность гарантируется составными внешними ключами — чанк из чужой единицы непредставим в схеме. Фильтр по `allowedSourceUnitIds` стоит в `WHERE` каждой ветки, то есть до `ORDER BY … LIMIT`. Проверка ответа по БД портала сохраняется как вторая линия: каждый возвращённый фрагмент сверяется с полной областью, ответ с фрагментом вне области отклоняется целиком и пишется в аудит. Отбрасывание отдельных строк после top-k по-прежнему не применяется.
9. **Деградация.** Если модель эмбеддингов недоступна или индекс не построен, ответ содержит `semantic: "unavailable"` с причиной; точный и полнотекстовый поиск продолжают работать. Тихого переключения на поиск по всему индексу нет (A42). Смысловой поиск выполняется заданием класса `gpu`: сервер во внешние системы не ходит, поэтому точный и полнотекстовый результат возвращаются синхронно с пометкой `preliminary`, а итоговое слияние трёх веток клиент читает из прогона поиска по готовности (`GET /search-runs/{id}`). Отказ или просрочка смысловой ветки дают прогон `degraded` с причиной и итогом по двум веткам (ADR-012 §14).
10. **Связь договора области не расширяет** (D-017). Договор входит в область, только если его единица есть в снимке. Подтверждённая связь договора с тендером лишь предлагает единицы договора кандидатами в состав источников этапа; ищутся они после явного включения инженером. Включение в снимок права чтения не даёт: единица договора ищется и читается только при `contract.read` (D-022 OD-3, этап 06a).
11. **Результат поиска** содержит `searchRunId`, область (`scopeHash`, число единиц по типам), признаки неполноты (неполное распознавание, единицы и страницы, ещё не проиндексированные активной версией, недоступный смысловой поиск с причиной, исключённые по правам единицы — без их содержимого), у каждого результата — `origin` и `matchedVia` (ADR-012 §23) и формулировку пустого результата: «не найдено в области: N единиц, M страниц распознано из K». Пустой результат не превращается в «не предусмотрено» (I07).
12. **Цитата** — ссылка на `evidence_fragment.id` + страница и координаты. Превью открывает локальный оригинал и выделяет фрагмент; внешний crop URL не нужен и не загружается (A17, A38).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Фильтр только по редакциям документов | пропускает поздний прогон того же PDF и не выражает письма и транскрипции (ревью 01-1, R01-02) |
| Список разрешённых ID фрагментов в каждом запросе | корректно, но списки в десятки тысяч ID на каждый запрос; единицы источника компактнее и дают тот же результат |
| Поиск по всему индексу с фильтром результатов | запрещено спецификацией; теряет релевантные результаты и может раскрыть счётчики |
| Собственный векторный индекс портала | **принято (D-013, D-015)**: после закрытия Locus второго RAG не возникает — портальный становится единственным. До D-013 отвергалось как второй RAG (C01) |
| ANN-индекс (HNSW) на векторах | с ним планировщик превращает `ORDER BY … LIMIT` в обход индекса и применяет `WHERE` после отбора — это постфильтрация top-k, запрещённая п. 5 (A42). Точный перебор по уже отфильтрованной области даёт требуемую семантику. Возврат к вопросу — только по замерам и отдельным ADR с измеренным recall |
| Отдельный индекс на каждый выпуск | дублирование индекса и пересборка при каждом выпуске; область задаётся снимком, а не отдельным индексом |

## Последствия

- Портал хранит тексты фрагментов в PostgreSQL и индексирует их полнотекстово; это производный индекс (`fragment_index_state`), пересобираемый без потери доказательств.
- **Уточнение D-013 и D-015 (2026-09-22):** Locus закрыт, смысловой поиск переносится в портал. X-04 и Q-13 сняты как неприменимые, приёмка этапа 05 от них больше не зависит. Доменная модель и контракт `SearchScope` не меняются — меняется только исполнитель.
- Индекс живёт в той же PostgreSQL: чанки, векторы (`pgvector`, тип `halfvec`) и состояние индексации. Таблица векторов исключается из резервной копии по данным как производная (ADR-011 §7).
- Смысловая ветка выполняется заданием класса `gpu`; точный и полнотекстовый результат отдаются синхронно.
- Полнотекстовый поиск требует локали базы с приведением регистра кириллицы (ADR-002): при `--locale=C` «договор» не находит «Договор».

## Проверка

Этап 05 — только на корпусе прогонов RDWeb (AR05-05): два тендера с одинаковой фразой; две единицы источника одного тендера, из которых в области одна; два этапа с противоположными ответами; два прогона одного PDF, где поздний ранжируется выше при `limit = 1`; переиндексация не ломает старую цитату; удаление индекса не уничтожает оригинал; пустой результат не утверждает отсутствие требования (A10–A12, A42, A44).

Этапы 07 и 16: письмо из недоступного ящика на первом месте по релевантности не участвует в ранжировании (A35, почтовая часть RT-02). Этап 06a: связь договора с тендером область не расширяет; документ договора не находится поиском по тендеру без явного включения в снимок. Бумажные сценарии — `docs/architecture/walkthroughs.md` §6 и §11.
