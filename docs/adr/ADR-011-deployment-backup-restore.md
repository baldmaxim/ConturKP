# ADR-011 — Запуск на Windows, миграции, резервное копирование и восстановление

Статус: accepted (этап 01 принят по `f8a0f20`, `docs/reviews/01-review-4.md`)
Дата: 2026-09-17

## Контекст

Портал размещается на локальном компьютере; сотрудники подключаются из LAN/VPN (спецификация §1). Нужны резервные копии БД и оригиналов, проверка восстановления, журнал событий, контроль диска (§12). Конфигурация целевого ПК неизвестна (U-01). Окончательный способ размещения PostgreSQL и служб выбирается на этапе 17 по фактическому окружению. Машина разработки — не целевой ПК (ADR-001).

## Решение

### Процессы и конфигурация

1. Три компонента: PostgreSQL, `server`, `worker`. На целевом ПК — службы Windows без видимых окон. Обёртка служб выбирается на этапе 17 из вариантов, подтверждённых на целевой ОС; критерии — автозапуск, перезапуск при сбое, запись stdout/stderr в файлы.
2. Предпочтительно PostgreSQL как нативная служба Windows. Docker — запасной вариант, если нативная установка недоступна (U-03).
3. Конфигурация — файл окружения вне репозитория и переменные службы: строка подключения, корень хранилища, корни наблюдаемых папок, адреса интеграций, секреты (ADR-006). Проверка конфигурации при старте выводит только признаки «задано / не задано», без значений.
4. Порядок старта: PostgreSQL → команда `migrate` (ADR-002) → `server` и `worker`. `server` отвечает `/health` (процесс жив) и `/ready` (БД доступна, версия схемы совпадает, хранилище доступно на запись, есть свежий heartbeat worker).
5. Логи — файлы с ротацией, без секретов и без текстов документов; аудит бизнес-действий — в `audit_event`.

### Обновление

6. Обновление: остановить `server` и `worker` → резервная копия → новая сборка → `migrate` → запуск → проверка `/ready`. Отката схемы нет: при неудаче — восстановление из копии, сделанной перед обновлением.

### Резервное копирование

7. **Состав копии:**
   - `pg_dump` в формате custom от роли `kontur_backup`;
   - копия каталога `sha256/` хранилища (добавляются только новые файлы);
   - манифест копии: время, версия схемы, число и SHA-256 файлов хранилища, хэш дампа.
   `derived/` хранилища не копируется: пересобирается. Индекс поиска портала (ADR-012 §10): таблицы векторов (`search_chunk_vector`) и кеша эмбеддингов (`embedding_cache`) исключаются из дампа по данным и остаются в схеме; версии индекса, чанки, связи и полнотекстовые данные копируются. Отдельного внешнего индекса после D-013 нет.
8. Копия пишется на другой диск или сетевой ресурс из конфигурации. Зеркала размещения выпусков (Яндекс Диск, SMB) резервной копией не считаются (спецификация §9).
9. Периодичность, срок хранения и RPO/RTO — после U-06 и U-07; до этого — ежедневная копия и перед каждым обновлением.
10. Контроль заполнения диска: предупреждение при пороге свободного места у хранилища, БД и каталога копий; задания записи в хранилище останавливаются до исчерпания места с явной ошибкой.

### Восстановление

11. Восстановление проверяется только на чистом тестовом окружении, никогда поверх рабочей системы (этап 17):
    - создать пустую БД → `pg_restore` → проверить версию схемы;
    - восстановить `sha256/` → сверить хэши всех файлов с манифестом копии;
    - сверить, что все `blob`, на которые ссылаются выпуски, существуют и совпадают по хэшу;
    - запустить `server` и `worker`, открыть исторический выпуск и цитату;
    - убедиться, что точный и полнотекстовый поиск работают сразу, а смысловая ветка честно недоступна (`semantic: unavailable`, причина `index_vectors_missing`) — это ожидаемая деградация, а не сбой;
    - пересобрать индекс: создать новую версию `search_index_version`, дождаться полноты и активации (ADR-012 §5); до активации поиск остаётся деградированным и сообщает причину, выпуски, решения и цитаты доступны (A42).
12. Результат проверки восстановления — отчёт этапа 17 с фактическими командами и хэшами (A40).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Запуск в консольных окнах | видимые окна и остановка при выходе пользователя (этап 17) |
| Весь стек в Docker Desktop | на Windows требует WSL2/Hyper-V и входа пользователя; допустим только как запасной вариант |
| Только снапшоты виртуальной машины | не проверяется согласованность БД и хранилища; зависит от платформы, которая не подтверждена |
| Автоматические миграции при старте в production | миграция без свежей копии и без контроля оператора |

## Последствия

- Этап 02 даёт скрипты разработки и тестовой БД на машине разработки; службы, копии и восстановление реализуются и проверяются на этапе 17 на целевом ПК.
- Недостаток диска на машине разработки (12 ГБ свободно) ограничивает тесты большими архивами (U-08).

## Проверка

Этап 02: чистый старт, `/ready`. Этап 17: перезапуск служб, обновление, копия, восстановление на чистом окружении со сверкой хэшей (A40), деградация смысловой ветки до пересборки индекса и её снятие после активации новой версии (A42), заполненный диск. Требование к кластеру целевого ПК: PostgreSQL ≥ 17 с расширениями `vector` ≥ 0.8 и `pg_trgm` (ADR-002).

## Связанные требования

I15, I17, I19; A39, A40, A42; F17, F19, F22, F23; спецификация §12.
