# ADR-012 — Собственный индекс портала, эмбеддинги и ранжирование

Статус: accepted (этап 05, решения D-013 и D-015); уточнён ревью 05-pre-1 (AR05-02…AR05-07, AR05-10) — решение D-021
Дата: 2026-09-22; уточнения 2026-09-28

## Контекст

ADR-008 §8–9 отдавал смысловой поиск внешнему LocalAI и ставил приёмку этапа 05 в зависимость от X-04 и Q-13 — доработки и согласия владельца LocalAI. Решением D-013 Locus (LocalAI) закрывается, его ядро переносится в портал; внешнего поставщика индекса больше нет, X-04 и Q-13 сняты как неприменимые.

Одновременно остаются в силе жёсткие требования: фильтр по разрешённым единицам источника применяется **до** ранжирования, постфильтрация top-k запрещена (ADR-008 §5, A42); цитата ссылается на стабильный ID фрагмента портала (ADR-008 §12); индекс — производные данные, его потеря не трогает доказательства и выпуски (I15, A42); сервер не обращается во внешние системы, это делает только worker (ADR-007); производный текст модели не выдаётся за основание (I06).

Ограничения среды: один GPU с лимитом одного задания (ADR-004, U-05); worker выполняет задания последовательно (ADR-004 §7a); машина разработки без GPU и с 12 ГБ свободного диска (U-08); одна СУБД без ORM (ADR-002).

## Решение

### Хранение

1. **Чанк — страница прогона.** Длинная страница режется с перекрытием; шапка (шифр, лист, наименование, тип, отметки, оси) повторяется в каждой части и получает больший вес при полнотекстовом поиске. Ключ чанка детерминирован, поэтому повторная индексация идемпотентна. В текст чанка входят только фрагменты доказательного происхождения (§21).
2. **Связь чанка с фрагментами — явная и упорядоченная, со смещениями.** Попадание в чанк сводится к конкретному `evidence_fragment.id`, у которого уже есть страница и координаты; отдельный слой «спанов» не заводится.
3. **Область гарантируется схемой.** Чанк и связь несут версию индекса, единицу источника и тендер, а составные внешние ключи ссылаются на соответствующие уникальные ключи чанка и фрагмента. Чанк, собравший фрагмент чужой единицы или чужого тендера, непредставим в схеме, а не только запрещён в коде. Мутационный тест обязан падать на уровне БД.
4. **Классы изменяемости.** `search_index_version` — `mutable` (статус версии; строки не удаляются, на них ссылаются прогоны поиска). Чанки, связи, векторы, кеш эмбеддингов и `fragment_index_state` — `derived`: полный DML для роли приложения, без триггеров неизменяемости. `search_run` — `frozen-after`: меняется только до терминального статуса. `search_run_result` — `immutable`, вставка разрешена только в нетерминальный прогон (охранник с блокировкой строки прогона, как у `recognition_page`, R04-04).
5. **Версия индекса — сущность `search_index_version` (AR05-03).**
   - **Параметры версии неизменны после создания:** `chunker_version`, `fts_config` (`russian`), `embedding_input_version` (шаблон входа модели: префикс, нормализация, обрезка), `embedding_model`, `embedding_model_fingerprint` и `embedding_dim`. Последние три — все заданы или все `NULL`: версия без векторов обслуживает только точную и полнотекстовую ветки. Смена любого параметра — только новая версия, поскольку прежние векторы и чанки несопоставимы.
   - **Статусы:** `building` → `active` → `retired`; `building` → `failed`. Частичные уникальные индексы: не более одной `active` и не более одной `building`.
   - **Активация атомарна и только после полноты.** Одна транзакция под блокировкой строк обеих версий проверяет: у каждого фрагмента, подлежащего индексации (прогон `complete` или `partial`), есть `fragment_index_state` этой версии в конечном состоянии (`indexed` или `skipped` с причиной); у версии с векторами у каждого чанка есть вектор. Затем прежняя `active` становится `retired`, новая — `active`. Неполную версию активировать нельзя; попытка — отказ с числом недостающих фрагментов.
   - **Новые прогоны после активации** дочитываются в `active` (и в `building`, если она есть) инкрементально заданиями §15. Пока они не проиндексированы, результат поиска показывает это в охвате (ADR-008 §11), а не молчит.
   - **Сборка мусора.** Данные версии `retired` (чанки, связи, векторы, состояния) удаляет задание `index.purge` и только когда нет прогона поиска `pending`, закреплённого за этой версией. Проверка и пометка `purged_at` выполняются под `FOR UPDATE` строки версии; создание прогона поиска и смысловое задание берут `FOR SHARE` той же строки и требуют `purged_at IS NULL`. Поэтому сценарий «прогон создан на N, пока задание ждало GPU, активирована N+1 и удалена N» невозможен: N становится `retired`, но её данные живут, пока прогон `pending`; прогон либо завершится на N, либо по сроку станет `degraded` (§14), после чего удаление пройдёт.

### Векторы

6. **pgvector в той же PostgreSQL**, тип `halfvec`, хранение без вынесения в TOAST (`SET STORAGE PLAIN`), отдельная узкая таблица. Причина узкой таблицы: перебор не должен читать тексты чанков. Причина `halfvec` и хранения в странице: вектор на 4 байта за измерение превышает порог TOAST, и точный перебор выродился бы в случайный ввод-вывод. **Размерность не зашивается в тип колонки** (AR05-03, AR05-10): колонка `halfvec` без модификатора, размерность хранится явно в `dim`, `CHECK (vector_dims(embedding) = dim)`, составной внешний ключ (`index_version_id`, `dim`) на `search_index_version (id, embedding_dim)` — вектор чужой размерности непредставим. Модель другой размерности даёт новую версию, а не миграцию колонки. Верхняя граница `dim` — 4000: при `STORAGE PLAIN` строка обязана поместиться в страницу 8 КБ (2 байта × 4000 плюс заголовки). Модель большей размерности отклоняется провайдером до записи и требует отдельного решения с замером перебора. Точному перебору типизированная колонка не нужна: ANN-индекса нет (§7).
7. **ANN-индекс не создаётся намеренно.** С HNSW планировщик превращает `ORDER BY … LIMIT` в обход индекса и применяет `WHERE` к тому, что вернул обход, — то есть после отбора. Это постфильтрация top-k, запрещённая ADR-008 §5 (A42). Точный перебор по уже отфильтрованной области даёт ровно требуемую семантику. Причина записывается в комментарий миграции и закрепляется тестом на плане запроса, падающим при появлении индексного обхода в векторной ветке.
8. **Порог возврата к вопросу:** p95 векторной ветки выше 800 мс на целевом ПК или устойчиво более 300 000 чанков в одном запросе. Порядок эскалации до ANN: параллельный перебор, затем секционирование по тендеру. ANN — только отдельным ADR с измеренным recall на регрессионном контракте.
9. **Кеш эмбеддингов (AR05-03).** Ключ — (`text_sha256`, `purpose` (`index`/`query`), `embedding_model`, `embedding_model_fingerprint`, `embedding_input_version`, `dim`), где `text_sha256` — хэш текста уже после применения шаблона входа этой `embedding_input_version`. Вектор берётся из кеша только при совпадении всех полей с версией индекса; ключ по одному тексту вернул бы вектор другой модели. Назначение прежнее: повторный прогон распознавания того же документа даёт те же тексты, и вектор не пересчитывается — это снимает удвоение нагрузки на GPU.
10. **Резервная копия.** Таблицы векторов и кеша эмбеддингов исключаются из дампа по данным, оставаясь в схеме; чанки, связи и полнотекстовые данные копируются, поэтому точный и полнотекстовый поиск работают сразу после восстановления. Смысловая ветка до пересборки честно недоступна: при старте worker сверяет число векторов активной версии с числом её чанков, расхождение даёт `unavailable` с причиной `index_vectors_missing` и постановку новой версии (ADR-011 §7, §11).

### Поиск

11. **Три ветки и слияние рангов.** Точный поиск обозначений, полнотекстовый с конфигурацией `russian` и смысловой на эмбеддингах; результаты сливаются RRF с постоянной `k = 60`, закреплённой в `ranking_version`. Взвешенное слияние счётчиков не применяется — двойное ранжирование не воспроизводимо. Итоговое слияние строится только по зафиксированному набору веток (§14).
12. **Фильтр в `WHERE` каждой ветки**, то есть в плане запроса до `ORDER BY … LIMIT`.
13. **Проверка ответа — вторая линия.** Каждый возвращённый фрагмент сверяется с полной областью по БД портала; несовпадение отклоняет ответ целиком с записью в аудит. После перехода на внутренний ретривал эта проверка избыточна по построению и ловит только перестановки ранжированием, устаревший индекс и посторонние изменения схемы. При повторном чтении прогона сервер заново применяет права: если закреплённый набор единиц шире допустимого сейчас (отозван доступ), результат не выдаётся (`state-machines.md` §21).
14. **Прогон поиска — `search_run` (AR05-02).** Сервер во внешние системы не ходит, а вектор запроса считает локальная модель, поэтому поиск — прогон с явным жизненным циклом:
    - `POST /search` одной транзакцией разворачивает область (ADR-008 §3) и создаёт прогон. В нём закрепляются: контекст (§24), текст запроса и `query_sha256`, `scope_hash`, эффективный набор единиц `allowed_source_unit_ids` после фильтра прав и ссылка на `evidence_scope` при сохранённом снимке, `index_version_id`, `ranking_version`, модель и её отпечаток (из версии), `deadline_at`.
    - Точная и полнотекстовая ветки выполняются синхронно в том же запросе; их ранги пишутся в `search_run_result` с веткой `exact` и `fts`.
    - Смысловая ветка: вектор запроса есть в кеше (§9) — ветка выполняется синхронно (перебор — SQL, внешних вызовов нет), прогон сразу `complete`; модель доступна по последней проверке и у версии есть векторы — задание `search.semantic` (класс `gpu`, приоритет по ADR-004 §7a), прогон `pending`; версия без векторов, модель недоступна или векторы не готовы — прогон сразу `degraded` с причиной.
    - **Итоговый RRF (`fused`) строится только при терминализации и только по зафиксированному набору веток:** `{exact, fts, vector}` для `complete`, `{exact, fts}` для `degraded`. Синхронный лексический результат помечается `preliminary` и за итоговый не выдаётся; итог клиент получает чтением прогона.
    - **Терминализация условна по `status = 'pending'`.** Пишет тот, кто успел первым: задание по готовности вектора или чтение прогона после `deadline_at` (тогда `degraded`, причина `semantic_timeout`, заданию — `cancel_requested`). Позднее завершение задания получает 0 строк и ничего не пишет.
    - **Терминальный прогон неизменен:** статус, ранги по веткам и итоговое слияние после терминализации не меняются.
    - **Отказ смысловой ветки** — ошибка модели, неверная размерность, отмена, срок — даёт `degraded` с причиной; семантика выдачи молча не меняется.
    - Тайминги веток, ожидание в очереди, число кандидатов и причина отказа пишутся в прогон: он и есть журнал поиска. Машина состояний — `state-machines.md` §21, API — `portal-api.md` §2.4, MCP — `mcp-tools.md` §2.
15. **Индексация — ограниченными пачками двух видов.** `index.build` (класс `default`) строит чанки и полнотекстовые данные версии; `index.embed` (класс `gpu`) считает векторы версии. Каждая пачка ограничена и ставит следующую в той же транзакции, которая фиксирует результат; одновременно существует не более одной незавершённой пачки каждого вида на версию; приоритет пачек ниже смыслового запроса, а запрос обслуживает интерактивная полоса worker (ADR-004 §7a). Иначе одно задание на тысячи чанков держало бы единственный GPU-слот минутами и выдавливало интерактивный поиск.
16. **Реранкер не заводится.** Метрики донора, принимаемые как приёмочные, получены офлайн без векторов и без реранкера — он их не доказывает, а сервис добавил бы второй серверный стек (отвергнут ADR-001) и третьего потребителя видеопамяти. Переносится интерфейс шлюза и поведение при недоступности: прежний порядок и явный признак, никогда молча. Решение по сервису принимается на целевом ПК по дельте качества против дельты задержки.
17. **Деградация честная.** Недоступная модель или непостроенный индекс дают признак недоступности смысловой ветки с причиной; точный и полнотекстовый поиск продолжают работать. Тихого перехода к поиску по всему индексу нет. Причины: `model_unavailable`, `model_fingerprint_mismatch`, `index_without_embeddings`, `index_vectors_missing`, `semantic_timeout`, `semantic_failed`, `dimension_mismatch`, `cancelled`.

### Среда

18. **Расширения** `vector` и `pg_trgm` — по ADR-002. `CREATE EXTENSION` выполняет административное подключение при создании базы, миграция только проверяет наличие и падает с внятной причиной.
19. **Локаль базы** — по ADR-002: PostgreSQL не ниже 17, провайдер `builtin`, `C.UTF-8`. При libc-локали `C` приведение регистра кириллицы не выполняется, и полнотекстовый поиск сломался бы тихо. Гейт до начала работ по поиску — тест создания базы штатным путём и проверка равенства векторов текста в разном регистре.
20. **Проверяемость без GPU.** Базовый гейт — точный и полнотекстовый поиск без векторов. Конвейер, фильтр области, жизненный цикл прогона и проверку цитат тестирует детерминированный поддельный провайдер эмбеддингов. Полный прогон с моделью выносится отдельным флагом на целевой ПК и честно помечается как здесь не выполненный (U-08). Поддельный провайдер не заменяет конкретный (§25).

### Происхождение (AR05-04, I06)

21. **Индексируется только доказательный корпус:** `document_text` и `recognized_text`; с этапа 07 — `email_body`, `attachment_text` и `negotiation_speech`. Реплика переговоров — устное основание с явным `origin` и ограничением I08: она не переводит ось разногласия в согласие.
22. **`model_description` и `negotiation_hint` на этапе 05 не индексируются ни одной веткой:** `fragment_index_state.status = 'skipped'`, `skip_reason = 'origin_not_evidence'`, в текст чанка они не входят. Производный текст модели не может стать результатом поиска и единственной цитатой. Использование описаний модели как подсказки поиска (`derived_hint`) — только отдельным решением на будущем этапе и при условиях: подсказка лишь помогает найти страницу или блок; результат обязан ссылаться на фрагмент доказательного происхождения той же страницы; совпадение только по подсказке помечается `matchedVia: derived_hint` и не проходит фактический и числовой гейты ответного ядра (08a).
23. **Каждый результат несёт происхождение:** `origin` фрагмента-цитаты, `matchedVia` — набор веток, нашедших его, и ссылку на документ, редакцию, прогон, страницу и координаты.

### Контекст поиска (AR05-06)

24. **Контекст — расширяемое объединение по виду.** `tender` реализуется на этапе 05: `tenderId` и режим `working`/`review`/`release`/`comparison` (ADR-008 §3). `contract` зарезервирован для этапа 06a: `contractId` и текущий корпус договора или его снимок доказательств, возможность `contract.read`. Базовая модель прогона — закрепление области и версии, статусы, результаты, чтение прогона — от вида контекста не зависит: этап 06a добавляет вид `contract` расширением `CHECK` и колонкой владельца, не меняя статусов, результатов и API чтения. Связь договора с тендером область не расширяет ни в одну сторону (D-017, ADR-008 §10). **Реализация (этап 06a, D-023):** вид `contract` — `contractId`, текущий корпус договора (последняя редакция основного договора, допсоглашений и приложений и хвост её распознавания), режим `working` без этапа; отдельного снимка договора нет (T06A-1). Колонка `search_run.contract_id`, CHECK вида и формы; охранники прогона и результата сверяют единицу и фрагмент с владельцем контекста. Единица договора в тендерном контексте — только из области (состав этапа или снимок) и только при `contract.read` (D-022 OD-3): иначе исключается до ранжирования и считается в `excludedByAcl`.

### Провайдер эмбеддингов (AR05-10)

25. **Конкретный локальный провайдер обязателен для заявления смысловой ветки.** PASS этапа 05 по смысловой ветке требует реализации за `ModelGatewayEmbeddings` хотя бы одного реального провайдера, а не только поддельного: HTTP-клиент OpenAI-совместимого `/v1/embeddings` локального сервера модели (как `RAG_EMBEDDINGS_*` в Locus), адрес — только loopback или LAN из настройки, облачного запасного пути нет (D-013). Реализуются и тестируются:
    - конфигурация без вывода секретов;
    - отпечаток модели: `embedding_model_fingerprint` — хэш имени модели, размерности и ревизии из настройки; версия индекса дополнительно хранит пробный вектор фиксированной строки, и при каждой проверке доступности косинус нового пробного вектора с сохранённым обязан быть не ниже 0,999, иначе смысловая ветка — `unavailable` с причиной `model_fingerprint_mismatch` до новой версии индекса;
    - проверка размерности каждого вектора до записи: против заявленной провайдером, против `embedding_dim` версии и против предела 4000 (§6).

    Контрактные тесты идут против поддельного HTTP-сервера. Живой прогон на машине разработки без GPU — `NOT_RUN`, статус провайдера — `VERIFIED_FIXTURE`, не `VERIFIED_LIVE`. Без конкретного провайдера смысловая ветка в отчёте этапа — `PARTIAL`, и готовность к эксплуатации не заявляется.

## Реализация (этап 05)

Миграции `docs/migrations/0009_search_index.sql` и `0010_evidence_scope_sealed.sql` (R05-01); код — `packages/core/src/search.ts` (правила), `packages/db/src/searchIndex.ts`, `searchScope.ts`, `searchRuns.ts`, `searchService.ts`, `packages/adapters/src/embeddings/`, `apps/worker/src/handlers/search.ts`, `apps/worker/src/maintenance.ts`, `apps/server/src/routes/search.ts`, `evidenceScopes.ts`.

- **Состав таблиц** — по `data-model.md` §4.13 с двумя дополнениями: `search_index_unit` (отметка «единица источника проиндексирована версией целиком» — основа проверки полноты за O(единиц), а не O(фрагментов)) и `integration_status` (data-model §4.12; первый писатель — worker, модель эмбеддингов). `fragment_index_state` ведётся для полнотекстовой системы (`portal_fts`): полнота векторов считается по чанкам (`search_chunk_vector`), а не по фрагментам.
- **Снимок области** `evidence_scope` / `evidence_scope_item` заведён на этом этапе: без него нельзя проверить исторический режим (A10, A11, RT-01). Неизменность состава обеспечивает БД (миграция 0010, R05-01; ADR-002, «Реализация (этап 05)»): единицы вставляются только транзакцией, создавшей снимок, одной командой; полнота и `content_hash` сверяются с фактическим составом после неё и при `COMMIT`. Регрессии — `tests/regressions-r05.test.ts`. Режимы поиска — `working` и `review`; `release` и `comparison` — с выпусками (этапы 13, 15), запрос с ними даёт `400`.
- **Подготовка текста (находка этапа).** Провайдер `builtin` приводит регистр, но парсер `to_tsvector` классифицирует символы по `LC_CTYPE` базы, а он остаётся `C`: в локали `C` любой не-ASCII символ считается буквой, и «Стромынка» в кавычках-ёлочках, тире, `№`, неразрывный пробел склеиваются со словами (`«стромынк`, `девелопмент»`). Функция `search_prepare(text)` (IMMUTABLE) заменяет знаки вне ASCII, не являющиеся буквой или цифрой, пробелом; применяется к тексту чанка, фрагмента и запроса. Гейт миграции проверяет и это. Требование к целевому ПК — ADR-002.
- **Ранжирование `r1`** (константа `RANKING_VERSION`, закрепляется в прогоне): точная ветка — обозначения запроса (цифра плюс буква или разделитель, либо ≥ 4 символа; заглавные шифры через разделитель) как подстроки свёрнутого текста (нижний регистр, ё → е, латинские двойники → кириллица); полнотекстовая — лексемы запроса через ИЛИ, основа от 5 символов по префиксу (`search_term`), чанк ранжируется суммой IDF найденных лексем по области, затем `ts_rank_cd` с весом шапки; смысловая — точный перебор `<=>` по отфильтрованной области. Проекция чанка — только в фрагменты его связей: шапка цитируется, лишь если совпадения нет в теле; до 2 фрагментов на чанк не слабее половины лучшего; фрагмент, уже занявший ранг в ветке, пропускается (уникальность `(run_id, branch, fragment_id)` закреплена и в схеме). Обзорный вопрос по договору (правило донора Locus `expandedChatRetrievalQuery`) расширяется договорными терминами и даёт по одному фрагменту на чанк — ведущий пункт раздела, не нумерованный заголовок. Итог — RRF `k = 60`.
- **G05-01 (build → embed).** `index.build` в транзакции единицы, создавшей чанки, ставит `index.embed`; `index.embed` ставит следующую пачку в той же транзакции, что и перевод в `succeeded` (хук `then` у `complete`, ADR-004 §7a), поэтому `dedupe_key` не конфликтует с самим заданием. Пустая векторная пачка ничего не закрывает: флага «векторы готовы» нет, активация пересчитывает полноту. Страховка от потерянной постановки — проход обслуживания worker (раз в 5 с): недостающие единицы и векторы, активация, удаление. Тест с принудительным порядком «embed раньше build» — `tests/searchSemantic.test.ts`.
- **G05-02 (pending и срок).** Прогон вставляется только `pending` (триггер), синхронные сценарии проходят через него в той же транзакции. Просроченные прогоны терминализует проход обслуживания worker без участия клиента; чтение прогона — дополнительная попутная проверка. Тест: брошенный прогон становится `degraded`, позднее завершение задания получает `not_pending`, удаление данных прежней версии ждёт терминализации.
- **G05-03.** Без активной версии `POST /search` — `409 STATE_CONFLICT`, `current.reason = search_index_not_ready`, прогон не создаётся.
- **G05-04.** Проекция детерминирована (`ORDER BY` с порядком фрагмента в чанке), цитата — всегда фрагмент связей этого чанка; векторная ветка фильтрует единицы в `WHERE` и проецирует через связи. Регрессии — `tests/searchSemantic.test.ts` («проекция чанка в цитату»).
- **G05-05.** Вектор размерности 4000 со всеми служебными колонками `search_chunk_vector` записан и прочитан при `STORAGE PLAIN` (`tests/searchSchema.test.ts`); размер строки меньше страницы — предел 4000 не понижается.
- **ANN.** Колонка `halfvec` без модификатора размерности: HNSW на ней не создаётся вовсе («column does not have dimensions») — дополнительная структурная защита к тесту плана.
- **Провайдер.** `OpenAiCompatibleEmbeddings` (конкретный, `EMBEDDING_PROVIDER=openai_compatible`), `FakeEmbeddings` (тесты и разработка, в production запрещён). Отпечаток и проверка размерности — как в §25. Живой прогон с моделью — `NOT_RUN` (на машине разработки модели нет).
- **Задания и приоритеты** — ADR-004 §7a: `search.semantic` 100 (интерактивная полоса), обычные задания 50, `index.build`/`index.embed` 10, `index.purge` 0.
- **Регрессионный контракт Locus** (9 случаев `stage05`, итог по `{exact, fts}`): Recall@5 = 0,929 (13/14), MRR = 0,759, утечка 0, точность цитаты 1 (`artifacts/stage-05/locus-regression.log`). Правила `r1` уточнялись по ходу этапа; измерения до каждого уточнения приведены в отчёте этапа.

## Реализация (этап 07)

- Индексируется `email_body` (ревизия письма — единица индекса, чанки по блокам тела; цитата прежней переписки индексируется как часть письма и помечена якорем `quoted`) и `negotiation_speech` (редакция транскрипции — единица). `negotiation_hint` пропускается (`origin_not_evidence`) и в поиск не попадает.

Вложение не индексируется, пока распознавание не завершено.
- `search_index_unit` и `search_chunk` получили типизированные колонки единицы (`mail_message_revision_id`, `transcript_revision_id`); полнота версии учитывает все три вида; `fragment_index_state.run_id` переименован в `source_unit_id`.
- Проекция попадания и цитата несут вид источника (`sourceKind`) и шапку: письмо (тема, отправитель, время, ящик; у вложения — письмо вложения) или сессия переговоров (название, говорящий, таймкод).

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Qdrant, как в Locus | второй сервис и второе хранилище при прямом указании спецификации §3 не плодить их; ломает единую резервную копию ADR-011 |
| Файловый снимок векторов | нет ссылочной целостности с фрагментами, рассыпается при переиндексации |
| HNSW ради скорости | применяет фильтр после обхода индекса — нарушение ADR-008 §5 (A42); допустим только отдельным ADR с измеренным recall |
| Вектор рядом с текстом чанка в одной таблице | перебор читает тексты, объём чтения удваивается |
| Тип вектора на 4 байта за измерение | превышает порог TOAST, точный перебор вырождается в случайный ввод-вывод |
| Размерность в типе колонки (`halfvec(1024)`) | смена модели другой размерности потребовала бы миграции колонки; размерность хранится явно и проверяется ограничениями (AR05-03) |
| Кеш эмбеддингов по одному тексту | вернул бы вектор другой модели, ревизии или шаблона входа (AR05-03) |
| Удаление прежней версии сразу при активации | ожидающий смысловой прогон читал бы удалённые данные (AR05-03) |
| Синхронный смысловой поиск из сервера | нарушает правило «во внешние системы ходит только worker» (ADR-007) и обходит учёт GPU-слота |
| Выдавать синхронный лексический результат за итоговый | итог зависел бы от того, успела ли смысловая ветка; слияние строится только по зафиксированному набору веток (AR05-02) |
| Индексировать `model_description` наравне с текстом документа | производный текст модели стал бы основанием — нарушение I06 (AR05-04) |
| Стриминг результатов ранжирования | не нужен: смысловая ветка асинхронна, а непроверенный текст ответа не показывается (D-019) |
| Второй BM25 в приложении поверх всего индекса | обход по всему корпусу на каждый запрос; полнотекстовый поиск делает СУБД по отфильтрованной области |

## Проверка

Этап 05, только на корпусе прогонов RDWeb: два тендера с одинаковой фразой (утечка равна нулю); две единицы источника одного тендера, из которых в области одна; два прогона одного PDF — поздний первым при `limit = 1`, исторический режим поздний не видит; вставка в связь чанка фрагмента чужой единицы падает на уровне БД; план векторной ветки не содержит индексного обхода, фильтр стоит до ограничения; удаление индекса не трогает доказательства и выпуски; пустой результат формулируется числом единиц и распознанных страниц; гейт локали; неполная версия не активируется; удаление выведенной версии ждёт ожидающий прогон; вектор из кеша другой модели не используется; вектор чужой размерности непредставим; `model_description` не находится ни одной веткой; просроченный прогон становится `degraded`, позднее задание его не перезаписывает; итоговое слияние строится только по зафиксированному набору веток; повторное чтение прогона после отзыва прав не выдаёт результат.

Почтовая часть (письмо из недоступного ящика не участвует в ранжировании) — гейт этапов 07 и 16; договорная (связь договора с тендером область не расширяет) — гейт этапа 06a (`docs/architecture/test-plan.md` §6).
