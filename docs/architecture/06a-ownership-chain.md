# Этап 06a — проверка T06A-3: цепочка владения документа договора

Статус: **требуется архитектурное решение AD-06a-1**. Миграция не начата, кода нет.
База: ветка `stage-06a` от `b77692f88383679c421286bf595a9c83dce2ae91` (этап 06 принят). Основание проверки — D-022, T06A-3.

## 1. Что проверялось

T06A-3 требует сначала проверить цепочку «связь договора → `document` → `document_revision` → `recognition_run` → `evidence_fragment` → индекс поиска». Права ниже редакции выводятся через неё. Около десяти таблиц разрешено расширять, только если доказано, что цепочка не обеспечивает инвариант, и только отдельным решением до миграции.

Нормативные инварианты (D-017, `docs/spec/prompts/stage-06a.md`, D-022):

- **И1.** У документа и всего, что ниже, ровно один владелец — тендер или договор. `tender_id` не является обязательным владельцем документа договора (OD-1).
- **И2.** Содержимое договора попадает в тендерный контекст только при двух условиях: редакция явно включена в снимок и у пользователя есть `contract.read` (OD-3).
- **И3.** Содержимое тендера не попадает в контекст `contract`.
- **И4.** У договора может быть распознанный текст (фикстурный `recognition_run`), и договор ищется в контексте `contract` (OD-4, ADR-012 §24).

## 2. Вывод

В нынешнем виде цепочка инвариант не обеспечивает: **строку договора ниже `document_revision` записать нельзя**. Каждая таблица от распознавания до индекса требует `tender_id NOT NULL`. Составной внешний ключ связывает этот `tender_id` с тендером редакции. Любой вариант, выполняющий одновременно OD-1 и OD-4, меняет одни и те же десять таблиц — сработало условие остановки T06A-3.

Ещё два охранника с той же привязкой: `search_run_result_insert_guard` (`f.tender_id = run.tender_id`) и `evidence_scope_item_insert_guard` (редакция из основы снимка того же этапа). В коде та же привязка у `fragmentsOutsideScope` (`f.tender_id = $2`), у проверок области в `packages/db/src/searchScope.ts` и у чтения прогона в `packages/db/src/searchRuns.ts` (`tender_id = ANY(contentTenderIds)`). Её же используют `packages/db/src/recognition.ts` и `packages/db/src/sources.ts`.

Цепочка вывода:

1. Чтобы вставить `recognition_run` по редакции R, нужен ненулевой `tender_id` T.
2. Внешний ключ требует строку `document_revision (R, T)`, то есть у редакции должен быть тендер T.
3. Если он есть, тендер становится обязательным владельцем документа договора — это нарушает OD-1 и D-017.
4. Если его нет, нельзя записать прогон, фрагменты и индекс. Тогда невыполнимы OD-4, контекст `contract` и включение договора в снимок (OD-3).

## 4. Обходы, которые отклонены без решения владельца

- **Технический «тендер договора»** — один на договор или общий. Формально проходит `NOT NULL`, но делает тендер обязательным владельцем (нарушает OD-1) и выводит принадлежность по косвенному признаку. Доступ к тендеру (`tender.read`, `contentTenderIds`, `admin.tender`) открыл бы содержимое договора без `contract.read` — нарушение OD-2.
- **Копия редакции договора в каждом связанном тендере.** Один файл получает разные `document_revision_id`, и снимок фиксирует копию, а не редакцию договора (T06A-1). Связь фактически расширяет область поиска вопреки D-017.
- **Отдельные таблицы распознавания и индекса для договоров** — запрещены T06A-2.
- **Договоры без распознавания и поиска** — противоречит OD-4 и обязательным тестам поиска.

## 5. Варианты для решения AD-06a-1

Общая часть обоих вариантов:

- `contract` и связь `contract_tender_link` «многие ко многим» со своей историей и аудитом; права по OD-2.
- `document` и `document_revision`: `tender_id` допускает NULL; добавляется `contract_id`; CHECK «ровно один владелец».
- Роли `contract` / `addendum` / `appendix` и ссылка на основной договор (T06A-2). Уникальность файла внутри договора — `(contract_id, blob_sha256)`.
- `search_run`: `context_kind IN ('tender', 'contract')`, колонка владельца `contract_id`, форма «ровно один владелец по виду» — ADR-012 §24 это уже предусматривает.
- `evidence_scope_item`: единица договора входит в снимок тендера через FK по редакции без тендера. Охранник требует подтверждённую связь договора с тендером снимка; охранники `search_run` и `search_run_result` принимают такую единицу только из снимка.
- Права по OD-3 проверяются при поиске и повторно при чтении и проекции.

Различие — в шести нижних таблицах: `recognition_run`, `evidence_fragment`, `search_index_unit`, `search_chunk`, `search_chunk_fragment`, `search_chunk_vector`. В обоих вариантах меняются одни и те же десять таблиц.

### Вариант A — владелец только у редакции

В шести нижних таблицах у строк договора `tender_id` равен NULL; новых колонок нет.

- Существующие составные FK по-прежнему запрещают строке договора нести чужой `tender_id`: у редакции договора он NULL, и пара не найдётся.
- При NULL составной FK не проверяется (MATCH SIMPLE). У `search_index_unit`, `search_chunk` и `search_chunk_fragment` других ссылок нет, поэтому для строк договора нужны новые FK без тендера и целевые уникальные ключи вида `(id, document_revision_id)`.
- Обратное направление — строка тендерной редакции с NULL — держат триггеры сверки с родителем, по одному на таблицу.
- Контекст `contract` фильтруется через `allowed_source_unit_ids`, вычисленные по `document_revision.contract_id`.

Плюс: ближе к формулировке T06A-3, меньше колонок.
Минус: «NULL = договор» — неявный признак. Половина второй линии держится на триггерах, а не на декларативных FK. Каждая будущая таблица цепочки (этап 07) должна не забыть свой триггер.

### Вариант B — дискриминатор во всех таблицах цепочки (D-017 дословно)

В шести нижних таблицах `tender_id` допускает NULL, добавляется `contract_id` и CHECK `num_nonnulls(tender_id, contract_id) = 1`. Составные FK дублируются по договору.

Плюс: вторая линия декларативна в обе стороны и без триггеров сверки — как принято для тендера (R05-01). Владелец строки явный, а фильтр контекста `contract` идёт по колонке. Будущая таблица без `contract_id` строку договора не примет — fail-closed.
Минус: больше DDL — на каждую таблицу колонка, CHECK, один-два FK и целевые UNIQUE. Это то механическое расширение, которого T06A-3 просил избегать без доказательства.

В обоих вариантах права выводятся через `document_revision`. Колонка варианта B нужна для целостности и фильтра, не для авторизации.

**Рекомендация: вариант B.**

- Шесть нижних таблиц меняются в любом варианте, а B делает это декларативно.
- B совпадает с принятым D-017 и промптом 06a: «составные внешние ключи дублируются по договору».
- Промпт называет эту миграцию самой опасной в плане из-за молчаливой утечки между тендером и договором. B закрывает утечку без триггеров сверки.
