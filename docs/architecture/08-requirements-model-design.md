## 3. Расхождения — остановка до миграции

Каждое расхождение касается одной из областей, для которых решение требует остановки: владение, кратность, идентичность ревизии, источник истины, права, машина состояний. Варианты пронумерованы; «предложение» — вариант исполнителя, решение остаётся за владельцем.

### Р-08-1. Q&A как источник при отсутствии фрагментов

**Решение.** OD-08-1 п. 4 разрешает Q&A этапа 07. Общее правило OD-08-1 — «только из доказательств, уже доступных через принятую evidence-архитектуру», п. 6 — «иные источники только через `evidence_fragment` или принятую ветку». AD-08-3: минимум `requirement_revision` ↔ `evidence_fragment`, ссылки на «immutable evidence revisions/fragments».

**Норматив.** И-07-5 (CONFIRMED, Review 07-1): Q&A не индексируется и фрагментов не имеет. `evidence_scope_item` знает только `document_recognition`, `mail_message`, `transcript_revision` (0018) — Q&A не входит в снимок, а анализ работает только по снимку («Source scope»).

**Почему остановка.** Источник истины и владение основания: Q&A либо становится новой веткой доказательств (меняет принятую модель 05–07, как AD-07-1a), либо основание перестаёт быть только фрагментом.

**Варианты.**
- A — ревизия вопроса–ответа получает фрагменты: новая ветка `evidence_fragment.source_unit_type = 'qa_item_revision'` (владелец — тендер ревизии, как у транскрипции), единица снимка `qa_item_revision`; в поисковый индекс не попадает (И-07-5 сохраняется для поиска). Цитата и права — общим путём.
- B — основание типизировано: фрагмент **или** ревизия Q&A (nullable FK + CHECK, без `owner_type`); Q&A в снимок не входит, модель его не читает, ручные основания допустимы.
- C — Q&A в этапе 08 не источник; п. 4 откладывается до отдельного решения.

**Предложение.** A: один путь оснований и цитат, Q&A попадает в область анализа и полноты.

**Блокирует.** Форму таблиц оснований (`*_evidence`) и состав снимка.

### Р-08-2. Модель покрытия

**Решение (AD-08-5).** `requirement_coverage` к **ревизии** требования; типы — document evidence, calculation revision, decision, implementation artifact, manual confirmation; состояния `uncovered` / `partial` / `covered` / `not_applicable` / `needs_review`. Модель может **предложить** покрытие.

**Норматив.** `data-model.md` §4.7: `coverage_link` к **требованию**, на ревизию расчёта, позицию и строку TenderHub; `kind` — `explicit_line` / `complex_rate` / `assumption`; `status` — `proposed` / `confirmed` / `rejected` / `stale`. `state-machines.md` §7: подтверждение человеком, `stale` при новой ревизии расчёта. A05: связь с комплексной расценкой подтверждается, отсутствие отдельной строки — не пропуск. `portal-api.md` §2.7: `/requirements/{id}/coverage-links`.

**Расхождения.**
1. Состояния решения — оценка полноты покрытия; состояния норматива — жизненный цикл связи (предложена, подтверждена, отклонена, устарела). В решении нет состояния «предложено», хотя модель может предлагать покрытие.
2. Различие `explicit_line` / `complex_rate` (A05) в типах решения не выражено.
3. Тип «implementation artifact» не определён ни в спецификации, ни в модели данных — такой сущности в Контуре нет. Тип «document evidence» — покрытие требования документом — в нормативе отсутствует.
4. Кратность: одна строка «требование — объект покрытия» (норматив, «многие ко многим») или одна оценка на ревизию требования с несколькими объектами.

**Варианты.**
- A — двухуровневая: `requirement_coverage` — неизменяемая оценка ревизии требования (история, последняя действует) с состоянием из решения, автором и причиной; `requirement_coverage_target` — объекты оценки с явным типом: позиция или строка ревизии расчёта (`match = explicit_line | complex_rate`), ревизия решения, фрагмент-основание. «Ручное подтверждение» — оценка без объекта с обязательной причиной. «Implementation artifact» не вводится до определения. Предложение модели — кандидат покрытия со статусом `proposed`, принимает человек. Новая ревизия расчёта или требования переводит действующую оценку в `needs_review` новой записью.
- B — норматив как есть (`coverage_link` с жизненным циклом связи), состояния решения вычисляются по связям ревизии требования и не хранятся.
- C — буквально по решению: одна строка на пару «ревизия требования — объект» со своим типом и состоянием из пяти значений; предложения модели — отдельно.

**Предложение.** A: выполняет AD-08-5 (тип явный, состояние хранится, ревизия не переписывается) и сохраняет A05.

**Блокирует.** Таблицы покрытия; задачу владельца — определить «implementation artifact» и «document evidence» или исключить их.

### Р-08-3. Решение: `decision_revision` и принятая таблица `decision`

**Решение (AD-08-6).** `decision` → `decision_revision`; требование ↔ решение 0..N; решение хранит формулировку, статус, автора, время, основания, замену. OD-08-5: принимает пользователь с `requirement.decide`.

**Норматив.** Таблица `decision` уже есть (0002): неизменяемая строка = одна версия, замена — `supersedes_decision_id`, один предмет (`subject_type`, `subject_id`), основания — массив `basis_fragment_ids` без FK, `decision_type` — только `import_item_disposition` (на неё ссылается `import_item.resolution_decision_id`, этап 03). Охранник `decision_author_guard` пускает только руководителя тендера по строке роли. `state-machines.md` §1.1: запись решения — событие барьера `decision_recorded`.

**Почему остановка.** Идентичность ревизии (строка-версия или ревизия под сущностью), права (строка роли в БД против возможности), изменение принятого контракта этапа 03.

**Варианты.**
- A — отдельные `requirement_decision` → `requirement_decision_revision` для этапа 08; таблица `decision` этапа 03 не меняется. Две таблицы решений.
- B — `decision` становится идентичностью, добавляется `decision_revision`; существующие решения импорта переносятся первой ревизией миграцией обновления; охранник — по виду решения.
- C — существующая строка `decision` уже является ревизией: добавляются виды решений 08, «корень» цепочки замен как идентичность, связь `requirement_decision` и таблица оснований с FK и ролью вместо массива; охранник — по виду решения.

**Предложение.** C — наименьшее изменение принятой модели при выполнении смысла AD-08-6, но буквально `decision_revision` не создаётся. Если владелец требует буквального имени — B.

**Блокирует.** Таблицы решений; статусы решения (в решении не перечислены — предлагается `active` / `superseded`).

### Р-08-4. Факты: AD-08-7 и D-018

**Решение.** OD-08-3: D-018 входит в 08, классы — только из D-018, без закрытого перечня — общая оболочка (kind, нормализованное значение, основание, происхождение, уверенность или статус, версия). AD-08-7: `fact` → `fact_revision`, кандидат модели ≠ подтверждённый факт, `fact.create`, `fact.confirm` — «если норматив требует подтверждение». «AI safety»: модель может предложить факт.

**Норматив (D-018).** `evidence_fact` — неизменяемое прочитанное значение (тип, сырое и нормализованное значение, единица, пункт, версия правил, прогон извлечения); `fact_state` — изменяемое производное состояние (действует / перекрыт / конфликт, период, кто кого заменил, решено правилом или человеком); граф редакций договора — детерминированная функция; извлечение — программное правило, не модель; основание — только `document_text`, `recognized_text`, `email_body`, `attachment_text` (триггер); 13 типов фактов, 9 из них — кандидаты в требования (`requirement_revision.origin = rule_extraction`).

**Расхождения.**
1. Источник фактов: D-018 — детерминированные правила; решение — также предложения модели с подтверждением человеком.
2. Состояние: D-018 — изменяемое `fact_state`, решаемое правилом; решение — ревизии и подтверждение. Подтверждение правилом-извлечённого факта D-018 не требует.
3. Перечень 13 типов в репозитории не записан (он есть только у донора Locus, который не исследуется). Без перечня правила-извлекатели писать нельзя — каждый тип и есть бизнес-класс; общая оболочка без правил даёт только ручные и модельные факты. Случай Locus 11 (`pv2-amendment-advance`, «какой сейчас аванс», `deferred:08`) требует типа «аванс» и графа «договор → допсоглашение».
4. Владение: факт из договора по D-023 принадлежит договору, требование — этапу тендера; решение («не копировать владение») говорит о требовании, а у факта есть собственный реестр.

**Варианты.**
- A — `fact` (идентичность: вид, предмет) → `fact_revision` (неизменяемое значение, происхождение `rule` / `model` / `human`, статус `candidate` / `confirmed` / `rejected`, прогон, основания); правило-извлечённые ревизии подтверждения не требуют, модельные и ручные — требуют `fact.confirm`; `fact_state` D-018 — производное состояние отдельной ревизионной таблицей. Владелец факта выводится из оснований; реестр — по области этапа.
- B — D-018 буквально (`evidence_fact` + `fact_state`), предложения модели — отдельные кандидаты; ревизий у факта нет, A→B→A — разные `evidence_fact`.
- C — в 08 только оболочка и ручные или модельные факты с подтверждением; правила и `fact_state` — после передачи перечня типов.

**Нужно от владельца.** Перечень 13 типов D-018 (или разрешение взять его у донора Locus) и выбор варианта. Без перечня правило-извлечение в 08 пустое, случай Locus 11 не закрывается.

**Предложение.** A; до перечня типов — правила не пишутся, оболочка и подтверждение работают.

**Блокирует.** Таблицы фактов; триггер происхождения основания D-018 не зависит от выбора.

### Р-08-5. Видимость формулировки требования из закрытого источника

**Решение (OD-08-4).** Метаданные требования видны при праве на реестр; содержимое основания, сниппет, цитата и исходный текст — только при текущем праве на источник; защищённый текст не копировать в требование в обход ACL.

**Неясность.** Формулировка требования и его параметры — производный текст, часто дословная выдержка из договора или письма (особенно у кандидата модели). Является ли формулировка «метаданными» — не сказано.

**Почему остановка.** Права и путь утечки: по формулировке читается содержимое закрытого источника.

**Варианты.**
- A — формулировка и параметры — данные тендера, видны при `requirement.read`; ограничены только основания.
- B — формулировка, параметры и обоснование кандидата видны, только если пользователь может читать **все** основания роли `supports`; иначе — метаданные: код, статус, даты, авторы, число оснований по видам, пометка «основание недоступно».
- C — B для кандидатов; после подтверждения человеком формулировка видна всем с `requirement.read`.

**Предложение.** B (fail-closed, буквально «не обходить ACL»). Тот же принцип — для фактов и для результата `analysis_run`.

**Блокирует.** Проекции API и UI; схему — нет.

### Р-08-6. Область этапа и «текущий scope»

**Решение.** Анализ — по конкретному `evidence_scope_id`. Инвариант 11: кандидата другого scope нельзя подтвердить как требование текущего scope без явной операции. «Completeness» хранится для каждого scope.

**Норматив.** Требование принадлежит этапу (`data-model.md` §4.7); основание «входит в область этапа». `evidence_scope` уникален по `(stage_id, content_hash)`; у этапа может быть много снимков, понятия «текущий снимок» в модели нет.

**Почему остановка.** Кратность и владение: реестр требований — один на этап или свой у каждого снимка; что такое «текущий scope».

**Варианты.**
- A — реестр один на этап; «текущий scope» — последний снимок этапа по времени создания; каждая ревизия требования записывает `evidence_scope_id`, в котором проверены её основания; подтверждение кандидата старого снимка — явная команда «перенести в текущий снимок», которая проверяет, что все основания входят в текущий снимок, иначе отказ.
- B — реестр на каждый снимок; новый снимок — новый реестр, перенос требований — явной операцией.
- C — «текущий scope» назначается явно (указатель у этапа, меняет `requirement.manage`).

**Предложение.** A. Ручной кандидат инженера тоже создаётся в снимке и цитирует фрагменты этого снимка.

**Блокирует.** Колонку области у кандидата, ревизии и проверки полноты, охранники оснований.

### Р-08-7. Единица полноты

**Решение (OD-08-7, «Completeness»).** Проход по «всем допустимым evidence units» снимка; единица связана с кандидатом или требованием, помечена `not_requirement` или `unreviewed`; счётчики `reviewed`, `total`, `covered`, `explicit_not_requirement`, `unreviewed`.

**Неясность.** Что такое единица: единица снимка (документ с прогоном, письмо, транскрипция — десятки), страница или лист (сотни), фрагмент (тысячи). Какие единицы «допустимы» (фрагменты `image_block`, `stamp_block`, `model_description`, подсказки переговоров). Соотношение `reviewed` и остальных состояний не задано.

**Почему остановка.** Кратность таблицы отметок и смысл «полноты».

**Варианты.**
- A — единица — фрагмент снимка с текстом проектного или исходного происхождения (`document_text`, `recognized_text`, `email_body`, `attachment_text`, `negotiation_speech`); «связана» — есть основание кандидата или требования; отметка `not_requirement` ставится на фрагмент, допускается пакетно по странице или документу; `reviewed = covered + explicit_not_requirement`.
- B — единица — страница или лист (по `page_index` и якорю 05a).
- C — единица — единица снимка (документ, письмо, транскрипция).

**Предложение.** A — детерминированно связывается с основаниями без нового слоя.

**Блокирует.** Таблицы полноты.

### Р-08-8. Механизм выдачи возможностей и вторая линия в БД

**Решение (OD-08-5).** Бизнес-правило не привязывается к строке роли; права — через возможности; по умолчанию инженер — предложения, руководитель «или ответственный пользователь» с `requirement.confirm` — подтверждение, `requirement.decide` — решение.

**Норматив.** Возможности тендера вычисляются из роли участника (`tenderCapabilities`, ADR-006 §1–3); явных выдач по тендеру нет (они есть только у договора и ящика). Вторая линия БД (`decision_author_guard`) проверяет строку роли `manager`.

**Почему остановка.** Права: «ответственный пользователь» с подтверждением без роли руководителя возможен только при явной выдаче.

**Варианты.**
- A — возможности по умолчанию из роли участника (раздел 6), явных выдач нет; БД проверяет одной функцией `tender_capabilities(user, tender)`, повторяющей таблицу кода, совпадение проверяется тестом.
- B — A + явные выдачи по тендеру (`tender_capability_grant`, как `contract_access`) для `requirement.confirm`, `.decide`, `.manage`, `fact.confirm`.
- C — только явные выдачи, роль ничего не даёт.

**Предложение.** A для этапа 08 (MVP, без выдач «на будущее»); B — отдельным решением, если нужен «ответственный инженер».

**Блокирует.** Охранники подтверждения и решения.

## 7. Инварианты БД решения → механизм

| № | Инвариант решения | Механизм | Негативный прямой SQL |
|---|---|---|---|
| 1 | подтверждённое требование не существует без ревизии | `current_revision_id` NOT NULL, отложенный FK, указатель на последнюю ревизию | вставка `requirement` без ревизии; указатель на чужую ревизию |
| 2 | кандидат модели не становится подтверждённым вставкой в обход перехода | ревизия из кандидата — только при `confirmed` кандидате с человеком-подтверждающим; `confirmed` кандидата — только вместе с ревизией | вставка ревизии с `candidate_id` кандидата `proposed`; `UPDATE status = 'confirmed'` без ревизии |
| 3 | ревизия требования неизменна | `forbid_mutation`, нет UPDATE у роли | UPDATE, DELETE, TRUNCATE |
| 4 | основание — существующий неизменяемый фрагмент | FK на `evidence_fragment`; фрагмент неизменяем с 05 | несуществующий ID; фрагмент вне снимка |
| 5 | факт и требование — разные сущности | разные таблицы, ревизия требования не ссылается на факт как на основание | ссылка ревизии требования на факт |
| 6 | ревизия решения неизменна | `forbid_mutation` | UPDATE, DELETE |
| 7 | замена решения не удаляет прежнюю | замена — новая запись с `supersedes`, удаления нет | DELETE прежней; цикл замен |
| 8 | покрытие указывает на конкретную ревизию требования | NOT NULL FK `requirement_revision_id` | вставка без ревизии; ревизия другого тендера |
| 9 | прогон закреплён на снимке | NOT NULL FK `evidence_scope_id`, неизменяем после финала; вход — подмножество снимка | смена снимка; вход из чужого снимка |
| 10 | завершённая проверка полноты невозможна при `unreviewed > 0` | охранник пересчитывает при завершении | `completed` при непросмотренной единице |
| 11 | кандидат другого снимка не подтверждается без явной операции | снимок ревизии = снимок кандидата, иначе только через команду переноса (Р-08-6) | ревизия со снимком, отличным от кандидата |
| 12 | закрытие или архив источника не уничтожают происхождение | основания неизменны; удаления у роли нет; архив договора и ящика — флаг | DELETE основания; архив договора → основания на месте |
| 13 | отзыв права на источник не открывается через цитату требования | проекция и `GET /evidence/{id}` проверяют право единицы при каждом чтении | тест API: отзыв `mail.read`, `contract.read` |
| 14 | конкурентное подтверждение предсказуемо | advisory-блокировка кандидата; повтор с тем же ключом идемпотентности — тот же результат; второй — `409` | два подтверждения одного кандидата |
| 15 | A → B → A — разные ревизии | `seq`, `supersedes`, без дедупликации по содержимому | третья ревизия с текстом A получает `seq = 3` |

Дополнительно, по образцу этапов 05–07: прямой SQL не создаёт кандидата, ревизию или основание другого тендера (составные FK); `analysis_run` не может сослаться на снимок другого этапа; удаления нет ни у одной таблицы этапа.

## 8. Шлюз модели и задание анализа

- **Контракт** (`adapters.md` §8, OD-08-2): `complete({ task, provider, model, promptVersion, schemaVersion, inputFragments: [{ id, text }], config }) → { json, usage, startedAt, finishedAt }`; инструкции — у сервера, текст фрагментов — данные (I16); инструментов у модели нет.
- **Провайдеры:** `fake` — детерминированные ответы по фикстурам (тесты, разработка); `openai_compatible` — локальный сервер (LM Studio, llama.cpp server) по адресу из окружения, ключ — только из окружения, облачного fallback нет. Живой прогон — `NOT_RUN` до целевого ПК.
- **Проверка ответа:** схема JSON; каждый `fragment_id` существует и входит во вход прогона; иначе кандидат отбрасывается до записи и учитывается в `coverage`.
- **Ошибки:** таймаут, отказ соединения, `429`, `5xx` — повтор с задержкой, не больше 3 попыток, затем прогон `failed` с причиной `provider_unavailable`; невалидный JSON, нарушение схемы, `401` / `403` — без повтора (`PermanentJobError`), прогон `completed_with_gaps` или `failed` с причиной; детерминированный отказ БД (`23xxx`) — без повтора.
- **Задание:** вид `analysis.extract`, класс `gpu`, пачки ограничены временем, следующая пачка ставится в транзакции результата предыдущей (`dedupe_key = analysis:<run_id>`), перезапуск worker — через аренду.

## 10. Интерпретации в пределах решения

Не меняют владения, кратности, идентичности ревизий и прав; приводятся для ревью.

| № | Интерпретация |
|---|---|
| И-08-1 | Расхождения с нормативом, которые решение снимает само: отдельный кандидат вместо `requirement.status = candidate` и `model_suggestion(requirement_candidate)`; статус — в ревизии требования; `analysis_run` вместо `review_run`; список возможностей решения вместо `portal-api.md` §2.7. Нормативные документы обновляются вместе с миграцией. |
| И-08-2 | Вход прогона — подмножество снимка, которое запустивший может читать (OD-08-1 «Запрет»); состав входа входит в `input_sha256`, поэтому два пользователя с разными правами получают разные прогоны. |
| И-08-3 | Идемпотентность прогона — для незавершённых и успешных; повтор после `failed` (провайдер недоступен) создаёт новую попытку того же ключа. |
| И-08-4 | Приоритет `analysis.extract` — 20: ниже импорта (50), выше пачек индексации (10); пачки ограничены временем, как `index.embed`. Поправка ADR-004 §7a. |
| И-08-5 | Правка предложения инженером — новый кандидат (`origin = human`, `derived_from_candidate_id`), прежний — `superseded`; содержимое кандидата не меняется. Подтверждение может уточнить формулировку: ревизия требования хранит текст подтверждающего, кандидат — исходный текст. |
| И-08-6 | Модель в 08 предлагает только кандидаты требований и фактов; предложения связей, покрытия и формулировок решений («может» в «AI safety») не реализуются без отдельного требования. |
| И-08-7 | Правило-извлечение — тоже `analysis_run` с провайдером `rules`; без перечня типов D-018 правил нет (Р-08-4). |
| И-08-8 | Единицы снимка, которые проверяющий читать не может, остаются `unreviewed` — завершить проход полноты может только пользователь с доступом ко всем единицам. |
| И-08-9 | Событие барьера `decision_recorded` пишется только для решений 08; решения импорта и удержаний его по-прежнему не порождают. |
