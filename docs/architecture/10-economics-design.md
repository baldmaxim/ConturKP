## 0. Границы этапа

**Делается:**
- экономический отчёт ревизии расчёта: составляющие по видам цены, сверка с итогом TenderHub, неподтверждённый остаток, неизвестные составляющие;
- сравнение двух выбранных ревизий расчёта одного тендера: разложение изменения по зафиксированному методу, Σ вкладов = итоговая разница;
- сопоставление позиций между ревизиями (детерминированные предложения и ручная проверка неоднозначных пар);
- причины изменений: модель предлагает, инженер подтверждает;
- расширение контракта адаптера для отсутствующих коммерческих составляющих;
- единая функция сопоставимости денег и десятичная арифметика (ADR-005).

**Не делается:**
- сравнение выпусков и отправок — этап 15. `comparison` из `data-model.md` §4.11 там строится поверх сравнения ревизий выпуска (§5.7);
- MCP-инструменты `get_economics`, `compare_releases`, `propose_change_reason` — этап 16;
- снятие `CALCULATION_PROVISIONAL` (X-01 и Q-01 в силе);
- извлечение цен поставщика из документов. Цены поставщика нет в модели источника (п. 1, И-10-1): этап вводит вид цены `supplier_quote` и правило сопоставимости, но не данные;
- собственная смета портала и корректировки сумм (ADR-007 §1);
- живая модель — `NOT_RUN` (U-01, U-05), проверка механизма — поддельной моделью.

## 3. Состояния

- **`revision_economics`** — без состояний. Отчёт пересчитывается только при новой `method_version` (новая строка, прежняя сохраняется).
- **`calculation_comparison`** — `computing` → `ready` | `failed`. Создаётся синхронно в одной транзакции (§6).
  - Считается **устаревшим** (вычисляемый признак, сравнение не меняется), если по паре ревизий появилось решение о сопоставлении с `seq` > `lineage_seq` или если основание подтверждённой причины инвалидировано.
  - Новое сравнение — новая строка. Подтверждённые причины прежнего сравнения для той же единицы (тот же состав позиций) предлагаются как «подтверждено в сравнении №N», но сами не переносятся.
- **`position_lineage`** — как в 0011: предложение `proposed` → решение `confirmed` / `rejected` новой строкой. Действует последняя строка по паре позиций.
- **`change_explanation`** — `unknown` (по умолчанию для каждой единицы с ненулевой дельтой) → `hypothesis` (человек записал предполагаемую причину без достаточного основания) → `confirmed` (человек с основанием). Любой статус можно вернуть в `unknown` новой версией. Предложения модели — отдельные объекты `change_reason_suggestion`: в причину они попадают только решением человека. Инвалидация основания даёт отметку «основание изменилось», объект не меняется.
- **`reason_run`** — `queued` → `running` → `completed` / `completed_with_gaps` / `failed`, как `review_run`.
- **`change_reason_suggestion`** — `open` → `accepted` (создаётся версия причины `confirmed` с основаниями предложения, решение человека) | `rejected` | `expired` (инвалидация).

## 5. Темы, которые задание требует описать отдельно

### 5.1. Метод разложения (В-10-3)

**Строка** (пара строк по ключу внутри единицы). Себестоимость:
- C = Q·K·(R·F·(1 + d) + D), где Q — количество, K — расход (1 у работ и привязанных материалов), R — цена в валюте, F — курс (1 у ₽), d = 0,03 при «не в цене», D — доставка «суммой»;
- для работ — C = Q·R·F (п. 7).

Цепные подстановки:
1. Количество: Q₁K₁·U₀ − C₀.
2. Цена в валюте: Q₁K₁·U(R₁, F₀) − Q₁K₁·U(R₀, F₀).
3. Курс: Q₁K₁·U(R₁, F₁) − Q₁K₁·U(R₁, F₀).
4. Доставка: смена вида или суммы.
5. Хвост источника: C₁(источник) − C₁(модель). Это float64 источника; L1 показывает расхождение не больше 1e-9.

Коммерческая мера — M = C·k, где k = `commercial_markup`:
- вклады себестоимости × k₀;
- вклад «коэффициент» = C₁·(k₁ − k₀) — тактика, наценки, НДС, раскладка;
- хвост источника.

Если у одной из сторон нет коммерческой стоимости, коммерческая мера единицы — `incomparable` (п. 11, Т-10-9).

**Без пары.** Строка без пары — «состав: добавлено» C₁ или «состав: удалено» −C₀. Неоднозначная группа строк — «состав: изменён» ΣC₁ − ΣC₀ без дальнейшего разложения.

**Колонки КП** не раскладываются: показываются дельты колонок «материалы» и «работы». Если Σ колонок не изменилась, а колонки изменились, ставится признак «перенос между колонками» с нулевым итогом (c71ceeb, Т-10-5).

**Уровень тендера** (коммерческая мера): Δ`cached_grand_total` − Σ коммерческих дельт единиц = `unexplained_remainder`. По ключу его не разделить на страхование, свежесть итога и округление (L3, Т-10-2, Т-10-3).

### 5.2. Общие затраты (В-10-4)

Наценки, накладные и прибыль сидят в коэффициенте строки (п. 8). Их изменение — вклад «коэффициент» по строкам, распределять нечего.

Затраты уровня тендера — страхование, снижение, перераспределение, корректировки позиций — по ключу недоступны (семантика §4) и **не распределяются по позициям**. Они видны отдельными строками уровня тендера со статусом «недоступно по ключу», а их совокупный эффект — внутри `unexplained_remainder`.

### 5.3. Сопоставление позиций (В-10-5, X-02)

Предложения строятся при создании сравнения, только для пар позиций без решения. Все методы детерминированные: TenderHub сам запрещает нечёткое сопоставление в аналитике версий (`TENDER_CHANGE_IMPACT_ANALYTICS.md:36-51`).

Методы по порядку:
1. **`source_lineage`** — та же внешняя позиция: обе ревизии получены из одной версии тендера TenderHub.
2. **`exact_key`** — ключ change-impact `норм(item_no) | норм(work_name) | норм(unit_code)`, уникальный с обеих сторон.
3. **`position_key`** — ключ clone `position_number | is_additional | work_name`, уникальный с обеих сторон.

Пара, на которой два ключа расходятся, не предлагается: она идёт на ручную проверку с обоими кандидатами. Разделы (`is_section`, без строк) не сопоставляются.

Неоднозначные группы (повтор ключа: одна работа в разных секциях и этажах) автоматически не склеиваются (спецификация §10). Инженер выбирает пары вручную, в том числе 1 → N и N → 1 (A22).

Живой масштаб (L7c, № 330 v4 → v5, позиции со строками): `exact_key` — 379 пар, `position_key` дополнительно разрешает 265, противоречий 0.

Решения пишутся append-only в `position_lineage` с `If-Match` по `lineage_seq` пары ревизий (I13). Пакетное подтверждение группы предложений одного метода — одна транзакция: строки с одним автором и временем и одна запись журнала со списком пар.

### 5.4. Сопоставимость (В-10-2)

Функция `comparable(a, b)` в `packages/core/src/money` — единственная точка сравнения денег (ADR-005; прямые сравнения ловятся ревью и тестом-сканером по `packages/` и `apps/`). Сравниваются валюта, `vat`, `priceKind`, база единицы.

Уточнение для ревизий TenderHub (по В-10-2 А): одно и то же поле источника (`total_amount` с `total_amount`, сумма колонок с суммой колонок) при одинаковой версии семантики адаптера сравнимо и при `vat: unknown` с обеих сторон. Изменение НДС в тактике видно вкладом «коэффициент». Любая другая пара с `unknown` — `incomparable` с причиной.

### 5.5. Сверка и неподтверждённый остаток (В-10-1, Q-05)

Отчёт ревизии:
- **цель сверки** — `cached_grand_total`;
- **подтверждённая часть** — Σ колонок по строкам (= Σ `commercial_total` позиций, L3);
- **остаток** = цель − round2(Σ); `reconciled`, если остаток ≤ допуска (0,01, пишется в результат, D-016), иначе `residual_unconfirmed` с суммой остатка и перечнем возможных составляющих «недоступно по ключу».

Остаток не выдаётся за страхование. `kp_total_rule` и `kpTotal` (итог КП для выпуска) этап 10 не задаёт: это решение этапа 13 и X-01.

### 5.6. Контракт адаптера `adapter-2` — отсутствующие составляющие

`docs/contracts/adapters.md` §2 дополняется: адаптер возвращает `commercialComponents[]`:

```
{ code: 'insurance' | 'reduction' | 'redistribution' | 'position_adjustments' | 'vat' | 'fi_breakdown' | 'calculation_state',
  status: 'available' | 'unavailable_by_key' | 'not_in_source_model',
  reason: string, source: { route, contractVersion }, value?: IMoney }
```

Для транспорта `api` все семь — `unavailable_by_key` с маршрутом JWT из семантики §4. Значение не выводится из других полей: остаток L3 в `insurance` не записывается.

Транспорт D-016 (прямое чтение БД) или доработка X-01 смогут заполнить `available` без изменения ядра. Версия контракта — `th-api-2026-09-02/adapter-2`, состав выгрузки и хэш содержимого не меняются.

### 5.7. Связь со сравнением выпусков (этап 15)

`data-model.md` §4.11 описывает `comparison` между выпусками. Этап 10 сравнивает ревизии, потому что выпусков до этапа 13 нет (И-10-3). Этап 15 строит сравнение выпусков поверх `calculation_comparison` ревизий, на которых выпуски закреплены, и добавляет различия файлов и отправок. Заготовка §4.11 уточняется в `data-model.md` при реализации.

### 5.8. Причины изменений (В-10-8)

Причина ставится на единицу сравнения: позицию или группу разделения и слияния.

Инженер может:
- поставить причину вручную с основанием;
- запустить `reason_run` по выбранным единицам.

Пакет модели содержит:
- наименование, единицу и вклады единицы — строками, только как контекст, модель не считает;
- кандидатов-основания: результат поиска портала в закреплённой области, только фрагменты, читаемые запустившим (`stageVisibility`).

Ответ модели — вид причины, обоснование и ссылки на фрагменты из пакета. Ссылки вне пакета отбрасываются, числа из ответа в суммы не превращаются.

Без подтверждения человека причина остаётся `unknown` (I11, A23). Отказ модели — `completed_with_gaps`, причины не меняются.

## 8. Экраны

Вкладка этапа «Экономика». Проверяется на 360, 390 и 1280 px, в тёмной и светлой теме.

1. **Отчёт ревизии.** Карточки: себестоимость, коммерческая стоимость и колонки, итог TenderHub, подтверждённая часть, неподтверждённый остаток; список «недоступно по ключу»; строки без коммерческой стоимости; плашка `CALCULATION_PROVISIONAL`.
2. **Сравнение.** Выбор двух ревизий (по умолчанию — предыдущая и последняя ревизии этапа). Сводная таблица вкладов по компонентам для обеих мер; остаток уровня тендера; признак «устарело». На телефоне — карточки.
3. **Сопоставление.** Группы предложений по методам с пакетным подтверждением; неоднозначные группы с ручным выбором пар; решения с автором.
4. **Единицы.** Таблица или карточки: Δ, вклады, сопоставимость, причина со статусом; диалог причины с основаниями; гипотезы модели отдельно от подтверждённых.

## 9. Инварианты БД (вторая линия)

1. `comparison_unit` и `comparison_effect` вставляются только в транзакции, создавшей сравнение, пока оно `computing`; после `ready` / `failed` — запрет (frozen-after).
2. Отложенно при COMMIT: Σ `comparison_effect.amount` по единице и мере = дельта единицы (точное `numeric`).
3. Отложенно при COMMIT: Σ дельт единиц + строки уровня тендера = Δ итога по мере. Для `commercial` есть ровно одна строка `unexplained_remainder`.
4. Стороны сравнения — разные ревизии одного `tender_id`. `lineage_seq` не больше последнего `seq` по паре.
5. Каждая позиция обеих ревизий (кроме разделов) входит ровно в одну единицу сравнения.
6. `change_explanation` со статусом `confirmed`: автор — человек с `change_reason.confirm`, есть решение `change_reason_decision`, основания соответствуют виду; у `unknown` оснований нет.
7. `position_lineage`: `decided_by` = служебный пользователь допустим только для `source_lineage` / `exact_key` / `position_key` и только при `confirmed`; `manual` — человек.
8. `revision_economics`: одна строка на (ревизия, версия метода), неизменна.
9. `change_reason_suggestion_evidence`: фрагмент из закреплённой области прогона. Принятие — человек с правом.
10. Права `kontur_app` — как в §2; `DELETE` и `TRUNCATE` запрещены.

## 11. Вопросы владельцу (В-10-N)

Вопросы по самому TenderHub — Т-10-1…Т-10-10 (семантика §8): их тоже задаём сейчас. Подтверждение таблицы семантики — В-10-9.

**В-10-1. Цель сверки итога (Q-05).**
- **А (рекомендуется)** — цель сверки `cached_grand_total`. Σ коммерческих стоимостей строк — подтверждённая часть; разница — «неподтверждённый остаток» с перечнем составляющих, недоступных по ключу. Последствия: отчёт строится на данных, доступных по ключу. На трёх живых тендерах остаток 0,01–1 % итога остаётся видимым и необъяснённым до Т-10-2 и Т-10-3. `kpTotal` для выпуска не задаётся.
- **Б** — цель сверки — итог «Финансовых показателей» (НДС сверху, снижение). Последствия: по ключу недоступен — сверка `BLOCKED_EXTERNAL` до доработки TenderHub.
- **В** — не сверять, показывать только суммы. Последствия: выход задания «сходится либо показывает остаток» не выполняется.

**В-10-2. НДС `unknown` при сравнении двух ревизий TenderHub (уточнение ADR-005 §5).**
- **А (рекомендуется)** — одно и то же поле источника при одной версии семантики сравнимо и при `vat: unknown`. Изменение НДС или тактики видно вкладом «коэффициент». Сравнение с ценой поставщика или между разными видами цены при `unknown` — `incomparable`. Последствия: сравнение ревизий работает до ответа на Т-10-1. Уточнение записывается в D-030 и ADR-005.
- **Б** — строго ADR-005: `unknown` с любой стороны → `incomparable`. Последствия: коммерческие и себестоимостные дельты не раскладываются до ответа на Т-10-1.

**В-10-3. Метод разложения совместных изменений.**
- **А (рекомендуется)** — цепные подстановки в фиксированном порядке: количество → цена в валюте → курс → доставка → коэффициент (§5.1). Последствия: каждый шаг проверяется вручную; совместный эффект относится к более позднему фактору, это записано в методе. Σ сходится точно.
- **Б** — те же шаги и отдельная строка «совместное изменение» (ΔQ·ΔP и т. п.). Последствия: прозрачнее, но больше строк; при пяти факторах — несколько строк взаимодействия.
- **В** — симметричное (интегральное) распределение совместного эффекта. Последствия: от порядка не зависит, вручную проверяется труднее.

**В-10-4. Общие затраты уровня тендера.**
- **А (рекомендуется)** — не распределять по позициям: отдельные строки уровня тендера со статусом «недоступно по ключу», эффект — в `unexplained_remainder`. Последствия: вклад позиции = только её строки; ничего не додумывается.
- **Б** — распределять пропорционально коммерческой стоимости, только для показа. Последствия: вклады позиций включают оценку, а не данные источника.

**В-10-5. Подтверждение пар позиций (X-02).** Живые данные (№ 330 v4 → v5, позиции со строками): `exact_key` даёт 379 однозначных пар, `position_key` — ещё 265, противоречий 0.
- **А (рекомендуется)** — система подтверждает пары `source_lineage` и `exact_key` (видно, отменяемо). Пары только по `position_key` — предложения, инженер подтверждает их пакетом. Расхождение ключей и неоднозначные группы — вручную. Последствия: ~40 % позиций на соседних версиях требуют одного пакетного решения; номер позиции, сдвигаемый вставкой, сам ничего не склеивает.
- **Б** — система подтверждает все три метода при отсутствии противоречий. Последствия: меньше ручной работы; риск ложной пары при сдвиге нумерации.
- **В** — каждую пару подтверждает инженер. Последствия: сотни решений на тендер.

**В-10-6. Курс без даты (ADR-005 §6).**
- **А (рекомендуется)** — курс ревизии — курс источника на момент выгрузки: `asOf` = время выгрузки с пометкой «дата наблюдения, не дата курса». Последствия: пересчёт валют возможен, происхождение курса прозрачно; ADR-005 уточняется в D-030.
- **Б** — валютные суммы не пересчитывать: вклады курса не выделять, валютные строки сравнивать только в валюте. Последствия: раскладка неполная, вклад «курс» уходит в «цену».

**В-10-7. Отрицательная согласованная корректировка и общий discount.**
- **А (рекомендуется)** — портал своих корректировок не вводит (ADR-007): отрицательные значения принимаются только из источника, знак нигде не ограничен, проверка — фикстурой. Discount — изменение коэффициента или составляющая уровня тендера. Последствия: портал не становится сметой.
- **Б** — ручная «согласованная корректировка» решением инженера как строка уровня тендера. Последствия: экономика перестаёт сходиться с TenderHub по построению; нужен отдельный поток согласования.

**В-10-8. Уровень причины изменения.**
- **А (рекомендуется)** — причина на единицу сравнения (позицию или группу разделения); модель запускается инженером по выбранным единицам. Последствия: обозримо, причина видна на уровне, на котором её подтверждают.
- **Б** — причина на каждый вклад (объём, цена, курс…). Последствия: точнее, но в разы больше решений.

**В-10-9. Семантика TenderHub.** Подтвердить таблицу `tenderhub-economics-semantics.md` §3 как есть или с поправками; ответить на Т-10-1…Т-10-10 (без ответа действует временная трактовка из её §8).
