## 0. Границы этапа

**Делается:**
- экономический отчёт ревизии расчёта: составляющие по видам цены, сверка с итогом TenderHub, неподтверждённый остаток, неизвестные составляющие;
- сравнение двух выбранных ревизий расчёта одного тендера: разложение изменения по зафиксированному методу, Σ вкладов = итоговая разница;
- сопоставление позиций между ревизиями (детерминированные предложения и ручная проверка неоднозначных пар);
- причины изменений: модель предлагает, инженер подтверждает;
- расширение контракта адаптера для отсутствующих коммерческих составляющих;
- единая функция сопоставимости денег и десятичная арифметика (ADR-005).

**Не делается:**
- сравнение выпусков и отправок — этап 15. `comparison` из `data-model.md` §4.11 там строится поверх сравнения ревизий выпуска (§5.7);
- MCP-инструменты `get_economics`, `compare_releases`, `propose_change_reason` — этап 16;
- снятие `CALCULATION_PROVISIONAL` (X-01 и Q-01 в силе);
- извлечение цен поставщика из документов. Цены поставщика нет в модели источника (п. 1, И-10-1): этап вводит вид цены `supplier_quote` и правило сопоставимости, но не данные;
- собственная смета портала и корректировки сумм (ADR-007 §1);
- живая модель — `NOT_RUN` (U-01, U-05), проверка механизма — поддельной моделью.

## 3. Состояния

- **`revision_economics`** — без состояний. Отчёт пересчитывается только при новой `method_version` (новая строка, прежняя сохраняется).
- **`calculation_comparison`** — `computing` → `ready` | `failed`. Создаётся синхронно в одной транзакции (§6).
  - Считается **устаревшим** (вычисляемый признак, сравнение не меняется), если по паре ревизий появилось решение о сопоставлении с `seq` > `lineage_seq` или если основание подтверждённой причины инвалидировано.
  - Новое сравнение — новая строка. Подтверждённые причины прежнего сравнения для той же единицы (тот же состав позиций) предлагаются как «подтверждено в сравнении №N», но сами не переносятся.
- **`position_lineage`** — как в 0011: предложение `proposed` → решение `confirmed` / `rejected` новой строкой. Действует последняя строка по паре позиций.
- **`change_explanation`** — `unknown` (по умолчанию для каждой единицы с ненулевой дельтой) → `hypothesis` (человек записал предполагаемую причину без достаточного основания) → `confirmed` (человек с основанием). Любой статус можно вернуть в `unknown` новой версией. Предложения модели — отдельные объекты `change_reason_suggestion`: в причину они попадают только решением человека. Инвалидация основания даёт отметку «основание изменилось», объект не меняется.
- **`reason_run`** — `queued` → `running` → `completed` / `completed_with_gaps` / `failed`, как `review_run`.
- **`change_reason_suggestion`** — `open` → `accepted` (создаётся версия причины `confirmed` с основаниями предложения, решение человека) | `rejected` | `expired` (инвалидация).

## 4. Проверки задания — матрица поведения

Каждый пункт «Проверки» задания имеет поведение и тест в этом этапе. Эталонные значения задаются до запуска и лежат рядом с тестом (`test-plan.md:24`).

| Проверка задания | Поведение | Тест (Unit / Integration) |
|---|---|---|
| decimal и округления | вся арифметика в `packages/core/src/money` на decimal.js с точностью, исключающей округление промежуточных значений: превышение точности — ошибка, а не тихое округление. Округление только в именованной политике `money2_half_away` (как `cached_grand_total`); разница округления — отдельная строка, не подгонка. Десятичный пересчёт строки хранится отдельно (`revision_line_check`) с явными методом и допуском; полученные `total_amount` не меняются, различия float64 показываются (D-030 п. 7) | U: 21 значащая цифра, 1.005 → 1.01, −1.005 → −1.01; I: Σ строк = Σ `numeric` в БД; строка с хвостом float вне допуска — видна в `line_check`, `calculation_line` не изменена |
| валюта | валютная строка: себестоимость по формуле источника, раскладка — цена в валюте × курс **своей** ревизии (курс каждой ревизии хранится в её содержимом, текущим не заменяется — D-030 В-10-6). Смена валюты строки между ревизиями — один вклад «цена (смена валюты)». Суммы разных валют без курса не складываются | U: USD-строка, курс изменился, цена нет → только вклад «курс»; I: строка CNY живого вида |
| цены с/без НДС | функция сопоставимости: разные `vat` → `incomparable` с причиной. При неизвестном НДС сравниваются только значения одного поля и одного вида цены между ревизиями (D-030 В-10-2); сравнение с ценой поставщика при `vat: unknown` — `incomparable` (A21). Вклад коэффициента не называется изменением НДС | U: `excluded` vs `unknown` → incomparable; cost vs commercial → incomparable (A19); одно поле одного вида цены при `unknown` → comparable; подпись вклада «коэффициент» без слова «НДС» |
| единичная цена vs итог | сравниваются итоги, а не единичные цены. Единичная цена = итог / количество (позиция — / объём ГП) — только для показа, по политике округления; при нуле или пустом объёме — «не определена» (L6b). Единица и база объёма входят в сопоставимость (A18) | U: 100 / шт против 1 000 за 10 шт → сопоставимо, вклад 0; позиция с пустым объёмом ГП → цена не определена, без деления на 0 |
| quantity = 0 | в исследованной версии источника количество строки > 0, но портал сохраняет и полученные нулевые и отрицательные значения и показывает их отклонением (D-030 п. 4, §5.9); объём позиции 0 / null бывает. Деление в разложении не используется: Q = 0 даёт нулевую базу подстановки, а не ошибку | U: Q₀ = 0 и Q₁ < 0 раскладываются, Σ = Δ; I: строка с quantity = 0 сохраняется, в отчёте — отклонение; позиция `manual_volume` = 0 |
| отрицательная согласованная корректировка | знак нигде не ограничен. Отрицательные суммы из источника сохраняются как получены, раскладываются и округляются симметрично; в отчёте — отклонение от ограничений исследованной версии, а не ошибка и не исправление (D-030). Своих корректировок портал не вводит (В-10-7) | U: отрицательная строка и разложение; I: фикстура с отрицательной строкой проходит выгрузку, отчёт и сравнение |
| замена / разделение позиции | единица сравнения = компонента связности пар (1 → 2, 2 → 1, замена — подтверждённая пара разных работ). Строки сопоставляются ключом строки внутри единицы; каждая строка входит в одну единицу — двойного эффекта нет (A22) | I: разделение 1 → 2 с подтверждёнными парами: Σ вкладов единицы = Δ, нет повторного учёта |
| цена + объём одновременно | метод цепных подстановок (В-10-3) в порядке количество → цена в валюте → курс → доставка → коэффициент (A20); порядок и отнесение совместного эффекта к более позднему фактору показываются в отчёте сравнения (D-030) | U: эталон A20 — числа заданы в тесте до кода |
| общий discount | скидка в тактике = изменение коэффициента у всех строк — вклад «коэффициент». Снижение тендера по ключу недоступно — составляющая «недоступно», а не 0. Скидка уровня тендера из будущего транспорта — строка уровня тендера без распределения (В-10-4) | U: −5 % коэффициента на всех строках → Σ вкладов «коэффициент» = Δ |
| сумма вкладов = итоговая разница | инвариант ядра и вторая линия в БД (§9, п. 2–3): по каждой единице и по сравнению, по мерам `cost` и `commercial`; остаток уровня тендера — строка `unexplained_remainder` | U: свойство на случайных парах (детерминированный генератор); I: триггер отвергает несходящиеся вклады |
| повторный импорт не меняет результат | повтор выгрузки с тем же содержимым ревизию не создаёт (0011); сравнение детерминировано: тот же вход → тот же `result_sha256`. Повтор POST с тем же `Idempotency-Key` → то же сравнение | I: выгрузка A → A, сравнение дважды → один хэш; A → B → A: ревизии разные, сравнение A↔A' — нулевые вклады |

Приёмочные A18–A23 (`test-plan.md:48-53,108`): A18 — U + I; A19 — U (incomparable, не ошибка); A20 — U; A21 — U (несопоставимость и неполнота, не уверенное замечание); A22 — I; A23 — I (цена изменилась без документа → причина `unknown`; гипотеза модели сама не подтверждается).

## 5. Темы, которые задание требует описать отдельно

### 5.1. Метод разложения (В-10-3)

**Строка** (пара строк по ключу внутри единицы). Себестоимость:
- C = Q·K·(R·F·(1 + d) + D), где Q — количество, K — расход (1 у работ и привязанных материалов), R — цена в валюте, F — курс (1 у ₽), d = 0,03 при «не в цене», D — доставка «суммой»;
- для работ — C = Q·R·F (п. 7).

Цепные подстановки:
1. Количество: Q₁K₁·U₀ − C₀.
2. Цена в валюте: Q₁K₁·U(R₁, F₀) − Q₁K₁·U(R₀, F₀).
3. Курс: Q₁K₁·U(R₁, F₁) − Q₁K₁·U(R₁, F₀).
4. Доставка: смена вида или суммы.
5. Хвост источника: C₁(источник) − C₁(модель). Это float64 источника; L1 показывает расхождение не больше 1e-9.

Совместный эффект (например, ΔQ·ΔR) по построению относится к более позднему фактору порядка. Это правило и сам порядок выводятся в отчёте сравнения рядом со сводкой вкладов (`method_description`, D-030 В-10-3). Курсы F₀ и F₁ берутся из содержимого своих ревизий.

Коммерческая мера — M = C·k, где k = `commercial_markup`:
- вклады себестоимости × k₀;
- вклад «коэффициент строки (наценки, тактика, раскладка)» = C₁·(k₁ − k₀). Изменением НДС он не называется без подтверждённого основания (D-030 В-10-2);
- хвост источника.

Если у одной из сторон нет коммерческой стоимости, коммерческая мера единицы — `incomparable` (пустая стоимость ≠ 0, Т-10-9).

Опора разложения — полученные суммы C₀ и C₁ (`total_amount` как получено, D-030 п. 7); модель формулы нужна только для промежуточных подстановок. Строка с типом вне явного перечня (`formula = not_applicable`) не раскладывается: её дельта целиком — вклад «без разложения» с причиной.

**Без пары.** Строка без пары — «состав: добавлено» C₁ или «состав: удалено» −C₀. Неоднозначная группа строк — «состав: изменён» ΣC₁ − ΣC₀ без дальнейшего разложения.

**Колонки КП** не раскладываются: показываются дельты колонок «материалы» и «работы». Если Σ колонок не изменилась, а колонки изменились, ставится признак «перенос между колонками» с нулевым итогом (c71ceeb, Т-10-5).

**Уровень тендера** (коммерческая мера): Δ`cached_grand_total` − Σ коммерческих дельт единиц = `unexplained_remainder`. Остаток показывается отдельно и по единицам не распределяется (D-030 В-10-1). По ключу его не разделить на страхование, свежесть итога и округление (L3); составляющие и статус пересчёта — неизвестны (временная трактовка Т-10-2, Т-10-3).

### 5.2. Общие затраты (В-10-4)

Наценки, накладные и прибыль сидят в коэффициенте строки (п. 8). Их изменение — вклад «коэффициент» по строкам, распределять нечего.

Затраты уровня тендера — страхование, снижение, перераспределение, корректировки позиций — по ключу недоступны (семантика §4) и **не распределяются по позициям**. Они видны отдельными строками уровня тендера со статусом «недоступно по ключу», а их совокупный эффект — внутри `unexplained_remainder`.

### 5.3. Сопоставление позиций (В-10-5, X-02)

Предложения строятся при создании сравнения, только для пар позиций без решения. Все методы детерминированные: TenderHub сам запрещает нечёткое сопоставление в аналитике версий (`TENDER_CHANGE_IMPACT_ANALYTICS.md:36-51`).

Методы по порядку (D-030 В-10-5):
1. **`source_lineage`** — та же внешняя позиция. Система подтверждает пару только при одновременном совпадении экземпляра (идентификатор из конфигурации), тендера, версии и UUID позиции и строгом соответствии один к одному (D-030 «Дополнение»; условия — §2). Экземпляр неизвестен (идентификатор не задан, выгрузки до этапа 10) или соответствие не один к одному — предложение.
2. **`exact_key`** — ключ change-impact `норм(item_no) | норм(work_name) | норм(unit_code)`, уникальный с обеих сторон — **предложение**: уникальность совпадения не доказывает устойчивую идентичность.
3. **`position_key`** — ключ clone `position_number | is_additional | work_name`, уникальный с обеих сторон — **предложение**.

Предложения `exact_key` и `position_key` подтверждает инженер, в том числе пакетом по методу. Автоподтверждение по ключу TenderHub включается только после подтверждения канонического ключа (Т-10-6) — отдельным решением владельца.

Пара, на которой два ключа расходятся, не предлагается: она идёт на ручную проверку с обоими кандидатами. Разделы (`is_section`, без строк) не сопоставляются.

Неоднозначные группы (повтор ключа: одна работа в разных секциях и этажах) автоматически не склеиваются (спецификация §10). Неоднозначные пары и разделения инженер выбирает вручную, в том числе 1 → N и N → 1 (A22); пакетом они не подтверждаются.

Живой масштаб (L7c, № 330 v4 → v5, позиции со строками): `exact_key` — 379 пар, `position_key` дополнительно разрешает 265, противоречий 0.

Решения пишутся append-only в `position_lineage` с `If-Match` по `lineage_seq` пары ревизий (I13). Пакетное подтверждение группы предложений одного метода — одна транзакция: строки с одним автором и временем и одна запись журнала со списком пар.

### 5.4. Сопоставимость (В-10-2)

Функция `comparable(a, b)` в `packages/core/src/money` — единственная точка сравнения денег (ADR-005; прямые сравнения ловятся ревью и тестом-сканером по `packages/` и `apps/`). Сравниваются валюта, `vat`, `priceKind`, база единицы.

Уточнение ADR-005 §5 (D-030 В-10-2): при неизвестном НДС сравниваются значения **одного поля и одного вида цены** между ревизиями (`total_amount` с `total_amount`, сумма колонок с суммой колонок) при одинаковой версии семантики адаптера. Любая другая пара с `unknown` — `incomparable` с причиной. Изменение коэффициента не называется изменением НДС без подтверждённого основания. Валюта сумм TenderHub — RUB (п. 7; у коммерческих — вывод из принятой формулы, D-030 «Дополнение»), `unit_rate` — валюта строки; суммы разных валют без курса ревизии не складываются.

### 5.5. Сверка и неподтверждённый остаток (В-10-1, Q-05)

Отчёт ревизии:
- **цель сверки** — `cached_grand_total` как последнее наблюдаемое материализованное значение (формула со страхованием — описанный алгоритм исследованного кода, D-030 п. 11);
- **подтверждённая часть** — Σ колонок по строкам (= Σ `commercial_total` позиций, L3);
- **остаток** = цель − round2(Σ); `reconciled`, если остаток ≤ допуска (0,01, пишется в результат, D-016), иначе `residual_unconfirmed` с суммой остатка. Рядом — перечень составляющих, недоступных по ключу, и статус пересчёта «неизвестен» — без утверждения, что они объясняют остаток (D-030 п. 11).

Остаток показывается отдельно, искусственно не распределяется, не объясняется страхованием, округлением или задержкой пересчёта и утверждённым итогом КП не считается (D-030 В-10-1, п. 11). `kp_total_rule` и `kpTotal` (итог КП для выпуска) этап 10 не задаёт: это решение этапа 13 и X-01.

Отдельной строкой отчёт показывает привязанные материалы, у которых количество строки не равно выводу из работы (L1b): стоимость — от хранимого количества, выведенное хранится как диагностика и его не заменяет, причина не угадывается (D-030 п. 4, временная трактовка Т-10-7).

### 5.6. Контракт адаптера `adapter-2` — отсутствующие составляющие

`docs/contracts/adapters.md` §2 дополняется: адаптер возвращает `commercialComponents[]`:

```
{ code: 'insurance' | 'reduction' | 'redistribution' | 'position_adjustments' | 'vat' | 'fi_breakdown' | 'calculation_state',
  status: 'available' | 'unavailable_by_key' | 'not_in_source_model',
  reason: string, source: { route, contractVersion }, value?: IMoney }
```

Для транспорта `api` все семь — `unavailable_by_key` с маршрутом JWT из семантики §4. Значение не выводится из других полей: остаток L3 в `insurance` не записывается.

Результат выгрузки дополняется `sourceInstanceId` (из конфигурации) и `sourceOrigin` (адрес подключения, §2). Даты цены и действия предложения адаптер не получает (п. 10): в API они — явно «неизвестно».

Транспорт D-016 (прямое чтение БД) или доработка X-01 смогут заполнить `available` без изменения ядра. Версия контракта — `th-api-2026-09-02/adapter-2`, состав выгрузки и хэш содержимого не меняются.

### 5.7. Связь со сравнением выпусков (этап 15)

`data-model.md` §4.11 описывает `comparison` между выпусками. Этап 10 сравнивает ревизии, потому что выпусков до этапа 13 нет (И-10-3). Этап 15 строит сравнение выпусков поверх `calculation_comparison` ревизий, на которых выпуски закреплены, и добавляет различия файлов и отправок. Заготовка §4.11 уточняется в `data-model.md` при реализации.

### 5.8. Причины изменений (В-10-8)

Причина ставится на единицу сравнения: позицию или группу разделения и слияния.

Инженер может:
- поставить причину вручную с основанием;
- запустить `reason_run` по выбранным единицам.

Пакет модели содержит:
- наименование, единицу и вклады единицы — строками, только как контекст, модель не считает;
- кандидатов-основания: результат поиска портала в закреплённой области, только фрагменты, читаемые запустившим (`stageVisibility`).

Ответ модели — вид причины, обоснование и ссылки на фрагменты из пакета. Ссылки вне пакета отбрасываются, числа из ответа в суммы не превращаются.

Без подтверждения человека причина остаётся `unknown` (I11, A23). Отказ модели — `completed_with_gaps`, причины не меняются.

### 5.9. Отклонения от ограничений источника (D-030)

Ограничения исследованной версии TenderHub — не основание молча отбрасывать или исправлять полученные данные. Строка сохраняется как получена, а отчёт ревизии показывает отклонения по видам (`revision_line_check.flags`, сводка `revision_economics.deviations`):
- `quantity_nonpositive` — количество ≤ 0 или пусто;
- `negative_amount` — отрицательные `unit_rate`, `delivery_amount`, `total_amount` или коммерческие колонки;
- `unknown_item_type` — тип вне явного перечня п. 13 (`formula = not_applicable`);
- `missing_commercial` — пустая коммерческая стоимость (не 0);
- `missing_fx_rate` — валютная строка без курса ревизии;
- `bound_quantity_mismatch` — количество привязанного материала ≠ вывод из работы (диагностика п. 4);
- `recompute_outside_tolerance` — десятичный пересчёт вне допуска (п. 7).

Группировка материалов и работ — только по явному перечню типов п. 13, не по префиксу строки.

## 8. Экраны

Вкладка этапа «Экономика». Проверяется на 360, 390 и 1280 px, в тёмной и светлой теме.

1. **Отчёт ревизии.** Карточки: себестоимость, коммерческая стоимость и колонки, итог TenderHub, подтверждённая часть, неподтверждённый остаток (отдельно, «не итог КП», без объяснения причины); список «недоступно по ключу» и статус пересчёта «неизвестен»; сводка десятичного пересчёта с методом и допуском; отклонения по видам §5.9 со списком строк; курсы ревизии с пометкой «дата наблюдения»; плашка `CALCULATION_PROVISIONAL`.
2. **Сравнение.** Выбор двух ревизий (по умолчанию — предыдущая и последняя ревизии этапа). Сводная таблица вкладов по компонентам для обеих мер; под ней — порядок подстановок и правило отнесения совместного эффекта; остаток уровня тендера; признак «устарело». На телефоне — карточки.
3. **Сопоставление.** Группы предложений по методам с пакетным подтверждением; неоднозначные группы с ручным выбором пар; решения с автором.
4. **Единицы.** Таблица или карточки: Δ, вклады, сопоставимость, причина со статусом; диалог причины с основаниями; гипотезы модели отдельно от подтверждённых.

## 9. Инварианты БД (вторая линия)

1. `comparison_unit` и `comparison_effect` вставляются только в транзакции, создавшей сравнение, пока оно `computing`; после `ready` / `failed` — запрет (frozen-after).
2. Отложенно при COMMIT: Σ `comparison_effect.amount` по единице и мере = дельта единицы (точное `numeric`).
3. Отложенно при COMMIT: Σ дельт единиц + строки уровня тендера = Δ итога по мере. Для `commercial` есть ровно одна строка `unexplained_remainder`.
4. Стороны сравнения — разные ревизии одного `tender_id`. `lineage_seq` не больше последнего `seq` по паре.
5. Каждая позиция обеих ревизий (кроме разделов) входит ровно в одну единицу сравнения.
6. `change_explanation` со статусом `confirmed`: автор — человек с `change_reason.confirm`, есть решение `change_reason_decision`, основания соответствуют виду; у `unknown` оснований нет.
7. `position_lineage`: `decided_by` = служебный пользователь допустим только для `source_lineage`, только при `confirmed` и только если выгрузки обеих ревизий имеют одинаковый ненулевой `source_instance_id` и один `external_tender_id`, а `from_external_position_id = to_external_position_id` (D-030); `exact_key` / `position_key` и `manual` подтверждает человек.
8. `revision_line_check`: вставка только вместе с `revision_economics` той же версии метода; неизменна. `calculation_capture.source_instance_id` и `source_origin` после создания выгрузки не меняются.
9. `revision_economics`: одна строка на (ревизия, версия метода), неизменна.
10. `change_reason_suggestion_evidence`: фрагмент из закреплённой области прогона. Принятие — человек с правом.
11. Права `kontur_app` — как в §2; `DELETE` и `TRUNCATE` запрещены.

- Т-10-1…Т-10-10: временные трактовки, не ответы владельца TenderHub (§11.1).

Ниже — исходные формулировки вопросов, сохранённые для истории.

**В-10-1. Цель сверки итога (Q-05).**
- **А (рекомендуется)** — цель сверки `cached_grand_total`. Σ коммерческих стоимостей строк — подтверждённая часть; разница — «неподтверждённый остаток» с перечнем составляющих, недоступных по ключу. Последствия: отчёт строится на данных, доступных по ключу. На трёх живых тендерах остаток 0,01–1 % итога остаётся видимым и необъяснённым до Т-10-2 и Т-10-3. `kpTotal` для выпуска не задаётся.
- **Б** — цель сверки — итог «Финансовых показателей» (НДС сверху, снижение). Последствия: по ключу недоступен — сверка `BLOCKED_EXTERNAL` до доработки TenderHub.
- **В** — не сверять, показывать только суммы. Последствия: выход задания «сходится либо показывает остаток» не выполняется.

**В-10-2. НДС `unknown` при сравнении двух ревизий TenderHub (уточнение ADR-005 §5).**
- **А (рекомендуется)** — одно и то же поле источника при одной версии семантики сравнимо и при `vat: unknown`. Изменение НДС или тактики видно вкладом «коэффициент». Сравнение с ценой поставщика или между разными видами цены при `unknown` — `incomparable`. Последствия: сравнение ревизий работает до ответа на Т-10-1. Уточнение записывается в D-030 и ADR-005.
- **Б** — строго ADR-005: `unknown` с любой стороны → `incomparable`. Последствия: коммерческие и себестоимостные дельты не раскладываются до ответа на Т-10-1.

**В-10-3. Метод разложения совместных изменений.**
- **А (рекомендуется)** — цепные подстановки в фиксированном порядке: количество → цена в валюте → курс → доставка → коэффициент (§5.1). Последствия: каждый шаг проверяется вручную; совместный эффект относится к более позднему фактору, это записано в методе. Σ сходится точно.
- **Б** — те же шаги и отдельная строка «совместное изменение» (ΔQ·ΔP и т. п.). Последствия: прозрачнее, но больше строк; при пяти факторах — несколько строк взаимодействия.
- **В** — симметричное (интегральное) распределение совместного эффекта. Последствия: от порядка не зависит, вручную проверяется труднее.

**В-10-4. Общие затраты уровня тендера.**
- **А (рекомендуется)** — не распределять по позициям: отдельные строки уровня тендера со статусом «недоступно по ключу», эффект — в `unexplained_remainder`. Последствия: вклад позиции = только её строки; ничего не додумывается.
- **Б** — распределять пропорционально коммерческой стоимости, только для показа. Последствия: вклады позиций включают оценку, а не данные источника.

**В-10-5. Подтверждение пар позиций (X-02).** Живые данные (№ 330 v4 → v5, позиции со строками): `exact_key` даёт 379 однозначных пар, `position_key` — ещё 265, противоречий 0.
- **А (рекомендуется)** — система подтверждает пары `source_lineage` и `exact_key` (видно, отменяемо). Пары только по `position_key` — предложения, инженер подтверждает их пакетом. Расхождение ключей и неоднозначные группы — вручную. Последствия: ~40 % позиций на соседних версиях требуют одного пакетного решения; номер позиции, сдвигаемый вставкой, сам ничего не склеивает.
- **Б** — система подтверждает все три метода при отсутствии противоречий. Последствия: меньше ручной работы; риск ложной пары при сдвиге нумерации.
- **В** — каждую пару подтверждает инженер. Последствия: сотни решений на тендер.

**В-10-6. Курс без даты (ADR-005 §6).**
- **А (рекомендуется)** — курс ревизии — курс источника на момент выгрузки: `asOf` = время выгрузки с пометкой «дата наблюдения, не дата курса». Последствия: пересчёт валют возможен, происхождение курса прозрачно; ADR-005 уточняется в D-030.
- **Б** — валютные суммы не пересчитывать: вклады курса не выделять, валютные строки сравнивать только в валюте. Последствия: раскладка неполная, вклад «курс» уходит в «цену».

**В-10-7. Отрицательная согласованная корректировка и общий discount.**
- **А (рекомендуется)** — портал своих корректировок не вводит (ADR-007): отрицательные значения принимаются только из источника, знак нигде не ограничен, проверка — фикстурой. Discount — изменение коэффициента или составляющая уровня тендера. Последствия: портал не становится сметой.
- **Б** — ручная «согласованная корректировка» решением инженера как строка уровня тендера. Последствия: экономика перестаёт сходиться с TenderHub по построению; нужен отдельный поток согласования.

**В-10-8. Уровень причины изменения.**
- **А (рекомендуется)** — причина на единицу сравнения (позицию или группу разделения); модель запускается инженером по выбранным единицам. Последствия: обозримо, причина видна на уровне, на котором её подтверждают.
- **Б** — причина на каждый вклад (объём, цена, курс…). Последствия: точнее, но в разы больше решений.

## 13. Реализация и уточнения (после D-030)

Технические уточнения при реализации; решений владельца они не меняют.

1. **Причина без отдельной записи `decision`.** Версия `change_explanation` — неизменяемая запись решения человека: автор, право `change_reason.confirm`, `If-Match` по версии единицы. Вид `decision_type` не расширялся. Основания — фрагменты и (для внутреннего решения) решения тендера.
2. **Решения по парам** — по-прежнему с правом `calculation.capture`. В БД добавлен охранник автора `position_lineage`: человек — участник тендера с этим правом; служебный пользователь `system.lineage` — только `source_lineage`, `confirmed`, тот же UUID, один экземпляр, тендер и известная одинаковая версия, без других решений по этим позициям.
3. **Отчёт ревизии** строится при первом запросе в отдельной транзакции под рекомендательной блокировкой ревизии, затем неизменен. Ключевые суммы — колонками, подробности — в `report`. Суммы и остаток сверяет охранник по содержимому ревизии. Пересчёт каждой строки — в `revision_line_check`; отчёт без него не фиксируется.
4. **Экземпляр источника** записывается при завершении выгрузки, а не при запросе: идентификатор есть только в конфигурации worker, который и читает TenderHub. Неверный формат `TENDERHUB_INSTANCE_ID` — ошибка конфигурации.
5. **Единицы сравнения.** Раздел без строк в сравнение не входит. Раздел со строками участвует как позиция, чтобы строки не терялись.
6. **Несопоставимая мера.** Если у строки единицы нет `total_amount` или коммерческой стоимости, мера единицы несопоставима, вкладов по ней нет. Суммы известных строк сохраняются, их дельта — в строке уровня тендера `incomparable_units`. Остаток уровня тендера — отдельная строка `unexplained_remainder`. Нулевые вклады не записываются.
7. **Пара строк без разложения.** Разная или неприменимая формула либо отсутствие курса ревизии — вклад «без разложения». Нет коэффициента у одной из сторон — коммерческая мера пары не раскладывается.
8. **Перенос между колонками КП** определяется с допуском 0,01: сумма колонок не изменилась, колонка «Материалы» изменилась.
9. **Дельты единиц считает сервер** (SQL `numeric`). Интерфейс денежной арифметики не выполняет.
10. **Гипотезы причин.**
    - Кандидаты-основания — полнотекстовая ветка поиска портала по наименованию единицы в последнем снимке области этапа: до 5 фрагментов на единицу, до 50 единиц на прогон. Закрепляются только фрагменты, читаемые запустившим; недоступные учитываются в охвате.
    - Модель предлагает только «документ», «ответ» и «поставщик»; происхождение цитаты должно соответствовать виду.
11. **Инвалидация.**
    - Замена основания (точное событие) отмечает подтверждённую причину и гасит открытую гипотезу.
    - Новые документы и переписка (консервативное событие, не расчёт) гасят открытые гипотезы прогонов на более старом снимке.
    - Гипотезы, записанные после обработанного события, сверяются с ним сразу (как R09-01).
12. **Нейтральная пометка сверки агрегатов.** Пометка сверки агрегатов выгрузки больше не говорит, что остаток — страхование (D-030 п. 11).
13. **Ввод цитат в диалоге причины.** В диалоге причины цитаты-основания вводятся идентификаторами фрагментов из поиска этапа; выбора цитат из списка в интерфейсе нет. Подтверждённые причины вида «документ», «ответ», «поставщик» в основном появляются принятием гипотезы модели.
14. **Инструмент живой пробы** — `artifacts/stage-10/semantics-probe.ts` и `.sql`. Это не часть продукта: он закоммичен как доказательство подтверждения семантики (шаг 1).
