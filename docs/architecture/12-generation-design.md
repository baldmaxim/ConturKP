## 0. Границы этапа

Делается:
- разметка образца шаблона и её проверка; генерация файлов приложений в формате образца из значений полей «заполненного» приложения;
- неизменяемый кандидат выпуска: закреплённые входы (ревизия расчёта, снимок области с ревизией набора источников, прогоны проверок, набор действующих решений, ревизии шаблонов, приложения и версии значений полей, вложения), точные файлы, manifest с SHA-256 и размерами, разделение «заказчику» / «внутреннее»;
- проверки сборки: остатки плейсхолдеров, заполненность, совпадение связанных чисел с расчётом, кириллица и полнота текста в отрисовке;
- превью именно того файла, который будет согласован; выдача файлов только через API по правам;
- чтение кандидата его не пересобирает; повтор задания сборки не создаёт второго комплекта.

Не делается:
- согласование, возврат, отзыв, выпуск, матрица блокеров с принятием риска, удержания по событиям входов (`readiness_hold`) — этап 13 (в этапе 12 — только базы актуальности и показ изменений входов после сборки, В-12-9);
- размещение и отправка — этап 14; сравнение выпусков — этап 15;
- правило итога КП (Q-05) — решение владельца (В-12-6); снятие Q-08 и `TEMPLATE_DEMO` — владелец после проверки реальных форм.

## 2. Форматы и инструменты — проект ADR-013 «Формирование файлов выпуска»

Набор форматов и способ превью — решение владельца (В-12-1, В-12-2); выбор библиотек в рамках решения — технический (раздел 6 `06_TRACKER_AND_TEMPLATES.md`).

**Поддерживаемые форматы (предложение):**
- генерация: DOCX и XLSX — в формате размеченного образца (байты образца сохраняются, меняются только размеченные места);
- вложения «как есть»: DOCX, DOC, XLSX, PDF — без изменения байтов;
- превью: PDF, полученный конвертацией именно сгенерированного файла; хранится в кандидате как внутренний файл со ссылкой на SHA-256 исходного;
- других форматов портал не заявляет: загрузка образца иного формата — отказ с причиной.

**Инструменты (предложение, технический выбор):**
- DOCX — `docxtemplater` + `pizzip` (MIT): плейсхолдеры, разорванные Word на несколько фрагментов текста, повторяемые и условные блоки; остальное содержимое пакета не трогается;
- XLSX — собственная замена текста ячеек в `sharedStrings`/`inlineStr` листа той же библиотекой ZIP (без пересохранения книги сторонним движком — не теряются область печати, объединения, стили); ячейка, целиком занятая плейсхолдером числового поля, получает числовое значение;
- ZIP — детерминированная запись (порядок и даты записей образца): одинаковые входы дают одинаковые байты (I14, тест на стабильность);
- PDF для превью — LibreOffice в режиме без интерфейса (`soffice --headless --convert-to pdf`), отдельный процесс worker с ограничением времени, отдельным профилем и без сети; путь к программе — настройка; без конвертера сборка завершается `assembly_failed` с причиной `converter_unavailable` (I18 — неполный комплект не выдаётся за готовый);
- проверки отрисовки — pdf.js + `@napi-rs/canvas` (уже в зависимостях): извлечение текста страниц и PNG страниц для визуальной проверки.

**Ограничения:** отрисовка LibreOffice может отличаться от Word (шрифты, переносы); поэтому визуальная проверка A41 сравнивает PDF с ожиданиями по тексту и страницам, а страницы показываются человеку. Шрифты образцов (Times New Roman, Calibri и т. п.) должны быть установлены на сервере, иначе подстановка шрифта меняет переносы — это проверка установки (U-08, этап 17).

## 4. Разметка образца и генерация (В-12-3)

1. Владелец шаблона берёт копию образца и заменяет переменные части плейсхолдерами: `{{ключ}}` — значение поля; `{{#ключ}}…{{/ключ}}` — блок, выводимый только для применимого поля (или повторяемый для строк таблицы-перечня); `{{ключ.колонка}}` — ячейка строки перечня. Ключи — ключи полей схемы `forms/1` той же ревизии.
2. Размеченный файл загружается образцом ревизии. Проверка разметки (ядро, до утверждения): каждый плейсхолдер — ключ схемы подходящего типа; каждое обязательное поле выводится или явно помечено «не печатается»; нет незакрытых блоков; нет плейсхолдеров в колонтитулах, которые генератор не обрабатывает. Итог — в `markup`; ревизия с ошибками разметки не утверждается.
3. Значения выводятся по правилам формата: число — с запятой и неразрывным пробелом разрядов, с единицей схемы, если она не написана в образце; дата — ДД.ММ.ГГГГ; вариант — подпись варианта или его утверждённая формулировка; текст — как есть, переносы строк — переносы абзаца; таблица — повторение строки образца. Текст значения — данные, а не разметка: фигурные скобки и управляющие последовательности в значении экранируются (I16).
4. Неприменимое поле: его блок не выводится; плейсхолдер вне блока — пустая строка и проверка §6 «пустое место» (решает разметка, не генератор).
5. Режим `test` и демо-шаблон: видимая отметка «ТЕСТОВЫЙ ВЫПУСК» / «ДЕМОНСТРАЦИОННАЯ ФОРМА — НЕ ДЛЯ ВЫПУСКА» в каждом сгенерированном файле (DOCX — первый абзац и колонтитул; XLSX — первая строка листа и колонтитул печати) (В-12-8).

## 5. Кандидат: входы, сборка, manifest

**Создание** (`POST /stages/{id}/release-candidates`, под блокировкой этапа, одна транзакция):
- проверки: право `candidate.create`; пользователь видит все входы (В-12-7); выбранные приложения этапа — в статусе «заполнено», не заменены; у ревизий шаблонов — успешная разметка; нет другого `assembling` кандидата этапа;
- закрепление: последняя ревизия расчёта этапа; последний снимок области (с ревизией набора источников); последние завершённые прогоны проверок этапа; действующие решения этапа (не заменённые); ревизии шаблонов; последние версии каждого поля приложений (точные ID версий); выбранные вложения; базы `calculation_baseline_version` и `content_baseline_version` = `input_version` этапа;
- `inputs_sha256` — SHA-256 канонической записи входов; запись задания `candidate.assemble`.

**Сборка** (задание `candidate.assemble`, очередь `io`, `dedupe_key = assemble:<candidate_id>`, lease):
- генерация каждого документа, превью каждого файла, проверки §6, запись blob, `candidate_file`, `candidate_check`, манифест — в одной транзакции завершения; повтор после сбоя начинает заново (частичных файлов кандидат не получает); уже собранный кандидат задание не трогает;
- итог: `ready_for_approval` (все проверки `passed`) или `assembly_failed` с кодом и списком проблем; прежний `ready_for_approval` кандидат этапа становится `superseded` при готовности нового.

**Manifest** (`manifest.json`, канонический JSON: ключи по алфавиту, без пробелов, UTF-8, числа — строками decimal; тест на стабильность):
- `schema: "kontur-manifest/1"`, кандидат, этап, тендер, `mode`;
- входы: ревизия расчёта (ID, `kind`, хэш содержимого), снимок области и ревизия набора источников (ID, `content_hash`), прогоны проверок (ID, `input_sha256`), решения (ID), ревизии шаблонов (ID, `schema_sha256`, `markup_sha256`, `is_demo`), приложения и версии полей (ID), вложения (ID, SHA-256), базы актуальности;
- файлы: `path`, `role`, `audience`, `media_type`, `sha256`, `size`, у превью — SHA-256 исходного;
- `content_hash` кандидата = SHA-256 байтов манифеста (`data-model.md` §5).
- Манифест сам — внутренний файл кандидата; отправляемая часть — файлы `audience = customer` (этап 14).

**Чтение** не пересобирает: `GET /release-candidates/{id}` возвращает записанное; повторный `POST` с тем же ключом идемпотентности — тот же кандидат; новый `POST` — новый кандидат (A09).

**Изменения после сборки:** события барьера после базы показываются у кандидата («после сборки изменились: …») и делают его неактуальным для согласования этапа 13 (`INPUTS_CHANGED`); сам кандидат не меняется (I02, I03).

## 6. Проверки сборки

| Код | Что проверяется | Провал |
|---|---|---|
| `placeholders_left` | в тексте сгенерированного DOCX/XLSX (включая колонтитулы, сноски, надписи, общие строки) нет `{{`/`}}` и меток разметки | `assembly_failed` |
| `fields_complete` | все выводимые обязательные поля имеют значения; приложения «заполнено»; нет «устарело» по цепочке (R11-05) на момент закрепления | отказ при создании (409) |
| `numbers_match_calculation` | поля со смыслом `calc:<ключ>` равны величине закреплённой ревизии расчёта в единицах поля (точный сдвиг, `forms/quantity.ts`); неизвестная или неутверждённая величина — «не сверено» (В-12-6) | расхождение — `assembly_failed`; «не сверено» — отметка кандидата для этапа 13 |
| `render_complete` | конвертация в PDF прошла; страниц > 0; текст каждого значения поля найден в тексте PDF целиком (кириллица, длинные тексты, переносы); нет символов-заменителей | `assembly_failed` |
| `cell_overflow` (XLSX) | текст ячейки помещается при заданных ширине, переносе и высоте строки (оценка по числу символов и строк; превышение — проблема с адресом ячейки) | `assembly_failed` |
| `hashes` | SHA-256 и размер каждого файла пересчитаны из blob перед записью манифеста (ADR-003) | `assembly_failed` |

## 7. Превью и права

- Превью — внутренний PDF кандидата, полученный из того же файла, который будет согласован (ссылка `source_file_id`, SHA-256 исходного в манифесте); показывается pdf.js на canvas (как `EvidenceViewer`), без фрейма (CSP `frame-ancestors 'none'`). Скачивание — исходный DOCX/XLSX.
- `GET /candidate-files/{id}/content` — по ID, не по пути; `Content-Disposition: attachment` для офисных форматов, `inline` для PDF в песочнице; `X-Content-SHA256`; `no-store`; аудит чтения.
- Права (В-12-7, урок R11-01): файл и состав кандидата показываются, только если пользователь видит все входы — значения всех закреплённых версий полей с источниками и решения; иначе — оболочка без содержимого (`restricted: true`).

## 10. Инварианты БД (вторая линия)

1. Кандидат: `mode` неизменен; содержимое, входы и базы неизменны после создания; `ready_for_approval` — только с манифестом, его хэшем и хотя бы одним файлом; один `assembling` на этап.
2. `candidate_input` — только в транзакции создания кандидата; ссылки — объекты этапа и тендера кандидата.
3. `candidate_file`, `candidate_check` — только транзакцией задания сборки этого кандидата; неизменны; blob существует; путь уникален.
4. Создатель — human с `candidate.create` на этапе (триггер).
5. Ревизия шаблона утверждается только с успешной разметкой; `markup` неизменен вместе с образцом.
6. Права `kontur_app`: таблицы кандидата — `SELECT, INSERT` (+ `UPDATE` у `release_candidate` для статуса); `DELETE`/`TRUNCATE` запрещены.

Ответ владельца 2026-10-06 (`docs/reviews/12-owner-decisions.md`): **1А; 2А; 3А; 4А; 5А; 6А; 7А; 8А; 9А; 10А** с уточнениями, записанными в D-032:
- В-12-2: версия конвертера и использованные шрифты фиксируются; отсутствие конвертера, ошибка преобразования или подмена шрифтов видны и не дают сборке пройти;
- В-12-3: размечается копия образца, оригинал сохраняется; до утверждения — соответствие плейсхолдеров схеме, включая обязательные поля, таблицы и условные блоки;
- В-12-6: связь числа с расчётом — явно: величина, ревизия, единица, валюта; точная десятичная арифметика; неизвестное — не совпадение; сверка с `cached_grand_total` не закрывает Q-05;
- В-12-7: права перепроверяются при сборке и при каждом получении содержимого (файл, PDF, снимки страниц, вложения, ZIP); отзыв доступа закрывает собранные файлы; закреплённые входы не подменяются текущими;
- В-12-8: боевой комплект с блокерами — кандидат без разрешения на выпуск; тестовая и демо-пометки видны в документах и превью; Q-08 и X-01 автоматически не снимаются;
- В-12-9: изменение использованного поля делает соответствующий комплект неактуальным; S12-01 — с сохранением инвалидации по реальным зависимостям, положительные и отрицательные регрессии;
- В-12-10: автоматические проверки дополняются просмотром страниц человеком.

Ниже — исходные формулировки вопросов, сохранённые для истории.

**В-12-1. Что получает заказчик (набор форматов, ADR-013).**
- **А (рекомендуется)** — файлы в формате образца компании (DOCX/XLSX, как отправляют сейчас) и вложения «как есть»; PDF-копии — внутренние, только для просмотра. Последствия: заказчик получает привычные редактируемые файлы; согласуются именно они.
- **Б** — заказчику и DOCX/XLSX, и PDF каждого документа. Последствия: PDF тоже согласуется и входит в отправку; расхождение отрисовки LibreOffice и Word становится видимым заказчику.
- **В** — заказчику только PDF. Последствия: нужна печатная точность PDF; исходные файлы — внутренние.

**В-12-2. Превью и конвертер.**
- **А (рекомендуется)** — LibreOffice без интерфейса на сервере (и на машине разработки) конвертирует каждый сгенерированный файл в PDF при сборке; PDF хранится в кандидате и показывается постранично. Без конвертера комплект не собирается. Последствия: нужна установка LibreOffice и шрифтов образцов на целевом ПК; отрисовка близка к Word, но не тождественна.
- **Б** — просмотр DOCX/XLSX библиотеками в браузере. Последствия: без серверной установки, но превью приблизительное и не является сохранённым артефактом кандидата.
- **В** — документы формируются сразу в PDF средствами портала (без формата образца). Последствия: точное превью, но вёрстка образцов компании не сохраняется.

**В-12-3. Разметка образца.**
- **А (рекомендуется)** — копия образца с плейсхолдерами `{{ключ}}`, блоками `{{#ключ}}…{{/ключ}}` для неприменимых полей и строк перечней; проверка разметки до утверждения ревизии. Последствия: разметку делает руководитель в Word/Excel по инструкции; выделенные цветом места реальных форм — первые кандидаты в плейсхолдеры.
- **Б** — закладки Word и именованные ячейки Excel. Последствия: разметка невидима в тексте, но её труднее делать и проверять.
- **В** — автоматическое сопоставление выделенных цветом фрагментов с полями. Последствия: без ручной разметки, но ненадёжно при изменении образца.

**В-12-4. Неизменяемые вложения (руководство, перечень исполнительной документации).**
- **А (рекомендуется)** — библиотека стандартных вложений компании: файл «как есть», ревизии, утверждает руководитель; выбираются при сборке комплекта. Последствия: одинаковые вложения не загружаются заново для каждого тендера.
- **Б** — вложения загружаются к этапу при каждой сборке. Последствия: проще, но версии вложений не управляются.

**В-12-5. Состав комплекта.**
- **А (рекомендуется)** — при сборке пользователь выбирает приложения этапа в статусе «заполнено» и вложения; порядок и имена файлов — по шаблонам; состав фиксируется в манифесте. Последствия: гибко для разных тендеров.
- **Б** — «комплект» как шаблон компании (фиксированный набор форм и вложений), собирается целиком. Последствия: меньше ошибок состава, но новый вид шаблона и правила для тендеров с другим набором.

**В-12-6. Числа и расчёт (Q-05).**
- **А (рекомендуется)** — числа приложения, связанные с расчётом, задаются в схеме явным ключом величины расчёта (`calc:<ключ>`) из подтверждённой таблицы семантики D-030; сборка проверяет точное совпадение в единицах поля (расхождение — сборка не проходит). Пока правило итога КП (Q-05) не утверждено, цена КП в письме сверяется с `cached_grand_total` закреплённой ревизии только как «итог источника», а кандидат получает отметку «итог КП не утверждён» — блокер production этапа 13. Последствия: цифры не расходятся с расчётом; утверждение итога КП остаётся решением владельца.
- **Б** — владелец сейчас утверждает правило итога КП (`kp_total_rule`: какая величина, с НДС или без, учёт доставки, страхования, снижения). Последствия: сверка цены КП становится полной уже в этапе 12.
- **В** — в этапе 12 числа не сверяются, только отмечаются «не сверено». Последствия: проще, но задание («согласованность цифр с расчётом») выполняется частично.

**В-12-7. Кто собирает и кто видит комплект.**
- **А (рекомендуется)** — собирает участник тендера (руководитель или инженер) с `candidate.create`; собрать можно только из входов, которые он видит целиком; файлы и состав кандидата видит только тот, кто видит все входы (значения полей с источниками, решения); остальным — оболочка без содержимого. Последствия: файл не раскрывает значения из закрытой переписки (урок R11-01).
- **Б** — собирает только руководитель тендера; файлы видят все участники тендера. Последствия: проще, но готовый файл может раскрыть значения, скрытые в приложении.

**В-12-8. Режимы, демо-формы, внутренние документы.**
- **А (рекомендуется)** — `test` и `production` собираются одинаково; файлы `test` и файлы по демо-шаблонам несут видимую отметку; production-кандидат на демо-шаблоне или предварительном расчёте собирается, но известные блокеры (`TEMPLATE_DEMO`, `CALCULATION_PROVISIONAL`) показываются сразу и снимаются только по правилам этапа 13. Аудитория файла задаётся ревизией шаблона (например, расчёт содержания площадки — «внутреннее»). Последствия: до X-01 и проверки реальных форм все комплекты фактически тестовые, но механизм проверяется целиком.
- **Б** — production-кандидат не собирается при известных блокерах. Последствия: до X-01 production-сборка недоступна вовсе.

**В-12-9. Изменения входов после сборки.**
- **А (рекомендуется)** — этап 12 записывает базы актуальности и показывает у кандидата события входов после сборки; удержания (`readiness_hold`) и решения руководителя по событиям — этап 13 вместе с согласованием. Последствия: этапы не пересекаются; кандидат не «молчит» об изменениях.
- **Б** — удержания создаются уже в этапе 12 при каждом событии для активного кандидата. Последствия: часть этапа 13 переносится в 12 без согласования, где они разрешаются.

**В-12-10. Визуальная проверка (A41).**
- **А (рекомендуется)** — автоматическая проверка отрисованного PDF (текст значений найден целиком, кириллица, нет плейсхолдеров, число страниц, переполнение ячеек XLSX) на демо-форме и синтетических длинных текстах плюс снимки страниц для просмотра человеком; реальные формы — после их разметки владельцем (Q-08). Последствия: проверяемо в CI; приёмка реальных форм — вместе со снятием Q-08.
- **Б** — только просмотр снимков человеком. Последствия: не автоматизируется; ревью не принимает по скриншотам (`04_CODEX_REVIEW.md`).

### 13.1. Реализация и уточнения (передача 12-1)

Уточнения без изменения решений D-032:
- **Модель 0032.** `markup_sha256` не вводился: размеченная копия хранится своим blob (`marked_sample_blob_sha256`, `marked_sample_name`) рядом с оригиналом `sample_blob_sha256`; в манифест входят SHA-256 схемы и размеченной копии. У `candidate_input` нет `ref_sha256`: хэши входов пишутся в манифест и `inputs_sha256`. У `candidate_check` добавлен исход `unverified` («не сверено»); у `candidate_file` — `attachment_revision_id`, `pages`, `fonts`; у кандидата — `converter_version`, `finished_at`, `created_xact`.
- **Разметка.** Колонка таблицы внутри повторения пишется `{{колонка}}`, а не `{{ключ.колонка}}`; неоднозначный ключ (колонка и поле схемы с одним именем) — ошибка разметки. Плейсхолдеры колонтитулов и сносок DOCX обрабатываются, поэтому запрета на них нет. Пробная проверка — `POST /template-markup-check` (без ревизии), а не `/template-revisions/{id}/markup-check`: итог пишется в ревизию при создании.
- **Проверки сборки.** `fields_complete` — отказ при создании (409 `drafts_not_complete`), а не проверка кандидата. Добавлены `fonts_embedded` и `font_substituted` (D-032 В-12-2). `render_complete` ищет слова каждого значения в тексте PDF в том же порядке: переносы и разрывы не мешают, пропуск слова виден. `cell_overflow` проверяет только ячейки, изменённые генерацией, в строках со своей высотой, с учётом объединения. Строки без своей высоты растут сами — их проверяют полнота отрисовки и просмотр человеком.
- **Отметки.** DOCX — абзацами в начале тела документа; XLSX — колонтитулом печати и в первой текстовой ячейке.
- **Просмотр страниц человеком (В-12-10)** нашёл S12-03 и правки демо-образцов: скрытый условный блок оставлял пустой абзац; ручные номера условий давали «1., 3.»; денежное поле печаталось «120», а не «120,00»; позиция заказчика по авансу выводилась без «%». Исправлено: генератор удаляет абзац, целиком занятый скрытым блоком; в размеченной копии письма — автоматический список; денежное поле — с `scale` знаками; образец XLSX — «… % от цены договора».
- **S12-04.** Проверка «без сети» (ADR-013 п. 4) показала: LibreOffice загружал картинку по внешней ссылке из DOCX. Профиль конвертации блокирует внешние ресурсы и макросы; регрессия — в `tests/releaseCore.test.ts`.
- **Конвертер — в worker** (`apps/worker/src/office/libreoffice.ts`): пакет адаптеров не работает с файлами и процессами (A38, `tests/adapters.test.ts`); в адаптерах — контракт `IOfficeConverter`.
- **Расширение файла вложения** берётся по содержимому: PDF с именем «.docx» уходит как «.pdf».
- **Экран ревизии шаблона.** Простой путь этапа 11 сохранён: выбор файла схемы сразу создаёт ревизию. Ревизия с образцом для генерации — переключателем «С образцом для генерации»: схема, оригинал, размеченная копия, аудитория, кнопка «Загрузить ревизию». Форма нового стандартного вложения раскрывается кнопкой. Регрессия интерфейса этапа 11 сначала падала: принятый сценарий загружает схему выбором первого поля файла.
- **Задание сборки** `candidate.assemble` — класс ресурса `default` (класса `io` в очереди нет), `dedupe_key = assemble:<id>`, до трёх попыток; при исчерпании — `assembly_failed` с причиной.
- **S12-02** (найден в тестах): отказ команды над шаблоном компании давал 500 — пустая строка вместо UUID тендера в журнале отказа.
