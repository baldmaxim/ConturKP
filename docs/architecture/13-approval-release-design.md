## 0. Границы этапа

Делается:
- серверные переходы кандидата: согласование, возврат, отзыв согласования, выпуск; одна команда — одна транзакция под блокировкой этапа; аудит каждого действия и отказа;
- матрица блокеров (§5) — одна функция ядра, одинаковая для карточки, согласования и выпуска; ответ `409 BLOCKER_PRESENT` со списком;
- принятие бизнес-риска руководителем с причиной; технические блокеры, полномочия и целостность риском не снимаются;
- актуальность по правилам покрытия §1.1 (по составу снимка, а не только «события после базы»); удержания `readiness_hold` и решения руководителя по ним; удержание отправки уже выпущенного комплекта;
- неизменяемый выпуск: запись `release` и манифест выпуска с согласованием, принятыми рисками и решениями по удержаниям; файлы — точные байты кандидата, без повторной генерации;
- журнал автора, времени и основания по кандидату; вторая линия в БД (миграция 0034);
- экраны: согласование и выпуск на карточке комплекта, удержания, история; смартфон 360–430 px (D-004).

Не делается:
- размещение (Яндекс Диск, SMB) — этап 14; регистрация отправки и `compliance_incident` — этап 15. Этап 13 вычисляет и показывает готовность выпуска к отправке («отправка удержана»), запрет отправки исполняет этап 15 той же функцией;
- MCP и токены `api_token` — этап 16 (ADR-010). Проверка «модель вызывает release» в этапе 13 — через вторую линию БД и сервисную учётную запись модели (§10);
- снятие Q-05, Q-08, X-01: боевой выпуск остаётся заблокированным `KP_TOTAL_NOT_APPROVED`, `TEMPLATE_DEMO`, `CALCULATION_PROVISIONAL` до решений владельца.

### 1a. Найдено при подготовке

**S13-01 (ограничение этапа 12, P2).** Актуальность кандидата этапа 12 (`candidateIsCurrent`) — «нет касающихся событий после базы». Правило §1.1 строже: событие источника покрыто, только если его предмет есть в снимке кандидата. Кандидат, собранный на старом снимке после регистрации нового документа (RT-03 «новый кандидат на старой проверке»), сейчас показывается актуальным. До этапа 13 это не давало обхода (согласования нет), но признак `current` на экране вводит в заблуждение. Исправление — §4: актуальность по правилам покрытия; регрессия — сценарий RT-03.

**S13-02 (порядок блокировок).** Завершение сборки (`finishCandidate`) заменяет прежний готовый кандидат без блокировки этапа. С этапом 13 замена касается и согласованного кандидата (его согласование становится `superseded`). Завершение сборки будет брать блокировку этапа первой — общий порядок «этап → кандидат → согласование и выпуск» (§1.2).

**S13-03 (контракт).** В `packages/contracts` нет кодов `BLOCKER_PRESENT`, `RELEASE_IS_TEST`, `ENVIRONMENT_MISMATCH` из `portal-api.md` §1. В этапе 13 добавляется `BLOCKER_PRESENT`; остальные — этапы 14–15.

Порядок блокировок: строка этапа → строка кандидата → согласование / выпуск → прочее (§1.2). Его соблюдают все команды этапа, завершение сборки (S13-02), запись событий входов и создание удержаний. Взаимная блокировка (`40P01`), если возникнет, — 409 `STATE_CONFLICT`, транзакция откатывается целиком.

Повторы и гонки:
- тот же `Idempotency-Key` — тот же ответ после проверки текущих прав (R02-01); новый ключ на уже согласованном или выпущенном кандидате — `409 STATE_CONFLICT` (`already_approved` / `already_released` со ссылкой на запись);
- два одновременных выпуска сериализуются блокировкой этапа: второй видит `released`; уникальность `release.candidate_id` — вторая линия (A26);
- устаревшая карточка — `412` по `If-Match`; согласование с `contentHash` не того содержимого — `409 content_changed`.

## 4. Актуальность, удержания, удержание отправки

### 4.1. Покрытие события кандидатом (реализация §1.1)

Событие e этапа **касается** кандидата C, кроме правки поля чужого приложения (`draft_field_changed` касается только кандидатов с этим приложением — D-032 В-12-9). Касающееся событие **покрыто** C по правилу класса:

| Событие (`ref_type`) | Покрыто, если |
|---|---|
| `calculation_revision_added` | `seq ≤ calculation_baseline_version` |
| `decision_recorded`, `draft_field_changed` | `seq ≤ content_baseline_version` |
| `document_revision_registered` (`document_revision`) | редакция есть в ревизии набора источников снимка C — включена, унаследована или исключена с причиной |
| `recognition_run_completed` (`recognition_run`) | редакция исключена с причиной, или единица снимка этой редакции ссылается на этот прогон или на прогон, созданный позже |
| `import_accepted` (`import_batch`) | партия завершена, и у каждого элемента покрытый исход: `registered` / `duplicate` — редакция покрыта по правилу выше; `rejected` / `skipped_partial` — `not_applicable` (решение руководителя) или `reimported` с покрытым элементом повторного импорта |
| `communication_linked` (`mail_message`) | письмо — единица снимка C, или связь письма с тендером снята до создания C |
| `transcript_revision_added` (`transcript_revision`) | снимок C содержит эту ревизию или более позднюю ревизию той же сессии |
| `qa_form_added` (`qa_import`) | `seq ≤ input_version` снимка C (снимок создан после импорта, вопросы–ответы — последние ревизии на момент снимка) |
| `source_set_changed` (`source_set_revision`) | ревизия — та, на которой основан снимок C, или более ранняя ревизия того же набора |
| неизвестный тип | не покрыто (неизвестное считается затрагивающим) |

Правила — SQL-функции миграции 0034. Ими пользуются сервер (карточка, команды) и охранники вставки `approval` и `release`. **Предикат актуальности C:** у каждого касающегося непокрытого события есть удержание (C, e) в статусе `resolved_not_applicable`. Предикат опирается на события, а не на наличие строк удержаний: пропущенное или ещё не созданное удержание дорогу не открывает. Нарушение — блокер `INPUTS_CHANGED`. Признак `current` в списке и карточке кандидата считается тем же предикатом (исправление S13-01).

### 4.2. Создание удержаний

- **При создании кандидата** — по каждому касающемуся непокрытому событию этапа с любым `seq` (новый кандидат на старой проверке, неразобранная партия: RT-03, RT-08).
- **При записи события** (`emitStageEvents`, в той же транзакции, под блокировкой этапа) — для каждого действующего кандидата этапа: `assembling`, `ready_for_approval`, `approved`, `released` (отправки до этапа 15 нет — все выпущенные). Создаётся только для касающегося непокрытого события.
- Удержаний не создают: решения по удержаниям, принятие риска, согласование, возврат, отзыв, выпуск, фоновая инвалидация (R01-07).

### 4.3. Решение по удержанию

Решает руководитель (`hold.resolve`) с причиной, одним событием или группой событий одного кандидата (у каждого — своё решение `input_event_disposition`):
- **«не влияет»** → `resolved_not_applicable`; событие перестаёт блокировать этого кандидата; событий барьера решение не создаёт;
- **«влияет»** → `resolved_requires_new_candidate`; невыпущенный кандидат → `returned`, действующее согласование → `revoked` с этой причиной; у выпущенного запись выпуска не меняется, но отправка этого выпуска исключена навсегда (предикат для него ложен).

Для `import_accepted` с неразобранными элементами «не влияет» допускается только с перечнем неразобранных элементов в причине (§3.1); пробелы остаются видимыми.

### 4.4. Готовность выпуска к отправке

Вычисляется, не хранится (I01): `test` — тестовый выпуск, отправка невозможна; `held` — есть касающиеся события без решения «не влияет» («Отправка удержана: после согласования поступил …», BRAND.md §4.3); `excluded` — решение «влияет»; `intake_not_current` — канал поступления устарел; `ready` — иначе. Этап 15 вызывает ту же функцию при регистрации отправки. Прежнее согласование при удержании остаётся видимым (I04).

## 5. Матрица блокеров (D-033; Q-09)

Одна функция ядра `evaluateGate(facts, action)` (`action`: `approve` / `release` / `send`), факты собирает слой БД под блокировкой этапа. Карточка показывает ту же оценку без блокировки (подсказка, не разрешение).

| Код | Условие | Класс | Риск | Режим |
|---|---|---|---|---|
| `ACTOR_NOT_AUTHORIZED` | не человек, нет роли или назначения; модель и сервисная учётная запись | полномочия | нет | оба; ответ `403` + аудит `denied` (A25) |
| `RESTRICTED_INPUTS` | действующий пользователь не видит всё содержимое кандидата (В-12-7) | полномочия | нет | оба |
| `APPROVAL_NOT_ACTIVE` | выпуск: нет действующего согласования, оно отозвано, заменено, другого кандидата или с другим хэшем | полномочия | нет | оба |
| `CANDIDATE_CONTENT_MISMATCH` | байты файла или манифеста в хранилище не совпадают с SHA-256 и размером кандидата | технический | нет | оба |
| `REVIEW_SCOPE_MISMATCH` | закреплённый прогон проверок построен на другом снимке или другой ревизии расчёта, чем кандидат | технический | нет | оба |
| `REVIEW_MISSING` | нет закреплённого прогона проверок или он не завершён | целостность (D-033 ут. 1) | нет | оба |
| `REVIEW_PROCESSING_INCOMPLETE` | по каждой проверке прогона: исход `error`; `incomplete` проверок обработки (непрочитанные страницы, распознавание, нет текста, элементы импорта без исхода, пустой снимок), реестра, параметров (объекты покрытия не найдены), конфликтов и устаревших оснований (факты не извлечены), модели (не настроена, отказ, вход сверх предела, недоступные основания) | целостность (D-033 ут. 1) | нет | оба |
| `INPUTS_CHANGED` | нарушен предикат актуальности §4.1 | целостность (I04) | нет; решение по каждому событию или новый кандидат | оба |
| `INTAKE_NOT_CURRENT` | активный канал поступления тендера не сканировался дольше `freshness_window` | целостность | нет; восстановить скан или отключить канал с причиной | оба |
| `FIELDS_STALE` | у закреплённой версии поля основание заменено или инвалидировано (по цепочке копий, R11-05) | целостность (D-033 ут. 2) | нет; новое значение и пересборка | оба |
| `CALCULATION_PROVISIONAL` | ревизия расчёта `provisional` | целостность (Q-01, X-01) | нет | боевой |
| `TEMPLATE_DEMO` | демонстрационный шаблон | целостность (Q-08, D-031 В-11-1) | нет | боевой |
| `KP_TOTAL_NOT_APPROVED` | правило итога КП не задано (D-032 В-12-6) | целостность (Q-05) | нет | боевой |
| `REVIEW_UNCERTAIN` | `incomplete` проверки покрытия: требования без оценки покрытия или с оценкой «требует пересмотра» на обработанных данных | бизнес (D-033 ут. 1) | да, по каждой проверке | оба |
| `CRITICAL_FINDINGS_OPEN` | замечание этапа `critical` в статусе `open` / `in_progress` / `stale` — по каждому; `accepted_risk` этапа 09 — только пока действует (ут. 3) | бизнес | да, по каждому (A45) | оба |
| `QUESTIONS_UNANSWERED` | вопрос заказчику этапа в статусе «отправлен» без ответа — по каждому (В-13-4); черновики — предупреждение | бизнес | да, по каждому | оба |
| `FIELDS_INCOMPLETE` | бизнес-пробел необязательного поля закреплённой версии: пункт «не сверено» списка незавершённых (толкование исполнителя, D-033) | бизнес (D-033 ут. 2) | да, если у поля нет других проблем | оба |
| `NUMBERS_UNVERIFIED` | проверка сборки «числа с расчётом» — «не сверено» (D-032 В-12-6) — по каждой | бизнес | да, по каждой | оба |

Правила оценки:
- согласование: все неснимаемые блокеры отсутствуют, у каждого пункта бизнес-блокера есть действующее принятие риска на этого кандидата;
- выпуск: то же на момент выпуска, плюс каждое принятие учтено **в действующем согласовании** (`accepted_risk_ids`). Новый бизнес-блокер после согласования — отзыв, принятие, новое согласование (В-13-3);
- перед оценкой согласование и выпуск обрабатывают необработанные события этапа (инвалидация, `processPendingStageEvents`) — в предварительной транзакции и повторно под блокировкой этапа, — чтобы замечания и поля были отмечены по текущим основаниям (D-033 ут. 3, 4; урок Review 09-1);
- решение «не влияет» убирает только `INPUTS_CHANGED` по своему событию; остальные коды проверяются независимо (D-033 ут. 4);
- ответ отказа: `409 BLOCKER_PRESENT`, `blockers: [{ code, class, acceptable, items: [{ subjectType, subjectId, subjectKey, title, acceptance? }] }]`; аудит `denied` с кодами;
- замечание с риском, принятым в этапе 09 (`accepted_risk`), блокером не считается, пока действует, и показывается в составе согласования и в манифесте выпуска с автором и причиной (D-029 В-09-3, D-033 ут. 3); после изменения оснований оно становится `stale` и снова блокирует, прежнее принятие остаётся в истории.
- необязательное поле, оставленное пустым, показывается в карточке справкой и не блокирует (толкование исполнителя, D-033).

## 6. Принятие риска (В-13-3)

- `POST /release-candidates/{id}/risk-acceptances` `{ blockerCode, subjectType, subjectId, subjectKey?, reason }` — руководитель (`risk.accept`), кандидат `ready_for_approval`, код — бизнес-блокер D-033, предмет — текущий пункт этого блокера у кандидата; причина обязательна (не короче 10 символов). Неснимаемый код — `409 risk_not_acceptable`, в БД — CHECK. Пункт `FIELDS_INCOMPLETE` принимается, только если у поля нет неснимаемой проблемы (`FIELDS_STALE`) — иначе `409 field_not_current` (D-033 ут. 2).
- Принятие закрепляет версию изменяемого предмета (`subject_version` — `row_version` замечания или вопроса): изменённый после принятия предмет снова блокирует и требует нового принятия; прежнее остаётся в истории (D-033 ут. 3).
- Принятие **не меняет** замечание, вопрос, поле или прогон: замечание остаётся `critical` и открытым, вопрос — без ответа, пробелы проверки — видимыми («принятый риск не скрывает вопрос»). Событий барьера не порождает.
- Действует только для этого кандидата (его содержимое неизменно). Новый кандидат требует нового принятия.
- Видно в карточке («Риск принят: кто, когда, причина»), в диалоге согласования, в записи согласования и в манифесте выпуска.

## 7. Согласование, возврат, отзыв (В-13-8, В-13-9)

- **Согласование.** Диалог показывает точный состав: ревизия расчёта и её вид, снимок и ревизия набора источников, прогон проверок и его итог, версии шаблонов и приложений, файлы заказчику и внутренние с размером и коротким SHA-256, отметки режима и демо-форм, открытые замечания, принятые риски, решения по удержаниям (BRAND.md §9.1 п. 5). Запрос несёт `contentHash` показанного содержимого и необязательный комментарий. Запись `approval` хранит оценку матрицы (`gate`) и `accepted_risk_ids` — что именно согласовано.
- **Возврат.** Только из `ready_for_approval`, причина обязательна; кандидат дальше не согласуется и не выпускается; доработка — новый кандидат.
- **Отзыв.** Только до выпуска, причина обязательна; согласование → `revoked`, кандидат → `ready_for_approval`. После выпуска отзыва нет: выпуск неизменен (§14 state-machines); исправление — новый кандидат и новый выпуск, прежний сохраняется.
- Ни одна из команд не создаёт событий барьера (R01-07).

## 8. Выпуск (В-13-7)

- `POST /release-candidates/{id}/release` `{ approvalId, contentHash }` — инженер тендера (`candidate.release`). Под блокировкой этапа: кандидат `approved`; `approvalId` — его действующее согласование, хэш совпадает (иначе `APPROVAL_NOT_ACTIVE` — «старое согласование за новое»); каждый файл и манифест читаются из хранилища и сверяются по SHA-256 и размеру (`CANDIDATE_CONTENT_MISMATCH` — «файл изменён после согласования»); матрица §5.
- **Запись `release`** (неизменяемая): кандидат, согласование, режим, `input_version` этапа, хэш содержимого, автор и время, оценка матрицы.
- **Манифест выпуска** `kontur-release/1` (канонический JSON, blob, SHA-256 в записи): выпуск (ID, режим, кто и когда), кандидат (ID, номер, `content_hash` = SHA-256 манифеста кандидата), согласование (ID, кто, когда, комментарий, `input_version`), принятые риски (код, предмет, причина, кто, когда), риски, принятые в этапе 09, решения по удержаниям (событие, решение, причина, кто, когда), файлы (путь, аудитория, тип, SHA-256, размер). Этап 14 размещает именно эти байты и этот манифест (I02).
- Файлы выпуска — файлы кандидата: ничего не генерируется заново. «Воспроизводимый выпуск» — по манифесту выпуска можно скачать и сверить каждый файл (`GET /releases/{id}/archive` — детерминированный ZIP, как у кандидата).
- Тестовый кандидат выпускается тестовым выпуском: отметки в файлах, режим `test` в записи и манифесте; отправка невозможна (§4.4).

## 9. Журнал автора, времени и основания

- Факты — в своих неизменяемых записях: создание и сборка (`release_candidate`), принятие риска (`risk_acceptance`), согласование и его отзыв или замена (`approval`), возврат (`candidate_return`), решения по удержаниям (`readiness_hold` + `decision`), выпуск (`release`).
- `GET /release-candidates/{id}/history` — хронология из этих записей: действие, кто, когда, основание (причина, комментарий, событие, хэш). Старое согласование видно в истории со статусом `revoked` / `superseded` (I04, A09).
- `audit_event` — каждая команда и каждый отказ (`denied` с кодом блокера или права).

## 12. Экраны

- **Карточка комплекта** (вкладка «Комплект»): цепочка «Согласование → Выпуск → Готовность к отправке» (BRAND.md §4.3; размещение и отправка — «этап 14/15», без имитации); баннер удержания отправки с действием «Оценить применимость»; блокеры списком с причинами и ссылками (замечание, вопрос, поле, проверка); у бизнес-пунктов руководителю — «Принять риск…» (вторичная кнопка, обязательная причина); удержания — «Не влияет…» / «Влияет…»; история.
- **Защищённые действия** (BRAND.md §9.1): «Согласовать…» (`stamp`) — руководителю, «Выпустить…» (`package-check`) — инженеру после согласования; «Вернуть на доработку…» и «Отозвать согласование…» — вторичные, отделены ≥ 24 px; без автофокуса; кнопку видит только тот, у кого есть право, остальные — «Согласует руководитель» / «Выпускает инженер»; при блокерах кнопка недоступна, причины рядом.

- Список кандидатов: статусы «Согласован», «Возвращён», «Выпущен»; выпуски этапа — отдельным блоком с готовностью к отправке.
- Тёмная и светлая темы, `prefers-reduced-motion`.

## 13. Инварианты БД (вторая линия)

1. Переходы кандидата — только по §3; `approved` ⇔ одно действующее согласование; `released` ⇔ запись выпуска; содержимое, входы, базы и режим неизменны (как в 0032).
2. `approval`: вставка — человек с `candidate.approve`; кандидат `ready_for_approval`; хэш = `manifest_sha256`; `candidate_inputs_changed` ложен; для боевого режима нет `CALCULATION_PROVISIONAL`, `TEMPLATE_DEMO`, `KP_TOTAL_NOT_APPROVED`; одно `active`; `accepted_risk_ids` — принятия рисков этого кандидата; меняются только поля завершения, только из `active`, отзыв — человек с `candidate.approve` и причиной.
3. `release`: вставка — человек с `candidate.release`; согласование `active`, того же кандидата, хэш равен; режим равен; `candidate_inputs_changed` ложен; одна на кандидата; неизменна.
4. `risk_acceptance`: код — бизнес-блокер (CHECK); человек с `risk.accept`; кандидат `ready_for_approval`; предмет — объект этапа кандидата; неизменна.
5. `readiness_hold`: вставка — `open`, событие и кандидат одного этапа; решение — только из `open`, человек с `hold.resolve`, решение `input_event_disposition` по этому событию; после решения неизменно.
6. `decision` вида `input_event_disposition` не вставляет `stage_input_event` (проверка в тесте: `input_version` не меняется).
7. `DELETE` / `TRUNCATE` новых таблиц запрещены; `kontur_app` без `UPDATE` у неизменяемых.

## 14. Вопросы владельцу — решено (D-033)

Ответ владельца 2026-10-07 (`docs/reviews/13-owner-decisions.md`): **1А; 2А; 3А; 4А; 5А; 6А; 7А; 8А; 9А** с уточнениями матрицы (D-033): `REVIEW_INCOMPLETE` разделён по причинам; устаревшее основание поля риском не снимается; риск этапа 09 действует, пока действуют замечание и его основания; «не влияет» снимает только своё удержание; S13-01 — с регрессией «документ до сборки вне снимка». Матрица §5 и §6 приведены к решению.

Ниже — исходные формулировки вопросов, сохранённые для истории.

**В-13-1. Матрица блокеров (Q-09).**
- **А (рекомендуется)** — таблица §5: технические, полномочия и целостность риском не снимаются, включая `KP_TOTAL_NOT_APPROVED` (Q-05 — ограничение боевого выпуска, как сказано при приёмке этапа 12) и `INTAKE_NOT_CURRENT`; бизнес-блокеры (`REVIEW_INCOMPLETE`, `CRITICAL_FINDINGS_OPEN`, `QUESTIONS_UNANSWERED`, `FIELDS_INCOMPLETE_OR_STALE` кроме обязательных полей формы заказчика, `NUMBERS_UNVERIFIED`) снимаются принятием риска по каждому пункту. Последствия: до решений по Q-01/X-01, Q-05, Q-08 боевой выпуск невозможен, механизм проверяется тестовым режимом.
- **Б** — как А, но `CRITICAL_FINDINGS_OPEN` риском не снимается: критическое замечание можно только решить. Последствия: строже; руководитель не выпустит КП с открытым критическим вопросом даже осознанно.
- **В** — как А, плюс открытые `major`-замечания тоже блокируют (снимаются риском). Последствия: больше решений перед каждым согласованием.

**В-13-2. Тестовый режим.**
- **А (рекомендуется)** — тестовый кандидат проходит ту же матрицу, кроме блокеров только боевого режима (`CALCULATION_PROVISIONAL`, `TEMPLATE_DEMO`, `KP_TOTAL_NOT_APPROVED`); согласуется и выпускается тестовым выпуском с отметками; отправка невозможна (этап 15), размещение — только в тестовые назначения (этап 14). Последствия: весь путь проверяется до снятия Q-05, Q-08, X-01.
- **Б** — в тестовом режиме бизнес-блокеры тоже не проверяются. Последствия: быстрее для демонстрации, но тестовый выпуск не проверяет матрицу.
- **В** — тестовые кандидаты не согласуются и не выпускаются. Последствия: до снятия ограничений этап 13 проверяется только тестами, без живого пути пользователя.

**В-13-3. Принятие риска.**
- **А (рекомендуется)** — §6: по каждому пункту, на конкретного кандидата, руководитель с причиной; замечание, вопрос и поле не меняются, событий барьера нет; принятия делаются до согласования и входят в его запись; новый бизнес-блокер после согласования — отзыв, принятие, новое согласование; риски, принятые в этапе 09 по замечаниям, не блокируют и показываются в составе. Последствия: согласование точно фиксирует, с какими рисками оно дано.
- **Б** — одно принятие на код блокера (покрывает все его пункты). Последствия: меньше действий, но новый пункт того же кода проходит без отдельного решения.
- **В** — принятие можно добавить после согласования без повторного согласования. Последствия: меньше шагов, но согласованный состав рисков меняется задним числом.

**В-13-4. Какие вопросы блокируют (`QUESTIONS_UNANSWERED`).** В модели нет признака «обязательный вопрос» (наблюдение).
- **А (рекомендуется)** — каждый вопрос заказчику этапа в статусе «отправлен» без ответа; черновики не блокируют, но показываются предупреждением. Последствия: молчание заказчика не теряется (D-029 В-09-4); черновик — ещё не вопрос заказчику.
- **Б** — черновики и отправленные. Последствия: незаданный вопрос тоже требует решения.
- **В** — новый признак «обязателен для выпуска» у вопроса; блокируют только отмеченные. Последствия: точнее, но новый признак и действие в интерфейсе; неотмеченный вопрос проходит молча.

**В-13-5. Удержания и решения по событиям.**
- **А (рекомендуется)** — §4: удержания по правилам покрытия (при создании кандидата — по более ранним непокрытым событиям источников, при каждом новом событии — для действующих кандидатов, включая выпущенные); решает руководитель «не влияет» / «влияет» с причиной, по одному событию или группой; «влияет» — невыпущенный кандидат возвращается, выпущенный исключается из отправки навсегда. Последствия: новая информация после согласования всегда останавливает выпуск или отправку до решения человека (I04).
- **Б** — как А, но «не влияет» по правкам полей своего приложения может решить и инженер. Последствия: меньше нагрузки на руководителя, но решение о применимости — не только у руководителя (ADR-006 относит `hold.resolve` к руководителю).
- **В** — без решений по событиям: любое касающееся событие требует нового кандидата. Последствия: проще, но каждая посторонняя правка заставляет пересобирать и заново согласовывать.

**В-13-6. Замена кандидатов.**
- **А (рекомендуется)** — новый готовый кандидат заменяет невыпущенные кандидаты этапа (`ready_for_approval`, `approved`, `returned`) **того же режима**; согласование заменённого → `superseded` и остаётся в истории; выпущенный не заменяется; тестовый не заменяет боевой. Последствия: тренировочная сборка не отменяет согласованный боевой комплект.
- **Б** — как сейчас в этапе 12: замена без учёта режима. Последствия: тестовая сборка отменяет согласование боевого.

**В-13-7. Кто выпускает и что такое выпуск.**
- **А (рекомендуется)** — любой инженер, назначенный на тендер (толкование ADR-006: «назначенный инженер» — назначенный на тендер); выпуск — неизменяемая запись и манифест `kontur-release/1` (§8); файлы — точные байты кандидата, сверяются по SHA-256 при выпуске; один выпуск на кандидата. Последствия: выпуск может сделать второй инженер, если первый недоступен.
- **Б** — только инженер, собравший кандидата (или отдельно назначенный ответственный этапа). Последствия: строже, но нужен новый признак ответственного или руководитель-сборщик не сможет передать выпуск.

**В-13-8. Что подтверждает руководитель.**
- **А (рекомендуется)** — диалог с точным составом (§7) и хэшем показанного содержимого; согласование со смартфона; просмотр каждого файла не обязателен (превью доступно из диалога); комментарий необязателен. Последствия: быстрое согласование с телефона; сервер гарантирует, что согласовано показанное содержимое.
- **Б** — согласование доступно только после открытия превью каждого файла заказчику (отметка просмотра). Последствия: доказуемый просмотр, но больше действий на смартфоне.

**В-13-9. Возврат и отзыв.**
- **А (рекомендуется)** — §7: возврат только из «готов к согласованию», отзыв только до выпуска, причина обязательна в обоих; после выпуска исправление — новым кандидатом и выпуском, прежний сохраняется. Последствия: согласованный кандидат сначала отзывается, затем возвращается — два явных действия.
- **Б** — возврат доступен и из «согласован» (отзыв и возврат одной командой). Последствия: одно действие, но отзыв согласования становится неявным.

### 15.1. Реализация и уточнения (передача 13-1)

Уточнения без изменения решений D-033:
- **Матрица в ядре** — `packages/core/src/release/gate.ts` (`BLOCKERS`, `evaluateGate`); факты — `packages/db/src/approvals.ts` (`candidateGateDbFacts`) и `apps/server/src/releaseGate.ts` (права, сверка байтов, пробелы полей). Сверка байтов с хранилищем (`CANDIDATE_CONTENT_MISMATCH`) выполняется в командах согласования и выпуска, а не в карточке: карточка — подсказка, решение — команда под блокировкой этапа.
- **Пункты бизнес-блокеров** — предметы: результат проверки прогона (`review_check_result`, только `coverage`), замечание, вопрос заказчику, закреплённая версия поля (ключ `unverified`), проверка сборки «числа». У изменяемых предметов (замечание, вопрос) принятие закрепляет `row_version` (`subject_version`): любое изменение предмета после принятия требует нового принятия (D-033 ут. 3). Пункт поля с устаревшим основанием помечен «не принимается» (ут. 2).
- **Пустые необязательные поля** — справка `emptyOptionalFields` в карточке (толкование D-033), черновики вопросов — `draftQuestions` (В-13-4), действующие риски этапа 09 — `reviewRisks`.
- **Покрытие событий** — SQL-функции 0034: `stage_event_affects`, `stage_event_covered`, `candidate_uncovered_events`, `candidate_gate_problem` (неснимаемые блокеры для охранников `approval` и `release`). Прогон распознавания, завершённый до создания снимка (`seq ≤ evidence_scope.input_version`), покрыт, если редакция есть в снимке: выбор прогона уже выполнило правило предпочтения 05a; поздний прогон покрыт, только если снимок ссылается на него или на более поздний.
- **Удержания** создаются в транзакции события триггером БД `stage_input_event_hold` (при любом пути записи события; код записи событий от схемы этапа 13 не зависит — тесты обновления схемы гоняют его на старых схемах) и при создании кандидата (`holdUncoveredEvents`). Удержание, событие которого стало покрыто составом (например, элементы партии получили исход), остаётся строкой «открыто», но предикат его не считает: в списке удержаний оно помечено «учтено составом».
- **Решение группой** — у каждого события своё решение `input_event_disposition`; при «влияет» первое решение возвращает невыпущенного кандидата, остальные события той же группы решаются следом (решение по удержанию «возвращённого» кандидата допускается, изменений кандидата не делает). Для `import_accepted` неразобранные элементы партии дописываются в основание решения автоматически (§3.1 state-machines).
- **Команды согласования, выпуска и принятия риска** обрабатывают необработанные события этапа в предварительной транзакции (`prepare`) и повторно под блокировкой этапа — риск этапа 09 и отметки полей оцениваются по текущим основаниям (D-033 ут. 3–4; урок Review 09-1).
- **Готовность к отправке** вычисляется и у тестового выпуска (`state`), но `sendable` — только у боевого со `state = ready`: путь удержаний проверяется тестовым режимом (В-13-2).
- **Контракт** — `blockerCode` принятия риска — любой код матрицы: неснимаемый даёт `409 risk_not_acceptable`, а не ошибку формы. Отказ матрицы — `409 BLOCKER_PRESENT` с полем `blockers`; в журнале — `outcome = denied` и коды блокеров.
- **Замена кандидатов** — только того же режима (В-13-6): охранник 0034 требует, чтобы заменяющий был того же режима; завершение сборки берёт блокировку этапа первой (S13-02).
- **Права на содержимое пунктов** — заголовок критического замечания и текст вопроса закрытого пользователю предмета (основания из чужого ящика, закрытое требование) в матрице не показываются (`restricted`, видимость — как в этапе 09), принять по такому пункту риск нельзя. В манифесте выпуска у замечаний и вопросов — вид и ID, у рисков этапа 09 — без заголовка. Удержания не отдают ID предмета события. Причины решений и чтение манифеста — §15.2 (R13-02).
- **S13-03** — код `BLOCKER_PRESENT` добавлен в `packages/contracts`; `RELEASE_IS_TEST` и `ENVIRONMENT_MISMATCH` — этапы 14–15.
- **Регрессии этапа 12** (`tests/reviewRegressions12.test.ts`): контрольный сценарий R12-02 и сценарий R12-03 ждали «актуален» для кандидата, собранного после регистрации документа вне снимка. По S13-01 (D-033) такой кандидат получает удержание; ожидания приведены к правилу: сборка проходит, «актуален» — после решения «не влияет».

### 15.2. Исправление Review 13-1 (передача 13-2)

Новых решений владельца не потребовалось: всё следует из D-033 ут. 1, ут. 4 и В-13-8.

- **R13-01 — устаревший вход прогона.** Кандидат закрепляет прогон проверок. Если отпечаток содержимого этапа, закреплённый при запуске прогона (`review_run_input.content_fingerprint`, R09-02), не совпадает с текущим, открыт неснимаемый технический блокер `REVIEW_OUTDATED`. Прогон без закреплённого входа — тоже `REVIEW_OUTDATED`.
  - В отпечаток входят реестр, покрытие, отметки, проходы реестра, допущения, вопросы и решения по требованиям; правки полей приложений не входят (S12-01).
  - Исправление пользователя — новый прогон и новый комплект; прежний вход сохраняется.
  - Вторая линия — миграция 0035: `stage_content_fingerprint` (повторяет расчёт сервера; совпадение проверяет тест) и `REVIEW_OUTDATED` в `candidate_gate_problem`.
- **R13-02 — закрытость производных текстов решений** (`apps/server/src/releaseVisibility.ts`). Права проверяются текущие; предмет неизвестного вида закрыт.
  - Причина принятия риска наследует закрытость предмета: замечание — по его основаниям, как в этапе 09; вопрос — по замыканию этапа 08; проверки прогона и сборки видны каждому, кто видит комплект; версия поля — по её основаниям.
  - Причина решения по удержанию наследует закрытость предмета события:
    - письмо — `mail.read`;
    - документ и распознавание — чтение документа, вложение письма — `mail.read`;
    - версия поля — по основаниям;
    - решение по требованию — по замыканию этапа 08; по замечанию — по замечанию; по разногласию — по замечанию и основаниям осей;
    - события уровня тендера (загрузка, расчёт, набор источников, вопросы–ответы, транскрипция) — доступ к содержимому тендера.
  - Где закрыто: карточка, список удержаний, журнал и возврат по «влияет» — без текста. Отзыв и возврат по «влияет» больше не копируют причину решения.
  - Манифест выпуска и ZIP «все файлы» — только тому, кто видит предмет каждого решения в манифесте; иначе `409 restricted_basis`. Запись не переписывается.
  - Решение по удержанию с закрытым предметом не принимается — `409 restricted_event`, как принятие риска по закрытому пункту (D-033 ут. 4).
- **R13-03 — исключение выпуска.** Решение «влияет» по кандидату даёт `excluded` независимо от текущего покрытия события. Решение неизменно, поэтому исключение постоянно (§4.3, В-13-5).
- **R13-04 — подтверждается показанный состав.** `compositionHash` ядра — SHA-256 канонической записи:
  - содержимого (хэш манифеста кандидата);
  - принятий рисков, снимающих пункты сейчас, с версией предмета;
  - действующих рисков этапа 09 (замечание и момент принятия);
