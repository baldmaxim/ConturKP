## 0. Границы этапа

Делается:
- назначения размещения:
  - тип (`yandex_disk` — папка синхронизации Яндекс Диска, `smb` — сетевая папка) и среда (`test` / `production`), оба неизменны;
  - версии путей и политики;
  - настраивает только администратор;
  - проверку доступа выполняет worker (D-034);
- доставки выпуска: по одной на каждое активное назначение среды выпуска. У каждой своя закреплённая версия назначения, своё состояние, свои попытки и файлы;
- задание worker `delivery.place`:
  - перехэширование байтов (A27);
  - стадирование в служебную папку, загрузка точных файлов, сверка каждого;
  - перенос в папку выпуска, сверка, признак готовности — последним;
  - сверка внешнего состояния перед любым повтором (A29);
- один адаптер поверх файловой системы для обоих назначений (`FsDeliveryTarget`);
- у Яндекс Диска отдельное состояние облака: портал проверяет файлы в локальной папке, доставку в облако подтверждает человек (D-034, §3.1);
- конфликт вместо перезаписи (A30); повтор, «повторить после проверки», перенаправление;
- политика внутренних материалов (В-14-3);
- экраны:
  - размещение на карточке выпуска;
  - раздел «Назначения размещения» в администрировании;
- обёртка файловой системы с внесением отказов для проверок на поддельных данных;
- сценарий живой проверки двух реальных тестовых назначений и сценарий сверки скачанной из облака папки (§16).

Не делается:
- REST API Яндекс Диска и OAuth (D-034); публичные ссылки — никогда;
- регистрация отправки, `send_event`, `compliance_incident` — этап 15. «Размещено» ≠ «отправлено» (I01, A31);
- снятие Q-01/X-01, Q-05, Q-08: боевой выпуск невозможен. Боевые назначения можно завести, но доставок в них не будет;
- квоты и сроки хранения (U-07) — этап 17. Зеркала — не резервная копия.

- **S14-03.** Команда выпуска этапа 13 доставок не создаёт. Этап 14 добавляет создание в той же транзакции и команду «Разместить» для выпусков, сделанных раньше.
- **S14-04.** Ключи `YANDEX_DISK_TOKEN`, `SMB_USERNAME`, `SMB_PASSWORD` объявлены заранее (этап 02), но по D-034 не используются. Они убираются из списка ключей конфигурации.

Поэтому служебная папка назначения Яндекс Диска — вне синхронизируемого дерева и на том же томе: тогда перенос в папку выпуска атомарен.

## 3. Переходы доставки (уточнение `state-machines.md` §16)

| Из | В | Кто | Условия и эффекты |
|---|---|---|---|
| — | `pending` | system (выпуск); инженер или руководитель (`delivery.manage`, «Разместить») | одна на активное назначение среды выпуска; закрепляются версия назначения, папка выпуска, набор файлов; задание `delivery.place` (`dedupe_key = delivery:<id>`) |
| `pending`, `outcome_unknown` | `staging` | worker под арендой | попытка `delivery_attempt`; сначала сверка состояния папок (§5.4) |
| `staging` | `committing` | worker | каждый файл в служебной папке сверен по SHA-256 и размеру |
| `committing` | `verifying` | worker | служебная папка перенесена в папку выпуска; если папка выпуска уже существует, её проверяют: совпадение — продолжение, иначе — `conflict` |
| `verifying` | `delivered` | worker | все файлы в папке выпуска сверены; признак готовности записан последним и сверен |
| любое рабочее | `failed` | worker | ошибка прав, места, пути, целостности или исчерпанные повторы сети; другое назначение не затрагивается (A28, I14) |
| любое рабочее | `outcome_unknown` | worker | истёк срок ожидания записи или переноса; следующий шаг — только сверка (A29) |
| любое рабочее | `conflict` | worker | в папке выпуска или на месте признака лежит файл с другим содержимым; перезаписи и удаления нет (A30) |
| `failed` | `pending` | `delivery.manage` | «Повторить»: `If-Match`, `Idempotency-Key`, причина; та же закреплённая версия (RT-05) |
| `conflict` | `pending` | `delivery.manage` | «Повторить после проверки»: человек убрал посторонний файл; причина; портал снова сверяет и не перезаписывает |
| `failed`, `conflict` | `superseded` | `delivery.manage` | «Перенаправить» на новую версию того же назначения; новая доставка; старая и её попытки сохраняются |

`delivered` и `superseded` — конечные. Частично загруженный набор не показывается размещённым: без признака готовности доставка не `delivered`.

### 3.1. Облако (только `yandex_disk`, D-034)

- `delivered` у Яндекс Диска означает «файлы проверены в локальной папке синхронизации». Это не «доставлено в облако».
- Портал синхронизацию не наблюдает: API клиента нет, REST API исключён. Поле `cloud_state` = `unconfirmed`.
- «Подтвердить облако…» (`delivery.manage`, примечание обязательно: как проверено) переводит `unconfirmed` → `confirmed`. Записываются кто и когда; это событие `delivery_event` и аудита.
- Помощь человеку — сценарий сверки скачанной из облака папки по `kontur-placement.json` (§16). Отмены подтверждения нет: ошибочное подтверждение исправляется новой доставкой.
- Этап 15 решает, нужно ли подтверждение облака для регистрации отправки.

## 4. Адаптер `FsDeliveryTarget`

- Оба назначения работают через `node:fs`:
  - корень Яндекс Диска — абсолютный путь внутри локальной папки синхронизации (например `C:\Users\<служба>\YandexDisk\Контур КП\Выпуски`);
  - корень сетевой папки — UNC-путь `\\сервер\ресурс\папка` (Windows) или абсолютный путь смонтированного ресурса (тесты, Linux).
- Адаптер получает корень и служебную папку только из закреплённой версии назначения (R01-05). Он ничего не удаляет вне служебной папки доставки и ничего не публикует.

```ts
interface IDeliveryTarget {
  readonly kind: 'yandex_disk' | 'smb';
  probe(): Promise<IProbeResult>;                              // корень и служебная папка есть, запись и перенос работают, тот же том
  inspect(where: 'root' | 'staging', rel: string): Promise<IRemoteEntry | null>;   // тип, размер, SHA-256 (чтение назад)
  ensureFolder(where: 'root' | 'staging', rel: string): Promise<void>;             // по уровням; существующая папка — не ошибка
  putStagingFile(rel: string, file: ILocalFile): Promise<IRemoteEntry>;           // запись в <файл>.part, затем переименование
  commitFolder(stagingRel: string, targetRel: string): Promise<'moved' | 'target_exists'>;  // rename без замены
  putMarker(targetRel: string, bytes: Buffer): Promise<'written' | 'exists'>;     // .part и перенос, только если признака нет
  removeOwnStaging(rel: string): Promise<void>;                // только внутри служебной папки доставки
}
// Ошибки — DeliveryAdapterError: FORBIDDEN | ROOT_NOT_FOUND | STAGING_NOT_FOUND | CROSS_DEVICE | NO_SPACE | UNAVAILABLE |
// TIMEOUT_UNKNOWN_OUTCOME | CONFLICT | INVALID_PATH; признак retryable; текст без путей пользователя и без секретов.
```

- Сверка содержимого — чтение файла назад и SHA-256, сравнение с SHA-256 и размером выпуска. В папке синхронизации чтение может касаться только локальной копии — это и есть «проверено в локальной папке».
- Перенос папки — `rename`, только если папки выпуска нет. Если она появилась между проверкой и переносом: на Windows — отказ; на POSIX — отказ для непустой папки, пустая заменяется без потери данных. Дальше — проверка папки выпуска.
- Ошибки ОС → коды адаптера:
  - `ENOSPC`, `EDQUOT` — нет места;
  - `EACCES`, `EPERM` — нет прав;
  - `ENOENT` у корня или служебной папки — не найдено;
  - `EXDEV` — разные тома;
  - `ETIMEDOUT`, `ECONNRESET`, `EHOSTUNREACH`, `ENETUNREACH`, `EIO`, `EBUSY` — сеть или устройство;
  - истёк срок ожидания записи или переноса — исход неизвестен.

  Каждая операция с файлами — со сроком ожидания.
- Особенности папки синхронизации (не наблюдаемы порталом, проверяются живой приёмкой):
  - клиент выгружает файлы в своём порядке, и признак готовности может появиться в облаке раньше файлов. Поэтому готовность в облаке определяется сверкой содержимого (§16), а не наличием признака;
  - при одновременной правке клиент может создать копию с конфликтом имени. Портал файлы после размещения не меняет.

## 5. Размещение

### 5.1. Раскладка (В-14-4)

- Папка выпуска — `<корень>/<код тендера>/Этап <N>/Выпуск <№ комплекта> <первые 8 знаков ID выпуска>`. Имена из данных очищаются (§6). Путь закрепляется в доставке.
- Внутри — файлы выпуска по их путям из манифеста кандидата. Признак готовности — `kontur-placement.json`.
- Служебная папка доставки — `<служебная папка назначения>/<ID доставки>/`. Она принадлежит доставке, и только в ней портал перезаписывает и удаляет свои незавершённые файлы.

### 5.2. Набор файлов (В-14-3)

- Назначение без внутренних материалов (по умолчанию) — набор «для заказчика»: аудитория `customer`, без превью.
- Назначение с отметкой «включать внутренние» — «все файлы»: внутренние, превью, `manifest.json` кандидата и `release-manifest.json` выпуска (в нём причины решений — R13-02).
- `kontur-placement.json` (схема `kontur-placement/1`) содержит:
  - выпуск, режим, хэш содержимого, SHA-256 манифеста выпуска;
  - набор и файлы набора с путём, размером и SHA-256.

  Причин решений и текстов в нём нет. Содержимое детерминировано: его SHA-256 вычисляется при создании доставки и сверяется.

### 5.3. Шаги задания `delivery.place`

Каждый шаг идемпотентен и начинается со сверки:
1. **Целостность (A27).** Перехэшировать байты каждого файла набора в хранилище и сверить с выпуском. Несовпадение → `failed` (`CONTENT_MISMATCH`), без повторов.
2. **Пути (A38).** Проверить корень, служебную папку, папку выпуска и пути файлов (§6). Недопустимый путь → `failed` (`INVALID_PATH`).
3. **Папка выпуска.** Если она уже существует:
   - признак есть и всё совпадает — `delivered` (прошлая попытка не успела записать итог);
   - файлы совпадают, признака нет — дописать признак;
   - иначе — `conflict` с перечнем расхождений.
4. **Корень, служебная папка и родители.** Корень и служебная папка назначения должны существовать: их создаёт администратор, «Проверить назначение» подтверждает доступ. Родительские папки `<код тендера>/Этап <N>` создаются по уровням.
5. **Стадирование.** Для каждого файла сначала посмотреть, что уже лежит в служебной папке:
   - совпадает — `staged`;
   - другой или частичный — переписать свой;
   - нет — записать.

   Запись идёт в `.part`, затем переименование; после неё — сверка. Истёк срок ожидания → `outcome_unknown`, задание переставляется на сверку.
6. **Перенос.** Служебная папка → папка выпуска без замены. Папка выпуска появилась — шаг 3. Исход неизвестен — сверка при следующем запуске: где сейчас файлы.
7. **Проверка и признак.** Сверить файлы в папке выпуска; записать признак без перезаписи; сверить признак → `delivered`. Убрать пустую служебную папку доставки.

Перезапуск worker на любом шаге: аренда истекает, задание восстанавливается, следующий запуск начинается со сверки. Дублей нет: служебная папка своя, папка выпуска появляется одним переносом, признак пишется без перезаписи.

### 5.4. Неизвестный исход (A29)

`outcome_unknown` не повторяет запись вслепую. Следующий запуск:
- читает папку выпуска (шаг 3), затем служебную (шаг 5);
- затем решает: продолжить, считать готовым или конфликт.

В `delivery_attempt` остаются обе попытки.

### 5.5. Ошибки и повторы

| Ошибка | Исход | Повтор |
|---|---|---|
| `UNAVAILABLE` (сеть, устройство) | задание повторяется с backoff (до 5 попыток) | исчерпаны → `failed` (`NETWORK`); дальше — человек |
| `TIMEOUT_UNKNOWN_OUTCOME` | `outcome_unknown` → сверка | автоматически, затем как выше |
| `FORBIDDEN`, `ROOT_NOT_FOUND`, `STAGING_NOT_FOUND`, `CROSS_DEVICE` | `failed` | только человек после исправления доступа или назначения |
| `NO_SPACE` | `failed` | только человек |
| `CONFLICT` | `conflict` | «Повторить после проверки» или «Перенаправить» |
| `CONTENT_MISMATCH`, `INVALID_PATH` | `failed` | повтор не поможет — новый комплект или исправление назначения |

## 6. Пути

- Корень и служебная папка: абсолютный путь — UNC `\\сервер\ресурс\…`, `X:\…` или `/…` (тесты, Linux). Без `..` и управляющих символов.
- У `yandex_disk` служебная папка не внутри корня, и корень не внутри служебной папки. Что тот же том — проверяет «Проверить назначение» (перенос пробной папки).
- Сегменты папки выпуска и путей файлов:
  - запрещены: пустой сегмент, `.`, `..`, `/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`, управляющие символы;
  - запрещены начальный и конечный пробел, конечная точка;
  - запрещены зарезервированные имена Windows (`CON`, `PRN`, `AUX`, `NUL`, `COM1…9`, `LPT1…9` с любым расширением);
  - сегмент — до 120 знаков, путь относительно корня — до 240.
- Имена из данных (код тендера) очищаются заменой запрещённого на `_`. Пути файлов из манифеста не переименовываются: недопустимый путь — отказ (A38).

## 7. Независимость направлений (A28, I14)

У каждого назначения — своя доставка, своё задание, свои попытки и файлы. Ошибка одного не меняет другое. «Повторить» действует только на выбранную доставку. На карточке выпуска — «размещено N из M» и отдельно «облако подтверждено» у Яндекс Диска.

## 13. Инварианты БД (вторая линия)

1. Доставка — только для выпуска со средой, равной среде назначения. Версия — текущая версия назначения. Не больше одной действующей доставки на (выпуск, назначение). Закреплённые поля неизменны.
2. Переходы — только по §3. `delivered` — только при всех файлах `verified`. `delivered` и `superseded` — конечные. Облако: `not_applicable` у `smb`; `confirmed` — только у `delivered` `yandex_disk`, с автором, временем и примечанием, один раз.
3. Человеческие переходы — пользователь с `delivery.manage` по тендеру, с причиной в `delivery_event`.
4. Назначение: `kind`, `environment` неизменны; версия — номер +1; меняет только администратор.
5. Версии назначения, проверки доступа, попытки, события неизменны. `DELETE` и `TRUNCATE` запрещены у всех таблиц этапа.

## 15. Матрица проверок задания → тесты

Проверки на поддельных данных идут через обёртку файловой системы с внесением отказов поверх временных папок: для Яндекс Диска — «папка синхронизации» и служебная вне неё, для сетевой папки — свой корень. Оба направления проходят одни и те же сценарии.

| Проверка задания | Поведение | Тест |
|---|---|---|
| обрыв сети / SMB | повтор с backoff, затем `failed` (`NETWORK`); после восстановления «Повторить» → `delivered`, дублей нет | `deliveryFlow` «отказы» |
| потеря доступа | `failed` (`FORBIDDEN`) без ложного успеха | `deliveryFlow` «отказы» |
| частичная запись | обрыв на середине файла: в папке выпуска ничего нет; повтор дописывает служебную и переносит | `deliveryFlow` «отказы» |
| перезапуск | worker останавливается после части файлов, после переноса, до признака; новый запуск сверяет и завершает без дублей | `deliveryFlow` «перезапуск» |
| истёк срок ожидания при неизвестном исходе | запись на самом деле прошла, ответа нет → `outcome_unknown` → сверка → `delivered` без повторной записи (A29) | `deliveryFlow` «отказы» |
| существующий файл | в папке выпуска уже есть файл с другим содержимым → `conflict`, без перезаписи и удаления (A30); то же содержимое → `delivered` | `deliveryFlow` «существующие файлы» |
| несовпадение хэша | байты в хранилище подменены после согласования → `failed` (`CONTENT_MISMATCH`), ничего не записано (A27); файл после записи читается с другим хэшем → перезапись в служебной папке, в папке выпуска — `conflict` | `deliveryFlow` «существующие файлы» |
| успех одного направления и ошибка другого | Яндекс Диск `delivered`, сетевая папка `failed`; повтор только сетевой (A28) | `deliveryFlow` «независимость» |
| вредоносный сегмент пути | `..`, абсолютный путь, `\`, зарезервированное имя в пути файла или пути назначения → отказ до записи (A38); код тендера с `/` и `..` — очищен | `deliverySchema` «вредоносные пути», `deliveryCore` «пути» |
| заполненный диск | `ENOSPC` → `failed` (`NO_SPACE`); служебная папка не выдаётся за размещение | `deliveryFlow` «отказы» |
| облако Яндекс Диска | `delivered` — «проверено локально, облако не подтверждено»; подтверждение — человек с примечанием, только `delivered` `yandex_disk` | `deliveryFlow` «облако» |
| проверка доступа под учётной записью worker | «Проверить назначение» выполняет worker; разные тома, нет служебной папки, нет прав — понятный отказ | `deliverySchema` «Проверить назначение», `deliveryCore` «адаптер» |
| среда | тестовый выпуск — только в тестовые назначения; повтор и перенаправление среду не меняют (RT-05) | `deliverySchema` «вторая линия», `deliveryFlow` «выпуск», «перенаправление» |
| вторая линия | прямые записи роли приложения в обход §3 и §13 — отказ | `deliverySchema` «вторая линия» |

Также: smoke на настоящих server и worker (временные папки), проверка интерфейса этапа 14, регрессия интерфейса 02–13.

Файлы тестов (передача 14-1): `tests/deliveryFlow.test.ts` — 20, `tests/deliverySchema.test.ts` — 12, `tests/deliveryCore.test.ts` — 13; заготовка и обёртка с отказами — `tests/deliveryFixtures.ts`. Остановка worker имитируется честно: операция «зависает», аренда задания снимается (как после истечения аренды и прохода восстановления), «умерший» запуск доигрывает без аренды и ничего не записывает (`crashAt`).

### 15.1. Уточнения реализации (передача 14-1)

1. **Общий алгоритм.** Шаги §5.3 вынесены в `placeFolder` (адаптер, `packages/adapters/src/delivery/place.ts`). Его вызывают задание `delivery.place` и сценарий живой проверки — живая проверка гоняет тот же код, что worker.
2. **Файловая система — в `@kontur/storage`.** Пакет адаптеров файловую систему не трогает (правило A38, `tests/adapters.test.ts`): в нём интерфейс `IDeliveryFs`, реализация `nodeDeliveryFs` — `packages/storage/src/deliveryFs.ts`.
3. **Признак готовности без замены.** `rename` файла и на Windows (MoveFileEx с заменой), и на POSIX заменяет существующий файл. Поэтому признак переносится `moveNoReplace`: жёсткая ссылка (атомарно, `EEXIST`) и удаление исходного; где ссылки не поддерживаются — проверка и `rename`. Папка выпуска переносится `rename` папки: занятое имя на Windows — отказ, на POSIX — отказ для непустой папки.
4. **Ровно файлы набора.** В существующей папке выпуска посторонний файл — конфликт (кроме `desktop.ini`, `Thumbs.db`, `.DS_Store`). Портал не дописывает и не удаляет чужое: при частично заполненной чужой папке человек убирает папку и выбирает «Повторить после проверки».
5. **Служебная папка по умолчанию** (`<корень>/.kontur-staging`, сетевая папка) создаётся порталом. Явно заданную служебную папку портал не создаёт: опечатка в пути — `STAGING_NOT_FOUND`, а не новая папка.
6. **Набор закрепляется в транзакции создания.** У `delivery` — `created_xact`; вставка `delivery_file_state` — только в ней. Отложенная проверка `delivery_set_check` в конце транзакции: признак соответствует выпуску (ID, режим, хэш содержимого, манифест выпуска, набор), файлы набора — ровно файлы кандидата выбранного набора с теми же байтами и размером, манифесты — только в наборе «все файлы», признак — один, с закреплённым отпечатком; набор — по политике закреплённой версии назначения; папка выпуска — по раскладке В-14-4.
7. **Worker сверяет набор с признаком** до записи: расхождение — `CONTENT_MISMATCH` (защита сверх второй линии).
8. **Возможность администратора** — `admin.delivery` (глобальная, у роли `admin`).
9. **Статус после перезапуска не откатывается**: `committing`/`verifying` не возвращаются в `staging`.
10. **Попытки.** На последней попытке промежуточная запись «прервано» не пишется — попытку записывает терминальная фиксация («ошибка»). Текст внутренней ошибки (`internal`) в доставку не попадает: в нём могут быть полные пути; подробности — в журнале заданий.
11. **Сравнение вложенности путей** схлопывает повторные разделители (`/a//b` внутри `/a/b`).
12. **Windows: кратковременная блокировка.** Антивирус и индексатор держат только что записанный файл или папку — `rename` отвечает `EPERM`/`EACCES`/`EBUSY`. На Windows — короткие повторы (около 2 с), пока имя назначения свободно (как graceful-fs); удаление — `maxRetries`. Без этого перенос становился бы «нет прав» без повтора.

## 16. Живая приёмка двух реальных назначений

`npm run delivery:live-smoke`. Коды выхода: 0 — PASS, 1 — FAIL, 3 — `NOT_RUN` (нет настроек). Сценарий:
- запускается под той же учётной записью, что и служба worker;
- размещает тестовый набор (синтетические файлы, без данных тендера) в оба назначения;
- сверяет файлы;
- повторяет размещение — дублей нет;
- создаёт конфликт своим тестовым файлом;
- убирает только свою служебную папку.

Журнал — `artifacts/stage-14/live-*.log`, без секретов и без полных путей пользователя.

Облако Яндекс Диска — отдельный шаг живой приёмки (D-034):
1. Дождаться синхронизации.
2. Скачать папку выпуска из веб-интерфейса Диска (или открыть её на другом устройстве с этой учётной записью).
3. Сверить: `npm run delivery:compare -- <скачанная папка>` — сверка файлов с `kontur-placement.json` по SHA-256 и размеру.

Итог записывается в журнал.

`VERIFIED_LIVE`:
- сетевая папка — по PASS живого сценария;
- Яндекс Диск — по PASS живого сценария **и** сверки скачанной из облака папки.

Без доступа адаптеры остаются `BLOCKED_EXTERNAL`. Окончательная приёмка этапа без двух реальных назначений не объявляется.

Нужно от владельца (в локальные настройки машины проверки, не в чат):
1. **Яндекс Диск:**
   - установленный клиент Яндекс Диска на Windows-машине проверки, вошедший в тестовую учётную запись;
   - тестовая папка внутри папки синхронизации — `DELIVERY_LIVE_YANDEX_ROOT`;
   - служебная папка вне папки синхронизации на том же диске — `DELIVERY_LIVE_YANDEX_STAGING`;
   - права учётной записи, под которой идёт проверка;
   - доступ к веб-интерфейсу Диска этой учётной записи — для шага проверки облака.
2. **Сетевая папка:**
   - тестовая папка, например `\\сервер\ресурс\Контур КП тест`, — `DELIVERY_LIVE_SMB_ROOT`;
   - права на создание, запись, чтение, переименование и удаление только внутри неё, для учётной записи проверки.
3. **Согласие:** портал пишет в тестовые папки и удаляет только свою служебную папку.
