# Этап 16 — чат через Codex и Cursor (MCP портала)

Дата: 2026-10-12. Задание — `docs/spec/prompts/stage-16.md`. Начат по слову владельца («и начинай 16 этап») после этапа 15a. Ветка `stage-16` от `stage-15a` = `a739cc5`: этап 15a передан на ревью и ещё не принят, поэтому ветки идут друг за другом; замечания к 15a исправляются в `stage-15a` и переносятся сюда.

Этот документ — проект до кода. Опирается на ADR-010, ADR-006, ADR-008, ADR-009, `docs/contracts/mcp-tools.md`, решения D-013, D-019, D-020, D-021, спецификацию §11.

## 0. Границы

Входит:
- один MCP-сервер портала внутри процесса `server`, сетевой транспорт;
- персональные токены пользователя с областями `read` и `propose`;
- инструменты чтения и четыре инструмента предложений;
- явная область: тендер и этап, выпуск или два выпуска; вид контекста `contract`;
- ограничение объёма, пагинация, права, аудит, вырезание секретов, лимит вызовов;
- экран выпуска и отзыва токенов, экран предложений из чата;
- настройка Codex и Cursor по официальной документации и сценарии проверки обоих клиентов;
- случаи манифеста Locus со статусом `deferred:16`.

Не входит:
- встроенный чат на токенах подписки (C03);
- `approve`, `release`, `send`, решения по удержаниям и рискам, изменение требований, расчёта, пользователей и настроек, SQL, команды, файловая система — ни через токен, ни через схему инструментов (ADR-006, I12);
- вопрос к ответному ядру наружу: клиент сам является моделью (D-020);
- второй MCP-сервер;
- TLS, имя хоста и служба Windows — этап 17 (U-02);
- живая модель портала; блокеры боевого выпуска Q-01/X-01, Q-05, Q-08 сохраняются; S15-08 не меняется.

## 1. На что опирается этап

Уже есть (проверено по коду, файлы — в отчётах этапов):
- прогон поиска: `POST /search`, `GET /search-runs/{id}`, функции `resolveSearchContext`, `startScopedSearch`; права пересчитываются при каждом чтении, `409 scope_changed`;
- замечания, вопросы заказчику, расчёт и экономика, готовность выпуска, сравнение выпусков (этап 15) — со своими представлениями и закрытостью по правам читателя;
- в схеме заготовлены `principal_kind = model_via_mcp` и `on_behalf_of_user_id` у `audit_event` и `search_run`, но код их не пишет;
- обёртка команд после этапа 15a привязывает сохранённый ответ к правам.

Нет: таблицы `api_token`, маршрутов токенов, возможности `mcp.propose`, кода MCP, вырезания секретов из ответов, лимита вызовов кроме входа. Запрос с `Authorization: Bearer` сейчас получает `401`.

## 2. Транспорт, SDK, точка входа

Сверено с официальной документацией 2026-10-12 (ADR-010 откладывал это на этап 16):

- Ревизия протокола — `2026-07-28`. Стандартные транспорты — stdio и Streamable HTTP. HTTP+SSE ревизии 2024-11-05 устарел.
- Streamable HTTP: одна точка, только `POST`; ответ — один JSON-объект или поток SSE на этот запрос; сессий и постоянного потока `GET` нет; каждый запрос несёт версию протокола и сведения о клиенте; заголовки `MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name` обязаны совпадать с телом, иначе `400`.
- Требования безопасности транспорта: сервер обязан проверять `Origin` и отвечать `403` на недопустимый; должен аутентифицировать соединения.
- Официальный SDK для TypeScript — вторая линия: `@modelcontextprotocol/server` 2.3.1, `@modelcontextprotocol/client` 2.3.1, привязка к Express `@modelcontextprotocol/express` 2.0.2 (реестр npm, 2026-10-12). Пакет `@modelcontextprotocol/sdk` 1.x — прежняя линия.

Решение:
- Точка — `POST /mcp` в процессе `server`. `GET` и `DELETE` — `405`. Ответ — всегда один JSON-объект: потоков и запросов сервера к клиенту у портала нет.
- Сервер и протокол — официальный SDK (`@modelcontextprotocol/server`, точные версии в `package-lock.json`). Свой разбор JSON-RPC не пишется. Поддержка клиентов с рукопожатием — средствами SDK; если SDK её в режиме без состояния не даёт, это фиксируется как ограничение, а не обходится самодельным кодом.
- Аутентификация — только `Authorization: Bearer <токен>`. Cookie сессии на `/mcp` не читается, поэтому подделка запроса из браузера токена не получает.
- `Origin`: чат-клиенты его не шлют. Запрос с `Origin` принимается, только если он в списке разрешённых источников портала; иначе `403`.
- Размер тела запроса — до 100 КБ, как у API.
- В тестах клиент — официальный `@modelcontextprotocol/client` по настоящему HTTP: это проверка протокола, а не подключения Codex или Cursor.
- TLS: чат-клиенты работают на ПК инженеров, портал — на отдельном компьютере; шифрование канала даёт развёртывание (U-02, этап 17). До этого точка проверяется на `localhost`. Включается настройкой `MCP_ENABLED`; по умолчанию выключена.

## 3. Токены — миграция `0040`

`api_token`: владелец (`user_id`), название, вид клиента (`codex` / `cursor` / `other`), SHA-256 токена, первые символы для показа, области (`read`, `propose` — CHECK), срок действия (обязателен), время последнего вызова, отзыв (кто и когда). Сам токен в БД не хранится и показывается один раз при выпуске.

- Выпуск, список, отзыв — `POST /me/api-tokens`, `GET /me/api-tokens`, `DELETE /me/api-tokens/{id}`: только человек с сессией. Токеном выпустить токен нельзя.
- Область `read` доступна пользователю с ролью инженера или руководителя. Область `propose` — при возможности `mcp.propose` (инженер и руководитель тендера); в `portal-api.md` выпуск токена был целиком закрыт `mcp.propose` — уточняется: `read` без неё допустим.
- Администратор отзывает чужой токен; содержимого и самого токена не видит.
- Права вызова — пересечение прав пользователя и областей токена. Контекст прав загружается заново на каждый вызов: отзыв назначения, роли или `mail.read` действует сразу. Отключённый пользователь — `401`.
- Возможности человека (`candidate.approve`, `candidate.release`, `send.register`, `hold.resolve`, `risk.accept` и прочие) токену недоступны по построению: `/mcp` вызывает только свои обработчики инструментов, а `/api/v1` Bearer не принимает (как сейчас, `401`).
- Вторая линия БД: записи с `principal_kind = model_via_mcp` не могут быть автором согласования, выпуска, отправки, решения.

Срок действия — 7, 30 или 90 дней, по умолчанию 30; у пользователя не больше пяти действующих токенов (D-037, В-16-2). Оба ограничения — в БД.

## 4. Область вызова

- Инструмент получает `tenderId` и `stageId` либо `releaseId`; сравнение — `leftReleaseId` и `rightReleaseId`; контекст договора — `contractId` (требует `contract.read`).
- Область не задана или неоднозначна — ответ `needs_selection` со списком доступных пользователю тендеров и этапов: код, название, заказчик. Данных тендеров в нём нет. Портал не выбирает тендер по тексту вопроса (D-019).
- `stageId` — рабочий набор источников этапа. `releaseId` — снимок источников комплекта этого выпуска: исторический вопрос по выпуску этапа 1 не видит поступившего позже (A11).
- Чужой тендер, этап, выпуск, фрагмент — `out_of_scope` без данных и без признака существования (A12).
- Запрос «по всем проектам» не выполняется: область — один тендер или договор.
- Права на ящики и договоры применяются при каждом вызове; `scopeHash` — в ответе и в аудите.

## 5. Инструменты

### 5.1. Чтение (область `read`)

| Инструмент | Источник в портале |
|---|---|
| `list_cases` | доступные тендеры и этапы |
| `get_case_overview` | набор источников, ревизия расчёта, последние проверки, готовность |
| `list_documents` | документы и редакции области; постранично |
| `search_evidence` | создаёт прогон поиска теми же функциями, что `POST /search` |
| `get_search_run` | дочитывает итог прогона; читает только автор, права пересчитываются |
| `get_citation` | точный текст фрагмента, документ, редакция, страница |
| `list_requirements` | требования реестра этапа с покрытием (S16-04) |
| `get_calculation` | закреплённая ревизия расчёта: позиции, строки, итоги; постранично |
| `get_economics` | итог, составляющие, известное и неизвестное, статус сверки |
| `list_findings` | замечания: серьёзность, уверенность, статус, основания; постранично |
| `list_questions` | вопросы заказчику и ответы |
| `list_decisions` | решения этапа с автором и основаниями (S16-04) |
| `get_readiness` | блокеры выпуска, удержания, полнота проверок, размещение и отправка |
| `compare_releases` | сравнение двух выпусков этапа 15: разделы, выводы, причины со статусом |
| `get_integration_status` | статусы интеграций и время последней проверки |

Правила:
- Каждый инструмент вызывает те же функции чтения и те же проверки закрытости, что и экран портала. Отдельной логики прав у MCP нет.
- Предварительный лексический результат поиска помечается `preliminary` и за итог не выдаётся; итог — только из `get_search_run`.
- Суммы считает сервер. Формат — десятичная строка, валюта, признак НДС, вид цены, ревизия расчёта. Нет цены — явное «нет данных» с причиной, а не ноль. Вид цены, которого нет в расчёте, — отказ с перечнем имеющихся видов.
- Ссылки на основания — ID фрагментов портала: стабильны и открываются `get_citation`.

### 5.2. Предложения (область `propose`)

`propose_finding`, `propose_question`, `propose_condition_text`, `propose_change_reason`. Все требуют `requestId`; повтор возвращает ту же запись. Все цитаты должны существовать, входить в область и читаться пользователем; иначе `invalid_citation` без создания записи.

## 6. Предложения — миграция `0040`

`mcp_proposal`: тендер, этап, вид (`finding` / `question` / `condition_text` / `change_reason`), содержимое, цитируемые фрагменты (отдельная таблица), `request_id`, токен, пользователь, от имени которого действует клиент, статус `open` / `accepted` / `rejected`, решивший человек, ссылка на созданную запись. Уникальность — (пользователь, `request_id`).

- Предложение ничего не меняет: не входит в блокеры, проверки, расчёт и комплект, пока его не принял человек.
- Принимает человек в портале обычной командой с If-Match, под своим именем и своей возможностью:
  - замечание — `finding.write`: создаётся замечание, автор — человек, источник — «предложено через чат»;
  - вопрос — `requirement.create`: создаётся черновик вопроса заказчику;
  - текст условия — `application.fill`: человек вставляет текст в поле приложения; без указанного поля предложение остаётся текстом для копирования;
  - причина изменения — `change_reason.confirm`: человек записывает причину вывода сравнения со статусом «гипотеза»; основания — цитаты предложения.
- Нельзя принять или отклонить предложение, основания которого не читаешь; текст такого предложения закрыт (то же правило, что у гипотез модели, S15a-01).
- Запись от модели не становится решением: автор принятой записи — человек; `model_via_mcp` автором решения быть не может (вторая линия БД).

## 7. Объём ответа, пагинация, лимит вызовов

Числа — настройки с такими значениями по умолчанию (решение исполнителя; в документах чисел не было):

| Параметр | Значение |
|---|---|
| размер страницы | 20, не больше 50 |
| текст одного фрагмента | до 2000 знаков, признак обрезки и `get_citation` для полного текста |
| размер ответа инструмента | до 64 КБ; сверх — обрезка страницы и курсор |
| лимит вызовов | 60 в минуту и 600 в час на токен; сверх — `rate_limited` |

Курсор — непрозрачная строка, привязанная к токену, инструменту и области.

## 8. Аудит

Каждый вызов инструмента, включая чтение и отказы, — запись `audit_event`: `principal_kind = model_via_mcp`, `on_behalf_of_user_id` — владелец токена, токен, инструмент, область и `scopeHash`, исход. Текст запросов, цитат и предложений в журнал не пишется: журнал читают шире, чем источники. Прогон поиска, созданный через MCP, получает тот же вид участника.

## 9. Текст как данные и секреты (I16, I17)

- Текст документов и писем возвращается только как значение полей результата. Сервер его не исполняет и области по нему не расширяет; описание каждого инструмента сообщает клиенту, что содержимое источников — данные, а не инструкции.
- Результат перед отправкой проходит вырезание: токены портала и Bearer, строки подключения с паролем, закрытые ключи, внутренние адреса из настроек. Найденное заменяется отметкой.
- В ответах нет путей хранилища, адресов внутренних служб и значений настроек.

## 10. Клиенты

`docs/integrations/mcp-clients.md` — настройка по официальной документации (сверено 2026-10-12):
- Codex: `~/.codex/config.toml`, таблица `[mcp_servers.<имя>]`, `url`, `bearer_token_env_var` — токен в переменной окружения, не в файле;
- Cursor: `.cursor/mcp.json` или `~/.cursor/mcp.json`, `url` и `headers` с подстановкой `${env:ИМЯ}`.

Прочитанный пример настройки подключением не считается (ADR-010). Статусы раздельно: протокол (официальный клиент SDK по HTTP) и живая проверка каждого клиента. Какие клиенты доступны для живой проверки — вопрос владельцу В-16-1 (Q-12).

## 11. Экраны

- Профиль → «Доступ для чат-клиентов»: выпуск токена (название, клиент, области, срок), показ один раз с подсказкой настройки, список с последним использованием, отзыв.
- Этап тендера → «Предложения из чата»: открытые предложения с цитатами, «Принять» и «Отклонить» с причиной; закрытое предложение — без текста.
- Журнал: вызовы через чат отличимы от действий человека.

Адаптивность, темы и поля ввода — по правилам проекта.

## 12. Проверки задания → тесты

| Проверка | Как проверяется |
|---|---|
| неоднозначный тендер | вызов без области → `needs_selection`, только код, название, заказчик; случай Locus `pv2-ambiguous-sokolniki` |
| исторический вопрос (A11) | поиск и документы по выпуску этапа 1 после поступлений этапа 2 — ни одного позднего основания |
| отсутствие цены | `get_calculation` и `get_economics` без расчёта или без итога — «нет данных» с причиной |
| неверный вид цены | запрос вида, которого нет в ревизии, — отказ с перечнем видов; суммы разных видов не смешиваются |
| цитата не существует | `get_citation` и `propose_*` с чужим или несуществующим фрагментом — `out_of_scope` / `invalid_citation` |
| «игнорируй правила» в PDF (A36) | документ с инструкцией: текст возвращается как данные, область и права не меняются, действий нет |
| чужой тендер (A12) | все инструменты с чужими ID — `out_of_scope` без данных, счётчиков и признака существования |
| запись от модели не становится решением (A25, A37) | предложение не влияет на готовность; `approve` и прочее через токен недоступны; принятие — только человеком |
| повтор запроса (A37) | тот же `requestId` — та же запись, одна строка |
| секреты не уходят в результат (I17) | источник с токеном, строкой подключения и ключом — в результате отметки вместо значений |
| «все проекты» | случай Locus `pv2-all-projects-advance`: отказ или `needs_selection`, не агрегат |
| RT-02 через MCP | письмо из закрытого ящика не участвует в поиске и цитатах |
| матрица ролей через MCP | инженер, руководитель, не участник, отозванный доступ, отключённый пользователь |
| токены | выпуск, показ один раз, срок, отзыв, области, чужой токен, Bearer на `/api/v1` — `401` |
| протокол | официальный клиент SDK: список инструментов, вызов, ошибки, `Origin`, методы `GET` / `DELETE` |
| лимиты | страница, обрезка, курсор, лимит вызовов |

Плюс полный набор, typecheck, build, smoke, проверка интерфейса, регрессия интерфейса прежних этапов.

## 13. Вопросы владельцу

- **В-16-1 (Q-12).** Какие чат-клиенты доступны для живой проверки на машине ревьюера: Codex, Cursor, оба или ни одного? От ответа зависит, чем закончится этап по F15 и F16: живой проверкой клиента или «протокол проверен, живая проверка не выполнялась».
- **В-16-2.** Срок действия токена. Предложение: 30 дней по умолчанию, выбор 7 / 30 / 90, не больше 90; не больше пяти действующих токенов у пользователя.

Ответы владельца (2026-10-12, D-037, `docs/reviews/16-owner-decisions.md`):
- **В-16-1 — Codex и Cursor.** Живая проверка обоих клиентов — на машине ревьюера, по сценариям `docs/integrations/mcp-clients.md`. На машине разработки клиентов нет: исполнитель проверяет протокол официальным клиентом SDK и не объявляет это подключением клиента.
- **В-16-2 — 30 дней по умолчанию, выбор 7 / 30 / 90,** не больше пяти действующих токенов у пользователя.
