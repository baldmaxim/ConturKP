# Этап 18 — проект: пилот, приёмка и передача

Дата: 2026-10-21. Задание — `docs/spec/prompts/stage-18.md` (`docs/spec/03_STAGE_PROMPTS.md`, раздел этапа 18). База — `main` = `47a8ad6` (этап 17 принят, D-042). Решения владельца — D-043 (`docs/reviews/18-owner-decisions.md`).

## 1. Цель и граница

Пилот проверяет продукт на одном реальном завершённом тендере полным циклом: источники → требования и проверки → экономика → формы и файлы → согласование → тестовый выпуск и размещение → копия и восстановление. Итог этапа — независимое финальное ревью и решение владельца: принять продукт или вернуть с конкретными условиями.

Не входит: отправка КП заказчику, изменение исторических исходников (TenderHub, письма, документы), этап 19 (вывод Locus), Telegram и прочие необязательные расширения — они в backlog (§8).

Ограничение итога. Пока открыты Q-01/X-01 (закрытый расчёт), Q-05 (правило итога КП) и Q-08 (реальные формы), итог — не «готово к эксплуатации», даже при прохождении всех ворот пилота (задание этапа 18). Варианты итога — §9.

## 2. Решения владельца (D-043)

| Пункт | Решение |
|---|---|
| Пилотный тендер | выбирают владелец и ревьюер на целевом ПК по критериям §3.1 |

## 3. Порядок

### 3.1. Выбор тендера (владелец и ревьюер, целевой ПК)

Критерии задания: завершённый тендер; не меньше двух отправок КП; договор; ТЗ; изменённая документация (не меньше двух редакций хотя бы одного документа); известные решения (итог торгов, согласованные условия). Объём реальных данных согласует владелец (В-18-2).

Пригодность проверяет команда `ops:pilot candidate` (§5.1) — только чтение: TenderHub — GET, портал — SELECT. Название и номер тендера в Git и в ZIP передачи не попадают: в отчёте — идентификатор портала и агрегаты.

### 3.2. Эталон до запуска

1. Составитель (D-043) по исходникам тендера заполняет эталон по шаблону `docs/pilot/reference-template.json` (§4).
2. `ops:pilot reference-seal` проверяет схему и печатает SHA-256, число пунктов и число критических. Владелец пересылает печать ревьюеру до начала цикла — внешний свидетель времени.
3. После печати эталон не правится. Ошибка составителя — новая версия с причиной; ворота считаются по запечатанной версии, новая версия показывается в отчёте рядом.

### 3.3. Цикл

Загрузка источников (TenderHub GET, документы, EML, переговоры), требования, проверки и разногласия, экономика, формы, файлы кандидата, согласование руководителем, тестовый выпуск, тестовое размещение в отдельную папку. Участники ведут журнал времени ручной работы (§6, М5). Модель не согласовывает выпуск (01_PRODUCT_SPEC).

### 3.4. Сопоставление и ворота

Составитель эталона (или ревьюер) размечает результат в файле сопоставления (§4.2). `ops:pilot report` считает метрики и ворота (§6) по рабочей базе — только чтение — и файлам эталона и сопоставления. Затем — копия и восстановление (G6), финальное ревью.

## 4. Форматы

### 4.1. Эталон `kontur.pilot-reference.v1`

```json
{
  "schema": "kontur.pilot-reference.v1",
  "tenderId": "<uuid тендера в портале>",
  "author": "<роль составителя, без ФИО>",
  "createdAt": "2026-10-..T..:..:..+03:00",
  "items": [
    {
      "id": "REF-001",
      "kind": "conflict | change | price_reason | decision",
      "critical": true,
      "summary": "что должно быть найдено",
      "sources": [{ "document": "<имя файла>", "locator": "стр./раздел/пункт", "quote": "дословный фрагмент" }],
      "expected": "ожидаемый вывод или решение"
    }
  ]
}
```

`kind`: `conflict` — противоречие между источниками; `change` — изменение между редакциями или отправками; `price_reason` — причина изменения цены; `decision` — известное решение. Файл с реальными данными хранится только на целевом ПК; в Git — схема, пустой шаблон и проверка схемы.

### 4.2. Сопоставление `kontur.pilot-matching.v1`

- для каждого пункта эталона: `found` (идентификаторы замечаний, разногласий или ответов портала) или `missed`;
- для каждого замечания портала по тендеру: `true` (совпало с эталоном), `valid_extra` (верно, в эталоне нет), `false` (ложное), `duplicate`;
- для выборки цитат принятых выводов: `supports` / `does_not_support`.

`report` сверяет идентификаторы с базой до расчёта G1, М1 и М3 (R18-01). В `found` допустимы: замечание этого тендера, кроме `rejected` и `stale`; разногласие этого тендера; завершённый прогон ответа этого тендера. Для `price_reason` допустима версия причины этого тендера. В выборке цитат допустимы: замечание `resolved` или `accepted_risk`; прогон ответа `confirmed_by_citations`. Неизвестный, чужой, другого вида или статуса идентификатор не засчитывается, и показатель получает FAIL со списком ошибок.

## 5. Инструменты (`scripts/ops/pilot.ts`, `npm run ops:pilot -- <команда>`)

Все команды только читают рабочую базу: отдельное соединение `default_transaction_read_only = on`; записей и заданий не создают. Результат — JSON и Markdown без текстов источников; секретов не печатают.

### 5.1. `candidate --tender <uuid>`

Признаки пригодности из базы: число отправок (этап 15), договор и ТЗ среди источников, документы с двумя и больше редакциями, ревизии расчёта TenderHub, этапы тендера. Итог — `SUITABLE` или список недостающего.

### 5.2. `reference-seal --file <путь>`

Проверка схемы §4.1, уникальность `id`, у критического пункта есть источник с цитатой; SHA-256 файла.

### 5.3. `report --tender <uuid> --reference <путь> --matching <путь>`

Сверяет SHA-256 эталона с печатью (`--sealed <sha>`), затем считает §6. Опора на существующий код:

| Что | Где |
|---|---|
| денежная сверка | `revision_economics` (миграция 0026), `buildRevisionEconomics` (`packages/core/src/money/report.ts`) |
| одобренные = размещённые | `delivery_file_state` (0038), сверка `scripts/delivery-compare.ts` |
| основания выводов | `answer_evidence` (0022), `finding_evidence` (0024) → `evidence_fragment` |
| замечания и разногласия | `finding`, `finding_event`, `discrepancy` (0024) |
| причины цены | `change_explanation.reason_status` (0026) |
| действия пользователей | `audit_event` (0001) |

Новая проверка — дословность цитаты: текст цитаты принятого вывода содержится в тексте своего фрагмента после нормализации пробелов и переносов. Сейчас происхождение фрагмента проверяется по набору входа (`checkClaim`), дословность — нет.

## 7. Данные и безопасность

- Реальные данные остаются на целевом ПК. В Git и ZIP — схемы, шаблоны, агрегаты, хэши, идентификаторы портала; без названий, адресов, ФИО и текстов источников.
- КП не отправляется: выпуск тестовый, размещение — в отдельную тестовую папку; боевой выпуск запрещён блокерами Q-01/X-01, Q-05, Q-08.
- Исторические исходники не меняются: TenderHub — только GET, оригиналы писем и документов хранятся как есть.
- Участники получают доступ к пилотному тендеру назначением; не больше двух инженеров (триггер миграции 0001).

## 14. Q-05 — правило итога КП (D-044)

- Правило `th_grand_total_vat_included`: `kp_total` = `source_grand_total` (cached_grand_total TenderHub), валюта RUB, смысл — «итог расчёта TenderHub, в т.ч. НДС (D-044)».
- Правило ставит захват расчёта при создании содержимого (`calculation_content`), если итог источника есть; без итога источника правило не ставится и `KP_TOTAL_NOT_APPROVED` остаётся. Правило входит в хэш содержимого: уже сохранённые содержимые неизменяемы и правила не получают — для пилота расчёт выгружается заново.
- Толкование исполнителя (на проверку владельцу и ревьюеру): итог источника — последнее материализованное значение TenderHub и может отставать от строк (D-030). Поэтому для боевого выпуска дополнительно требуется сверка экономики `reconciled` для этой ревизии; иначе — неснимаемый блокер `KP_TOTAL_UNRECONCILED`.
- В формах и письме итог КП показывается с подписью «в т.ч. НДС»; поле `source_grand_total` остаётся «итогом источника».

## 15. Q-01 — решение руководителя о закрытом расчёте (D-044)

Данные (миграция 0044, таблицы неизменяемые, `forbid_mutation`, TRUNCATE запрещён):
- `calculation_closure_decision`: тендер, этап, ревизия расчёта (`provisional` этого этапа), кто решил, причина (обязательна), время;
- `calculation_closure_revocation`: решение, кто отозвал, причина, время; не больше одного отзыва на решение.

Правила:
- решает и отзывает участник тендера с ролью руководителя (новое право `calculation.close`); модель и инженер — нет;
- на одну ревизию не больше одного действующего решения; сериализация — advisory-блокировка этапа (у `kontur_app` нет UPDATE — без `FOR UPDATE` на неизменяемых);
- решение относится только к своей ревизии: новая выгрузка — новая ревизия, не закрыта;
- кандидат закрепляет решение во входе (`candidate_input` вида `calculation_closure`) и в отпечатке входа; отзыв после закрепления делает вход устаревшим;
- `CALCULATION_PROVISIONAL` не ставится, если у ревизии кандидата есть действующее решение, закреплённое во входе; проверка — в ядре (`gate.ts`), на сервере (`releaseViews.ts`) и в БД (`candidate_gate_problem`, новая версия в 0044) — одним предикатом;
- отзыв до выпуска блокирует согласование и выпуск (проверка под блокировкой); выпущенное не меняется, история показывает отзыв;
- журнал аудита: `calculation.close`, `calculation.close_revoke`.

Интерфейс: на странице расчёта этапа — руководителю кнопка «Зафиксировать как закрытый расчёт» с причиной и «Отозвать»; всем участникам — отметка «Закрыт решением руководителя (дата, кто)» или «Решение отозвано».
