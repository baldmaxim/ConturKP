# Контур КП — состояния, переходы и границы транзакций

Этап 01. Имена таблиц и состояний — из `docs/architecture/data-model.md`.

## 1. Общие правила команд

- **Одна команда — одна транзакция PostgreSQL.** Порядок: блокировки в порядке §1.2 → проверка `row_version` из `If-Match` → проверка прав (ADR-006) → проверка охранных условий → запись → `audit_event` → постановка заданий в `job` → commit. При отказе — откат и `audit_event` с `outcome = denied` в отдельной короткой транзакции.
- **Уровень изоляции** — `READ COMMITTED` с явными блокировками строк и уникальными ограничениями. Там, где гонку ловит уникальный индекс (выпуск, активное согласование, идемпотентность), нарушение превращается в ответ «уже выполнено» или конфликт, а не в дубль. Появление новых строк, которое блокировка существующих строк не ловит, сериализуется барьером актуальности этапа (§1.1).
- **Внешние вызовы** (TenderHub, MailHub, LocalAI, RDWeb, Яндекс Диск, SMB, модель) никогда не выполняются внутри транзакции БД. Их делает `job`, результаты записываются короткими транзакциями под действующей арендой (§2).
- **Идемпотентность команд API** — заголовок `Idempotency-Key` и `idempotency_record` (ADR-005). **Идемпотентность заданий** — `job.dedupe_key` и естественные уникальные ключи результата.
- **Роли в таблицах:** `engineer` — назначенный на тендер инженер; `manager` — руководитель тендера; `admin` — технический администратор; `model` — сервисная учётная запись модели или MCP-токен; `integration` — обработчик интеграции; `system` — внутренние задания.

### 1.1. Барьер актуальности этапа

Барьер закрывает окно между поступлением значимого изменения и фоновой инвалидацией (R01-03). Он синхронный и не зависит от того, обработано ли задание инвалидации.

**Значимые изменения** и затронутые этапы:

| Изменение | `event_type` | Затронутые этапы |
|---|---|---|
| принята загрузка файлов или архива через API (до разбора) | `import_accepted` | этап из запроса; если не указан — все активные этапы тендера |
| зарегистрирована редакция документа (загрузка, наблюдаемая папка, вложение) | `document_revision_registered` | все активные этапы тендера |
| завершён прогон распознавания | `recognition_run_completed` | все активные этапы тендера, где редакция входит в набор источников или ещё не отнесена |
| подтверждена связь письма с тендером | `communication_linked` | этап из связи; если не указан — все активные этапы тендера |
| добавлена редакция транскрипции или форма Q&A | `transcript_revision_added`, `qa_form_added` | все активные этапы тендера |
| добавлена ревизия расчёта | `calculation_revision_added` | этап расчёта |
| записано решение | `decision_recorded` | этап решения |
| изменено поле приложения | `draft_field_changed` | этап заполнения |
| изменён набор источников | `source_set_changed` | этап набора |

Неизвестная применимость источника к этапу означает «затрагивает»: событие создаётся для всех активных этапов тендера.

**В той же транзакции, что и изменение:**
1. блокируются строки затронутых `tender_stage` (`FOR UPDATE`, по возрастанию `id`);
2. `input_version = input_version + 1` для каждого этапа;
3. вставляется `stage_input_event` с `seq = input_version`;
4. если у этапа есть активный кандидат (`assembling`, `ready_for_approval`, `approved` или `released` без зарегистрированной отправки), создаётся `readiness_hold(status=open)` на пару (кандидат, событие);
5. ставится задание инвалидации (§12) — тяжёлая работа остаётся фоновой.

**Что не порождает событий барьера (R01-07).** Решения по удержаниям (`decision_type = input_event_disposition`) и по элементам импорта (`decision_type = import_item_disposition`), переходы самих удержаний, согласование, отзыв и возврат, выпуск, регистрация отправки и нарушений, создание снимка области, проверочный запуск и его результаты, фоновая инвалидация (перевод в `stale` и `expired`), записи аудита. Эти действия меняют состояние вокруг барьера, а не входы этапа. Поэтому решение «не влияет» не создаёт нового события и нового удержания, и цепочки блокировок не возникает.

**Покрытие события кандидатом (R01-03).** Актуальность подтверждают обработанные входы кандидата, а не момент нажатия кнопки сборки и не номер версии снимка. Событие e этапа **покрыто** кандидатом C по правилу своего класса:

| Класс | События | Покрыто, если |
|---|---|---|
| `source` | `import_accepted` | партия завершена и **каждый** её элемент имеет проверяемый исход (§3.1): `registered` — редакция покрыта по правилу `document_revision_registered`; `duplicate` — связанная существующая редакция покрыта по тому же правилу; `rejected` или `skipped_partial` — элемент разрешён повторным импортом, чей элемент покрыт, либо отдельным решением руководителя о неприменимости. Статус `completed_with_errors` сам по себе покрытия не даёт; партия, в которой не зарегистрировано ни одного элемента, без таких решений не покрыта; незавершённая партия не покрыта никогда (R01-09) |
| `source` | `document_revision_registered` | редакция есть в ревизии набора источников снимка кандидата — включена или явно исключена с причиной |
| `source` | `recognition_run_completed` | снимок кандидата ссылается на этот прогон или более поздний прогон той же редакции, либо редакция в наборе исключена |
| `source` | `communication_linked` | письмо входит в снимок кандидата |
| `source` | `transcript_revision_added` | снимок содержит эту редакцию транскрипции или более позднюю той же сессии |
| `source` | `qa_form_added` | редакция документа формы покрыта по правилу `document_revision_registered` |
| `source` | `source_set_changed` | изменена ревизия набора, на которой основан снимок кандидата, или более ранняя |
| `calculation` | `calculation_revision_added` | событие относится к закреплённой ревизии расчёта кандидата или к более ранней (`seq` не больше `calculation_baseline_version`) |
| `content` | `decision_recorded`, `draft_field_changed` | `seq` не больше `content_baseline_version` — версии этапа в транзакции создания кандидата, в которой решения и значения полей копируются в его входы |

Правило для источников смотрит на состав, поэтому дедупликация снимка (`evidence_scope` с тем же хэшем и прежним `input_version`) на покрытие не влияет: номер версии снимка актуальность не подтверждает. Новый кандидат на старой проверке не поглощает поступления после её снимка: они остаются непокрытыми, пока не войдут в новый снимок с новой проверкой или не получат решение «не влияет». Незавершённый импорт при остановленном worker не покрыт ни одним кандидатом.

**Единая граница фиксации.** Обе числовые базы (`calculation_baseline_version`, `content_baseline_version`) и входы кандидата фиксируются в одной транзакции создания кандидата под блокировкой этапа. Заморозка содержимого (`ready_for_approval`) базы не меняет. События, пришедшие во время сборки, не покрыты и создают удержания: кандидат в `assembling` считается активным.

**Предикат актуальности кандидата C:** для каждого события этапа, не покрытого C, есть `readiness_hold` (C, e) в статусе `resolved_not_applicable`. Предикат проверяется под блокировкой строки этапа в командах согласования, выпуска и регистрации отправки. Нарушение — блокер `INPUTS_CHANGED` (§11.1). Предикат опирается на события и правила покрытия, а не на наличие строк удержаний, поэтому пропущенное или ещё не созданное удержание не открывает дорогу выпуску.

**Граница «источник поступил»:**
- загрузка через API — в момент принятия `import_batch` (событие `import_accepted`), до разбора файлов;
- наблюдаемая папка и синхронизация почты — в момент регистрации сканом worker; то, что лежит в папке и ещё не просканировано, системе неизвестно. Поэтому согласование, выпуск и отправка требуют свежих каналов: у каждого активного `intake_channel` тендера `last_successful_scan_at >= now() - freshness_window`, иначе блокер `INTAKE_NOT_CURRENT`;
- ручной импорт письма, транскрипции, формы Q&A — в момент принятия команды.

**Два порядка исполнения:**

| Порядок | Что происходит |
|---|---|
| Импорт фиксируется раньше выпуска | выпуск ждёт блокировку этапа, затем видит непокрытое событие без решения → `INPUTS_CHANGED`, выпуск отклонён |
| Выпуск фиксируется раньше импорта | импорт ждёт блокировку этапа; выпуск законен на момент фиксации. Событие импорта создаёт удержание для выпущенного, но не отправленного кандидата; регистрация отправки блокируется до решения |

### 1.2. Порядок блокировок

1. `tender_stage` (по возрастанию `id`);
2. `release_candidate`;
3. `approval`, `release`;
4. `delivery`;
5. прочие строки.

Обработчики заданий, регистрирующие источники, соблюдают тот же порядок. Блокировка `job` (§2) берётся отдельно и не вкладывается в доменные блокировки чужих этапов.

## 2. Задание (`job`) и аренда

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `queued` | постановка | любая команда или задание | в той же транзакции, что и доменное изменение; при активном задании с тем же `dedupe_key` новое не создаётся |
| `queued` | `running` | захват | worker | `FOR UPDATE SKIP LOCKED`, `run_after <= now()`, свободен ресурс класса; новый `lease_token`, `locked_by`, `locked_until = now() + lease`, `attempts + 1` |
| `running` | `running` | heartbeat | worker | условное обновление `WHERE id AND lease_token AND status = 'running'`; 0 строк — аренда потеряна |
| `running` | `succeeded` | успех | worker | в одной транзакции: блокировка задания с проверкой `lease_token` и `status`, запись доменного результата, перевод статуса |
| `running` | `queued` | повторяемая ошибка | worker | условно по `lease_token`; `attempts < max_attempts`; `run_after` с экспоненциальной задержкой |
| `running` | `failed` | неповторяемая ошибка или исчерпаны попытки | worker | условно по `lease_token` |
| `running` | `queued` | истёк `locked_until` | recovery-проход worker | `lease_token = null`; следующий захват выдаёт новый токен (A15) |
| `queued` | `cancelled` | отмена | engineer / manager / admin | сразу |
| `running` | `cancelled` | отмена | engineer / manager / admin → worker | команда ставит `cancel_requested = true`; действующий обработчик видит флаг при heartbeat и подтверждает отмену условной записью; новый владелец после перехвата видит флаг при захвате и завершает `cancelled` |

**Протокол аренды (R01-06):**
1. Любая запись обработчика — heartbeat, успех, ошибка, подтверждение отмены, доменный результат — условна по текущему `lease_token`. Обработчик, у которого условная запись вернула 0 строк, прекращает работу и больше ничего не пишет.
2. Доменный результат пишется только в транзакции, которая сначала проверяет `lease_token` под блокировкой задания. Проверка «результата ещё нет» до внешнего действия не заменяет этого условия.
3. Токен аренды не отменяет уже начатый внешний запрос. Поэтому каждое внешнее действие имеет собственный ключ идемпотентности или естественную уникальность (путь и хэш файла, `requestId`), а новая попытка после перехвата сначала сверяет внешнее состояние (исход `outcome_unknown`, §16).
4. **GPU.** Задание класса `gpu` захватывает слот `resource_slot('gpu')` (таблица `resource_slot`) тем же `lease_token`. Обработчик, потерявший аренду, прерывает вызов модели и освобождает локальный исполнитель. Новый захват слота возможен только после `locked_until + gpu_takeover_grace`: защитный интервал больше максимального шага GPU-задания, чтобы приостановленный процесс не работал параллельно с новым.

## 3. Импорт источников (`import_batch`, `import_item`, `document_revision`)

| Шаг | Состояние | Правило |
|---|---|---|
| Принятие загрузки | `import_batch.running` | команда API; в той же транзакции — событие `import_accepted` (§1.1) |
| Обнаружение | `import_item.pending` | файл из загрузки, наблюдаемой папки или архива |
| Проверка стабильности | `skipped_partial` | размер и время изменения не менялись заданный интервал, файл открывается на чтение без блокировки; иначе повтор позже (A15) |
| Проверка безопасности | `rejected` | выход за корень, `..`, абсолютные пути, ссылки, лимиты распаковки и размера, запрещённый тип (A38) |
| Копирование | — | во временный файл хранилища → SHA-256 → атомарное переименование в `blob` (ADR-003); существующий хэш — дедупликация |
| Регистрация | `registered` / `duplicate` | транзакция по §1.1: блокировки этапов, `document_revision` по (`document_id`, `blob_sha256`) или связь с существующей, `document_occurrence`, событие `document_revision_registered`, удержания (A13, A14) |
| Завершение партии | `import_batch.completed` / `completed_with_errors` | `import_batch` замораживается; наблюдаемая папка обновляет `intake_channel.last_successful_scan_at` только после полного прохода; ошибки элементов остаются видимыми до разрешения (§3.1) |

**Реализация этапа 03.** Скан наблюдаемой папки, нашедший новые или изменённые стабильные файлы, создаёт партию и в той же транзакции событие `import_accepted` для всех активных этапов тендера — так неразобранные элементы папки блокируют кандидата тем же правилом покрытия партии, что и загрузка через API (строже, чем граница «поступил» для папки в §1.1). Файл стабилен, если размер и время изменения не менялись `INTAKE_STABILITY_SECONDS` и не изменились за время копирования; занятый или исчезнувший при чтении файл остаётся «ожидающим», скан с такими файлами не считается успешным. ZIP из наблюдаемой папки не распаковывается (отказ `type_not_allowed` с исходом); архивы загружаются через портал.

### 3.1. Исход элементов партии (R01-09)

Технический отказ импорта (`corrupt`, `size_limit`, `type_not_allowed`, `unstable_file`, `path_traversal`) не означает, что документ неприменим. Поэтому у каждого элемента должен быть проверяемый исход:

| Статус элемента | Исход, достаточный для покрытия |
|---|---|
| `registered` | редакция включена в набор источников снимка или явно исключена с причиной |
| `duplicate` | элемент связан с существующей редакцией (`document_revision_id`), и она покрыта так же; ложной неполноты дубликаты не создают |
| `rejected`, `skipped_partial` | `resolution = reimported`: инженер связал элемент с элементом повторного импорта (`resolved_by_item_id`), и тот покрыт; или `resolution = not_applicable`: руководитель принял решение `import_item_disposition` с причиной |

- Разрешение элемента — команда `POST /import-items/{id}/resolve` под блокировкой этапа; решение по элементу событий барьера не порождает.
- Пока хотя бы один элемент без исхода, событие `import_accepted` не покрыто: кандидат получает удержание, а согласование, выпуск и отправка блокируются `INPUTS_CHANGED`. Решение руководителя «не влияет» по самому событию партии тоже допустимо, но только с перечнем неразобранных элементов в причине; пробелы остаются видимыми в карточке кандидата.
- Проверочный запуск видит неразобранные элементы партий тендера в момент фиксации снимка: они попадают в `coverage` и дают `completed_with_gaps` (§8), так что `REVIEW_INCOMPLETE` тоже срабатывает.

Ключи: `job.dedupe_key = import:<batch_id>:<member_path>`; результат — уникальность (`document_id`, `blob_sha256`) и `import_item` (`batch_id`, `member_path`). Удаление файла из наблюдаемой папки не удаляет `blob` и редакцию (I15).

## 4. Распознавание (`recognition_run`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `queued` | загрузка экспорта RDWeb или запрос распознавания | engineer / system | `dedupe_key = recognition:<document_revision_id>:<source_artifact_sha256>` |
| `queued` | `running` | захват задания | worker | — |
| `running` | `complete` | все страницы разобраны | worker | SHA-256 PDF из экспорта совпадает с `document_revision.blob_sha256`; `pages_total` равно фактическому числу страниц оригинала, и распознаны все они; страницы и фрагменты вставлены; событие `recognition_run_completed` (§1.1) |
| `running` | `partial` | разобраны не все страницы | worker | `pages_recognized < pages_total`, отсутствующие страницы `missing` (A16); событие `recognition_run_completed` |
| `running` | `failed` | схема не распознана, файл повреждён, PDF другого документа, оригинал не читается | worker | чужой или старый результат не принимается (этап 04) |
| `queued` / `running` | `cancelled` | отмена задания | engineer / manager / admin → API или worker | доменная отмена фиксируется вместе с переводом задания: `queued` — одной транзакцией команды `POST /jobs/{id}/cancel`, `running` — обработчиком под действующей арендой (`onCancel`). `failure_code` пуст: отмена не ошибка. Повторная загрузка того же архива после отмены создаёт новый прогон (R04-02) |

Новая версия распознавания того же PDF — новый `recognition_run` с `supersedes_run_id`. Прежние фрагменты и ссылки на них остаются (A10). Снимки области, созданные раньше, продолжают указывать на прежний прогон (§5.1).

**История версий линейна (R04-12).** У редакции одновременно не более одного незавершённого прогона: приём второго архива до окончания первого отклоняется `409 STATE_CONFLICT`. Новый прогон встаёт за хвостом цепочки; второй корень и второй потомок у одного предшественника запрещены второй линией — охранником вставки и частичными уникальными индексами (миграция 0008). Отказавшая и отменённая попытка места потомка не занимает: повтор после сбоя возможен.

**Реализация (этап 04).** Задание `recognition.import`, класс ресурса `default`: распознавание выполнил RDWeb, портал только принимает результат, поэтому единственный слот `resource_slot('gpu')` этим заданием не занимается. Страницы, фрагменты, происхождение `rdweb_export`, терминальный статус и событие барьера пишутся **одной** транзакцией `ctx.complete` под действующей арендой; порядок блокировок — этапы тендера, затем строка прогона (§1.2). Терминальный отказ разбора переводит прогон в `failed` в той же транзакции, что и задание (`onTerminalFailure`): расхождения «задание failed, прогон running» не возникает.

**Полнота (после ревью 04-1).** `pages_total` — фактическое число страниц зарегистрированного оригинала: его считает worker по локальному PDF (`apps/worker/src/pdfPages.ts`, pdfjs-dist) до разбора экспорта и передаёт в адаптер параметром. Экспорт, не перечисливший страницу, теперь даёт неполноту, а не тихий `complete` (R04-03, D-012). Оригинал, который не открывается, полноты не подтверждает: прогон получает `failed` с кодом `pdf_unreadable`.

Страница считается `recognized` только по содержательному признаку: получен хотя бы один фрагмент с непустым текстом либо у блока страницы явно указан `status`/`export_status` = `recognized`. Одного заголовка `## Page N` в `_results.md` недостаточно, а отсутствие статуса у блока больше не трактуется как «распознано» (R04-03). Строка `recognition_page` заводится на каждую страницу оригинала, а не только на перечисленные в экспорте; расхождение состава называется предупреждениями `blocks_page_count_mismatch`, `page_index_out_of_range`, `page_output_empty`.

Вторая линия — БД (миграция 0006, R04-04): страницы и фрагменты принимает только выполняющийся прогон (строка прогона блокируется, поэтому вставка сериализуется с финальной транзакцией worker), а переход в `complete`/`partial` сверяет `pages_total` и `pages_recognized` с фактическими строками `recognition_page`.

## 5. Ревизия набора источников (`source_set_revision`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `draft` | создание | engineer | копия состава базовой ревизии; `base_revision_id` |
| `draft` | `draft` | изменение состава | engineer | `If-Match`; каждое исключение — с причиной; событие `source_set_changed` |
| `draft` | `frozen` | заморозка | engineer | у всех включённых редакций есть завершённое или явно неполное распознавание; вычислен `content_hash`; после этого состав неизменен |

Новый документ после заморозки не меняет замороженную ревизию: он попадает в новую `draft`-ревизию и проходит через барьер §1.1.

### 5.1. Снимок области доказательств (`evidence_scope`)

Снимок фиксирует полный состав входов до начала проверки (R01-01).

| Шаг | Правило |
|---|---|
| Создание | команда «зафиксировать область» или автоматически при запуске проверки; транзакция под блокировкой этапа; основа — `frozen`-ревизия набора источников |
| Редакции документов | для каждой включённой редакции явно записывается выбранный `recognition_run_id` (по умолчанию последний `complete` или `partial` на момент создания) или явное `null` — «только оригинал» |
| Письма | все письма с подтверждённой связью с этапом или тендером на момент создания |
| Транскрипции | для каждой сессии переговоров тендера — последняя редакция транскрипции на момент создания |
| Хэш | `content_hash` по §5 модели данных; одинаковый состав — та же строка |
| Неизменность | после создания снимок не меняется; новый прогон R2, новое письмо или новая редакция транскрипции дают новый снимок только при следующей фиксации |

Использование снимка:
- `review_run` ссылается на снимок; проверка читает только его единицы;
- кандидат выпуска принимает `evidence_scope_id` общий для всех включённых проверок; проверки на разных снимках в один кандидат не собираются (блокер `REVIEW_SCOPE_MISMATCH`);
- манифест кандидата содержит ID и хэш снимка; исторический поиск и MCP по выпуску строят область из этого снимка (ADR-008);
- права пользователя применяются поверх снимка при каждом чтении: письма из недоступных ящиков исключаются из результата до ранжирования; снимок не даёт вечного разрешения.

## 6. Расчёт (`calculation_capture`, `calculation_content`, `calculation_revision`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `capturing` | запрос выгрузки или наступление `submission_deadline` | engineer / system | `dedupe_key = capture:<stage_id>:<external_tender_id>:<window>`; только чтение TenderHub |
| `capturing` | `complete` | выгрузка согласована | worker | до и после чтения совпадают `updated_at`, итог и счётчики позиций и строк; сырые ответы в `blob`; далее — правила идентичности ниже |
| `capturing` | `inconsistent` | данные менялись во время чтения | worker | повтор ограниченное число раз; затем видимая ошибка |
| `capturing` | `failed` | 401/403/429/сеть/несовпадение контракта | worker | статус интеграции и код ошибки видны пользователю (A39) |

**Правила идентичности (R01-04):**
1. Нормализованная выгрузка превращается в канонический JSON: позиции, строки, итог КП с валютой и семантикой, составляющие итога, курсы с датами, `normalization_version`. Его хэш — `calculation_content.content_hash`; одинаковое содержимое хранится один раз.
2. `calculation_revision` — наблюдение источника, отдельное от содержимого:
   - `provisional`: под блокировкой строки этапа читается последняя ревизия для (`stage_id`, `external_tender_id`). Если содержимое выгрузки совпадает с содержимым **последней** ревизии, выгрузка связывается с ней (повтор идемпотентен). Иначе создаётся новая ревизия `seq + 1` с `supersedes_revision_id` = последняя — даже если такое содержимое встречалось раньше: возврат A → B → A фиксируется третьей ревизией со ссылкой на то же `calculation_content` A (R01-08);
   - `verified` (после X-01): уникальна по (`stage_id`, `external_revision_ref`); повтор получения той же ревизии идемпотентен; совпадение содержимого с `provisional` не мешает создать `verified`-ревизию — она ссылается на тот же `calculation_content`, прежняя запись не меняется.
3. Разные курсы, итог КП или его составляющие при одинаковых строках дают разное содержимое и новую ревизию.
4. Факт закрытия, повторного открытия или замены у источника — событие `calculation_revision_status_event`; прежние записи не меняются.
5. Каждая новая ревизия проходит барьер §1.1 (`calculation_revision_added`).

`calculation_revision` неизменна. Изменение в TenderHub после закрытия — новая ревизия; прежняя и всё, что на неё ссылается, сохраняются (A07).

**`requirement`**

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `candidate` | извлечение правилом, моделью или вручную | system / engineer | первая `requirement_revision` с цитатами; от модели — через `model_suggestion` |
| `candidate` | `confirmed` | подтверждение | engineer | цитаты существуют и входят в область этапа |

| `confirmed` | `confirmed` | правка формулировки | engineer | новая `requirement_revision`; прежняя и цитаты остаются |

## 10. Замечание (`finding`) и разногласие (`discrepancy`)

**`finding`**

| Из | В | Событие | Кто | Охранные условия |
|---|---|---|---|---|
| — | `open` | создание | rule / engineer / принятие гипотезы | основания с обеих сторон, если это конфликт |
| `open` | `in_progress` | взять в работу | engineer | ответственный назначен |
| `open`, `in_progress` | `resolved` | решено | engineer | есть `decision` или изменение, на которое ссылается решение |
| `open`, `in_progress` | `accepted_risk` | принять риск | manager | `risk_acceptance` с причиной; только для бизнес-блокеров (§11.1) |
| `open`, `in_progress` | `rejected` | не является проблемой | engineer | причина обязательна |

Каждый переход пишет `finding_event`. Критичность и уверенность меняются отдельными командами. Запись `decision` проходит барьер §1.1 (`decision_recorded`).

**`discrepancy`**: оси `customer_position`, `calculation`, `proposal`, `documents` меняются независимо событиями `discrepancy_status_event` с основаниями (I09). Поздняя дата письма сама не меняет ось и не закрывает конфликт (A04). Реплика из переговоров даёт не больше `discussed_orally` (I08, A03).

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `assembling` | сформировать кандидата | engineer | задаётся `mode` (`production`/`test`), дальше неизменен; под блокировкой этапа закрепляются входы (ревизия расчёта, проверки на одном `evidence_scope` и той же ревизии расчёта, решения и значения полей, версии шаблонов) и числовые базы актуальности (§1.1); для всех уже существующих событий этапа, не покрытых кандидатом, сразу создаются удержания; `seq + 1`; задание генерации файлов |
| `assembling` | `ready_for_approval` | файлы сформированы | worker | условно по аренде; файлы в `blob`; проверки плейсхолдеров и заполненности выполнены; манифест (включая `mode`, базы актуальности `calculation_baseline_version` и `content_baseline_version`, `evidence_scope`) и `content_hash` записаны; дальше содержимое неизменно |

| `ready_for_approval` | `returned` | вернуть на доработку | manager | причина обязательна |
| `approved` | `ready_for_approval` | отзыв согласования до выпуска | manager | `approval` → `revoked` в той же транзакции (§14); выпуска нет |
| `approved` | `released` | выпустить | engineer (human, назначен на тендер) | блокировки §1.2; матрица §11.1; `approval.status = active`; хэш манифеста равен `approval.candidate_content_hash`; вставка `release` (уникальность `candidate_id`) с `mode` кандидата; в той же транзакции — доставки на активные назначения той же среды (§16) |
| `ready_for_approval`, `approved`, `returned` | `superseded` | новый кандидат этапа | system | согласование старого остаётся в истории и к новому не применяется (A09) |

Ручная правка приложения, новое решение или новая ревизия расчёта не меняют существующего кандидата: они проходят барьер §1.1 и требуют нового кандидата либо решения «не влияет» (I03).

### 11.1. Матрица блокеров

Проверяется сервером под блокировкой этапа при согласовании, при выпуске и при регистрации отправки.

| Код | Условие | Класс | Снимается принятием риска |
|---|---|---|---|
| `CANDIDATE_CONTENT_MISMATCH` | хэш файла или манифеста не совпадает с записанным | технический | нет |
| `APPROVAL_NOT_ACTIVE` | согласование отозвано, заменено или относится к другому содержимому | полномочия | нет |
| `ACTOR_NOT_AUTHORIZED` | не human, нет роли или назначения на тендер | полномочия | нет |
| `INPUTS_CHANGED` | нарушен предикат актуальности §1.1 | целостность (I04) | нет; только решение руководителя по каждому событию |
| `INTAKE_NOT_CURRENT` | канал поступления тендера не сканировался дольше `freshness_window` | целостность | нет; восстановить сканирование или отключить канал с причиной |
| `REVIEW_SCOPE_MISMATCH` | проверки кандидата построены на разных снимках области или на другой ревизии расчёта, чем закреплена в кандидате | технический | нет |
| `CALCULATION_PROVISIONAL` | ревизия расчёта `provisional` при `mode = production` | целостность (этап 06) | нет; меняется только решением владельца в журнале решений (Q-01) |
| `TEMPLATE_DEMO` | демо-шаблон при `mode = production` | целостность (этап 11) | нет |
| `REVIEW_INCOMPLETE` | последний запуск `completed_with_gaps` или устарел | бизнес | да, с причиной; пробелы остаются видимыми |
| `CRITICAL_FINDINGS_OPEN` | открытые `critical`-замечания | бизнес | да, по каждому замечанию (A45) |
| `QUESTIONS_UNANSWERED` | неотвеченные обязательные вопросы | бизнес | да |
| `FIELDS_INCOMPLETE_OR_STALE` | обязательные поля пусты или `stale` | бизнес | да, кроме полей, помеченных шаблоном как обязательные для заказчика |

Блокеры боевого режима проверяются по `mode` кандидата, а не по списку назначений доставки (R01-05). Окончательная матрица согласуется владельцем (Q-09); структура и классы — часть ядра и от ответа не зависят.

**Тестовый режим (`mode = test`).** Допускает `provisional`-расчёт и демо-шаблон. Файлы кандидата получают видимую отметку «ТЕСТОВЫЙ ВЫПУСК» (реализация — этап 12). Тестовый выпуск доставляется только в назначения с `environment = test` и не может получить `send_event`.

## 12. Инвалидация по зависимостям (`evidence_dependency`)

Каждое событие §1.1 ставит задание `invalidate:<event_id>`. Оно переводит зависимые объекты в `stale` (`coverage_link`, `finding`, `draft_field_value`, `model_suggestion` → `expired`) и записывает причину. Прежние отчёты и решения не удаляются. Если область влияния нельзя определить надёжно, помечаются все объекты этапа того же типа. Задание может запаздывать или стоять — барьер §1.1 от него не зависит.

## 13. Удержание готовности (`readiness_hold`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `open` | событие §1.1 при активном кандидате; при создании кандидата — каждое уже существующее непокрытое событие | system, в транзакции события или создания кандидата | блокирует согласование, выпуск и регистрацию отправки через предикат актуальности; согласование не удаляется |
| `open` | `resolved_not_applicable` | «не влияет» с причиной | manager | создаётся `decision` с `decision_type = input_event_disposition`; событие барьера не создаётся (R01-07); событие перестаёт блокировать этого кандидата |
| `open` | `resolved_requires_new_candidate` | «влияет» | manager | создаётся `decision`; невыпущенный кандидат → `superseded`. Для выпущенного кандидата выпуск навсегда исключён из обычной отправки (§17): событие остаётся без решения «не влияет», предикат для этого кандидата ложен |

Если событие пришло, когда активного кандидата не было, удержание сразу не создаётся. Будущий кандидат его не пропустит: если событие не покрыто его базами, удержание создаётся при создании кандидата.

## 14. Согласование (`approval`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `active` | согласование кандидата | manager (human) | один `active` на кандидата (уникальный индекс); `input_version` этапа в момент согласования записывается для аудита; повтор с тем же ключом идемпотентности — тот же ответ |

## 15. Выпуск (`release`)

Выпуск только создаётся (§11) и никогда не меняется; `mode` копируется из кандидата, `input_version` этапа в момент выпуска записывается для аудита. Актуальность выпуска для отправки проверяется по базам его кандидата. Производные статусы «размещено N из M» и «отправка зарегистрирована» вычисляются из `delivery` и `send_event` и хранятся отдельно (I01).

## 16. Размещение (`delivery`, `delivery_file_state`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `pending` | создание при выпуске | system | по одной на активное назначение; закрепляется текущая `delivery_destination_version`; `environment` назначения равна `release.mode`, иначе доставка не создаётся |
| `pending` | `staging` | начало попытки | worker | условно по аренде; `delivery_attempt`; корень берётся только из закреплённой версии; байты — точные файлы из `blob` (I02) |
| `staging` | `committing` | все файлы загружены | worker | размер и хэш (или доступный отпечаток) каждого файла сверены |
| `committing` | `verifying` | перенос в целевую папку и маркер завершённости | worker | файл с тем же именем и другим хэшем — `conflict`, перезаписи нет (A30) |
| `verifying` | `delivered` | удалённое состояние совпало с манифестом | worker | все `delivery_file_state.verified` |
| любое рабочее | `failed` | ошибка сети, прав, места | worker | повтор только этого назначения (A28); другое назначение не откатывается (I14) |
| любое рабочее | `outcome_unknown` | таймаут после отправки данных | worker | следующий шаг — только сверка удалённого состояния, без слепой повторной загрузки (A29) |
| `outcome_unknown` | `verifying` | сверка | worker | — |
| `conflict` | `pending` | решение человека (подтвердить совпадение или перенаправить) | engineer | решение в аудите |
| `failed` | `pending` | повтор | engineer / system | `Idempotency-Key`; `dedupe_key = delivery:<delivery_id>`; используется та же закреплённая версия назначения |
| `failed`, `conflict` | `superseded` | перенаправить на новую версию назначения | engineer | создаётся новая `delivery` с новой версией той же среды; старая запись и её попытки сохраняются |

Изменение корня или политики назначения создаёт новую версию и не влияет на существующие доставки. Среда назначения не меняется, поэтому повтор не может превратить тестовую доставку в боевую (R01-05). Частично загруженный набор не показывается как размещённый.

## 17. Отправка (`send_event`) и нарушения (`compliance_incident`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `registered` | регистрация отправки | engineer (human) | под блокировкой этапа: `release.mode = production`; предикат актуальности §1.1 для кандидата выпуска истинен (в том числе нет решения `resolved_requires_new_candidate`); нет `INTAKE_NOT_CURRENT`; канал, дата, адресаты, основание; (`registered_by`, `idempotency_key`) уникальны |
| `registered` | `verified` | состав вложений совпал с манифестом выпуска | engineer / system | сверка хэшей вложений из основания |
| `registered` | `disputed` | состав не совпал | system / engineer | несовпадение не считается отправкой согласованного комплекта (A32) |

- Тестовый выпуск нельзя зарегистрировать как отправку. Если тестовый комплект или комплект с неснятым блокером фактически ушёл заказчику вне системы, регистрируется `compliance_incident` с основанием. Это отдельная запись о нарушении, она не создаёт `send_event` и не подтверждает выпуск.
- Черновик письма и размещение — не отправка (A31). Письмо не доказывает получение или согласие заказчика (A46). Найденное в MailHub отправленное письмо создаёт только кандидат в основание, который инженер подтверждает.

## 18. Сравнение (`comparison`, `change_explanation`)

`comparison`: `computing` → `ready` / `failed`. `change_explanation.reason_status`: `hypothesis` (модель или правило) → `confirmed` (human с основанием) или `unknown`. Строка `unexplained_remainder` существует всегда; сумма вкладов равна итоговой разнице по зафиксированному методу разложения (I11, A20).

## 19. Статус интеграции (`integration_status`)

| Статус | Когда ставится | Кем |
|---|---|---|
| `NOT_IMPLEMENTED` | адаптера нет | по умолчанию |
| `VERIFIED_FIXTURE` | пройдены contract-тесты на фикстурах | скрипт проверки этапа |
| `VERIFIED_LIVE` | пройден разрешённый live-smoke; есть ссылка на артефакт | администратор после live-smoke |
| `BLOCKED_EXTERNAL` | нужен внешний доступ или доработка | администратор / скрипт проверки |

Переход в `VERIFIED_LIVE` из фикстурного теста невозможен: требуется `evidence_ref` на отчёт live-smoke.
