# Контур КП — состояния, переходы и границы транзакций

Этап 01. Имена таблиц и состояний — из `docs/architecture/data-model.md`.

## 1. Общие правила команд

- **Одна команда — одна транзакция PostgreSQL.** Порядок: блокировка корня агрегата `SELECT … FOR UPDATE` → проверка `row_version` из `If-Match` → проверка прав (ADR-006) → проверка охранных условий → запись → `audit_event` → постановка заданий в `job` → commit. При отказе — откат и `audit_event` с `outcome = denied` в отдельной короткой транзакции.
- **Уровень изоляции** — `READ COMMITTED` с явными блокировками строк и уникальными ограничениями. Там, где гонку ловит уникальный индекс (выпуск, активное согласование, идемпотентность), нарушение превращается в ответ «уже выполнено» или конфликт, а не в дубль.
- **Внешние вызовы** (TenderHub, MailHub, LocalAI, RDWeb, Яндекс Диск, SMB, модель) никогда не выполняются внутри транзакции БД. Их делает `job`, результаты записываются короткими транзакциями.
- **Идемпотентность команд API** — заголовок `Idempotency-Key` и `idempotency_record` (ADR-005). **Идемпотентность заданий** — `job.dedupe_key` и естественные уникальные ключи результата.
- **Роли в таблицах:** `engineer` — назначенный на тендер инженер; `manager` — руководитель тендера; `admin` — технический администратор; `model` — сервисная учётная запись модели или MCP-токен; `integration` — обработчик интеграции; `system` — внутренние задания.

## 2. Задание (`job`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `queued` | постановка | любая команда или задание | в той же транзакции, что и доменное изменение; при активном задании с тем же `dedupe_key` новое не создаётся |
| `queued` | `running` | захват | worker | `FOR UPDATE SKIP LOCKED`, `run_after <= now()`, лимит `resource_class` (`gpu` ≤ 1); `locked_until = now() + lease`, `attempts + 1` |
| `running` | `running` | heartbeat | worker | продление `locked_until` |
| `running` | `succeeded` | успех | worker | результат и статус в одной транзакции |
| `running` | `queued` | повторяемая ошибка | worker | `attempts < max_attempts`; `run_after` с экспоненциальной задержкой; код ошибки без секретов |
| `running` | `failed` | неповторяемая ошибка или исчерпаны попытки | worker | ошибка видна пользователю через статус объекта |
| `running` | `queued` | истёк `locked_until` | recovery-проход worker | восстановление после падения процесса (A15) |
| `queued` | `cancelled` | отмена | engineer/manager/admin | задание ещё не захвачено |
| `running` | `cancelled` | отмена | engineer/manager/admin | флаг отмены; обработчик завершает шаг и фиксирует отмену |

Обработчик обязан быть идемпотентным: повтор после неизвестного исхода сначала проверяет уже записанный результат (I14).

## 3. Импорт источников (`import_batch`, `import_item`, `document_revision`)

| Шаг | Состояние | Правило |
|---|---|---|
| Обнаружение | `import_item.pending` | файл из загрузки, наблюдаемой папки или архива |
| Проверка стабильности | `skipped_partial` | размер и время изменения не менялись заданный интервал, файл открывается на чтение без блокировки; иначе повтор позже (A15) |
| Проверка безопасности | `rejected` | выход за корень, `..`, абсолютные пути, ссылки, лимиты распаковки и размера, запрещённый тип (A38) |
| Копирование | — | во временный файл хранилища → SHA-256 → атомарное переименование в `blob` (ADR-003); существующий хэш — дедупликация |
| Регистрация | `registered` / `duplicate` | транзакция: `document_revision` по (`document_id`, `blob_sha256`) или связь с существующей; `document_occurrence` всегда добавляется (A13, A14) |
| Завершение партии | `import_batch.completed` / `completed_with_errors` | `import_batch` замораживается |

Ключи: `job.dedupe_key = import:<batch_id>:<member_path>`; результат — уникальность (`document_id`, `blob_sha256`) и `import_item` (`batch_id`, `member_path`). Удаление файла из наблюдаемой папки не удаляет `blob` и редакцию (I15).

Новая редакция после согласования кандидата создаёт `readiness_hold` (§13), если редакция отнесена к этапу. Отнесение неочевидное — удержание создаётся консервативно, с причиной.

## 4. Распознавание (`recognition_run`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `queued` | загрузка экспорта RDWeb или запрос распознавания | engineer / system | `dedupe_key = recognition:<document_revision_id>:<source_artifact_sha256>` |
| `queued` | `running` | захват задания | worker | — |
| `running` | `complete` | все страницы разобраны | worker | SHA-256 PDF из экспорта совпадает с `document_revision.blob_sha256`; число страниц совпадает; страницы и фрагменты вставлены |
| `running` | `partial` | разобраны не все страницы | worker | `pages_recognized < pages_total`, отсутствующие страницы `missing` (A16) |
| `running` | `failed` | схема не распознана, файл повреждён, PDF другого документа | worker | чужой или старый результат не принимается (этап 04) |

Новая версия распознавания того же PDF — новый `recognition_run` с `supersedes_run_id`. Прежние фрагменты и ссылки на них остаются (A10). Фрагменты, на которые опирались решения и требования, помечаются для пересмотра через `evidence_dependency` (§12).

## 5. Ревизия набора источников (`source_set_revision`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `draft` | создание | engineer | копия состава базовой ревизии; `base_revision_id` |
| `draft` | `draft` | изменение состава | engineer | `If-Match`; каждое исключение — с причиной |
| `draft` | `frozen` | заморозка | engineer | у всех включённых редакций есть завершённое или явно неполное распознавание; вычислен `content_hash`; после этого состав неизменен |

Новый документ после заморозки не меняет замороженную ревизию: он попадает в новую `draft`-ревизию, а при наличии согласования создаёт `readiness_hold`.

## 6. Расчёт (`calculation_capture`, `calculation_revision`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `capturing` | запрос выгрузки или наступление `submission_deadline` | engineer / system | `dedupe_key = capture:<stage_id>:<external_tender_id>:<window>`; только чтение TenderHub |
| `capturing` | `complete` | выгрузка согласована | worker | до и после чтения совпадают `updated_at`, итог и счётчики позиций и строк; сырые ответы в `blob`; создана `calculation_revision` вида `provisional` (до X-01) или `verified` (по ID ревизии TenderHub после X-01) |
| `capturing` | `inconsistent` | данные менялись во время чтения | worker | повтор ограниченное число раз; затем видимая ошибка |
| `capturing` | `failed` | 401/403/429/сеть/несовпадение контракта | worker | статус интеграции и код ошибки видны пользователю (A39) |

`calculation_revision` неизменна. Изменение в TenderHub после закрытия — новая выгрузка и новая ревизия с `supersedes_revision_id`; прежняя и всё, что на неё ссылается, сохраняются (A07). Совпадающий `content_hash` новой ревизии не создаёт: выгрузка связывается с существующей.

## 7. Требования и покрытие

**`requirement`**

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `candidate` | извлечение правилом, моделью или вручную | system / engineer | первая `requirement_revision` с цитатами; от модели — через `model_suggestion` |
| `candidate` | `confirmed` | подтверждение | engineer | цитаты существуют и входят в область этапа |
| `candidate` | `rejected` | отклонение с причиной | engineer | — |
| `confirmed` | `confirmed` | правка формулировки | engineer | новая `requirement_revision`; прежняя и цитаты остаются |
| любое | `superseded` | замена новым требованием | engineer | ссылка на заменяющее |

**`coverage_link`**: `proposed` → `confirmed` / `rejected` (engineer); `confirmed` → `stale` при новой ревизии расчёта или изменении основания (system); `stale` → `confirmed` после проверки. Отсутствие отдельной строки не делает покрытие отсутствующим: возможен `kind = complex_rate` (A05).

## 8. Проверочный запуск (`review_run`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `queued` | запуск | engineer / system | входы закреплены: `source_set_revision_id` (frozen), `calculation_revision_id`, `rules_version`, `model_config` |
| `queued` | `running` | захват | worker | — |
| `running` | `completed` | все проверки выполнены при полной обработке | worker | нет `incomplete`/`error`; распознавание всех документов `complete` |
| `running` | `completed_with_gaps` | часть входов неполная или проверка с ошибкой | worker | перечень пробелов в `coverage`; «всё проверено» не показывается (I18, A16, A44) |
| `running` | `failed` | сбой | worker | прежние запуски не меняются |

## 9. Гипотеза модели (`model_suggestion`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `open` | создание | model / system | JSON прошёл схему; все `cited_fragment_ids` существуют и входят в область; иначе гипотеза отклоняется до записи; повтор с тем же `request_id` возвращает ту же запись (A37) |
| `open` | `accepted` | принятие | engineer (human) | создаётся требование, замечание, решение или значение поля с автором-человеком |
| `open` | `rejected` | отклонение | engineer | — |
| `open` | `expired` | изменились входы | system | по `evidence_dependency` |

Модель не может перевести гипотезу в `accepted` и не может менять решения, расчёт и статусы выпуска (I12).

## 10. Замечание (`finding`) и разногласие (`discrepancy`)

**`finding`**

| Из | В | Событие | Кто | Охранные условия |
|---|---|---|---|---|
| — | `open` | создание | rule / engineer / принятие гипотезы | основания с обеих сторон, если это конфликт |
| `open` | `in_progress` | взять в работу | engineer | ответственный назначен |
| `open`, `in_progress` | `resolved` | решено | engineer | есть `decision` или изменение, на которое ссылается решение |
| `open`, `in_progress` | `accepted_risk` | принять риск | manager | `risk_acceptance` с причиной; только для бизнес-блокеров (§11.1) |
| `open`, `in_progress` | `rejected` | не является проблемой | engineer | причина обязательна |
| любое, кроме `stale` | `stale` | изменилось основание | system | через `evidence_dependency`; при неясной области — консервативно |
| `stale` | `open` | пересмотр | engineer | — |

Каждый переход пишет `finding_event`. Критичность и уверенность меняются отдельными командами.

**`discrepancy`**: оси `customer_position`, `calculation`, `proposal`, `documents` меняются независимо событиями `discrepancy_status_event` с основаниями (I09). Поздняя дата письма сама не меняет ось и не закрывает конфликт (A04). Реплика из переговоров даёт не больше `discussed_orally` (I08, A03).

## 11. Кандидат выпуска (`release_candidate`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `assembling` | сформировать кандидата | engineer | `seq + 1`; входы закреплены; задание генерации файлов |
| `assembling` | `ready_for_approval` | файлы сформированы | worker | файлы в `blob`; проверки плейсхолдеров и заполненности выполнены; манифест и `content_hash` записаны; дальше содержимое неизменно |
| `assembling` | `assembly_failed` | ошибка генерации | worker | причина видна |
| `ready_for_approval` | `approved` | согласовать | manager (human) | §11.1; блокировка строки кандидата; `If-Match`; создаётся `approval` с `candidate_content_hash`; открытых `readiness_hold` нет |
| `ready_for_approval` | `returned` | вернуть на доработку | manager | причина обязательна |
| `approved` | `ready_for_approval` | отзыв согласования до выпуска | manager | `approval` → `revoked` в той же транзакции (§14); выпуска нет |
| `approved` | `released` | выпустить | engineer (human, назначен на тендер) | §11.1; `approval.status = active`; хэш манифеста равен `approval.candidate_content_hash`; открытых `readiness_hold` нет; вставка `release` (уникальность `candidate_id`); в той же транзакции задания `delivery` на каждое активное назначение |
| `ready_for_approval`, `approved`, `returned` | `superseded` | новый кандидат этапа | system | при создании следующего кандидата; согласование старого остаётся в истории и к новому не применяется (A09) |

Ручная правка приложения, новое решение или новая ревизия расчёта не меняют существующего кандидата: они требуют нового кандидата (I03).

### 11.1. Матрица блокеров

Проверяется сервером при согласовании и повторно при выпуске.

| Код | Условие | Класс | Снимается принятием риска |
|---|---|---|---|
| `CANDIDATE_CONTENT_MISMATCH` | хэш файла или манифеста не совпадает с записанным | технический | нет |
| `APPROVAL_NOT_ACTIVE` | согласование отозвано, заменено или относится к другому содержимому | полномочия | нет |
| `ACTOR_NOT_AUTHORIZED` | не human, нет роли или назначения на тендер | полномочия | нет |
| `READINESS_HOLD_OPEN` | есть открытое удержание | целостность (I04) | нет, только решение по удержанию |
| `CALCULATION_PROVISIONAL` | ревизия расчёта `provisional` при выпуске в production-назначения | целостность (этап 06) | нет; меняется только решением владельца в журнале решений (Q-01) |
| `TEMPLATE_DEMO` | использован демо-шаблон при выпуске в production-назначения | целостность (этап 11) | нет |
| `REVIEW_INCOMPLETE` | последний запуск `completed_with_gaps` или устарел | бизнес | да, с причиной; пробелы остаются видимыми |
| `CRITICAL_FINDINGS_OPEN` | открытые `critical`-замечания | бизнес | да, по каждому замечанию (A45) |
| `QUESTIONS_UNANSWERED` | неотвеченные обязательные вопросы | бизнес | да |
| `FIELDS_INCOMPLETE_OR_STALE` | обязательные поля пусты или `stale` | бизнес | да, кроме полей, помеченных шаблоном как обязательные для заказчика |

Окончательная матрица согласуется владельцем (Q-09). Структура таблицы и разделение на классы — часть ядра и от ответа не зависят.

## 12. Инвалидация по зависимостям (`evidence_dependency`)

Новая редакция документа, новый прогон распознавания, новая ревизия расчёта или новое решение порождают задание `invalidate:<source_type>:<source_id>`. Оно переводит зависимые объекты в `stale` (`coverage_link`, `finding`, `draft_field_value`, `model_suggestion` → `expired`) и записывает причину. Прежние отчёты и решения не удаляются. Если область влияния нельзя определить надёжно, помечаются все объекты этапа того же типа.

## 13. Удержание готовности (`readiness_hold`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `open` | новый потенциально относящийся к этапу источник после существования `approval` (активного или уже с выпуском без отправки) | system | блокирует выпуск и регистрацию отправки; согласование не удаляется |
| `open` | `resolved_not_applicable` | «не влияет» с причиной | manager | создаётся `decision` |
| `open` | `resolved_requires_new_candidate` | «влияет» | manager | создаётся `decision`; текущий кандидат переводится в `superseded`, если не выпущен; для выпущенного — новая отправка только из нового выпуска |

## 14. Согласование (`approval`)

| Из | В | Событие | Кто | Эффекты |
|---|---|---|---|---|
| — | `active` | согласование кандидата | manager (human) | один `active` на кандидата (уникальный индекс); повтор с тем же ключом идемпотентности — тот же ответ |
| `active` | `revoked` | отзыв до выпуска | manager | причина; кандидат возвращается в `ready_for_approval` |
| `active` | `superseded` | кандидат заменён | system | запись сохраняется |

Выпущенное согласование не отзывается: выпуск неизменен. Старое согласование нельзя применить к новому кандидату: `release` проверяет совпадение `candidate_id` и хэша.

## 15. Выпуск (`release`)

Выпуск только создаётся (§11) и никогда не меняется. Производные статусы «размещено N из M» и «отправка зарегистрирована» вычисляются из `delivery` и `send_event` и хранятся отдельно (I01).

## 16. Размещение (`delivery`, `delivery_file_state`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `pending` | создание при выпуске | system | по одной на назначение |
| `pending` | `staging` | начало попытки | worker | `delivery_attempt`; файлы пишутся в служебную область назначения; байты — точные файлы из `blob`, без повторной генерации (I02) |
| `staging` | `committing` | все файлы загружены | worker | размер и хэш (или доступный отпечаток) каждого файла сверены |
| `committing` | `verifying` | перенос в целевую папку и маркер завершённости | worker | файл с тем же именем и другим хэшем — `conflict`, перезаписи нет (A30) |
| `verifying` | `delivered` | удалённое состояние совпало с манифестом | worker | все `delivery_file_state.verified` |
| любое рабочее | `failed` | ошибка сети, прав, места | worker | повтор только этого назначения (A28); другое назначение не откатывается (I14) |
| любое рабочее | `outcome_unknown` | таймаут после отправки данных | worker | следующий шаг — только сверка удалённого состояния, без слепой повторной загрузки (A29) |
| `outcome_unknown` | `verifying` | сверка | worker | — |
| `conflict` | `pending` | решение человека (переименовать корень или подтвердить совпадение) | engineer | решение в аудите |
| `failed` | `pending` | повтор | engineer / system | `Idempotency-Key`; `dedupe_key = delivery:<delivery_id>` |

Частично загруженный набор не показывается как размещённый.

## 17. Отправка (`send_event`)

| Из | В | Событие | Кто | Охранные условия и эффекты |
|---|---|---|---|---|
| — | `registered` | регистрация отправки | engineer (human) | выпуск существует; открытых `readiness_hold` нет; канал, дата, адресаты, основание; (`registered_by`, `idempotency_key`) уникальны |
| `registered` | `verified` | состав вложений совпал с манифестом выпуска | engineer / system | сверка хэшей вложений из основания |
| `registered` | `disputed` | состав не совпал | system / engineer | несовпадение не считается отправкой согласованного комплекта (A32) |

Черновик письма и размещение — не отправка (A31). Письмо не доказывает получение или согласие заказчика (A46). Найденное в MailHub отправленное письмо создаёт только кандидат в основание, который инженер подтверждает.

## 18. Сравнение (`comparison`, `change_explanation`)

`comparison`: `computing` → `ready` / `failed`. `change_explanation.reason_status`: `hypothesis` (модель или правило) → `confirmed` (human с основанием) или `unknown`. Строка `unexplained_remainder` существует всегда; сумма вкладов равна итоговой разнице по зафиксированному методу разложения (I11, A20).

## 19. Статус интеграции (`integration_status`)

| Статус | Когда ставится | Кем |
|---|---|---|
| `NOT_IMPLEMENTED` | адаптера нет | по умолчанию |
| `VERIFIED_FIXTURE` | пройдены contract-тесты на фикстурах | скрипт проверки этапа |
| `VERIFIED_LIVE` | пройден разрешённый live-smoke; есть ссылка на артефакт | администратор после live-smoke |
| `BLOCKED_EXTERNAL` | нужен внешний доступ или доработка | администратор / скрипт проверки |

Переход в `VERIFIED_LIVE` из фикстурного теста невозможен: требуется `evidence_ref` на отчёт live-smoke.
