# Контур КП — сквозной план тестирования

Этап 01. План покрывает все сценарии `docs/spec/05_ACCEPTANCE_CASES.md`. Реализация тестов идёт вместе с этапами; здесь зафиксировано, что и на каком уровне доказывается.

## 1. Уровни

| Уровень | Что доказывает | Инструменты |
|---|---|---|
| Unit | доменные правила без ввода-вывода: деньги, сопоставимость, разложение цены, переходы состояний, матрица блокеров, канонический JSON | vitest на `packages/core` |
| Integration (БД) | транзакции, ограничения, неизменяемость, права, конкурентность, идемпотентность, очередь | vitest + изолированная тестовая БД |
| Contract (адаптеры) | разбор реальных форматов на обезличенных фикстурах, коды ошибок, отсутствие побочных эффектов | vitest + фикстуры в `fixtures/` |
| UI/E2E | путь инженера и руководителя, видимость блокеров, различимость статусов, смартфон | Playwright с этапа 13 |
| Visual QA | реальные приложения, превью оригинала, выделение фрагмента | ручная проверка с артефактами в `artifacts/stage-XX/` |
| Live smoke | разрешённые тестовые ресурсы внешних систем | отдельные сценарии, запуск только по явному флагу и разрешению |
| Пилот | эталонный тендер, сравнение с человеческим эталоном | этап 18 |

Мок всех зависимостей не доказывает интеграцию: `VERIFIED_LIVE` ставится только по live smoke с артефактом (`state-machines.md` §19).

## 2. Среды и данные

1. **Тестовая БД** — отдельная база, имя содержит `test`; раннер миграций отказывается работать с базой без `test` в тестовом режиме (ADR-002 §7). Каждый тест выполняется в транзакции с откатом или на отдельной схеме.
2. **Данные** — только синтетические: тендер A (два этапа, минимум две отправки), тендер B с похожими названиями, документы ПД/ТЗ v1, ТЗ v2, договор, ВОР, смета, предложение поставщика, Q&A, письмо о замене светильника, встреча с поправкой транскрипции, редакция с непрочитанной страницей (05, «Набор данных»). Реальные документы, адреса, цены и ключи в репозиторий не попадают.
3. **Фикстуры форматов** — обезличенный экспорт RDWeb схемы 1, ответы TenderHub, EML, manifest переговоров. Фикстура помечается как фикстура в статусе интеграции.
4. **Эталонные значения** формул и разложений задаются до запуска и хранятся рядом с тестом.
5. **Live smoke** выполняется на согласованных тестовых ресурсах: тендер TenderHub, тестовый ящик MailHub, тестовые корни Яндекс Диска и SMB. Реальные КП не отправляются.

## 5. Статусы проверок этапов

Скрипты проверки этапов различают четыре исхода: `PASS` (проверка выполнена и пройдена), `FAIL`, `BLOCKED` (материал или доступ недоступен) и `PARTIAL` (осознанно ограниченный режим). Полный `PASS` возможен только при выполненных проверках; недоступность материала не даёт нулевого кода возврата (урок R00-02, I18).
