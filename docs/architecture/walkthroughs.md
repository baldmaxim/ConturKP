# Контур КП — сквозные сценарии на бумаге

Этап 01. Проверка модели данных и переходов без кода: что создаётся, что меняется, что остаётся неизменным. Имена — из `data-model.md`, переходы — из `state-machines.md`.

## 1. Светильник: ТЗ требует №1, письмо согласует №2, смета считает №2, ТЗ не изменено (A01)

| Шаг | Записи |
|---|---|
| 1. Импорт ТЗ ред. 1 | `blob` → `document_revision(ТЗ, ред.1)` → `document_occurrence` |
| 2. Распознавание | `recognition_run(complete)` → `evidence_fragment(origin=recognized_text)` с пунктом про светильник №1 |
| 3. Требование | `requirement(code=R-014, status=candidate)` → `requirement_revision(seq=1)` → `requirement_evidence(basis)` → инженер подтверждает: `status=confirmed` |
| 4. Письмо заказчика | `communication` + `communication_occurrence(ящик)` + фрагмент `origin=email_body` со согласованием светильника №2; `communication_tender_link(status=suggested)` → инженер подтверждает |
| 5. Расчёт | `calculation_revision` со строкой светильника №2; `coverage_link(requirement=R-014, kind=explicit_line, status=proposed)` |
| 6. Проверка | `review_run` → правило «параметр требования ≠ параметр строки расчёта» создаёт `finding(kind=parameter, severity=major)` с `finding_evidence(left=фрагмент ТЗ, right=строка расчёта)` |
| 7. Разногласие | `discrepancy(topic=Светильник)`; события осей: `customer_position=agreed_in_writing` (основание — письмо), `calculation=reflected`, `proposal=not_reflected`, `documents=not_fixed` |
| 8. Решение | `decision(subject=discrepancy, statement=«применять №2», basis=письмо)`; ось `proposal` переводится в `reflected` после включения условия в приложение |

**Итог.** Видны обе цитаты (ТЗ и письмо), четыре статуса независимы (I09), «согласовано письмом» не превращается в «закреплено в ТЗ» (I08). Замечание не закрывается автоматически: его закрывает решение человека.

## 2. Новый документ после согласования, до выпуска и отправки (A08, I04)

| Шаг | Записи |
|---|---|
| 1. Кандидат | `release_candidate(seq=3, status=ready_for_approval)` с `source_set_revision(frozen)`, `calculation_revision`, файлами и манифестом; `content_hash` записан |
| 2. Согласование | `approval(status=active, candidate_content_hash=H3)`; кандидат `approved` |
| 3. Поступает «Ответ на вопрос № 14» | импорт создаёт `document_revision`; задание относит редакцию к этапу; создаётся `readiness_hold(status=open, trigger=new_document_revision)` |
| 4. Попытка выпуска | блокер `READINESS_HOLD_OPEN`; выпуск отклонён, `audit_event(outcome=denied)` |
| 5. Решение руководителя | вариант «не влияет»: `readiness_hold=resolved_not_applicable` + `decision`; кандидат остаётся `approved`, выпуск разрешён. Вариант «влияет»: `resolved_requires_new_candidate` + `decision`; кандидат → `superseded`, `approval` → `superseded`, создаётся кандидат `seq=4`, который согласуется заново |

**Итог.** Старое согласование не стирается ни в одном варианте (I04). Новый комплект не выпускается по старому согласованию: `release` сверяет `candidate_id` и хэш (I02).

## 3. Изменение расчёта после закрытия (A07)

| Шаг | Записи |
|---|---|
| 1. Закрытие по сроку | наступил `submission_deadline`; выгрузка создаёт `calculation_capture(complete)` и `calculation_revision(seq=5, kind=provisional, content_hash=C5)` |
| 2. Работа этапа | `review_run`, `coverage_link`, кандидат и согласование ссылаются на ревизию 5 |
| 3. В TenderHub правят строку | следующая выгрузка даёт `calculation_revision(seq=6, supersedes=5, content_hash=C6)`; ревизия 5 не меняется |
| 4. Инвалидация | задание `invalidate:calculation_revision:5` переводит зависимые `coverage_link` и `finding` в `stale`, `model_suggestion` — в `expired` |
| 5. Выпуск | уже выпущенный комплект по ревизии 5 остаётся воспроизводимым: его манифест ссылается на 5. Новый кандидат строится на 6 |

**Итог.** Исторический расчёт воспроизводим, изменения видны как новая ревизия (I03, I15). Разница 5 → 6 объясняется на этапе сравнения со строкой `unexplained_remainder`, если причина не установлена (I11).

## 4. Две параллельные правки одного условия (A24)

| Шаг | Записи |
|---|---|
| 1. Оба инженера открывают поле приложения | `GET` возвращает `draft_field_value` с `ETag "F:7"` |
| 2. Инженер A сохраняет | `PATCH` с `If-Match: "F:7"`; транзакция: блокировка строки, проверка `row_version=7`, запись значения, `row_version=8`, `draft_field_event` |
| 3. Инженер B сохраняет | `PATCH` с `If-Match: "F:7"`; `row_version` уже 8 → `412 VERSION_CONFLICT` с текущим значением и автором |
| 4. Инженер B решает | видит правку A, объединяет текст и сохраняет с `If-Match: "F:8"` |

**Итог.** Молчаливой перезаписи нет (I13). История обеих правок — в `draft_field_event`; ручной текст не теряется.

## 5. Повторная доставка после неизвестного исхода (A29, A28, A30)

| Шаг | Записи |
|---|---|
| 1. Выпуск | `release` создаёт `delivery(Яндекс Диск, pending)` и `delivery(SMB, pending)` |
| 2. Яндекс Диск | `staging` → `committing` → таймаут без ответа → `outcome_unknown`; повторная загрузка запрещена |
| 3. Сверка | задание `verify_delivery` читает удалённое состояние: файлы на месте, отпечатки совпадают → `verifying` → `delivered`; в `delivery_attempt` две записи |
| 4. SMB | сеть недоступна → `failed`; состояние Яндекс Диска не меняется (A28) |
| 5. Повтор SMB | `POST /deliveries/{smb}/retry` с `Idempotency-Key`; в целевой папке уже лежит файл с тем же именем и другим хэшем → `conflict`, перезаписи нет (A30) |
| 6. Решение | инженер выбирает другой корень или подтверждает, что файл посторонний; решение в аудите; повтор завершается `delivered` |
| 7. Отправка | только после `delivered` инженер регистрирует `send_event` с основанием; «размещено» и «отправлено» — разные записи (I01, A31) |

**Итог.** Повтор не создаёт дублей и не перезаписывает чужие файлы (I14). Частичное размещение не выглядит готовым.

## Что эти сценарии подтверждают в модели

| Сценарий | Проверенное свойство модели |
|---|---|
| 1 | независимые оси статусов, двусторонние основания, цитаты из разных типов источников |
| 2 | удержание готовности, неизменность согласования, привязка согласования к хэшу содержимого |
| 3 | неизменяемые ревизии расчёта, инвалидация по зависимостям, воспроизводимость истории |
| 4 | оптимистичная конкуренция и история правок |
| 5 | идемпотентность, независимость назначений, запрет перезаписи, разделение размещения и отправки |

Ни один сценарий не потребовал изменения таблицы задним числом и не потребовал перестройки ядра.
