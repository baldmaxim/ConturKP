# Контур КП — сквозные сценарии на бумаге

Этап 01. Проверка модели данных и переходов без кода: что создаётся, что меняется, что остаётся неизменным. Имена — из `data-model.md`, переходы — из `state-machines.md`. Сценарии §6–§11 добавлены по ревью 01-1 (R01-01…R01-06).

## 1. Светильник: ТЗ требует №1, письмо согласует №2, смета считает №2, ТЗ не изменено (A01)

| Шаг | Записи |
|---|---|
| 1. Импорт ТЗ ред. 1 | `blob` → `document_revision(ТЗ, ред.1)` → `document_occurrence`; событие `document_revision_registered` |
| 2. Распознавание | `recognition_run(complete)` → `evidence_fragment(origin=recognized_text)` с пунктом про светильник №1 |
| 3. Требование | `requirement(code=R-014, status=candidate)` → `requirement_revision(seq=1)` → `requirement_evidence(basis)` → инженер подтверждает: `status=confirmed` |
| 4. Письмо заказчика | `communication` + `communication_occurrence(ящик)` + фрагмент `origin=email_body` со согласованием светильника №2; `communication_tender_link(status=suggested)` → инженер подтверждает; событие `communication_linked` |
| 5. Расчёт | `calculation_revision` со строкой светильника №2; `coverage_link(requirement=R-014, kind=explicit_line, status=proposed)` |
| 6. Проверка | `review_run` на снимке `evidence_scope` (ТЗ с прогоном распознавания и письмо) → правило «параметр требования ≠ параметр строки расчёта» создаёт `finding(kind=parameter, severity=major)` с `finding_evidence(left=фрагмент ТЗ, right=строка расчёта)` |
| 7. Разногласие | `discrepancy(topic=Светильник)`; события осей: `customer_position=agreed_in_writing` (основание — письмо), `calculation=reflected`, `proposal=not_reflected`, `documents=not_fixed` |
| 8. Решение | `decision(subject=discrepancy, statement=«применять №2», basis=письмо)`; ось `proposal` переводится в `reflected` после включения условия в приложение |

**Итог.** Видны обе цитаты (ТЗ и письмо), четыре статуса независимы (I09), «согласовано письмом» не превращается в «закреплено в ТЗ» (I08). Замечание не закрывается автоматически: его закрывает решение человека.

## 2. Новый документ после согласования, до выпуска и отправки (A08, I04)

| Шаг | Записи |
|---|---|
| 1. Кандидат | `release_candidate(seq=3, mode=production, input_version=41, status=ready_for_approval)` на снимке `evidence_scope` и ревизии расчёта; `content_hash` записан |
| 2. Согласование | под блокировкой этапа предикат актуальности истинен; `approval(status=active, candidate_content_hash=H3, input_version=41)`; кандидат `approved` |
| 3. Поступает «Ответ на вопрос № 14» | транзакция регистрации редакции: блокировка строки этапа → `input_version=42` → `stage_input_event(seq=42, document_revision_registered)` → `readiness_hold(candidate=3, event=42, open)`; задание инвалидации поставлено, но ещё не выполнено |
| 4. Попытка выпуска | под блокировкой этапа: событие 42 > 41 без решения «не влияет» → блокер `INPUTS_CHANGED`; выпуск отклонён, `audit_event(outcome=denied)` |
| 5. Решение руководителя | вариант «не влияет»: удержание → `resolved_not_applicable` + `decision`; предикат снова истинен, выпуск разрешён. Вариант «влияет»: `resolved_requires_new_candidate` + `decision`; кандидат → `superseded`, `approval` → `superseded`, создаётся кандидат `seq=4`, который согласуется заново |

**Итог.** Старое согласование не стирается ни в одном варианте (I04). Выпуск заблокирован синхронно, до фоновой инвалидации. Новый комплект не выпускается по старому согласованию: `release` сверяет `candidate_id` и хэш (I02).

## 5. Повторная доставка после неизвестного исхода (A29, A28, A30)

| Шаг | Записи |
|---|---|
| 1. Выпуск | `release(mode=production)` создаёт `delivery(Яндекс Диск, версия назначения v3, pending)` и `delivery(SMB, версия v1, pending)` |
| 2. Яндекс Диск | `staging` → `committing` → таймаут без ответа → `outcome_unknown`; повторная загрузка запрещена |
| 3. Сверка | задание `verify_delivery` читает удалённое состояние в корне из версии v3: файлы на месте, отпечатки совпадают → `verifying` → `delivered`; в `delivery_attempt` две записи |
| 4. SMB | сеть недоступна → `failed`; состояние Яндекс Диска не меняется (A28) |
| 5. Повтор SMB | `POST /deliveries/{smb}/retry` с `Idempotency-Key`; в целевой папке уже лежит файл с тем же именем и другим хэшем → `conflict`, перезаписи нет (A30) |
| 6. Решение | инженер подтверждает, что файл посторонний, и перенаправляет доставку на новую версию назначения v2 с другим корнем: создаётся новая `delivery`, старая → `superseded`; решение в аудите; доставка завершается `delivered` |
| 7. Отправка | только после размещения и под барьером актуальности инженер регистрирует `send_event` с основанием; «размещено» и «отправлено» — разные записи (I01, A31) |

**Итог.** Повтор не создаёт дублей и не перезаписывает чужие файлы (I14). Частичное размещение не выглядит готовым.

## 6. Новый OCR, письмо и исправленная транскрипция во время проверки (R01-01; A10, A11)

| Шаг | Записи |
|---|---|
| 1. Набор источников | `source_set_revision(S7, frozen)` включает PDF D |
| 2. Запуск проверки | в транзакции запуска создаётся `evidence_scope(E1)`: элементы `document_recognition(D, R1)`, `communication(M1)`, `transcript_revision(T1)`; `content_hash` E1; `review_run(P1, evidence_scope=E1)` |
| 3. Во время проверки | импортирован экспорт RDWeb R2 для того же D; подтверждена связь письма M2; импортирована исправленная транскрипция T2. Каждое — событие барьера; `E1` не меняется |
| 4. Результат P1 | проверка читает только единицы E1: R1, M1, T1. Полный состав проверенного набора восстанавливается из `evidence_scope_item`, включая источники, которые не дали замечаний |
| 5. Кандидат | кандидат принимает `evidence_scope_id = E1` от P1; манифест содержит ID и хэш E1; R2, M2, T2 в кандидат не попадают |
| 6. Новая проверка | инженер фиксирует новую область `E2` (D с R2, M1, M2, T2) и запускает P2; кандидат, собранный из P1 и P2 одновременно, отклоняется блокером `REVIEW_SCOPE_MISMATCH` |
| 7. Исторический поиск | поиск по выпуску из P1 строит область из E1: фрагменты R2, M2, T2 не участвуют в ранжировании |
| 8. Права | если у пользователя отозвали доступ к ящику M1, исторический поиск исключает M1 при чтении; снимок E1 при этом не меняется |

**Итог.** Проверка, кандидат, манифест и исторический поиск работают на одном неизменяемом составе (I02, I05, I15, I18). Новые источники не подменяют старые, а права применяются поверх исторического состава.

## 7. Изменение входов против согласования и выпуска (R01-03; A08, A09)

| Порядок | Шаги | Итог |
|---|---|---|
| Импорт раньше выпуска | импорт регистрирует редакцию: блокировка этапа, `input_version 41 → 42`, событие 42, удержание; commit. Выпуск берёт блокировку этапа, видит событие 42 > 41 без решения | `INPUTS_CHANGED`, выпуск отклонён |
| Выпуск раньше импорта | выпуск держит блокировку этапа, предикат истинен, `release(input_version=41)` фиксируется. Импорт ждёт блокировку, затем событие 42 и удержание для выпущенного, но не отправленного кандидата | выпуск законен; регистрация отправки блокирована до решения по событию 42 |
| Решение после согласования | руководитель записывает `decision` по разногласию: блокировка этапа, событие `decision_recorded(43)`, удержание; поля приложения ещё не помечены `stale`, задание инвалидации стоит | выпуск и отправка кандидата с прежним решением блокированы событием 43 |
| Остановленный worker, загрузка через API | инженер загружает архив; API принимает `import_batch` и в той же транзакции создаёт событие `import_accepted(44)`; worker остановлен, файлы не разобраны | барьер уже действует: выпуск блокирован до решения по событию 44 или до нового кандидата |
| Остановленный worker, наблюдаемая папка | файл лежит в папке, скан не выполнялся дольше `freshness_window` | `INTAKE_NOT_CURRENT` блокирует согласование, выпуск и отправку, пока скан не восстановлен или канал не отключён руководителем с причиной |
| «Влияет» после выпуска | руководитель по событию 42 решает `resolved_requires_new_candidate` | предикат для выпущенного кандидата ложен навсегда: обычная отправка старого выпуска невозможна; нужен новый кандидат |

**Итог.** Согласование, выпуск и отправка сериализованы с поступлением значимых изменений через блокировку этапа и события; фоновая инвалидация может опаздывать без вреда (I03, I04, I13).

## 8. Идентичность расчёта (R01-04; A07, A20)

| Шаг | Записи |
|---|---|
| 1. Первая выгрузка | `calculation_content(C1)`: строки L, итог КП 100 000 000,00 RUB, курсы USD/EUR/CNY на 16.09; `calculation_revision(seq=5, provisional, content=C1)` |
| 2. Повтор той же выгрузки | содержимое снова C1; ревизия `provisional` для (этап, тендер TenderHub, C1) уже есть → выгрузка связывается с ревизией 5, новой строки нет |
| 3. Те же строки, другие курсы | строки L, но курсы на 17.09 → содержимое C2 ≠ C1 → `calculation_revision(seq=6, provisional, content=C2, supersedes=5)` |
| 4. Те же строки, другой итог КП | например, изменилось страхование, итог 100 500 000,00 → C3 → ревизия 7 |
| 5. Ревизия TenderHub после X-01 | внешняя ревизия `TH-88` с содержимым, совпадающим с C3 → `calculation_revision(seq=8, verified, external_revision_ref=TH-88, content=C3)`; ревизия 7 не меняется |
| 6. Повтор получения TH-88 | уникальность (этап, TH-88) → та же ревизия 8 |
| 7. Закрытие у источника | `calculation_revision_status_event(revision=8, closed_at_source)`; запись ревизии 8 не меняется |

**Итог.** Ни курсы, ни итог, ни переход `provisional` → `verified` не теряются, а повторы идемпотентны (I02, I03, I10).

## 9. Тестовый выпуск и изменение назначения (R01-05)

| Шаг | Записи |
|---|---|
| 1. Кандидат | `release_candidate(mode=test)` с `provisional`-расчётом и демо-шаблоном; файлы помечены «ТЕСТОВЫЙ ВЫПУСК»; `mode` входит в манифест и хэш |
| 2. Согласование и выпуск | блокеры `CALCULATION_PROVISIONAL` и `TEMPLATE_DEMO` к `mode=test` не применяются; `release(mode=test)` |
| 3. Доставки | создаются только для назначений с `environment=test`; production-назначение для этого выпуска не создаётся (`ENVIRONMENT_MISMATCH`) |
| 4. Попытка зарегистрировать отправку | `POST /releases/{id}/send-events` → `RELEASE_IS_TEST`; `send_event` не создаётся |
| 5. Комплект всё же ушёл заказчику вне системы | инженер регистрирует `compliance_incident(test_release_sent_externally)` с основанием; это нарушение, а не отправка; выпуск остаётся тестовым |
| 6. Изменение назначения между попытками | доставка D1 закреплена за версией v1 тестового назначения; администратор меняет корень → версия v2. Повтор D1 использует корень v1; перенаправление создаёт D2 с v2 той же среды |
| 7. Попытка превратить тестовое назначение в боевое | `environment` назначения не меняется после создания; нужно создать новое назначение `production`, и тестовый выпуск в него не доставляется |

**Итог.** Боевой режим определяется кандидатом и выпуском, а не списком назначений; тестовый выпуск не может стать отправкой или боевой доставкой (I01–I03, I14).

## 10. Возобновление старого обработчика после перехвата (R01-06; A15, A29)

| Шаг | Записи |
|---|---|
| 1. Захват | обработчик A захватывает задание J: `lease_token=T1`, `locked_until=t+5 мин` |
| 2. Пауза A | процесс A приостановлен на 10 минут |
| 3. Recovery | `locked_until` истёк → J `queued`, `lease_token=null` |
| 4. Перехват | обработчик B захватывает J: `lease_token=T2`, `attempts=2`; B сверяет внешнее состояние (исход неизвестен) и продолжает |
| 5. A возобновился | heartbeat A: `WHERE lease_token=T1` → 0 строк; A прекращает работу. Если A успел начать внешнюю загрузку, она идёт под ключом идемпотентности файла (путь + хэш) и не может создать дубль; результат A в БД не записывается |
| 6. Завершение B | транзакция: блокировка J с проверкой `T2` → запись доменного результата → `succeeded` |
| 7. Отмена во время перехвата | пользователь отменяет J, пока A приостановлен: `cancel_requested=true`. B видит флаг при захвате или heartbeat и подтверждает `cancelled` условной записью по `T2`; A подтвердить не может |
| 8. GPU | если J — задание класса `gpu`, слот `resource_slot('gpu')` захвачен токеном T1; B не получает слот до `locked_until + gpu_takeover_grace`; A при потере аренды прерывает вызов модели |

**Итог.** Устаревший обработчик не может завершить, провалить или отменить чужую попытку и записать доменный результат; внешние действия защищены своей идемпотентностью (I14).

## 11. Поиск LocalAI при двух прогонах и закрытом ящике (R01-02; A10–A12, A35)

| Шаг | Записи |
|---|---|
| 1. Индекс | LocalAI проиндексировал фрагменты R1 и R2 одного PDF D как разные единицы источника |
| 2. Исторический поиск | область выпуска из E1 содержит единицу R1; `allowedSourceUnitIds = {R1, M1, T1}`; запрос с `limit=1`, фрагмент R2 ранжируется выше |
| 3. Фильтр до ранжирования | LocalAI отбирает кандидатов только из R1, M1, T1; возвращает лучший фрагмент R1. R2 не участвует, результат не теряется |
| 4. Проверка ответа | портал сверяет каждый фрагмент: существует, принадлежит указанной единице, единица в области. Ответ с фрагментом R2 был бы отклонён целиком и записан в аудит |
| 5. Закрытый ящик | у пользователя нет доступа к ящику письма M1; сервер исключает M1 из `allowedSourceUnitIds` до вызова; самый релевантный фрагмент M1 не ранжируется и не раскрывается; ответ указывает, что часть области исключена по правам, без содержимого |

**Итог.** Полный фильтр области применяется до top-k и проверяется в ответе (I05, I17).

## Что эти сценарии подтверждают в модели

| Сценарий | Проверенное свойство модели |
|---|---|
| 1 | независимые оси статусов, двусторонние основания, цитаты из разных типов источников |
| 2 | синхронное удержание, неизменность согласования, привязка согласования к хэшу содержимого |
| 3 | неизменяемые ревизии расчёта, инвалидация по зависимостям, воспроизводимость истории |
| 4 | оптимистичная конкуренция и история правок |
| 5 | идемпотентность, независимость назначений, запрет перезаписи, закреплённая версия назначения, разделение размещения и отправки |
| 6 | неизменяемый снимок области для проверки, кандидата, манифеста и исторического поиска |
| 7 | барьер актуальности в обоих порядках исполнения и при остановленном worker |
| 8 | разделение содержимого расчёта и наблюдения источника |
| 9 | неизменяемый режим выпуска и закреплённые версии назначений |
| 10 | ограждение записей обработчика токеном аренды |
| 11 | фильтр по единицам источника до ранжирования и проверка ответа |

Ни один сценарий не потребовал изменения записи задним числом и не потребовал перестройки ядра.
