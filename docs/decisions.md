### D-006 — Технические решения этапа 02

Дата / автор / основание полномочия: 2026-09-18 / Claude / технический выбор в рамках ADR-001, ADR-002, ADR-006.

Проблема: ADR оставили на этап 02 выбор версий, библиотеки паролей, способа запуска TypeScript и границ видимости администратора.

Варианты и последствия:
- пароли: пакет `argon2` (нативная сборка) или встроенный `node:crypto.argon2` (Node ≥ 24.7, без зависимостей, API помечен экспериментальным) — выбран встроенный, формат PHC позволяет сменить реализацию без миграции;
- запуск сервера: сборка `tsc`/`tsx` или встроенное удаление типов Node 24 — выбрано встроенное, без шага сборки; разрешён только стираемый синтаксис;
- администратор без назначения: видит всё или только администрирование — видит карточку тендера и участников, но не этапы и содержимое (ADR-006: «без членства не видит данных тендера»);
- создание этапов: администратор (как в контракте этапа 01) или руководитель тендера — руководитель (`stage.manage`), чтобы у роли руководителя было проверяемое право уже на этапе 02; контракт обновлён;
- тестовая БД: общий кластер разработки или локальный кластер `runtime/pg` на 127.0.0.1:55432 с trust — выбран локальный одноразовый кластер; на каждый файл тестов — своя база `kontur_kp_test_*`.

Принято: как выше; версии — ADR-001 «Реализация (этап 02)»; сессии, CSRF, перебор паролей — ADR-006 «Реализация (этап 02)».

Статус: proposed

Что изменяет в требованиях/контрактах/тестах: `docs/contracts/portal-api.md` §2.1–2.2 (эндпоинты администрирования, `PATCH /stages/{id}`, право `stage.manage`); `data-model.md` §4.1, §4.12 (`process_heartbeat`, `revoke_reason`, `removed_by`, `audit_event.seq`, `principal_kind = anonymous`). Бизнес-требования не меняются.

Ссылка на подтверждение владельца: не требуется для технического выбора.

### D-008 — Технические решения этапа 03

Дата / автор / основание полномочия: 2026-09-18 / Claude / технический выбор в рамках ADR-003, ADR-004 и state-machines §1.1, §3.

Проблема: этап 03 требует выбрать формат загрузки, поддерживаемые архивы, правила группировки редакций и объём барьера актуальности до появления кандидатов выпуска.

Принято:
- загрузка — один файл или ZIP на запрос, тело — сам файл (`application/octet-stream`), имя — параметр `name`; интерфейс отправляет несколько файлов отдельными запросами со своими ключами идемпотентности;
- архивы: только ZIP (библиотека `yauzl` 3, имена без флага UTF-8 декодируются как CP866); RAR и 7z отклоняются явно (`type_not_allowed`); вложенные архивы не распаковываются; повреждённый каталог архива даёт элемент `(архив)` с отказом `corrupt`;
- одно содержимое в тендере — одна редакция (`document_revision` уникальна по `tender_id, blob_sha256`); новая редакция документа — при совпадении ключа имени файла (`name_key`), иначе новый документ; перегруппировка редакций инженером — позже, на этапе 08 вместе с требованиями;
- наблюдаемые папки допускаются только внутри `INTAKE_ROOTS` (realpath при каждом скане), не пересекаются с хранилищем, ссылки и junction не открываются; «Яндекс Диск» и «SMB» на этапе 03 — папки, синхронизированные клиентом ОС (`origin`), а не API; размещение выпусков на Яндекс Диск и SMB — этап 14;
- скан папки со стабильными новыми файлами порождает `import_accepted` (строже §1.1);
- `readiness_hold` и задание инвалидации (§1.1 п. 4–5) не создаются: кандидатов выпуска и зависимостей ещё нет (этапы 09, 12, 13); события барьера пишутся уже сейчас;
- заморозка ревизии набора источников — этап 04 (охранное условие требует распознавания);
- таблица `decision` введена с одним видом `import_item_disposition`; остальные виды добавят миграции этапов 08–13.

Статус: proposed

Что изменяет в требованиях/контрактах/тестах: `docs/contracts/portal-api.md` §2.1, §2.3; `data-model.md` §4.2, §4.3; `state-machines.md` §3 («Реализация этапа 03»). Бизнес-требования не меняются.

Ссылка на подтверждение владельца: не требуется для технического выбора.

### D-010 — Объём этапа 04 сужен до импорта результатов распознавания

Дата / автор / основание полномочия: 2026-09-21 / Claude / по указанию владельца.

Проблема: промпт этапа 04 (`docs/spec/prompts/stage-04.md`) требовал и импорт экспортного архива RDWeb, и адаптер API RDWeb с постановкой задач, статусом, retry и разрешённым live-smoke. API RDWeb не подтверждён (Q-02), документированного контракта нет (X-05).

Варианты: (а) писать клиента API по предположительному контракту и оставить его неработающим; (б) оставить в этапе только импорт результатов, полученных человеком из RDWeb.

Принято (вариант «б», указание владельца — «оставляем только импорт результатов в виде zip»):
- реализуется `RdwebExportImporter`: приём ZIP-экспорта (PDF + `_blocks.json` + `_results.md`, `_results.html` необязателен) к **уже зарегистрированной** редакции документа;
- соответствие подтверждается SHA-256 PDF из архива и `document_revision.blob_sha256`; несовпадение — отказ `pdf_mismatch`, чужой или старый результат не принимается;
- `RdwebApiClient` (submit / getStatus / fetchResult, retry, timeout, live-smoke) **не пишется**; X-05 остаётся `BLOCKED_EXTERNAL`, автоматическая постановка распознавания выносится за пределы этапа 04;
- фикстура рабочей интеграцией не объявляется: статус `RDWeb (импорт экспорта)` — `VERIFIED_FIXTURE`.

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: `docs/contracts/adapters.md` §3 и §9; `docs/integrations/status.md`; `docs/requirements-traceability.md` F04. Бизнес-требования не меняются: способ доставки результата меняется, состав данных — нет.

Ссылка на подтверждение владельца: сообщение владельца в сессии 2026-09-21 («давай начнем этап 4, но изменим план так, что мы оставляем только импорт результатов… в виде zip»).

### D-011 — Технические решения импорта распознавания

Дата / автор / основание полномочия: 2026-09-21 / Claude / технический выбор в рамках этапа 04.

Проблема: формат экспорта подтверждён одним образцом (R-05), PDF-парсера в портале нет, а доказательство обязано открывать правильный участок оригинала (A17) и честно показывать неполноту (A16, I18).

Принято:
- **пространство координат фиксируется, а не угадывается**: колонка `evidence_fragment.bbox_space`; для `rdweb_export` — `page_rotated` (экспорт даёт растровое пространство). Пересчёт в рамку делает браузер (`apps/web/src/utils/bbox.ts`), обе ветки покрыты `tests/bbox.test.ts`; при расхождении пропорций страницы интерфейс предупреждает, а не сдвигает рамку молча;
- **превью строит браузер на pdf.js** поверх `GET /document-revisions/{id}/content`; серверного рендера PDF нет, маршрут `GET /evidence/{id}/preview` не регистрируется. В CSP добавлено `font-src 'self' blob:` — pdf.js подключает шрифты документа через `FontFace` с blob-URL, созданным нашим же скриптом; `script-src 'self'` не ослабляется (pdf.js 5 не использует eval);
- **`crop_url` не загружается никогда** — ни при импорте, ни при показе: хранится и отдаётся текстом. В адаптере физически нет сетевых вызовов (статическая проверка в тесте), это и есть защита от SSRF (A38);
- **полнота проверяется по согласованности файлов экспорта**, а не по числу страниц PDF (парсера нет). Ограничение записано в `state-machines.md` §4 и `discovery.md` (R-05) и не выдаётся за проверку PDF;
- **`fragment_index_state` не создаётся**: до этапа 05 (X-04) у таблицы нет ни писателя, ни читателя, а её форма зависит от контракта индекса. Заводится миграцией этапа 05;
- **класс ресурса задания — `default`**: разбор архива локален, слот `resource_slot('gpu')` занимать нечем и незачем (ADR-004);
- **фикстура — генератор `tests/rdweb.ts`, а не бинарный файл**: обезличенность доказывается конструкцией, негативные варианты (повёрнутая страница, отсутствующий crop, несовпадение числа страниц, неизвестный тип блока, повторная версия OCR, небезопасный член архива) параметризуются;
- **заморозка состава источников** реализована здесь же: охранное условие — у каждой включённой редакции есть прогон `complete` или `partial`; `content_hash` считается по составу (`packages/core/src/contentHash.ts`) и прогоны распознавания в него не входят — их фиксирует снимок области (этап 05).

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: `data-model.md` §4.4 (колонки `fragment_key`, `bbox_space`); `state-machines.md` §4; `portal-api.md` §2.3–2.4; `contracts/adapters.md` §3.

Ссылка на подтверждение владельца: выбор способа превью и объёма заморозки подтверждён владельцем в сессии 2026-09-21; остальное — технический выбор.
