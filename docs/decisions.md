Дата / автор / основание полномочия: 2026-09-18 / Claude / технический выбор в рамках ADR-003, ADR-004 и state-machines §1.1, §3.

### D-011 — Технические решения импорта распознавания

Дата / автор / основание полномочия: 2026-09-21 / Claude / технический выбор в рамках этапа 04.

Проблема: формат экспорта подтверждён одним образцом (R-05), PDF-парсера в портале нет, а доказательство обязано открывать правильный участок оригинала (A17) и честно показывать неполноту (A16, I18).

Принято:
- **пространство координат фиксируется, а не угадывается**: колонка `evidence_fragment.bbox_space`; для `rdweb_export` — `page_rotated` (экспорт даёт растровое пространство). Пересчёт в рамку делает браузер (`apps/web/src/utils/bbox.ts`), обе ветки покрыты `tests/bbox.test.ts`; при расхождении пропорций страницы интерфейс предупреждает, а не сдвигает рамку молча;
- **превью строит браузер на pdf.js** поверх `GET /document-revisions/{id}/content`; серверного рендера PDF нет, маршрут `GET /evidence/{id}/preview` не регистрируется. В CSP добавлено `font-src 'self' blob:` — pdf.js подключает шрифты документа через `FontFace` с blob-URL, созданным нашим же скриптом; `script-src 'self'` не ослабляется (pdf.js 5 не использует eval);
- **`crop_url` не загружается никогда** — ни при импорте, ни при показе: хранится и отдаётся текстом. В адаптере физически нет сетевых вызовов (статическая проверка в тесте), это и есть защита от SSRF (A38);
- ~~**полнота проверяется по согласованности файлов экспорта**, а не по числу страниц PDF (парсера нет)~~ — **вытеснено D-012** по ревью 04-1 (R04-03): полнота меряется по фактическому числу страниц оригинала;
- **`fragment_index_state` не создаётся**: до этапа 05 (X-04) у таблицы нет ни писателя, ни читателя, а её форма зависит от контракта индекса. Заводится миграцией этапа 05;
- **класс ресурса задания — `default`**: разбор архива локален, слот `resource_slot('gpu')` занимать нечем и незачем (ADR-004);
- **фикстура — генератор `tests/rdweb.ts`, а не бинарный файл**: обезличенность доказывается конструкцией, негативные варианты (повёрнутая страница, отсутствующий crop, несовпадение числа страниц, неизвестный тип блока, повторная версия OCR, небезопасный член архива) параметризуются;
- **заморозка состава источников** реализована здесь же: охранное условие — у каждой включённой редакции есть прогон `complete` или `partial`; `content_hash` считается по составу (`packages/core/src/contentHash.ts`) и прогоны распознавания в него не входят — их фиксирует снимок области (этап 05).

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: `data-model.md` §4.4 (колонки `fragment_key`, `bbox_space`); `state-machines.md` §4; `portal-api.md` §2.3–2.4; `contracts/adapters.md` §3.

### D-012 — Полнота по оригиналу, отмена прогона и неусечённое доказательство

Дата / автор / основание полномочия: 2026-09-22 / Claude / по указанию владельца в ответ на ревью 04-1.

Проблема: независимое ревью 04-1 (`docs/reviews/04-review-1.md`) показало, что этап 04 может объявить `complete` без доказательства обработки всех страниц (R04-03), оставляет прогон активным навсегда при отмене задания (R04-02) и сохраняет длинный текст блока с потерей хвоста (R04-06).

Варианты по полноте: (а) оставить проверку согласованности двух файлов экспорта и зафиксировать ограничение документом; (б) добавить в цепочку поставки новый PDF-парсер; (в) переиспользовать `pdfjs-dist`, уже присутствующий в репозитории для просмотра доказательства в браузере.

Принято (вариант «в», выбор владельца 2026-09-22):

- **число страниц оригинала считает worker** (`apps/worker/src/pdfPages.ts`) на `pdfjs-dist` — том же движке, которым портал показывает участок доказательства (A17). Новой записи в цепочке поставки не появляется. Счёт идёт по локальному файлу: сети у разбора нет, `enableScripting` выключен, шрифты не догружаются, размер ограничен `RECOGNITION_MAX_PDF_MB`;
- **оригинал, который не открывается, полноты не подтверждает**: прогон получает `failed` с кодом `pdf_unreadable`. Основание: тем же pdf.js портал рисует доказательство, поэтому нечитаемый оригинал всё равно не даёт показать участок;
- **страница считается распознанной только по содержательному признаку** — полученному фрагменту с непустым текстом либо блоку с явно указанным статусом обработки. Заголовок `## Page N` выводом не считается, отсутствие `status` у блока «распознано» не означает;
- **у прогона появился терминальный статус `cancelled`** (а не `failed` со специальным кодом): отмена — не ошибка разбора, и смешивать их в отчётности незачем. Отмена `queued`-задания терминализует прогон в транзакции команды, отмена `running` — в транзакции worker под действующей арендой (`IJobHandlerSpec.onCancel`). Захват задания сам доменных объектов больше не трогает: пакет `@kontur/db` о них не знает;
- **длинный текст блока разбивается без потерь** на части со стабильными ключами `<ключ>#pN` и полями `part_index`/`part_total` вместо усечения: этап 05 будет индексировать полный текст, а не хвост без продолжения;
- **терминальный прогон стал неизменяемым агрегатом на уровне БД**: дочерние строки принимает только выполняющийся прогон, а счётчики полноты сверяются с фактическими строками `recognition_page` (миграция 0006).

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: `state-machines.md` §4; `data-model.md` §4.4; `contracts/adapters.md` §3; `contracts/portal-api.md` §2.3–2.4; `docs/migrations/0006_recognition_evidence_integrity.sql`; регрессии `tests/regressions-r04.test.ts` и `tests/regressions-r04b.test.ts`. Бизнес-требования не меняются: portal честнее сообщает о полноте и отмене.

**D-010 не меняется**: API RDWeb остаётся `BLOCKED_EXTERNAL`, автоматическая постановка задач не появляется.

### D-013 — Слияние Locus (LocalAI) в Контур КП

Дата / автор / основание полномочия: 2026-09-22 / владелец процесса / решение в рабочей сессии.

Проблема: владелец в одиночку ведёт два продукта с пересекающейся задачей. Locus (`Odintsov/Locus/LocalAI`) отвечает на вопросы по документации проектов с проверяемыми цитатами; Контур КП ведёт жизненный цикл коммерческого предложения. Поиск с цитатами — содержание этапа 05 Контура, а извлекаемые Locus факты договора (аванс, удержание, неустойка, сроки, цена) — кандидаты в требования этапа 08. При этом приёмка этапа 05 была заблокирована X-04 и Q-13 — доработкой и согласием «владельца LocalAI», то есть самого владельца процесса.

Варианты и последствия:
- оставить как есть: два сервиса, адаптер `LocalAiIndex`, X-04 и Q-13 висят бессрочно;
- поглотить Locus: один сервис, блокировки исчезают, но объём Контура растёт и требуются правки принятых документов.

Принято: **Locus закрывается, его ядро переносится в Контур КП.** Locus замораживается — новые функции не разрабатываются — и остаётся запущенным как рабочий инструмент и донор алгоритмов до замены (этап 19).

- переносится всё ядро, включая локальное распознавание; не переносятся удалённый LM Studio (`RAG_REMOTE_LLM_*`, `allowRemoteContext`), Telegram-бот, адаптер Dify, Google Drive OAuth, интерфейс `rag-ui`, хранилища SQLite и файловый снимок векторов, переносимый индекс в папку тендера, Qdrant;
- TenderHub получает одно централизованное подключение на все цели; сам HUBTender **не** поглощается и остаётся источником истины по расчёту (ADR-007);
- корпус действующих договоров выигранных тендеров переносится внутрь Контура (D-017);
- ценовой аудит Locus как экономическая проверка не переиспользуется — риск R-03 (`docs/discovery.md` §3) остаётся в силе;
- размещение не меняется: локальный ПК, LAN/VPN;
- `DifyRAG` (последний коммит 2026-07-13) в расчёт не берётся как выведенный из эксплуатации.

Ограничение C01 не нарушается: оно запрещает **второй** OCR/RAG. После закрытия Locus второго не остаётся — портальный становится единственным.

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: спецификация §3 (существующие сервисы остаются самостоятельными) и §13 (объединение исходников за пределами первого выпуска); ADR-007 §10 и таблица владения; ADR-008 §8–10; `docs/contracts/adapters.md` §4 (`LocalAiIndex` удаляется); `docs/integrations/status.md` (строка LocalAI снимается); `docs/architecture/unknowns.md` (X-04 и Q-13 закрываются как неприменимые); `docs/requirements-traceability.md` (C01, F05, новые F26–F28); карта этапов (D-020).

Ссылка на подтверждение владельца: сообщения владельца в сессии 2026-09-22 — «есть мысль в данный момент объединить два сервиса — localAI и текущий проект», «я предлагаю закрыть locus и продолжить работу внутри уже этого сервиса», «весь локус целиком, тендерхаб — делаем централизованное подключение для всех целей», «есть мысль чуть обрезать лишнее из локуса… подключение к стороннему lmstudio — если будет необходимо, вернём эту функцию».

### D-014 — Локальное распознавание как дополнительный движок

Дата / автор / основание полномочия: 2026-09-22 / владелец процесса + технический выбор / в рамках D-013.

Проблема: RDWeb распознаёт только PDF проектной документации. Договоры, допсоглашения, письма, `.docx` и `.xlsx` он не обрабатывает, поэтому договорному корпусу нечем попасть в индекс. При этом ADR-007 отвергает «повторный OCR в портале вместо RDWeb» как нарушение C01.

Принято:
- **движок `local_ocr` заводится рядом с `rdweb_export`, не вместо него.** Значение уже разрешено боевым DDL этапа 04 (`docs/migrations/0005_recognition_evidence.sql`, CHECK на `recognition_run.engine`), миграция колонки не нужна;
- покрываются форматы вне охвата RDWeb: текстовый слой PDF, `.docx`, `.xlsx`, `.csv`, сканы без текстового слоя;
- задание `local_ocr` не ставится на редакцию, у которой есть или ожидается завершённый прогон RDWeb; пришедший позже прогон RDWeb перекрывает локальный через существующий `supersedes_run_id`; при автоподборе прогона в снимок области локальный никогда не выигрывает у RDWeb;
- происхождение различается по I06: извлечённый текст документа — `document_text`, распознанный — `recognized_text`;
- координат у этих форматов нет. Интерфейс показывает текст и якорь страницы и прямо пишет, что координаты недоступны — по принципу D-011 «неверно нанесённая рамка хуже её отсутствия»;
- признаки непригодного текста и неполноты пишутся в `recognition_run.quality`; страница ниже порога не даёт статус `complete` (I18).

Приёмочный случай A43 («RDWeb недоступен, есть локальная предварительная обработка → явная маркировка качества и происхождения, не тихая подмена основной обработки») сформулирован именно под этот сценарий и остаётся гейтом.

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: ADR-007 (строка альтернатив сужается, добавляется принятая); ADR-004 (`resource_slot` получает класс `ocr`); `docs/requirements-traceability.md` (C01, новая F28); этап 05a.

**Уточнение D-021 (ревью 05-pre-1, AR05-08, 2026-09-28).** Отдельного класса `ocr` в ADR-004 нет: строка выше записывала намерение без протокола слота. Извлечение текста и распознавание на CPU — класс `default` с низким приоритетом, движок на GPU — класс `gpu` по существующему протоколу `resource_slot` (ADR-004 §7b). Отдельный слот вводится только поправкой ADR-004 с полной семантикой слота, если замеры 05a покажут вытеснение импорта. Смысл D-014 не меняется.

### D-015 — Собственный индекс портала, pgvector без ANN-индекса

Дата / автор / основание полномочия: 2026-09-22 / технический выбор в рамках D-013.

Проблема: ADR-008 §8–9 отдавал смысловой поиск внешнему LocalAI, а строка альтернатив отвергала «собственный векторный индекс портала» как второй RAG. После D-013 внешнего поставщика нет. Одновременно ADR-008 §5 требует фильтровать по разрешённым единицам источника **до** ранжирования, а постфильтрацию top-k запрещает (A42).

Принято:
- **индекс и смысловой поиск — внутри портала**, поверх неизменяемых `evidence_fragment`; адаптер `LocalAiIndex` удаляется;
- **векторы — pgvector в той же PostgreSQL**, тип `halfvec`, хранение без вынесения в TOAST, отдельная узкая таблица. Qdrant не вводится: это был бы второй сервис при прямом указании спецификации §3 не плодить их;
- **ANN-индекс не создаётся намеренно.** С HNSW планировщик превратил бы `ORDER BY … LIMIT` в обход индекса и применил бы `WHERE` к тому, что вернул обход, то есть после отбора — это нарушение A42. Точный перебор по уже отфильтрованной области даёт ровно требуемую семантику. Причина фиксируется в комментарии миграции и закрепляется тестом на плане запроса;
- измеренный порог возврата к вопросу: p95 векторной ветки выше 800 мс или устойчиво более 300 000 чанков в запросе. Раньше ANN применяются параллельный перебор и секционирование по тендеру; ANN — только отдельным ADR с измеренным recall;
- **область гарантируется схемой**: чанк связан с фрагментами составными внешними ключами по единице источника и тендеру, поэтому чанк из чужой единицы непредставим. Проверка ответа по БД остаётся второй линией;
- **смысловой поиск асинхронный**: сервер во внешние системы не ходит, поэтому точный и полнотекстовый результат возвращаются синхронно, а смысловой выполняется заданием класса `gpu`. Индексация берёт ограниченную пачку и ставит себя заново, чтобы не занимать единственный GPU-слот надолго;
- **реранкер не заводится.** Метрики Locus, принимаемые как приёмочные, получены офлайн без векторов и без реранкера — он их не доказывает. Переносится интерфейс шлюза и поведение при недоступности; решение по сервису — на целевом ПК по дельте качества против дельты задержки;
- **расширения PostgreSQL**: `vector` и `pg_trgm`. `CREATE EXTENSION` выполняет административное подключение в `packages/db/src/setup.ts`, миграция только проверяет наличие;
- **таблица эмбеддингов исключается из резервной копии по данным**: индекс — производные данные и пересобирается (продолжение ADR-011 §7).

Отдельная находка, ставшая гейтом: локальный кластер создаётся `scripts/pg-local.mjs` с `--locale=C`, из-за чего `lower()` и `to_tsvector('russian', …)` не приводят регистр кириллицы — «договор» не находит «Договор». Сегодня это ничего не ломает, потому что всё приведение регистра делается в JavaScript (`packages/core/src/paths.ts`), а в миграциях и `packages/db` нет ни `lower()`, ни полнотекстового поиска. Полнотекстовый поиск этапа 05 сломало бы тихо. Лечится локалью при создании базы, без пересоздания кластера.

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: новый ADR-012; ADR-008 §7–9 и таблица альтернатив; ADR-002 §1 (расширения, локаль); ADR-011 (установка расширения, состав копии, требование к кластеру); `docs/contracts/adapters.md` §4; `docs/requirements-traceability.md` F05; ключи `LOCALAI_URL`/`LOCALAI_TOKEN` удаляются на этапе 05 вместе с реализацией.

Ссылка на подтверждение владельца: выбор хранилища векторов и асинхронного смыслового поиска подтверждён владельцем в сессии 2026-09-22; остальное — технический выбор.

### D-017 — Договорной контур внутри портала

Дата / автор / основание полномочия: 2026-09-22 / владелец процесса / в рамках D-013.

Проблема: ежедневная польза Locus — ответы по действующим договорам выигранных тендеров (аванс, удержание, неустойка, сроки). Без этого корпуса Locus не закрыть. В модели Контура сущности «договор» нет: есть `tender` и значение `document.doc_type = 'contract'`.

Варианты и последствия:
- статус «выигран» у тендера — договор живёт годами после закрытия тендера и обрастает допсоглашениями; каждое ДС писало бы `stage_input_event` и через барьер актуальности переоткрывало готовность давно выпущенных этапов;
- надсущность «проект/объект» — четвёртая ось доступа над тендером, переписывающая `AccessContext`, все триггеры второй линии и ADR-006 целиком;
- отдельная сущность `contract` рядом с `tender` — изменение локальное, модель доступа берётся готовая.

Принято: **`contract` рядом с `tender`.** Надсущность «проект» остаётся в backlog.

- доступ строится по образцу уже принятого `mailbox_access` (ADR-006 §9–10): общий внешний корпус, явная выдача, администратор ведёт строки; возможности `contract.read`, `contract.write`, `admin.contract`;
- документы, редакции, прогоны распознавания и фрагменты получают необязательную принадлежность договору при обязательном ровно одном владельце — тендер или договор; составные внешние ключи дублируются по договору;
- связь договора с тендером подтверждает человек и **она не расширяет область поиска**: единицы договора лишь предлагаются кандидатами в состав источников этапа и ищутся только после явного включения в снимок. ADR-008 §10 остаётся в силе дословно.

Статус: accepted

Что изменяет в требованиях/контрактах/тестах: ADR-006 (новая ось изоляции, возможности, вторая линия); ADR-008 §10 (уточнение про кандидатов); `docs/architecture/data-model.md`; новая F26; этап 06a.

Ссылка на подтверждение владельца: ответ владельца «Да, договоры выигранных тендеров» на вопрос о корпусе (сессия 2026-09-22). Доступ по умолчанию и кардинальность связи с тендером владельцем ещё не подтверждены — открытые вопросы до этапа 06a.

**Уточнение D-022 (решения владельца по этапу 06a, 2026-09-29).** Связь с тендером — многие ко многим (OD-1); доступ — fail-closed, возможности `contract.create`, `contract.read`, `contract.link`, `contract.manage` вместо `contract.read` / `contract.write`; `admin.contract` только ведёт строки доступа, администратор без `contract.read` содержимого не видит (OD-2). Составные ключи дублируются по договору только там, где это доказано матрицей миграции (D-023, `docs/architecture/06a-ownership-chain.md` §7). Смысл D-017 не меняется.

### D-018 — Факты: прочитанное значение отдельно от производного состояния

Дата / автор / основание полномочия: 2026-09-22 / технический выбор в рамках D-013.

Проблема: Locus хранит факт одной строкой и мутирует её на месте при появлении допсоглашения. В Контуре прочитанное из документа значение неизменно, а производное состояние пересчитывается и может быть переопределено человеком.

Принято:
- **`evidence_fact` (immutable)** — что прочитано: тип, сырое и нормализованное значение, единица, ссылка на пункт, версия правил извлечения, прогон извлечения;
- **`fact_state` (mutable)** — что из этого следует: действует / перекрыт / конфликт, период действия, кто кого заменил, решено правилом или человеком;
- граф редакций (договор → допсоглашение → приложение) считается детерминированной функцией; неоднозначность не разрешается автоматически, а порождает замечание для человека;
- **защита I06 — триггером, а не дисциплиной кода**: фрагмент-основание обязан иметь `origin` из `document_text`, `recognized_text`, `email_body`, `attachment_text`. Факты не извлекаются из `model_description` (описание модели, не документ) и из речи переговоров (устное ≠ согласованное, I08);
- 13 типов фактов расходятся по трём судьбам: стороны договора — в карточку договора; цена договора и итог сметы — в экономику этапа 10; остальные девять — кандидаты в требования;
- чтобы это не нарушило I10–I12, `requirement_revision.origin` получает третье значение `rule_extraction`: детерминированная регулярка над процитированным фрагментом — программное правило, а не модель. Решение «этот пункт договора — требование этого этапа» остаётся человеческим, статус требования рождается кандидатом;
- покрытие извлечения измеряется и пишется в прогон; низкое покрытие даёт неполноту, а не «фактов нет» (I07).

### D-022 — Решения владельца по этапу 06a

Дата / автор / основание полномочия: 2026-09-29 / владелец процесса / ответ на preflight этапа 06a, статус READY_FOR_STAGE_06A.

Проблема: preflight 06a (статус BLOCKED_FOR_STAGE_06A) показал, что D-017 не задаёт кардинальность связи договора с тендером, доступ по умолчанию, соотношение снимка и права чтения, порядок относительно 05a и политику удаления, а капабилити D-017 не различают создание, чтение и связывание.

Принято:
- **OD-1 — многие ко многим.** Тендер может иметь несколько договоров, договор — относиться к нескольким тендерам. Связь хранится отдельной сущностью с собственным аудитом. `tender_id` не является обязательным владельцем документа договора. Связь с `tender_stage` — дополнительная и необязательная, если её требует этап. Принадлежность договора тендеру не выводится по имени, папке или косвенным признакам.
- **OD-2 — fail-closed.** Возможности `contract.create`, `contract.read`, `contract.link`, при необходимости `contract.manage` (архив и метаданные); они заменяют `contract.read` / `contract.write` из D-017. Строки доступа по-прежнему ведёт администратор (образец `mailbox_access`, D-017) — глобальной возможностью `admin.contract`, которая содержимого не открывает. Создатель получает доступ к созданному договору. Связь с тендером подтверждает пользователь с `contract.link`. Администратор не читает содержимое только из-за системной роли. Без `contract.read` доступны только минимальные административные метаданные: без текста, файла, фрагментов, результатов анализа, цитат и поисковой выдачи содержимого.
- **OD-3 — включение в снимок права чтения не даёт.** Нужно одновременно: `document_revision` входит в разрешённую область (`evidence_scope`) и у пользователя есть `contract.read`. Проверка — при поиске и повторно при чтении или проекции результата. Обход через Locus или поиск недопустим.
- **OD-4 — 06a до 05a.** Хранение, редакции, связи, права, аудит и интеграция с доказательствами для уже распознанного текста. `.docx` и сканы не распознаются; договор может существовать без текста для поиска. Тесты поиска — на фикстурных или существующих `recognition_run`.
- **OD-5 — физического удаления нет.** Только архив и замена новой редакцией. Редакции, участвовавшие в снимке, поиске, цитировании, выпуске или проверке, не удаляются. U-07 остаётся открытым.
- **T06A-1.** Отдельный `contract_snapshot` не создаётся: снимок фиксирует неизменяемый `document_revision_id`. Новая редакция не меняет исторический снимок; исторический поиск работает с зафиксированной редакцией.
- **T06A-2.** Единая модель `document` / `document_revision`. Роли — минимум `contract`, `addendum`, `appendix`; допсоглашение и приложение связаны с основным договором явной ссылкой. Отдельных хранилищ и конвейеров по типам нет.
- **T06A-3.** `contract_id` / `owner_type` не добавляются механически во все таблицы от распознавания до индекса. Сначала проверяется цепочка «связь договора → `document` → `document_revision` → `recognition_run` → `evidence_fragment` → индекс»; права ниже редакции выводятся через неё. Расширение около десяти таблиц — только если доказано, что цепочка не обеспечивает инвариант, и только отдельным архитектурным решением до миграции. Результат проверки — `docs/architecture/06a-ownership-chain.md`: цепочка строки договора ниже редакции не принимает, нужно решение AD-06a-1.
- **Порядок реализации:** ветка `stage-06a` от принятого `stage-06`; переиспользование blob / document / document_revision / recognition / evidence / search; связи и возможности; fail-closed поиск; история редакций; аудит; без OCR (05a), без юридического анализа моделью, без изменений этапа 06.
- **Обязательные тесты:** один договор ↔ один тендер, два договора ↔ один тендер, один договор ↔ два тендера; отсутствие связи, создание, изменение и архивирование связи; пользователь без `contract.read`, администратор без `contract.read`, пользователь с `contract.read`; договор в снимке без права и с правом; право отозвано после построения индекса; старая редакция остаётся в историческом снимке, новая её не подменяет; `contract` / `addendum` / `appendix` и связь приложения с основным договором; повторная загрузка того же файла, то же имя при другом содержимом, конкурентная загрузка; архив без физического удаления; договор без `recognition_run` и с фикстурным; отсутствие утечки через поиск и цитирование.
- **Передача:** полный набор тестов, typecheck, build, smoke, UI-check этапа 06a, регрессия этапов 02–06, негативные проверки прав, инварианты БД, отдельная регрессия утечки через поиск; отчёт и ZIP на Review 06a-1; следующий этап самостоятельно не начинается.

Смысл D-017 сохраняется: `contract` рядом с `tender`, связь подтверждает человек и она не расширяет область поиска, ADR-008 §10 в силе.

**Уточнение Review 06a-1 (2026-09-29): подтверждённые интерпретации — часть контракта этапа 06a** (`docs/reviews/06a-review-1.md`):

### D-023 — AD-06a-1: владение договора — явный `contract_id` (вариант B)

Дата / автор / основание полномочия: 2026-09-29 / владелец процесса / решение AD-06a-1 по проверке T06A-3 (`docs/reviews/06a-arch-decision-1.md`).

Проблема: проверка T06A-3 показала, что цепочка «документ → редакция → прогон → фрагмент → индекс» привязана к `tender_id NOT NULL` и составным FK по тендеру; строку договора ниже редакции записать нельзя (`docs/architecture/06a-ownership-chain.md` §2–3).

Варианты: A — у строк договора `tender_id` = NULL, принадлежность восстанавливают триггеры; B — явный `contract_id` и составные FK по договору.

Принято: **вариант B**, вариант A отклонён (неявный владелец «NULL = договор», nullable-владение ниже по цепочке, права труднее доказать в БД, одна ошибка охранника ломает весь контур).

- Колонка владельца ниже по цепочке добавляется только там, где она нужна для самостоятельного инварианта БД, уникальности, внешнего ключа или безопасного запроса, — и каждая обоснована в матрице миграции (§7 документа проверки), не «для удобства JOIN».

- Допсоглашение и приложение — самостоятельные документы того же `contract_id` с явной ссылкой на основной документ договора.
- Масштаб: изменение схемы только ради владения договора, без перепроектирования этапов 03–05; новое изменение фундаментальных инвариантов 03–05 — остановка и отдельное решение.

### D-024 — Решения владельца по этапу 05a

Дата / автор / основание полномочия: 2026-09-30 / владелец процесса / ответ на preflight этапа 05a (статус BLOCKED_FOR_STAGE_05A), текст решения — `docs/reviews/05a-owner-decisions.md`.

Проблема: preflight 05a показал, что норматив не проводит границу RDWeb и локального распознавания для PDF, не задаёт способ постановки, охват договоров и форматов, OCR-движок и языки, порог качества, использование Locus, а схема этапа 04 не вмещает страницы без пиксельной геометрии, идентичность локального прогона и второй линии приоритета RDWeb.

Принято:
- **OD-1 — маршрут PDF fail-closed.** Явная политика `rdweb` / `local` / `auto`; эвристики «PDF — значит RDWeb» и угадывания по имени, тендеру, папке или содержимому нет. PDF, пришедший импортом RDWeb, относится к `rdweb`; имеющийся успешный прогон RDWeb локальный не вытесняет. Для PDF без доказанного происхождения RDWeb локальное распознавание — только при политике `local` или по явной команде пользователя; при `auto` конкурирующий локальный OCR молча не запускается.
- **OD-2 — запуск гибридный.** `.docx`, `.xlsx`, `.csv` — автоматически; PDF — по явной политике `local`, ручной команде или иному доказанному нормативному источнику. Повтор той же редакции с той же версией распознавателя и конфигурацией идемпотентен.
- **OD-3 — договоры входят в 05a.** Результат — `document_revision → recognition_run → структурный текст и фрагменты` в существующем контуре доказательств и поиска; права 06a сохраняются полностью, распознавание договора `contract.read` не выдаёт. Юридического анализа, извлечения условий, оценки рисков, ответов ИИ, сравнения договоров и выводов нет.
- **OD-4 — закрытый перечень форматов:** PDF (только локальный маршрут по OD-1), DOCX, XLSX, CSV. `.doc`, `.xls`, изображения как самостоятельные документы, ODT, RTF, PPT/PPTX, архивы, почта и иные форматы не входят; для них — явный `unsupported_format`.
- **OD-5 — OCR только без пригодного текстового слоя.** DOCX, XLSX, CSV и текстовый PDF не распознаются OCR; у PDF сначала извлекается встроенный текст, OCR — для страниц без достаточного текстового слоя. Движок — за контрактом адаптера `LocalOcrEngine` (идентификатор и версия движка, модель, языки, хэш конфигурации); первый рабочий адаптер — локальный движок, устанавливаемый на целевом Windows-ПК, без облачных API, сети и несовместимой лицензии, выбор — после короткого spike на фикстурах. Языки — `ru` и `en`.
- **OD-6 — качество.** Технический успех и качество разделены; итоговые статусы `complete`, `needs_review`, `failed`. Уверенность OCR — диагностическая метрика, не единственный критерий. Числовой порог фиксируется только после замера корпуса фикстур Locus и 05a с показом распределения метрик; начала разработки разборщиков это не блокирует.
- **OD-7 — Locus как донор.** Переиспользовать проверенные части (OCR-адаптер, извлечение текста, разбор DOCX, XLSX, CSV, нормализация, метрики качества) с сохранением происхождения и тестами Контура; зависимости во время работы от Locus, его интерфейса, поиска, бизнес-логики и состояния БД нет. Источник требований — контракт Контура.
- **AD-05a-1 — единица источника вместо фиктивной страницы.** Модель страницы расширяется видом единицы (`unit_kind`): у физической страницы PDF размеры обязательны, у логической (лист XLSX, таблица CSV, тело DOCX) отсутствуют; структурный якорь фрагмента хранится типизированно. Размеров вида `1 × 1` нет. Если это невозможно без фундаментальной переделки этапов 04–05 — остановка до миграции.
- **AD-05a-2 — источник локального прогона — неизменяемая редакция.** Идентичность: редакция, SHA-256 оригинала, распознаватель и его версия, хэш конфигурации, формат, языки, способ обработки. Пути, временные папки и имена файлов в идентичность не входят.
- **AD-05a-3 — «действительный RDWeb выше локального».** Правило выбора детерминированно и защищено второй линией (функция или охранник БД), обойти его прямым прикладным вызовом нельзя; время создания, номер задания и порядок worker правилом не являются. Ручного переопределения спецификация не предусматривает.
- Настоящая синтетическая `.xlsx` — детерминированная, с несколькими листами, текстом, числами, пустыми ячейками, формулой, русским текстом; структура случаев 10, 14, 15 манифеста Locus воспроизводится.
- `packages/adapters/src/rdweb/import.ts` (504 строки) — не блокер; нового кода 05a в нём нет, косметического рефакторинга нет.
- Граница и обязательные проверки — по тексту решения (23 пункта); порядок: решения, ветка `stage-05a` от `007dd13`, проект миграции, реализация, полный набор тестов, отчёт, ZIP, Review 05a-1; этап 07 не начинается.

Проект миграции и технические уточнения (маршрут в `document`, отпечаток считает БД, `needs_review` прогона — статус `partial` с единицами `needs_review`, вид движка `local_ocr` для всех локальных прогонов) — `docs/architecture/05a-local-recognition-design.md`.


**Уточнение Review 05a-1 (2026-09-30): подтверждённые интерпретации — часть контракта этапа 05a** (`docs/reviews/05a-review-1.md`):

2. движок `local_ocr` — у всех локальных прогонов; способ обработки — в описании распознавателя;

5. автоматическую постановку отличает отсутствие `created_by`; автоматический PDF при `auto` так запрещён;
