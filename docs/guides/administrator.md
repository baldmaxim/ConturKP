# Руководство администратора

Для администратора портала и целевого ПК. Подробности и команды — в runbooks; здесь порядок и ссылки. Значения секретов (пароли, ключи, токены, строки подключения) в документы, журналы и чат не пишутся.

Документы:
- установка, службы, обновление, неисправности — `docs/runbooks/release.md`;
- копии и восстановление — `docs/runbooks/backup-restore.md`;
- чат-клиенты — `docs/integrations/mcp-clients.md`;
- статусы интеграций — `docs/integrations/status.md`;
- LibreOffice и шрифты образцов — `docs/runbooks/libreoffice.md`.

Администратор управляет пользователями, тендерами и настройками, но **содержимое тендеров без назначения не видит** (разделение по ролям).

## 1. Установка

Целевой ПК — Windows-ПК в офисе; сотрудники открывают `https://<IP ПК>:3200`. Порядок (release runbook §0–§9):
1. Осмотр ПК: `npm run ops:preflight` (отчёт без секретов).
2. Каталоги кода, окружения, хранилища и копий (§3). Копии — на другом физическом диске или сетевом ресурсе.
3. Код: ZIP сборки, `npm ci`, `npm run build`; в файл окружения — `KONTUR_BUILD=<полный коммит>`.
4. PostgreSQL 18 нативной службой с `pgvector` и `pg_trgm`, порт 5433 (§5, вариант А). Docker — только для тестовых кластеров.
5. Файл окружения вне каталога кода (§6); проверка `config:check`.
6. TLS: сертификат mkcert на IP ПК; корень `rootCA.pem` — на компьютеры и телефоны сотрудников (§7).
7. Брандмауэр: порт портала — только локальная подсеть, порт PostgreSQL наружу не открывается (§8).
8. `db:setup` → `db:migrate` → `bootstrap` (первый администратор); затем удалить из файла окружения `DATABASE_ADMIN_URL` и пароли ролей `KONTUR_*_DB_PASSWORD` (§9).
9. Требования: Windows 10/11 x64 без сна от сети, Node.js 24.11+ (не 25), LibreOffice, WinSW 2.12.0, mkcert, LM Studio (если модель на этом ПК).

## 2. Службы

1. `npm run ops:service -- render …` → `install` → `start` (§10). Службы `kontur-server` и `kontur-worker`, зависимость от службы PostgreSQL.
2. Учётные записи служб задаются в оснастке «Службы». Worker — запись с доступом к папкам размещения и шрифтам; ей нужно право «Вход в качестве службы». При смене пароля записи ввести новый пароль в оснастке.
3. **S17-27 — отложенный старт.** Сборка `509857a` и более ранние ставили службам отложенный автозапуск: после перезагрузки они поднимались только со входом пользователя в Windows. С этапа 18 шаблон служб исправлен (`delayedAutoStart=false`). У ранее установленных служб снимите задержку: `sc.exe config kontur-server start= auto` и `sc.exe config kontur-worker start= auto`; проверка — `Get-CimInstance Win32_Service -Filter "Name LIKE 'kontur-%'" | Select Name,StartMode,DelayedAutoStart` → `Auto`, `False` (§10).
4. Проверка после перезагрузки **без входа** в систему: через 5 минут с другого компьютера `/api/v1/ready` → 200 (§11).
5. Остановка и сбои: штатная остановка возвращает задания в очередь без потери попытки; при сбое WinSW перезапускает процесс; принудительное завершение — задания возвращаются в очередь за ~4 минуты (§11).
6. Журналы: `logs\kontur-server.*.log`, `kontur-worker.*.log` (ротация 10 МБ × 8), секретов и текстов документов в них нет.
7. LM Studio работает в сеансе пользователя: без входа смысловой поиск и ответы честно недоступны (§12).

## 3. Копии и восстановление

1. Копия: `npm run ops:backup` вручную и перед каждым обновлением; ежедневно — задача планировщика `ops:service -- backup-task` (release §13). Последняя копия видна в «Администрирование» → «Состояние».
2. Копия — дамп базы и файлы хранилища на одном снимке, SHA-256 всех файлов, манифест `kontur.backup.v1`. Каталог без манифеста — незавершённая копия. Зеркала Яндекс Диска и сетевой папки копией не считаются.
3. Ничего не удаляется автоматически. Срок хранения — решение владельца (В-17-3).
4. Проверка восстановления: `npm run ops:restore-check` — только в **чистом** окружении (отдельный кластер PostgreSQL и пустой каталог), никогда поверх рабочей системы (`backup-restore.md` §3).
5. Аварийное восстановление на новом ПК: `backup-restore.md` §4; после него интеграции проверяются заново — `VERIFIED_LIVE` из копии относится к прежней установке.

## 4. Интеграции и живые проверки

Состояние: «Администрирование» → «Состояние» → «Интеграции». Статусы: «Проверена живьём», «Только на поддельных данных», «Нужна доработка другой системы», «Нет адаптера».

1. Обязательный живой набор для ввода: TenderHub, импорт EML, Яндекс Диск и SMB, OCR, LibreOffice, LM Studio с эмбеддингами, Codex и Cursor по HTTPS, iPhone и Android (release §15).
2. Каждая проверка пишет журнал с отметкой «Режим: LIVE», коммитом сборки и «Итог: PASS». Статус в базе записывает `npm run ops:integration-verify` (журнал другой сборки и фикстурный не принимаются).
3. TenderHub: адрес и ключ `X-API-Key` — только в файле окружения; ключ с минимально нужной областью доступа. Связь этапа с тендером TenderHub («Расчёт» → «Связать с TenderHub») задаёт администратор.
4. Яндекс Диск и сетевая папка: «Администрирование» → «Назначения размещения» → «Новое назначение» (корень, служебная папка, состав — только файлы для заказчика или все) → «Проверить назначение». Тестовые и боевые назначения разделяйте. Яндекс Диск — через локальную папку синхронизации; доставку в облако подтверждает человек.
5. Почтовые ящики: «Почта» → «Зарегистрировать ящик» и выдача доступа (чтение, импорт, связь). Автоматического чтения MailHub нет (X-03).
6. Договоры: «Администрирование» → «Создание договоров» — кто может создавать договоры; связь с тендером выдаётся отдельным правом.
7. Наблюдаемые папки: вкладка тендера «Каналы поступления» → «Добавить папку».
8. Модель и эмбеддинги — через LM Studio на loopback (release §12); измерение — `npm run model:live-smoke`.
9. Отказ интеграции виден без секретов: `AUTH_FAILED` — ключ, `UNAVAILABLE` — сеть или DNS.

## 5. Пользователи, роли, тендеры

1. «Администрирование» → «Пользователи» → «Создать пользователя»: логин, имя, роли, начальный пароль (не короче минимума; передаётся лично). «Изменить» — роли и статус (отключённый пользователь теряет доступ), «Сбросить пароль».
2. Роли: «Администратор», «Руководитель», «Инженер». Администратор не получает доступа к содержимому тендеров без назначения.
3. Тендер создаёт администратор («Тендеры» → «Создать тендер»: код, название). Участников назначает администратор: вкладка «Участники» → «Назначить». Не больше двух инженеров на тендер; роль в тендере должна совпадать с ролью пользователя.
4. Снятие роли сразу лишает прав по тендерам.
5. «Журнал вне тендеров» — входы и изменения пользователей; журнал тендера — вкладка «Журнал» тендера.
6. Пользователь сам меняет пароль («Сменить пароль»).

## 6. Токены чат-клиентов

1. Включение: `MCP_ENABLED=true` в файле окружения (по умолчанию выключено), перезапуск server.
2. Токен выпускает сам инженер или руководитель: шапка → «Доступ для чат-клиентов» → «Выпустить токен» (название, клиент, срок 7/30/90 дней, право предлагать). Значение показывается один раз; в базе не хранится.
3. Настройка Codex и Cursor — `mcp-clients.md`: адрес `https://<IP ПК>:3200/mcp`, токен — в переменной окружения клиента, а не в файле настроек. Корень mkcert должен быть доверенным на компьютере клиента.
4. Отзыв токена — «Отозвать» в том же окне (клиент сразу получает 401). Отключение пользователя тоже закрывает токены.
5. Чат читает только материалы тендеров пользователя; согласования, выпуска, отправки через него нет.

## 7. Схема обновления

Основа — release runbook §14. Порядок:
1. **Копия** перед обновлением: сначала остановить службы (`ops:service -- stop`), затем `npm run ops:backup`. Убедиться, что копия завершена (есть манифест). Первое обновление установки этапов 14–16 на 17 — `ops:backup -- --pre-update`.
2. **Новая сборка:** распаковать ZIP поверх кода (каталоги `services`, `logs` сохраняются), `npm ci`, `npm run build`, обновить `KONTUR_BUILD` на новый полный коммит.
3. **Миграции:** `db-migrate` с файлом окружения. Отката схемы нет.
4. **Службы:** `ops:service -- render …` (если менялись параметры служб), `ops:service -- start`. Службы, установленные до исправления S17-27, сохраняют отложенный старт, пока его не снимут (§2 п. 3).
5. **`ready`:** `/api/v1/ready` → 200, все проверки `ok`; «Состояние»: сборка и схема новой версии.
6. **Живые проверки** по набору, затронутому изменением (§4): повторять на новой сборке; журнал другой сборки статус не повышает.
7. Неудача на любом шаге после миграций — восстановление из копии шага 1 в чистое окружение (`backup-restore.md` §4), не поверх рабочей базы.

## 8. Неисправности

| Признак | Где смотреть | Действие |
|---|---|---|
| `/ready` 503, `schema` | «Состояние» → Установка | `db:migrate` новой сборкой |
| `/ready` 503, `worker` | журнал worker | запустить службу worker; при зависании — перезапуск |
| `/ready` 503, `queue` | «Состояние» → Очередь | перезапустить worker |
| `/ready` 503, `storage`: «запись остановлена» | «Состояние» → Хранилище | освободить место; задания продолжатся сами |
| Загрузка: «Нет места в хранилище» (507) | то же | то же |
| Интеграция — «Последняя ошибка» | «Состояние» → Интеграции | `AUTH_FAILED` — ключ; `UNAVAILABLE` — сеть или DNS (причина — в журнале worker) |
| Службы не поднялись после перезагрузки | `Win32_Service`, журнал | снять отложенный старт (§2 п. 3); база должна подниматься сама |
| Телефон не открывает портал | сертификат, брандмауэр | корень mkcert на устройстве; правило порта; профиль сети не «Общедоступная» |

Остальные признаки — `release.md` §16.

## 9. Пороги и объёмы

SLO первой версии действуют только для профиля D-040 (10 000 позиций, ~30 000 строк, до 1 ГиБ Markdown) — `limitations-v1.md`. Порог свободного места: предупреждение 10 ГБ, остановка записи 2 ГБ (`STORAGE_WARN_FREE_MB`, `STORAGE_STOP_FREE_MB`).
