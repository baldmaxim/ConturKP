# Внешние доработки

Что нужно сделать в соседних системах, чтобы снять ограничения портала. Портал соседние системы не переписывает (C02): каждая доработка — отдельное задание владельцу системы. Источники: `docs/architecture/unknowns.md` §3, `docs/integrations/status.md`.

Состояние на 2026-10-21 (после приёмки этапа 17, D-042). Владельцы доработок пока не назначены.

| ID | Система | Статус в портале | Блокирует |
|---|---|---|---|
| X-01 | TenderHub — ревизия и закрытие расчёта | `BLOCKED_EXTERNAL` | снятие `CALCULATION_PROVISIONAL` у источника |
| X-02 | TenderHub — lineage позиций | открыт, обход есть | точность сравнения этапов |
| X-03 | MailHub — сервисное чтение | `BLOCKED_EXTERNAL` | автоматический импорт писем и подтверждение отправки |
| X-05 | RDWeb — документированный API | `BLOCKED_EXTERNAL` | автоматическая постановка распознавания |
| Q-06 | Сервис переговоров — API | `BLOCKED_EXTERNAL` | автоматический импорт переговоров |
| Q-02, Q-07 | RDWeb: схемы экспорта; MailHub: ящики | открыты | см. ниже |

## X-01. TenderHub: ревизия и закрытие расчёта

**Нужно от владельца TenderHub:**
- неизменяемый снимок ревизии расчёта по идентификатору;
- статус закрытия и состояние расчёта и согласования в API (чтобы портал читал его, а не имитировал);
- событие изменений (закрытие, переоткрытие) либо возможность опроса с позицией синхронизации;
- исправление после закрытия — новой ревизией.

**Что даст порталу:**
- адаптер `TenderHubRevisionReader` отдаёт ревизии со статусом `verified`;
- блокер `CALCULATION_PROVISIONAL` снимается по данным источника, а не по решению руководителя;
- закрытие по сроку подачи берётся из TenderHub, портал свой таймер не строит.

**Пока нет:** портал выгружает расчёт по официальному API как предварительную ревизию. Закрытым без X-01 считается ревизия, зафиксированная отзывным решением руководителя на одну ревизию (D-044). Это не подтверждает закрытие в самом TenderHub, статус X-01 остаётся `BLOCKED_EXTERNAL`.

## X-02. TenderHub: lineage позиций между версиями

**Нужно:** сохранение связи позиций при копировании версии (постоянный идентификатор позиции между версиями).

**Что даст:** сравнение этапов и причины изменения цены без ручного подтверждения пар позиций.

**Пока нет:** портал предлагает пары по ключу TenderHub и номеру позиции, подтверждает инженер (в том числе пакетом).

## X-03. MailHub: сервисное чтение

**Нужно от владельца MailHub:**
- машинный доступ (сервисная учётная запись) вместо сессии человека с cookie и CSRF;
- чтение без изменения прочитанности;
- курсор изменений, полная пагинация цепочки;
- Message-ID писем и байты или SHA-256 вложений;
- перечень отправленных писем ящика;
- ответ по Q-07: какие ящики доступны порталу, допустима ли локальная копия писем.

**Что даст:**
- `MailHubMailboxReader`: автоматический импорт писем;
- `MailHubSentReader`: автоматическое подтверждение отправки комплекта с проверкой вложений.

**Пока нет:** письма загружаются файлами EML вручную; отправка регистрируется вручную (письмо из почты портала, файл-основание или пояснение).

## X-05. RDWeb: документированный API (и Q-02)

**Нужно от владельца RDWeb:**
- документированный API постановки и получения распознавания;
- ответ по Q-02: другие варианты схемы экспорта, срок хранения вырезок, допустимость передачи документов во внешнюю обработку.

**Что даст:** автоматическая постановка распознавания проектной документации вместо ручной загрузки экспорта. Сейчас реализован только импорт архива экспорта; по решению владельца он на паузе, живая работа с настоящим экспортом не проверялась.

## Q-06. Сервис переговоров

**Нужно:** определить проект и API сервиса, место хранения аудио и права доступа.

**Что даст:** автоматический импорт сессий, транскрипций и подсказок. **Пока нет:** импорт файла `kontur.negotiation.v1`.
