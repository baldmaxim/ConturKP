# Руководство руководителя

Для руководителя тендера: состав и этапы, подтверждение требований, решение о закрытом расчёте, формы, согласование, контроль выпуска. Работу инженера описывает `engineer.md`; ограничения — `limitations-v1.md`.

Руководитель согласует конкретный комплект или возвращает его на доработку. Модель согласовать выпуск не может. Выпускает инженер.

## 1. Что решает руководитель

| Действие | Где |
|---|---|
| Создать этап | Тендер → «Этапы» → «Создать этап» |
| Создать реестр требований, подтвердить или отклонить кандидатов, завершить проход полноты | Этап → «Требования» |
| Принять риск по замечанию, задать приоритет источников | Этап → «Разногласия»; тендер → «Приоритет источников» |
| Решение о закрытом расчёте и его отзыв | Этап → «Расчёт» (§3) |
| Шаблоны, ревизии шаблонов, формулировки, стандартные вложения | Раздел «Шаблоны» (§4) |
| Согласовать, вернуть, отозвать согласование, принять риск блокера, решить по событиям | Этап → «Комплект» (§6) |
| Принять лишние вложения письма об отправке | Выпуск → «Отправка» (§9) |
| Исход отклонённого при загрузке файла («неприменим») | Этап → «Импорт» → партия |

## 2. Состав тендера

1. Тендер создаёт и участников назначает **администратор** портала (вкладка тендера «Участники»; руководитель список видит, но не меняет). Роль в тендере должна совпадать с ролью пользователя в портале.
2. В тендере не больше двух инженеров и один руководитель. Попытка назначить третьего инженера отклоняется.
3. Снятие участника лишает его доступа к материалам тендера сразу.
4. Журнал тендера («Журнал») виден руководителю полностью: входы, согласования, решения, отзывы.

## 3. Закрытый расчёт (Q-01, D-044)

Расчёт, выгруженный порталом из TenderHub, — **предварительная** ревизия: TenderHub пока не отдаёт неизменяемую закрытую ревизию (X-01). Пока ревизия предварительная, боевой выпуск запрещён (блокер `CALCULATION_PROVISIONAL`). Решение руководителя заменяет закрытие внутри портала; в самом TenderHub закрытие это не подтверждает.

Правила:
- решает и отзывает только руководитель тендера; инженер и модель — нет;
- решение — на **одну ревизию** с обязательной причиной; новая выгрузка даёт новую ревизию, она не закрыта;
- на ревизию не больше одного действующего решения;
- комплект закрепляет решение при сборке. Решение нужно принять **до** сборки комплекта;
- отзыв после закрепления делает вход комплекта устаревшим; отзыв до выпуска блокирует согласование и выпуск; выпущенное не меняется, история показывает отзыв.

Порядок (этап → «Расчёт», панель решения у ревизии):
1. Инженер выгрузил расчёт («Расчёт» → «Выгрузить расчёт»).
2. Проверьте ревизию: «Экономика» — сверка с итогом TenderHub, остаток, строки вне допуска.
3. «Расчёт» → ревизия → «Зафиксировать как закрытый расчёт» → причина → подтвердить. Всем участникам показывается отметка «Закрыт решением руководителя (дата, кто)».
4. Передумали — «Отозвать» с причиной; показывается «Решение отозвано». Нужен новый комплект.
5. Появилась новая выгрузка — решение к ней не относится, повторите шаги 2–3.

## 4. Реальные формы и снятие демо-шаблона (Q-08)

Демонстрационный шаблон помечен «демо»; в боевой комплект он не допускается (блокер `TEMPLATE_DEMO`). Признак «демо» у шаблона не меняется — нужен **новый** шаблон без этого признака.

1. Владелец проверяет реальные формы компании и заказчика (вне портала): схему полей, размеченную копию образца (DOCX/XLSX) и формулировки.
2. Создайте шаблон: «Шаблоны» → «Шаблоны приложений» → «Новый шаблон компании», флажок «Демонстрационный (не для выпуска)» снимите → «Создать». Шаблон заказчика для тендера загружает администратор загрузчиком `forms-load.mjs` с параметром тендера.
3. Загрузите ревизию схемы черновиком: в карточке шаблона «Ревизии» → «Загрузить ревизию» (файл схемы `forms/1`; для генерации файла — «С образцом»: оригинал, размеченная копия, аудитория «Заказчику»/«Внутреннее»). Альтернатива — загрузчик `forms-load.mjs` (запускает администратор). Ошибки разметки показаны списком; ревизию с ошибками утвердить нельзя.
4. Проверьте результат и нажмите «Утвердить» у ревизии.
5. Формулировки: «Утверждённые формулировки» → «Утвердить» предложенные, «Вывести» устаревшие.
6. Стандартные вложения: «Стандартные вложения комплекта» → «Новое вложение» → «Утвердить».
7. Инженеры создают черновики приложений **на новой ревизии** (старые черновики на демо-шаблоне не переносятся: «Перенести» работает между ревизиями одного шаблона).
8. Просмотр страниц собранного файла человеком обязателен: превью — тот же файл, что согласуется.

Когда все приложения комплекта на утверждённых недемонстрационных шаблонах, блокер `TEMPLATE_DEMO` не ставится.

## 5. Требования и проверки

1. «Требования» → «Создать реестр» (закрепляется на снимке области, нужна причина). Новый снимок — «Перенести на новый снимок».
2. «Кандидаты»: «Подтвердить» (формулировку можно уточнить), «Отклонить» (причина). При конфликте с действующим требованием подтверждение — только с пояснением.
3. «Полнота»: после просмотра всех фрагментов — «Завершить проход полноты». Не просмотренное не считается проверенным.
4. «Допущения и вопросы»: допущения ПД — «Подтвердить»/«Отклонить»; вопросы заказчику — статусы «Черновик», «Отправлен», «Ответ получен», «Закрыт».
5. Замечания: «Принять риск» — формулировка принимаемого риска и причина. Принятый риск остаётся виден, замечание не закрывается; техническое замечание риском не принимается.
6. Ответы и гипотезы модели — только после решения человека.

## 6. Согласование

1. «Комплект» → откройте кандидата со статусом «готов к согласованию». Проверьте:
   - режим (тестовый/боевой);
   - ревизию расчёта (предварительная/подтверждённая решением);
   - прогон проверок (завершён или с пробелами);
   - приложения и их шаблоны;
   - файлы и превью PDF;
   - принятые риски и решения по событиям.
2. Блок «Согласование: что мешает» перечисляет блокеры. Неснимаемые устраняет инженер. Бизнес-блокеры снимаются «Принять риск…» по каждому пункту с причиной: принятие действует только для этого комплекта, пункт остаётся видимым.
3. Появились события после сборки (новый документ, письмо, правка поля): раздел «Решения по событиям» → отметьте события → «Не влияет…» (с основанием; комплект остаётся) или «Влияет…» (невыпущенный комплект возвращается, согласование отзывается; у выпущенного отправка исключается навсегда).
4. «Согласовать…» → проверьте состав в окне → «Согласовать комплект № N». Согласование привязано к SHA-256 манифеста именно этого содержимого. Правка поля после согласования создаёт новый комплект; старое согласование к нему не применяется.
5. «Вернуть на доработку…» — укажите, что исправить. «Отозвать согласование…» — до выпуска, с причиной; запись остаётся в истории.
6. Выпускает инженер («Выпустить…»). После выпуска согласование не отзывается.

## 7. Тестовый и боевой выпуск

| | Тестовый | Боевой |
|---|---|---|
| Метка в файлах | «ТЕСТОВЫЙ ВЫПУСК — НЕ ДЛЯ ОТПРАВКИ ЗАКАЗЧИКУ» | нет |
| Отправка заказчику | невозможна («Тестовый — не отправляется») | возможна после выпуска, если готовность `ready` |
| Блокеры расчёта, форм и итога КП | не применяются | применяются |
| Размещение в папки | можно (в тестовое назначение) | можно |

Если тестовый комплект всё же ушёл заказчику, инженер регистрирует «нарушение» (§9).

Боевой комплект с неснятыми блокерами (§8) собирается, но согласовать и выпустить его нельзя. Окончательно проверяет сервер при действии.

## 8. Блокеры боевого выпуска

| Код | Что значит | Как снять |
|---|---|---|
| `CALCULATION_PROVISIONAL` | ревизия расчёта предварительная (выгрузка портала), закрытие у источника не подтверждено (Q-01/X-01) | действующее решение руководителя о закрытом расчёте на эту ревизию, закреплённое в комплекте (§3); пересобрать комплект |
| `TEMPLATE_DEMO` | в комплекте приложение на демонстрационном шаблоне (Q-08) | перейти на утверждённый недемонстрационный шаблон (§4); приложения на новой ревизии; пересобрать |
| `KP_TOTAL_NOT_APPROVED` | не задано правило итога КП (Q-05) | правило D-044 «итог TenderHub, НДС включён» ставится при выгрузке расчёта, если TenderHub отдал итог. Без итога источника блокер остаётся: нужна новая выгрузка, итог должен появиться |
| `KP_TOTAL_UNRECONCILED` | итог КП не подтверждён сверкой: экономика этой ревизии не «сходится» (итог TenderHub отстаёт от строк или остаток вне допуска) | не снимается принятием риска. Разберите «Экономика» → «Неподтверждённый остаток», строки вне допуска; при необходимости новая выгрузка и новая ревизия. Толкование блокера — на проверке владельца и ревьюера (D-044) |

Остальные блокеры: см. список в блоке «что мешает». Неснимаемые — полномочия, технические (устаревшие проверки, несовпадение файлов), целостность. Снимаемые принятием риска по пункту — непокрытые требования, открытые критичные замечания, вопросы без ответа, незавершённые поля, несверенные числа.

Пока блокеры Q-01/X-01, Q-05, Q-08 не сняты полностью, продукт к боевой эксплуатации не допущен (решение владельца).

## 9. Размещение, отправка, сравнение

Размещение, отправка и сравнение — отдельные события. «Размещено» не означает «отправлено заказчику».

**Размещение** (выпуск → «Размещение»)
1. Назначения (Яндекс Диск через локальную папку синхронизации и сетевая папка) настраивает администратор; тестовые и боевые назначения разделены.
2. Выпуск → «Разместить в новые назначения (N)». Файлы пишутся точными байтами из хранилища, чтение назад сверяется по SHA-256 и размеру. Ошибка одного назначения другое не отменяет.
3. «Повторить…», «Повторить после проверки…» (после ручной уборки папки), «Перенаправить…» (новая версия путей) — с причиной.
4. «Подтвердить облако…»: портал видит только локальную папку Яндекс Диска. Подтверждение, что папка появилась в облаке и содержимое совпало, делает человек; отменить его нельзя.
5. Во внутренние назначения разместит только тот, кому открыты основания решений в манифесте выпуска.

**Отправка** (выпуск → «Отправка»)
1. Портал письма не отправляет и рассылку не делает. Он только регистрирует факт отправки, уже выполненной вне портала. Регистрирует инженер («Зарегистрировать отправку…»): письмо из почты портала (вложения сверяются с комплектом по SHA-256), файл-основание или пояснение.
2. «Состав не совпал» не засчитывается как отправка. Лишние вложения при полном комплекте (например, картинка подписи) принимает руководитель: «Принять лишние вложения…», причина, отмена невозможна. Принять может тот, кто сам читает письмо.
3. Новые события после отправки: повторная отправка — только после вашего решения.
4. Запись отправки не подтверждает получение или согласие заказчика.

**Сравнение** (тендер → «Сравнение выпусков»)
1. Выберите «Первый выпуск» и «Второй выпуск» → «Сравнить».
2. Сравнение идёт по записям, закреплённым в выпусках: источники, требования, расчёт, вопросы, условия, решения, приложения; отдельно — что получено между выпусками.
3. Причины изменения цены: подтверждено / гипотезы / не установлено; необъяснённый остаток показан явно. Разложение по позициям — «Экономика» этапа.
