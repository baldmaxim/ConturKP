## Новый дефект

### R01-09 · P1 · Завершённый импорт с потерянными документами считается покрытым

Основное место: `docs/architecture/state-machines.md:46`.
Связанные места: `state-machines.md:60`, `:199–200`, `:261`; `docs/architecture/data-model.md:174–175`.

Новое правило считает событие `import_accepted` покрытым, если партия имеет статус `completed` **или `completed_with_errors`** и покрыты все зарегистрированные редакции. Элементы, которые не удалось зарегистрировать, в условии не участвуют. Между тем модель предусматривает `import_item.rejected` с причинами `corrupt`, `size_limit`, `type_not_allowed` и другими. Технический отказ импорта не является решением о неприменимости документа.

Минимальная последовательность:

1. Принимается архив с двумя документами заказчика: D1 и изменением договора D2. Возникает событие `import_accepted`.
2. D1 успешно зарегистрирован. D2 повреждён или превышает лимит: `import_item.rejected`, `document_revision` для него отсутствует. Партия завершается как `completed_with_errors`.
3. Создаётся снимок и проверка, включающие D1. Все входы этой проверки обработаны, поэтому она может получить `completed`: D2 в снимок не попал и собственного прогона не имеет.
4. Создаётся кандидат на этом снимке. Событие регистрации D1 покрыто; событие партии также покрыто по строке 46 — все успешно зарегистрированные редакции включены.
5. Для непрочитанного D2 отдельного события редакции нет. Предикат актуальности не требует решения руководителя по ошибке. Блокер `REVIEW_INCOMPLETE` проверяет состояние запуска, но обязательного переноса ошибок импорта в этот запуск не определено. При отсутствии других проблем правила разрешают согласование/выпуск неполного комплекта.

Общее требование API показывать неполноту не устраняет противоречие: конкретный предикат признаёт такую партию покрытой, а связь между потерянными элементами партии и блокером выпуска отсутствует. В предельном случае при нуле зарегистрированных редакций проверка «каждая зарегистрированная редакция покрыта» также истинна.

**Ожидается:** партия с непрочитанными потенциально значимыми элементами не признаётся автоматически учтённой. Для каждого элемента должен быть проверяемый исход: зарегистрирован и включён/явно исключён; подтверждённый дубликат с привязкой; либо отдельное решение уполномоченного человека о неприменимости. Ошибка разбора, неизвестный формат или превышение лимита сами по себе не подтверждают неприменимость.

Минимальное исправление: не считать `completed_with_errors` достаточным условием покрытия; сохранять блокировку партии до явного решения либо определить покрытие всех её элементов и явную обработку ошибок. Можно обойтись существующим удержанием партии — вводить отдельный сервис или перестраивать архитектуру не требуется. Если допускается выпуск с принятием риска неполноты, он должен требовать предусмотренного решения и оставлять пробелы видимыми, а не автоматически становиться «всё учтено».

Добавить бумажные сценарии и будущую регрессию:

- один документ принят, второй повреждён;
- ни один документ не зарегистрирован, но партия завершена с ошибками;
- партия состоит из подтверждённых дубликатов;
- ошибка устранена повторным импортом либо руководитель явно признал элемент неприменимым.

В первых двух случаях выпуск блокируется до предусмотренного решения/устранения ошибки; дубликаты не создают ложной неполноты. Связанные инварианты: I04, I18; критерии неполной обработки A16/A44 и приёмка модели переходов этапа 01.
