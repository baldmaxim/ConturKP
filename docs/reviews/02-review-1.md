## R02-01 — P1: повтор команды возвращает данные после отзыва доступа

**Место:** `apps/server/src/http/command.ts:100–111`, особенно возврат сохранённого результата на строке 108.

**Триггер:** руководитель создаёт этап с `Idempotency-Key`, затем администратор снимает его назначение на тендер. Руководитель повторяет тот же POST с прежним ключом и телом.

**Факт:** GET созданного этапа уже отвечает 404, однако повтор POST отвечает 201, `Idempotent-Replayed: true` и возвращает сохранённые данные этапа. Проверки возможностей и назначения находятся внутри `spec.run`, до которого ветка replay не доходит. Наличие действующей сессии не заменяет проверку доступа к объекту.

**Ожидается:** актуальные права на объект проверяются и перед выдачей сохранённого результата. После снятия назначения данные недоступного тендера не возвращаются. Повторно выполнять саму мутацию для этого не нужно.

**Влияние / правило:** обход текущей серверной авторизации; I13, граница доступа ADR-006. Это возврат ранее сохранённых данных, а не повторное создание этапа или доказанная выдача новых данных.

**Воспроизведение:** создать этап от руководителя → удалить его членство через администратора с корректным If-Match → GET этапа → повтор исходного POST. Получено: `201 → 200 → 404 → 201`.

**Исправление и регрессия:** отделить проверку текущих возможностей и области объекта от исполнения команды и выполнять её до replay. Добавить сценарии отзыва назначения и соответствующей глобальной роли; отказ должен попадать в аудит.

## R02-02 — P1: администратор без назначения читает содержимое этапов через журнал

**Место:** `packages/core/src/capabilities.ts:31`; выдача журнала — `apps/server/src/routes/tenders.ts:213–221`. Содержимое попадает в аудит в `apps/server/src/routes/stages.ts:53` и при обновлении этапа на строках 86–93.

**Триггер:** администратор без членства в тендере запрашивает `/tenders/{id}/audit-events`.

**Факт:** GET этапа отвечает 404, но журнал отвечает 200 и содержит название этого этапа в `details` события `stage.create`. Код обновления также записывает старые и новые значения названия и срока подачи. `listTenderAudit` выдаёт события тендера без ограничения бизнес-содержимого по членству.

**Ожидается:** выбранная в D-006 граница «карточка и участники, но не этапы и содержимое» действует также для производных представлений данных — журнала. Администратору можно оставить административные события, не выдавая закрытое содержимое этапов.

**Влияние / правило:** обход ограничения видимости через вторичный канал; ADR-006, D-006, серверная граница доступа I13. Обновлённый ADR одновременно предоставляет администратору `audit.read` и запрещает содержимое этапов без назначения; реализация должна устранить это противоречие, а не считать журнал исключением по умолчанию.

**Воспроизведение:** на синтетическом тендере без назначения администратора: GET `/stages/{id}` → 404; GET `/tenders/{id}/audit-events` → 200, в событии создания есть `title: "Этап A1"`.

**Исправление и регрессия:** разделить доступ к административному аудиту и содержимому бизнес-событий либо фильтровать/редактировать события по текущим правам. Проверить также историю обновлений этапа, включая старые значения.

## R02-03 — P2: параллельное снятие ролей оставляет ноль администраторов

**Место:** `apps/server/src/routes/admin.ts:78–86` — блокировка изменяемого пользователя и отдельная проверка `countActiveAdmins`.

**Триггер:** при двух активных администраторах параллельно снять роль admin у каждого двумя PATCH-запросами с корректными версиями.

**Факт:** транзакции блокируют разные строки пользователей, обе успевают прочитать число администраторов 2 и обе выполняют изменение. Получено два HTTP 200; итоговый запрос в PostgreSQL вернул 0 активных администраторов.

**Ожидается:** хотя бы один запрос отклоняется с конфликтом; минимум один активный администратор остаётся.

**Влияние / правило:** нарушена реализуемая обработчиком защита последнего администратора. Управление пользователями становится недоступно из портала, требуется восстановление серверным способом. Это самостоятельное правило этапа 02, не новый инвариант последующих этапов.

**Воспроизведение:** сценарий выполнен через реальные обработчики HTTP и PostgreSQL. Для детерминированного пересечения в тестовой обёртке результаты обоих реальных `countActiveAdmins` задерживались до завершения обоих чтений. Результаты SQL не подменялись; продуктовый код не изменялся.

**Исправление и регрессия:** сериализовать изменения, затрагивающие наличие активного администратора, общей транзакционной блокировкой в согласованном порядке. Учесть и снятие роли, и отключение пользователя. Добавить конкурентный тест двух разных целевых пользователей, ожидающий сохранения хотя бы одного администратора.

## R02-04 — P2: формат хэшей несовместим с заявленным переходом на argon2

**Место:** `packages/core/src/password.ts:30`, парсер/декодирование — строки 33–40.

**Триггер:** передать созданный порталом хэш с символами `-` или `_` в полях соли/ключа в `argon2.verify` пакета `argon2`.

**Факт:** портал сериализует эти поля через base64url. Его собственная проверка успешна, но пакет `argon2` версии 0.45.1 отклоняет тот же хэш с ошибкой `params must be in the format name=value`. После преобразования только двух полей в обычный base64 без padding тот же пакет успешно проверяет пароль, без пересчёта ключа.

**Ожидается:** заявленная в D-006 совместимость PHC позволяет сменить реализацию без отказа проверки существующих паролей. Использование экспериментального API Node само по себе замечанием не является.

**Влияние / правило:** обещанный переход на пакет сейчас ломает вход для части существующих хэшей. Текущий вход через собственную реализацию работает; это не утверждение о слабости криптографии.

**Исправление и регрессия:** записывать совместимый формат и предусмотреть чтение уже записанных base64url-хэшей. Проверить совместимость в обе стороны с пакетом argon2 на синтетическом пароле и солях, дающих различающийся алфавит.

## Решения и ограничения

- Создание этапов руководителем: само изменение роли не является дефектом; соответствует назначению руководителя. Изменение отражено в контрактах. Замечаний к этому выбору не добавляю.
- Ограничение администратора карточкой/участниками: допустимая выбранная граница, но фактически не выдерживается в журнале (R02-02).
- Встроенный argon2 Node: выбор допустим с известной экспериментальностью API; заявленная совместимость хранения требует исправления R02-04.
- Заявленные 12 шагов Edge независимо в браузере не повторялись. Сборка интерфейса и серверный smoke выполнены; это не заменяет визуальную проверку.
- Установка PWA на телефоны, HTTPS с реальным сертификатом в LAN и службы Windows на целевом ПК не проверялись. Они не объявлены пройденными; учитываются как ограничения соответствующих последующих работ.
- Возможности этапов 03–17 не требовались от этапа 02. Прежние архитектурные замечания R01 повторно не открывались.

Для повторного ревью: передать исправления R02-01…R02-04 отдельным коммитом, обновить отчёт этапа и журнал дефектов, приложить регрессионные проверки. Текущий вердикт — **CHANGES_REQUIRED**, без merge/push со стороны Codex.
