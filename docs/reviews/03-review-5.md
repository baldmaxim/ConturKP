2. Итог по R03-13

R03-13 — CLOSED_BY_REVIEW.

Первопричина предыдущего дефекта устранена.

Новая схема finish() / requeueJob():

при самостоятельном вызове открывает короткую транзакцию;

определяет класс ресурса;

для GPU сначала блокирует и проверяет resource_slot по holder_job_id + lease_token;

затем блокирует и проверяет job по id + lease_token + status='running';

если любая проверка не пройдена — возвращает отказ до первой записи;

только действующий владелец очищает GPU-slot;

после этого в той же транзакции меняется job;

ошибка второй записи откатывает и освобождение слота, поэтому частичного состояния снаружи не возникает.

Старый обработчик после recoverExpiredJobs() больше не может через succeedJob, confirmCancel, retry-ветку failJob или requeueJob очистить оставшийся GPU-slot и тем самым сократить gpu_takeover_grace.

6. inTransaction: пул и уже открытый клиент

Текущую реализацию принимаю для этого проекта.

Она нужна, потому что одинаковые примитивы завершения вызываются в двух режимах:

напрямую с pg.Pool — тогда функция сама создаёт короткую транзакцию;

с клиентом уже открытой транзакции из withLease/терминальной фиксации — тогда вложенный BEGIN/COMMIT недопустим, и используется транзакция вызывающего.

Текущие production-call-sites соблюдают это соглашение, а регрессии проверяют оба режима. Дополнительного изменения перед Stage 04 не требуется.

Ограничение на будущее: не передавать в эти функции произвольный Queryable/клиент вне транзакции. Если библиотечный слой станет публичнее или появятся другие адаптеры БД, лучше заменить структурное isPoolLike на более явный внутренний контракт. Это улучшение, не дефект Stage 03.

7. PostgreSQL 18.3 на Windows

max_logical_replication_workers = 0 допустим для локального изолированного тестового кластера, где логическая репликация не используется.

Не переносить эту настройку автоматически на целевой PostgreSQL. На Stage 17 необходимо отдельно проверить:

только после диагностики решать, какие production-параметры менять.

Это не блокирует Stage 04.

8. Неблокирующие документационные правки перед Stage 04

N03-01

В ADR-004 в абзаце R03-10 осталось старое выражение, что «освобождение слота и перевод задания выполняются одним оператором». После R03-13 фактически используются две записи в одной короткой транзакции после подтверждения владения.

Исправить формулировку на смысл:

освобождение слота и перевод задания выполняются в одной короткой транзакции после блокировки и проверки resource_slot → job; ни одна запись не выполняется до подтверждения владения обеими строками.

Это документальная неточность, не дефект кода.
