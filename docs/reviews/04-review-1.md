R04-01 — P1 — импорт RDWeb обходит ресурсные ограничения безопасного ZIP-контура

Где

apps/worker/src/handlers/recognition.ts, readRdwebArchive(), строки примерно 49–110;

apps/worker/src/archive.ts, readZip();

для сравнения корректная защита Stage 03: apps/worker/src/handlers/imports.ts, строки примерно 64–140.

Факт

readRdwebArchive() использует общий readZip(), но не применяет уже существующие ограничения архива:

maxArchiveEntries;

maxArchiveTotalBytes;

maxEntryBytes;

maxCompressionRatio.

Для PDF выполняется неограниченный по распакованному размеру hashOf(await entry.open()). Для JSON/Markdown есть только лимит каждого отдельного metadata-файла, при этом все кандидаты сохраняются в Map, то есть суммарный объём буферизации не ограничен этим параметром.

readZip() сам проверяет безопасный путь, ссылку, шифрование и целостность размера, но ресурсные лимиты не реализует. Stage 03 специально накладывает их поверх readZip(), Stage 04 этот слой обходит.

Риск

Небольшой по размеру ZIP с очень высоким коэффициентом сжатия, огромным PDF либо большим числом элементов может занять worker распаковкой/хешированием или памятью. Это нарушение принятой модели A38 в части опасных архивов и регрессия относительно Stage 03.

Требуется

Для recognition.import применить тот же обязательный контур ограничений, что и для обычного ZIP-импорта:

максимум числа элементов;

максимум распакованного размера одного элемента;

максимум суммарного распакованного размера;

максимум коэффициента сжатия;

проверка фактического числа прочитанных байт при потоковом чтении;

отдельный разумный суммарный предел памяти для буферизуемых JSON/Markdown;

повторяющееся имя элемента не должно молча перезаписывать предыдущий элемент-кандидат.

Обязательные регрессии

PDF с declaredSize > maxEntryBytes не открывается/не хешируется, прогон получает явный отказ;

коэффициент сжатия выше лимита — отказ;

суммарный распакованный объём выше лимита — отказ;

число членов архива выше лимита — отказ;

несколько допустимых по отдельности metadata-файлов, но превышающих суммарный memory-limit — отказ без OOM;

повтор одного и того же пути в ZIP — явный отказ либо однозначно документированное безопасное правило без молчаливой подмены.

R04-02 — P1 — отмена задания оставляет recognition_run навсегда в queued/running

Где

packages/db/src/jobs.ts, requestCancel();

apps/worker/src/runtime.ts, ветка JobCancelledError;

apps/worker/src/handlers/recognition.ts, onTerminalFailure;

apps/server/src/routes/recognition.ts, findRunByArtifact()/повтор импорта;

packages/db/src/recognition.ts, blockingFreezeItems().

Факт

При отмене задания изменяется только строка job:

queued job сразу становится cancelled;

running job получает cancel_requested, затем worker вызывает confirmCancel().

Доменный объект recognition_run при отмене не переводится в терминальное состояние.

Это даёт два воспроизводимых сценария.

Queued:

загрузить экспорт;

до запуска worker отменить job;

job = cancelled, но recognition_run = queued навсегда.

Running:

worker перевёл прогон в running;

пользователь отменил job;

runtime подтверждает отмену задания;

recognition_run остаётся running.

Повторная загрузка того же ZIP не лечит queued-сценарий: findRunByArtifact() находит существующий прогон со статусом queued/running, возвращает reused=true, но активного задания уже нет.

Такой прогон также навсегда блокирует заморозку состава как recognition_in_progress.

Текущий тест отмена задания распознавания доступна участнику тендера проверяет только статус job и поэтому дефект не обнаруживает.

Требуется

Зафиксировать доменную семантику отмены и сделать изменение job + recognition_run согласованным.

Допустимы два подхода:

отдельный статус прогона cancelled с соответствующими правилами повтора;

failed с выделенным безопасным кодом cancelled, если это сознательно принято как модель состояния.

Критическое требование: отмена queued и running задания не должна оставлять активный доменный прогон без активного job. Для running-сценария доменная отмена и job=cancelled должны фиксироваться одной транзакцией под действующей арендой. Для queued-сценария отмена через API также должна атомарно терминализировать связанный прогон.

Повтор импорта того же архива после отмены должен иметь определённое рабочее поведение.

Обязательные регрессии

queued recognition job отменён → recognition_run терминален;

running recognition job отменён → job и run терминальны согласованно;

после отмены повтор того же ZIP не возвращает вечный reused без job;

заморозка не видит отменённый прогон как recognition_in_progress;

потерявший аренду старый worker не способен подтвердить доменную отмену.

R04-03 — P1 — статус complete может быть ложным; I18 и проверка «несовпадающее число страниц» не закрыты

Где

packages/adapters/src/rdweb/import.ts, примерно строки 175–205 и 241–381;

tests/rdweb.ts, генератор фикстуры;

docs/spec/prompts/stage-04.md, строка 11;

docs/architecture/state-machines.md, §4;

docs/decisions.md, D-011.

Факт 1 — число страниц PDF фактически не проверяется

pagesTotal берётся из doc.pages файла _blocks.json. Сам PDF используется только для SHA-256. Поэтому архив:

PDF реально содержит 4 страницы;

_blocks.json содержит 3 страницы;

_results.md содержит те же 3 страницы;

будет согласован внутри экспортных файлов и может получить complete 3/3.

Это прямо расходится с первоначальным обязательным тестом Stage 04 «несовпадающее число страниц» и с состоянием running → complete в §4, где указано «число страниц совпадает».

Текущий A16 не проверяет этот сценарий: tests/rdweb.ts создаёт настоящий PDF с тем же pageCount, что и массив pages; omitPagesInMd удаляет блоки/Markdown, но не страницу из _blocks.json, поэтому это другой тест.

Факт 2 — пустого заголовка Markdown достаточно, чтобы страница считалась распознанной

В адаптере:

pagesWithOutput = new Set([...mdPageIndex.values()]).

То есть сам факт наличия ## Page N уже делает страницу recognized, даже если на ней нет тела секции, нет фрагмента и нет успешно распознанного блока.

Дополнительно отсутствие block.status трактуется как recognized:

(b.status ?? 'recognized') === 'recognized'.

При неполном/неоднозначном формате это может поднять pagesRecognized и привести к complete без доказательства обработки страницы.

Почему D-011 не снимает дефект

D-011 — техническое решение реализации, а не отдельное решение владельца изменить I18. Оно честно описывает ограничение, но документация ограничения не делает ложный complete допустимым. Если фактическую полноту нельзя проверить, система должна обозначать неопределённость/частичность, а не выдавать complete.

Требуется

Получать фактическое число страниц локального PDF до присвоения complete — в worker или отдельном локальном безопасном компоненте. Серверный рендер не требуется; нужен только достоверный page count.

Либо, если фактическое число страниц по техническим причинам не проверено, такой прогон не может иметь семантику подтверждённого complete.

pages_total должен отражать проверяемую базу полноты, а не только число записей в _blocks.json.

Страница не должна считаться recognized только из-за пустого ## Page N. Нужен содержательный признак результата либо явно подтверждённый контрактом статус обработки. При неоднозначности — неполнота/unknown, а не optimistic complete.

Обязательные регрессии

настоящий PDF 4 страницы + _blocks.json/_results.md только 3 → complete невозможен;

PDF 4 страницы + _blocks.json 4 страницы + ## Page 4 без содержимого/успешных блоков → страница 4 не становится recognized только из-за заголовка;

полный корректный экспорт остаётся complete;

A16 3/4 остаётся partial и показывает правильный список отсутствующих страниц.

R04-04 — P1 — терминальный recognition_run не является неизменяемым агрегатом доказательств на уровне БД

Где

docs/migrations/0005_recognition_evidence.sql, таблицы recognition_page и evidence_fragment, права строк 224–230;

recognition_page_immutable и evidence_fragment_immutable запрещают только UPDATE/DELETE;

recognition_run_guard не проверяет фактический состав дочерних строк.

Факт

Роль kontur_app имеет INSERT в recognition_page и evidence_fragment без триггера, проверяющего состояние родительского прогона.

Следовательно после того, как recognition_run уже стал complete/partial, приложение всё ещё может добавить ему новую страницу или новый фрагмент. Историческое содержимое завершённого прогона изменится, хотя сам run frozen-after.

Кроме того, БД разрешает объявить прогон partial/complete по одним счётчикам, не сверяя их с recognition_page. Собственный тест схемы уже демонстрирует первую часть слабости модели: в tests/recognitionSchema.test.ts прогон переводится в partial с pages_total=3, pages_recognized=2 без вставки трёх строк страниц, и операция ожидается успешной.

Это нарушает смысл I15: recognition_run должен фиксировать неизменяемое историческое доказательство, а не только неизменяемый заголовок.

Требуется

BEFORE INSERT guard для recognition_page и evidence_fragment: родительский run блокируется и должен быть running; вставка в queued или терминальный run запрещена;

терминализация recognition_run должна на второй линии проверять согласованность фактически вставленных recognition_page со счётчиками pages_total/pages_recognized;

проверка должна корректно сериализоваться с финальной транзакцией worker, чтобы после терминализации новые дочерние строки физически не могли появиться.

Обязательные регрессии

INSERT страницы/фрагмента в queued run — отказ;

INSERT страницы/фрагмента после complete/partial — отказ;

прямой complete 3/3 при 0/2 фактических страницах — отказ;

прямой partial 3/2, если фактические строки страниц не соответствуют счётчикам, — отказ;

штатная финальная транзакция worker со вставкой children → finish остаётся рабочей.

R04-05 — P1 — evidence_fragment.document_revision_id не связан с редакцией своего прогона; возможна межтендерная подмена ссылки доказательства

Где

docs/migrations/0005_recognition_evidence.sql, evidence_fragment;

packages/db/src/recognition.ts, getScopedFragment();

apps/server/src/recognitionMappers.ts, toEvidence().

Факт

У evidence_fragment есть:

составной FK (run_id, tender_id) → recognition_run(id, tender_id);

отдельный простой FK document_revision_id → document_revision(id).

Но нет ограничения, что document_revision_id:

принадлежит тому же tender_id;

является именно recognition_run.document_revision_id.

Поэтому строка может иметь:

tender_id = A;

run_id прогона тендера A;

document_revision_id редакции тендера B.

Такой INSERT проходит существующие внешние ключи.

getScopedFragment() фильтрует доступ по f.tender_id, после чего JOIN по f.document_revision_id подмешивает метаданные чужой редакции. toEvidence() возвращает documentId, documentRevisionId и contentUrl на эту редакцию. Сам маршрут скачивания оригинала далее может снова отказать по ACL, но метаданные уже становятся неконсистентными/межтендерными, а Stage 05 будет индексировать доказательство с ложной связью.

Отчёт Stage 04 при этом утверждает «составные FK на тендер редакции и прогона» — для фрагмента это фактически не выполнено.

Требуется

Связать фрагмент с прогоном и его редакцией на уровне БД, например:

уникальный ключ на recognition_run(id, document_revision_id, tender_id);

составной FK evidence_fragment(run_id, document_revision_id, tender_id) на этот ключ.

Либо эквивалентный DB-инвариант с той же силой. Простой FK на document_revision_id сам по себе недостаточен.

Обязательные регрессии

run тендера A + revision тендера B → INSERT fragment отклоняется;

run на revision A1 + другая revision A2 того же тендера → INSERT fragment отклоняется;

корректный run/revision/tender → вставка проходит;

endpoint /evidence/:id не может получить documentId/contentUrl не из редакции собственного run.

R04-06 — P2 — длинный фрагмент сохраняется с потерей хвоста

Где

packages/adapters/src/rdweb/import.ts, pushFragment(), примерно строки 102–118.

Факт

При тексте длиннее maxFragmentChars код делает:

text = text.slice(0, maxFragmentChars)

и сохраняет SHA-256 уже усечённого текста. Есть предупреждение text_truncated, то есть потеря не скрыта, но сам фрагмент-доказательство уже не является полным текстом исходного блока. Stage 05 затем может индексировать только усечённую версию.

Требуется

Не делать доказательство lossy (с потерей данных):

либо отклонять такой экспорт как too_large;

либо детерминированно разбивать один блок на несколько неизменяемых фрагментов с полной восстановимостью текста и стабильными ключами.

Регрессия

Текст >1 000 000 символов либо сохраняется полностью через lossless split, либо импорт завершается явным отказом; вариант «успех + потерянный хвост» отсутствует.
