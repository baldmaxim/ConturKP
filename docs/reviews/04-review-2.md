R04-07 — P1 — пагинация фрагментов сломана после разбиения длинного доказательства

Факты

packages/contracts/src/index.ts сохраняет старый формат курсора из трёх компонентов:

/^-?\d{1,9}:-?\d{1,9}:[0-9a-f-]{36}$/

Но packages/db/src/recognition.ts уже работает с четырьмя компонентами:

page_index : ordinal : part_index : id

и именно такой nextCursor возвращает клиенту.

Следовательно, nextCursor, который сервер сам выдал после первой страницы, не проходит собственную валидацию query-контракта на следующем запросе.

Дополнительно apps/web/src/pages/sources/RecognitionRunView.tsx при наличии nextCursor вызывает fragmentsRes.reload(), то есть повторяет тот же запрос первой страницы вместо запроса с курсором.

Влияние

При количестве фрагментов > лимита страницы интерфейс и API не позволяют последовательно получить весь набор доказательств. После R04-06 длинный текст специально может разбиваться на дополнительные части, поэтому дефект стал практическим.

Требуется

синхронизировать контракт курсора с фактическим (page_index, ordinal, part_index, id);

клиент должен передавать nextCursor, а не перезагружать первый запрос;

обеспечить отсутствие пропусков и дублей между страницами.

Регрессия

Создать >200 фрагментов, получить первую страницу и nextCursor; второй запрос с этим курсором должен пройти валидацию и вернуть следующую страницу без пересечения/пропусков. Проверить UI-загрузку следующей порции.

R04-08 — P1 — можно смешать PDF одного документа с metadata другого документа

Факты

В apps/worker/src/handlers/recognition.ts роли архива выбираются независимо:

PDF-кандидат выбирается по SHA-256;

_blocks.json выбирается отдельно;

_results.md выбирается отдельно.

Нет инварианта, связывающего выбранный JSON/Markdown с тем же экспортным комплектом/именем, чей PDF прошёл SHA-256.

Сценарий

ZIP:

A.pdf               # правильный PDF, SHA совпадает с редакцией
B_blocks.json       # распознавание другого документа
B_results.md        # распознавание другого документа

Если схемы/количество страниц совместимы, данные B могут стать доказательствами для A.

Влияние

Нарушается смысл обязательной проверки «чужой результат не должен быть принят как результат этой редакции». SHA проверяет только PDF, но не принадлежность metadata выбранному экспортному комплекту.

Требуется

Формировать согласованную группу экспорта по наблюдаемому контракту имён/пути (A.pdf, A_blocks.json, A_results.md) и выбирать группу, PDF которой совпадает по SHA-256. Смешанные/неоднозначные группы отклонять, а не собирать роли независимо.

Регрессии

A.pdf + B_blocks.json + B_results.md → отказ;

архив с полными группами A и B → выбрать только согласованную группу A по SHA PDF;

неоднозначная группа → явный отказ.

R04-09 — P1 — координаты молча обрезаются, а рамка рисуется даже при несовместимом пространстве

Факты

В packages/adapters/src/rdweb/import.ts bboxOf()/polygonOf() ограничивают координаты диапазоном [0,1] через clamp.

В apps/web/src/utils/bbox.ts координаты снова ограничиваются перед рисованием.

В EvidenceViewer.tsx вычисляется spaceMatches, но даже если он false, предупреждение показывается вместе с рамкой/полигоном — наложение не подавляется.

При этом архитектурная документация Stage 04 фиксирует принцип: неверно нанесённая рамка хуже отсутствия рамки.

Влияние

Источник может дать некорректные координаты, а портал превратит их в визуально правдоподобную, но ложную область оригинала. Это проблема доказательности I18.

Требуется

не исправлять координаты доказательства молча;

координаты вне допустимого диапазона должны приводить к отсутствию overlay либо к явному invalid-state, но не к изменённой рамке;

при несовместимом bbox_space/aspect/размере overlay не рисовать;

текст/страница могут оставаться доступными с предупреждением.

Регрессии

bbox/polygon вне [0,1] → ложная рамка не появляется;

spaceMatches=false → предупреждение есть, overlay отсутствует;

валидные координаты рисуются без изменений.

R04-10 — P1 — БД проверяет количество страниц, но не точный диапазон индексов

Факты

Миграция 0006_recognition_evidence_integrity.sql при терминализации сверяет:

count(*) страниц;

число status='recognized';

с pages_total/pages_recognized.

Она не проверяет, что набор page_index равен ровно 0..pages_total-1.

Поэтому для pages_total=1 можно вставить единственную страницу page_index=999, затем установить complete, и счётчики совпадут.

Кроме того, evidence_fragment.page_index не связан внешним ключом с (run_id, recognition_page.page_index).

Адаптер предупреждает об out-of-range page index, но отдельные блоки/фрагменты могут сохранить такой индекс.

Влияние

Терминальный run может считаться полным, хотя реальная страница 0 отсутствует, а доказательство ссылается на страницу за пределами PDF. Просмотр такого доказательства затем пытается открыть несуществующую страницу.

Требуется

терминализация должна гарантировать точный набор индексов 0..pages_total-1;

для ненулевого evidence_fragment.page_index добавить DB-связь с существующей страницей того же run;

out-of-range ссылку из malformed-экспорта нельзя сохранять как валидную страницу доказательства; допустим page_index=null + warning либо явный reject.

Регрессии

одна страница page_index=999 при pages_total=1 не позволяет завершить run;

fragment с page index, отсутствующим в recognition_page, отклоняется БД;

malformed export не создаёт стабильную ложную ссылку на страницу.

R04-11 — P1 — maxPages не применяется к реальному числу страниц PDF

Факты

В адаптере лимит maxPages проверяется по doc.pages.length из export JSON.

Позже фактическое pagesTotal берётся из input.expect.pdfPageCount, полученного через pdf.js, но это значение не сравнивается с maxPages.

pdfPages.ts также возвращает doc.numPages, ограничивая размер PDF в байтах, но не количество страниц.

Затем код создаёт массив Array.from({ length: pagesTotal }, ...).

Влияние

PDF с количеством страниц выше настроенного лимита проходит именно тот ресурсный предел, который должен ограничивать число страниц, и вызывает создание большого количества объектов/DB rows.

Требуется

сразу после чтения PDF проверять numPages <= maxPages;

повторить защитную проверку в адаптере до любых выделений массива по pdfPageCount;

превышение → явный too_large.

Регрессия

pdfPageCount = maxPages + 1 должен отклоняться до формирования страниц/фрагментов.

R04-12 — P2 — история supersedes_run_id может ветвиться

Факты

latestFinishedRun ищет только завершённый complete/partial run.

Ограничения «не более одного активного recognition run на revision» нет.

Сценарий:

A завершён;

загружается B → queued, supersedes=A;

до завершения B загружается другой архив C → queued, supersedes=A.

Получается A → B и A → C.

supersededBy() при этом возвращает только первого ребёнка (LIMIT 1), то есть цепочка истории перестаёт быть цепочкой.

Требуется

Линеаризовать прогоны одной редакции. Практичный вариант:

partial unique index: не более одного queued/running run на revision;

при создании блокировать/сериализовать revision;

второй различающийся архив до завершения активного run получает 409/conflict;

после терминализации новый run указывает на последний подходящий предшественник.

Регрессия

Два разных экспорта одной revision до обработки первого не должны создавать двух sibling-run с одним supersedes_run_id.
