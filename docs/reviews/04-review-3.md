3. Найденные проблемы

R04-08 — P1 — неоднозначный комплект всё ещё выбирается, а не отклоняется

Файлы: packages/adapters/src/rdweb/members.ts, строки 57–63;
apps/worker/src/handlers/recognition.ts, строки 158–189.

Review 04-2 требовал не только связать роли общей группой, но и явно отклонять неоднозначную
группу. Текущая реализация pickMember() при нескольких кандидатах сортирует их по score,
выбирает первый, остальные переносит в ignored. Это не отказ.

Кроме того, совпавший PDF выбирается через первый .find() по SHA-256. Если в архиве два PDF
с одинаковыми байтами/хэшем, но разными group key, выбор зависит от порядка членов ZIP.

Примеры неоднозначности: A.pdf + A_blocks.json + A.json + A_results.md; два PDF с тем же
SHA-256 в группах A и B, обе группы имеют metadata.

Требуется: после определения группы совпавшего PDF каждая обязательная роль должна иметь
ровно одного кандидата. Несколько совпавших PDF-групп или несколько _blocks/results.md одной
группы — export_group_ambiguous (или эквивалентный терминальный код), без импорта доказательств.

Регрессии: A.pdf + A_blocks.json + A.json + A_results.md → отказ; два PDF с одинаковым SHA,
две полные группы → отказ, а не выбор по порядку ZIP.

R04-12 — P1 — линейность истории не обеспечена второй линией БД

Файлы: docs/migrations/0005_recognition_evidence.sql, строки 57–75 и 227;
docs/migrations/0007_recognition_page_integrity.sql, строки 18–23.

API теперь сериализует приём advisory lock и не допускает одновременно два queued/running
прогона. Это закрывает штатную гонку. Но роль kontur_app имеет прямой INSERT в
recognition_run, а DB guard проверяет только статус нового прогона и завершённость
предшественника. DB не проверяет, что предшественник — хвост цепочки, и не запрещает второй
корень истории.

Сценарий ветвления: A — complete; B — complete, supersedes=A; после завершения B вставить
C — queued, supersedes=A. Частичный индекс recognition_run_active_key не мешает. Также после
существующего завершённого A можно вставить новый queued C с supersedes_run_id = NULL.

Требуется: DB-инвариант линейности — один потомок у supersedes_run_id; supersedes_run_id
IS NULL допустим только для первого корня редакции; новый predecessor должен быть текущим
хвостом; конкурентные вставки сериализуются тем же DB-lock/ключом, что API.

Регрессии от kontur_app: после A -> B вставка C -> A отклоняется; после существующей успешной
истории новый C с supersedes=NULL отклоняется; штатное A -> B -> C проходит.

R04-14 — P1 — EvidenceViewer может показать рамку от другого фрагмента

Файлы: apps/web/src/pages/evidence/EvidenceViewer.tsx, строки 27–100;
apps/web/src/hooks/useApiResource.ts, строки 25–45.

EvidenceViewer перерисовывает PDF/overlay только при изменении contentUrl, pageIndex,
bboxSpace, rotation. В dependency list отсутствуют fragmentId, bboxNorm, polygonNorm,
pageWidthPx/pageHeightPx. Поэтому при SPA-переходе между двумя фрагментами одной страницы
одного PDF overlay может остаться от предыдущего фрагмента. Если новый фрагмент имеет
pageIndex=null, effect возвращается раньше, но render не сбрасывается.

useApiResource усиливает проблему: при смене key он ставит loading=true, но не очищает старое
data. Для экрана доказательства это нарушение I18.

Требуется: новый fragment key не должен использовать render/data предыдущего фрагмента;
reset render/renderError при смене fragment; effect должен зависеть от всех данных, влияющих
на overlay; при pageIndex=null старый canvas/overlay не должен оставаться как текущий результат.

Регрессия: два фрагмента одного PDF на одной странице с разными bbox; SPA-навигация A → B без
полного reload должна изменить рамку на B.

R04-15 — P1 — при переключении страниц UI временно смешивает фрагменты и курсоры

Файлы: apps/web/src/pages/sources/RecognitionRunView.tsx, строки 46–75 и 96–103;
apps/web/src/hooks/useApiResource.ts, строки 25–45.

При изменении pageIndex hook запускает новый запрос, но сохраняет fragmentsRes.data
предыдущей страницы. Интерфейс сразу считает выбранной новую страницу, продолжает рендерить
старые items, берёт старый nextCursor, и loadMore() отправляет этот старый cursor вместе с
новым pageIndex.

Требуется: data/cursor должны быть привязаны к fragmentsKey; при смене страницы старая выдача
немедленно перестаёт считаться текущей; more, moreError и cursor сбрасываются; load-more
недоступен до получения базовой порции текущего key.

Регрессия: две распознанные страницы, управляемая задержка запроса. После page0 → page1 до
ответа page1 ни один fragment/cursor page0 не должен использоваться.

R04-16 — P2 — контракт курсора допускает строку, которая падает на PostgreSQL UUID cast

Файлы: packages/contracts/src/index.ts, строка 150; packages/db/src/recognition.ts,
запрос listFragments.

Regex [0-9a-f-]{36} не является проверкой UUID. Строка из 36 дефисов проходит Zod, но затем
$6::uuid в PostgreSQL выдаёт 22P02, и клиент получает 500.

Требуется: валидировать четвёртый компонент как настоящий UUID до DB.

Регрессия: синтаксически похожий, но невалидный UUID cursor → HTTP 400 VALIDATION_FAILED.
