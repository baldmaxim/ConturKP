4. R04-14 — P1 — старое доказательство ещё может рендериться под новым ключом

Файлы:

apps/web/src/hooks/useApiResource.ts, строки примерно 30–48

apps/web/src/pages/evidence/EvidenceViewer.tsx, строки примерно 28–126

4.1. Старые data очищаются слишком поздно

useApiResource хранит data обычным state. При смене key выполняется новый React render с новым ключом, но state data всё ещё содержит результат старого ключа. Только после commit запускается useEffect, который выполняет:

    if (shownKey.current !== key) {
      shownKey.current = key;
      setData(null);
    }

Следовательно, invariant из комментария «при смене key прежний результат немедленно перестаёт быть текущим» фактически не выполнен. Очистка в effect не запрещает промежуточный render/commit старого результата под новым URL/ключом.

Для /evidence/:id сценарий выглядит так:

открыт фрагмент A, data=A;

маршрут меняется на /evidence/B;

компонент рендерится с fragmentId=B, но res.data ещё A;

только затем effect обнуляет data и запускает загрузку B.

Текущий browser test ждёт конечной смены рамки; он не доказывает отсутствие старого доказательства на каждом промежуточном рендере, что было обязательным требованием Review 04-3.

Требование

Состояние результата должно быть связано с ключом синхронно на этапе render, например хранить {dataKey, data} и возвращать data только когда dataKey === key. Аналогично ошибка должна принадлежать ключу. reload того же ключа может сохранять старое значение, но смена ключа не должна ни одного render считать старые данные текущими.

4.2. Canvas сохраняет старую страницу после прихода нового фрагмента

Исправление overlay хорошее: drawn хранится с overlayKey, поэтому старая рамка не считается рамкой нового фрагмента.

Однако сам DOM canvas остаётся тем же объектом. Его пиксели не очищаются при смене overlayKey. После прихода фрагмента B новый текст/метаданные уже показываются, а pdf.js только начинает асинхронно загружать/рисовать страницу B. До окончания page.render(...) canvas физически содержит страницу A.

Для перехода между разными страницами это даёт состояние:

текст B + старая страница A, хотя старая рамка уже скрыта.

Это всё ещё неверное доказательство.

Требование

Старый canvas должен синхронно перестать считаться текущим при смене ключа. Подходы:

remount canvas через React key={overlayKey} и показывать его только после готовности рендера текущего ключа; или

явно хранить renderedPageKey и не показывать canvas, пока он не равен overlayKey.

Простого setDrawn(null) в effect недостаточно по той же причине — effect выполняется после render.

Обязательная регрессия

Browser/component scenario:

A и B — разные evidence fragments;

сначала A полностью отрисован;

перейти внутри SPA на B;

задержать getEvidence(B) и отдельно задержать/контролировать PDF render B;

после изменения маршрута ни один промежуточный render не показывает текст/страницу A как данные B;

после получения метаданных B, но до готовности страницы B, старая страница A отсутствует/скрыта;

после готовности показана страница B и только её overlay.

5. R04-15 — P1 — выдача страницы всё ещё не полностью привязана к ключу

Файлы:

apps/web/src/hooks/useApiResource.ts

apps/web/src/pages/sources/RecognitionRunView.tsx, строки примерно 47–85

Первопричина первого промежуточного render та же: после setPageIndex(1) fragmentsKey уже новый, но fragmentsRes.data до запуска effect остаётся результатом прежнего ключа. Поэтому выражение:

    const base = fragmentsRes.data;

может один render считать старую порцию базой новой страницы.

UI-check с ожиданием 600 мс подтверждает, что через некоторое время старые данные исчезают, но не проверяет требование Review 04-3 «не отображаются или используются ни на одном промежуточном рендере».

Дополнительная гонка loadMore

loadMore() не имеет AbortSignal и его moreError / loadingMore не принадлежат fragmentsKey.

Достижимый сценарий:

на page 0 запущена следующая порция;

пользователь переключился на page 1, moreError очищен;

базовая порция page 1 успешно пришла;

старый запрос page 0 позже падает;

его .catch() вызывает setMoreError(reason);

при base page 1 и more === null текущий shownMoreError показывает ошибку старой page 0 как ошибку page 1.

loadingMore также может временно блокировать кнопку новой страницы состоянием старого запроса.

Требование

базовые data/error/loading должны принадлежать ключу синхронно, а не после effect;

request следующей порции должен иметь собственный request key / AbortController;

поздний success/error/finally старого ключа не должен менять состояния текущей страницы;

при смене fragmentsKey старый load-more запрос желательно abort.

Обязательные регрессии

Смена page0 → page1: сразу после смены ключа, до выполнения нового effect/ответа, DOM не содержит фрагментов/курсора page0.

Запустить loadMore page0, переключиться на page1, затем завершить старый запрос ошибкой: на page1 не появляется ошибка page0 и её кнопка не зависит от старого loadingMore.

6. R04-18 — P2 — supersededByRunId может указывать на отказавшую попытку

Файл: packages/db/src/recognition.ts, supersededBy(), строки примерно 114–116.

Миграция 0008 сознательно определяет: failed/cancelled попытка не занимает место потомка. Это позволяет:

    A complete
    ├─ F failed
    └─ B complete

где эффективная история успешных версий — A → B.

Но supersededBy() сейчас выполняет:

    SELECT id
    FROM recognition_run
    WHERE supersedes_run_id = $1
    ORDER BY created_at
    LIMIT 1

и не фильтрует failed / cancelled.

Если F создан раньше B, GET /recognition-runs/A вернёт supersededByRunId = F, хотя F по самой модели данных не является прогоном, занявшим место следующей версии. Если есть только F, A вообще не должен считаться перекрытым.

Требование

supersededBy() должен использовать то же определение эффективного потомка, что и линейность истории:

    status NOT IN ('failed', 'cancelled')

Частичный уникальный индекс уже гарантирует не более одного такого потомка.

Регрессии

A complete → F failed → B complete: supersededBy(A) = B;

A complete → F cancelled: supersededBy(A) = null;

обычная A → B queued/running/complete: supersededBy(A) = B.
