AR05-01 — P1 — PostgreSQL >=16 против LOCALE_PROVIDER=builtin

Файлы: docs/adr/ADR-002-postgresql-and-migrations.md, спецификация/README со стеком.

ADR-002 одновременно говорит:
- PostgreSQL не ниже 16;
- используются только возможности PostgreSQL 16;
- база создаётся с LOCALE_PROVIDER = builtin, BUILTIN_LOCALE = 'C.UTF-8'.

Это несовместимо. В PostgreSQL 16 встроенного locale provider builtin нет: доступны libc и icu. Провайдер builtin появляется в PostgreSQL 17.

Требование: выбрать одну линию и зафиксировать её во всех документах и скриптах.

Рекомендация ревью: поднять минимальную версию проекта до PostgreSQL >=17, сохранив builtin/C.UTF-8. Машина разработки уже на PostgreSQL 18.3, а доказанной необходимости поддерживать 16 нет. Если поддержка 16 обязательна — вместо builtin проектировать ICU и отдельно доказать русское приведение регистра на Windows/Linux.

Гейт Stage 05: тест создания БД + проверка to_tsvector('russian','Договор') = to_tsvector('russian','договор').

AR05-02 — P1 — асинхронный semantic search не имеет доменной модели и API

Файлы: ADR-012, ADR-008, data-model.md, state-machines.md, portal-api.md, mcp-tools.md, overview.md.

ADR-012 требует:
- точный и полнотекстовый результат вернуть синхронно;
- смысловую ветку выполнять GPU-job;
- затем объединить три ветки RRF;
- писать «прогон поиска» с областью, версией индекса, моделью, таймингами и причиной отказа.

Но в архитектуре нет:
- таблицы/сущности search_run;
- состояний прогона;
- контракта хранения результатов;
- endpoint для чтения завершившейся смысловой ветки;
- правил, что именно является «финальным RRF», если третья ветка приходит позже;
- API для polling/повторного чтения;
- соответствующего MCP-поведения.

portal-api.md содержит только POST /search, а overview.md всё ещё говорит, что модуль поиска не имеет таблиц и заданий.

Требование: до кода Stage 05 определить first-class search run.

Минимальный контракт:
- POST /search строит область и создаёт search_run; возвращает searchRunId, scopeHash, синхронный lexical result и статус semantic (queued / unavailable / complete);
- GET /search-runs/{id} возвращает терминальный статус и финальный fused result;
- итоговый RRF появляется только при фиксированном наборе веток; синхронный lexical результат не выдаётся за финальный fused result;
- run закрепляет query hash/text, scope hash, effective source-unit set (или ссылку на неизменяемый scope), версии индекса/ранжирования/модели;
- результаты/ранги терминального run после завершения неизменяемы;
- отказ смысловой ветки даёт degraded, а не молчаливую смену семантики.

AR05-03 — P1 — жизненный цикл версии индекса и embedding cache недоопределены

Файл: ADR-012 пункты 5, 9, 14; data-model.md.

Сейчас сказано: новая версия индекса строится рядом, поиск читает активную, старая удаляется. Но отсутствует сущность версии индекса и правила активации/сборки мусора.

Опасный сценарий:
1. semantic search создаётся на active index N;
2. job ждёт GPU;
3. rebuild активирует N+1 и удаляет N;
4. старый search job начинает выполняться.

Также «кеш эмбеддингов по содержимому» недостаточен: один и тот же текст у другой модели/версии/нормализации имеет другой вектор. Смена модели по ADR-012 обязана давать новую версию индекса, но cache, ключованный только текстом, способен вернуть старый вектор.

Требование: завести search_index_version (или эквивалент) со статусами как минимум building -> active -> retired/failed; активация атомарная и разрешена только после полноты индекса. search_run закрепляет конкретную версию. Удаление старой версии допустимо только когда нет queued/running run, который её использует.

Ключ кеша эмбеддингов обязан включать минимум:

text_sha256 + model + model_version/fingerprint + embedding_input_version (+ dim).

Размерность вектора должна валидироваться против версии модели/индекса. Архитектура должна переживать модель с другой размерностью, а не предполагать одну размерность навсегда.

AR05-04 — P1 — не определена политика model_description в поиске (I06)

Файлы: 01_PRODUCT_SPEC.md I06, data-model.md, ADR-012, stage-05.md.

Stage 04 специально отделил recognized_text от model_description. D-018 дополнительно запрещает извлекать факты из model_description. Однако Stage 05 говорит «индекс поверх evidence_fragment» без origin policy.

Если индексировать все строки одинаково, модельное описание картинки может стать результатом поиска и единственной «цитатой», то есть производный текст модели начнёт выглядеть как основание документа.

Требование: зафиксировать policy по origin до реализации chunk builder.

Рекомендуемая схема:
- document_text, recognized_text, позднее email_body, attachment_text — evidence corpus;
- model_description — только derived_hint: может улучшать нахождение страницы/блока, но не становится самостоятельным подтверждающим основанием;
- результат обязан показывать matchedVia, origin и ссылаться на исходный документ/страницу; derived hint не может сам пройти factual/numeric gate;
- negotiation_hint по той же причине не становится доказательством; negotiation_speech остаётся устным основанием с явным origin и ограничением I08.

Если на Stage 05 derived hints решено не использовать — исключить model_description из индекса явно и перенести их использование на отдельный этап.

AR05-06 — P1/P2 — долгоживущий Contract не имеет собственного SearchScope

Файлы: D-017, ADR-008, mcp-tools.md, portal-api.md.

D-017 правильно отделяет contract от tender: договор живёт годами и не должен переоткрывать готовность старых КП. Но текущий SearchScope всегда начинается с tenderId и stage/release.

Это позволяет безопасно включать договор в конкретный tender scope, но не описывает основной сценарий, ради которого Locus поглощается: отдельный поиск/вопрос по действующему договору после завершения тендера.

Если оставить API tender-only, Stage 06a/08a придётся либо искусственно выбирать старый tender stage, либо ломать контракт поиска после Stage 05.

Требование до фиксации API Stage 05: определить search context как расширяемый union. На Stage 05 реализовать tender-вариант; зарезервировать contract-вариант для 06a без изменения базовой модели search run.

Например:
- tender: существующие working/review/release/comparison;
- contract: contractId + contract evidence scope/current corpus, с contract.read;
- связь contract↔tender сама область не расширяет в обе стороны.

AR05-07 — P2 — GPU scheduling не закрепляет приоритет интерактивного поиска

job уже поддерживает priority, но ADR-012 говорит только «маленькие пачки индексации». Этого недостаточно как формального правила очереди.

Требование: semantic query имеет больший priority, чем background indexing; одновременно существует не более одного незавершённого следующего batch индексации на версию. После batch новое задание ставится с низким priority. Это защищает двух пользователей от starvation при большой переиндексации.

AR05-10 — P2 — реальный embedding provider и размерность

Fake provider нужен и правильно предусмотрен для deterministic tests, но PASS Stage 05 не должен означать, что semantic branch реализован, если в коде существует только fake.

Требование к Stage 05: реализовать хотя бы один конкретный локальный provider за ModelGatewayEmbeddings либо явно оставить semantic branch PARTIAL/BLOCKED_TARGET и не заявлять её production-ready.
