pgvector

Отказ от ANN на Stage 05 принят. Приближённый индекс с фильтрацией меняет семантику отбора; точный перебор после WHERE allowed_source_unit_ids соответствует A42. halfvec и явная размерность допустимы. Обязательные условия реализации Stage 05

Ниже не новый архитектурный блокер и не причина для 05-pre-3. Это условия implementation review: если они не выполнены, Stage 05 не будет принят.

G05-01 — зависимость index.build → index.embed

Нельзя полагаться на случайный порядок двух заданий одинакового приоритета. index.embed, запущенный до появления чанков, не должен «успешно закончить» векторную часть навсегда.

Допустимая реализация должна гарантировать одно из эквивалентных поведений:
- первоначально ставится index.build, а он после появления чанков атомарно обеспечивает index.embed;
- либо пустой index.embed видит незавершённый index.build и оставляет/ставит продолжение;
- либо используется другой явный dependency protocol.

Активация версии разрешена только после того, как текстовый frontier завершён и backlog векторов равен нулю. Нужен детерминированный регрессионный тест с принудительным порядком «embed раньше build».

G05-02 — search_run: внутренне сначала pending, терминализация не зависит от клиента

search_run_result разрешает вставку только в нетерминальный прогон. Поэтому даже синхронные сценарии, внешне возвращающие сразу complete/degraded, внутри транзакции должны пройти через нетерминальное состояние: создать прогон → записать exact/fts/(vector)/fused → терминализировать.

Срок deadline_at не должен зависеть только от того, вызовет ли клиент GET /search-runs/{id}. Брошенный клиентом pending-прогон не может вечно удерживать retired index от purge. Нужен автономный путь терминализации просроченных прогонов (например, отдельное отложенное задание/периодический sweep/эквивалент), при этом GET может остаться дополнительной opportunistic-проверкой. Нужен тест: клиент создал pending run и больше его не читает → после deadline он становится degraded, а старая версия позже может быть очищена.

G05-03 — поведение без активной версии

До появления первой active версии POST /search не должен частично работать по «чему-то текущему» или по building. Требуется явный отказ (STATE_CONFLICT с машинно-читаемой причиной вроде search_index_not_ready, либо другой единообразный контракт), без создания ложного успешного результата. Отдельный тест обязателен.

G05-04 — проекция чанка в цитату должна быть детерминированной

Ветка может ранжировать чанки, но наружный контракт возвращает evidence_fragment.id. Реализация обязана иметь один детерминированный алгоритм «chunk hit → evidence fragment result», дедуплицировать один и тот же фрагмент до RRF и никогда не выбирать фрагмент вне связей search_chunk_fragment.

Минимальные регрессии:
- один чанк содержит два evidence-фрагмента, искомая точная фраза есть только во втором — exact/fts не имеет права процитировать первый;
- один фрагмент попал в два перекрывающихся чанка — в одной ветке он не занимает два ранга;
- vector hit может сослаться только на evidence-фрагмент, связанный с этим чанком и входящий в закреплённую область.

Точный способ выбора для vector-ветки допускается выбрать в реализации, но он должен быть зафиксирован в ranking_version/тестах, а не зависеть от порядка строк без ORDER BY.

G05-05 — граничная размерность halfvec

Предел проекта 4000 должен быть подтверждён интеграционным тестом реальной схемы PostgreSQL/pgvector при STORAGE PLAIN: вставить и прочитать вектор проектной максимальной размерности вместе со всеми служебными колонками search_chunk_vector. Если строка физически не помещается, предел понижается на основании теста без смены архитектуры.
