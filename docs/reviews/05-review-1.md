## R05-01 — evidence_scope_item не является фактически immutable

**Severity:** BLOCKER  
**Статус:** OPEN

`evidence_scope` и `evidence_scope_item` нормативно являются неизменяемым снимком области доказательств.

Сейчас миграция `0009_search_index.sql` запрещает UPDATE/DELETE для `evidence_scope_item`, но не запрещает INSERT после создания снимка.

Роль `kontur_app` имеет:

`GRANT SELECT, INSERT ON evidence_scope, evidence_scope_item TO kontur_app`

а `evidence_scope_item_insert_guard()` разрешает добавить в существующий scope новую редакцию/recognition_run, если она входит в исходную замороженную `source_set_revision`.

Следовательно, после создания снимка возможно:

1. создать `evidence_scope` с составом A;
2. получить зафиксированный `content_hash`;
3. позднее INSERT добавить допустимый item B;
4. `content_hash` останется прежним;
5. фактическая область review-поиска станет A+B.

Это нарушает `data-model.md §4.3`, историческую воспроизводимость и назначение `evidence_scope`.

### Требуемое исправление

Обеспечить атомарное создание полного снимка и невозможность его расширения после фиксации.

Конкретную реализацию выбери сам, но она должна обеспечивать на уровне БД:

- после завершения создания снимка нельзя INSERT/UPDATE/DELETE его items;
- приложение не может прямым SQL расширить существующий снимок;
- `content_hash` всегда соответствует неизменяемому составу;
- повторное создание того же состава остаётся идемпотентным;
- создание нового снимка с другим составом создаёт новый immutable snapshot (неизменяемый снимок), а не изменяет старый.

Не решать это только проверкой в HTTP/API — нужна вторая линия на уровне БД, поскольку `kontur_app` имеет прямые права на таблицы.

Добавить интеграционные регрессии минимум:

1. создать scope штатным способом;
2. попытаться INSERT нового допустимого `evidence_scope_item` в уже созданный scope;
3. операция обязана завершиться отказом БД;
4. исходный состав и `content_hash` не меняются;
5. штатное создание scope с несколькими items по-прежнему проходит;
6. повторное создание того же снимка возвращает существующий scope без изменения состава.

Проверь также конкурентное создание одинакового снимка, чтобы исправление не породило частично заполненный scope или гонку между двумя транзакциями.
