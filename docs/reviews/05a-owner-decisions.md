# OD-1 — граница RDWeb / локального распознавания для PDF

**Решение: fail-closed (запрет по умолчанию) при неоднозначности.**

Не определять «ожидается ли RDWeb» эвристикой по имени файла, тендеру, папке или содержимому.

Для PDF использовать явную политику маршрутизации.

Минимально различать:

- `rdweb` — распознавание только через RDWeb;
- `local` — разрешено локальное распознавание;
- `auto` — система выбирает по нормативным правилам.

Правила:

1. PDF, пришедший импортом RDWeb, относится к `rdweb`.
2. Если для конкретной `document_revision` уже имеется допустимый успешный RDWeb recognition run (прогон распознавания), локальный прогон при автоматическом выборе не может его вытеснить.
3. Ручной PDF без доказанного происхождения RDWeb не считать автоматически «RDWeb-обязательным».
4. Для такого PDF локальное распознавание разрешается только:
   - при явной политике `local`, либо
   - по явной пользовательской команде.
5. При `auto`, если система не может доказать маршрут, не запускать конкурирующее локальное OCR молча.

Не создавать эвристику «если PDF — значит RDWeb».

# OD-2 — способ запуска

**Решение: гибридный.**

## Автоматический запуск

Автоматически запускать локальную обработку для форматов, для которых RDWeb нормативно не используется:

- `.docx`;
- `.xlsx`;
- `.csv`.

## PDF

PDF автоматически локально не распознавать при неоднозначном маршруте.

Разрешать:

- явный `local`;
- ручную команду пользователя;
- иной доказанный нормативный источник `local`.

## Повтор

Повторный одинаковый запрос должен быть идемпотентным.

Нельзя создавать новый recognition run только потому, что пользователь дважды нажал кнопку для той же:

`document_revision + recognizer_version + configuration`.

# OD-3 — договоры

**Решение: договоры входят в Stage 05a.**

Это необходимо для принятого Stage 06a.

Stage 05a должен уметь получать текст из договорных документов поддерживаемых форматов.

Но Stage 05a **не выполняет**:

- юридический анализ;
- извлечение условий договора в бизнес-модель;
- оценку рисков;
- ответы ИИ по договору;
- сравнение договоров;
- автоматические выводы.

Его результат:

`document_revision → recognition_run → structural text/fragments`

с существующим контуром evidence/search.

Права Stage 06a сохраняются полностью.

Распознавание договора не выдаёт `contract.read`.

# OD-5 — OCR-движок и языки

## Когда OCR вообще используется

OCR (оптическое распознавание текста) применять только там, где нет пригодного текстового слоя.

Не OCR-ить:

- DOCX;
- XLSX;
- CSV;
- текстовый PDF, если его текстовый слой успешно извлекается.

Для PDF:

1. сначала native text extraction (извлечение встроенного текста);
2. OCR только для страниц без достаточного текстового слоя или для сканированного PDF.

## Движок

Не вшивать один конкретный OCR-движок в доменную модель.

Ввести adapter contract (контракт адаптера):

`LocalOcrEngine`

с фиксируемыми:

- engine id;
- engine version;
- model/version;
- languages;
- configuration hash.

Первый production adapter (рабочий адаптер) должен использовать **локальный OCR-движок, реально устанавливаемый на целевом Windows-ПК без облачных API**.

Выбор конкретной библиотеки допускается разработчику после короткого технического spike (проверочного прогона) на существующих fixture (фикстурах), но:

- без отправки документов наружу;
- без сетевого OCR;
- без лицензии, несовместимой с продуктом.

Если Locus уже содержит рабочий локальный OCR adapter — см. OD-7.

## Языки

Обязательные:

- `ru`;
- `en`.

Другие языки не входят в Stage 05a.

# OD-6 — качество распознавания

**Решение: не использовать один магический confidence threshold как PASS/FAIL всего документа.**

Разделить:

- технический успех распознавания;
- качество результата.

Минимальные статусы:

- `complete`;
- `needs_review`;
- `failed`.

## failed

Например:

- parser/OCR завершился ошибкой;
- ни одного пригодного фрагмента получить невозможно;
- повреждён входной файл;
- неподдерживаемая структура.

## needs_review

Использовать, если:

- OCR дал текст, но качество ниже принятого порога;
- существенная часть страниц практически пустая;
- есть проблемные страницы;
- parser смог частично прочитать документ;
- нарушена ожидаемая структура таблицы.

## complete

Технически успешно и quality gate (шлюз качества) пройден.

### Важно

Engine confidence (уверенность OCR-движка) хранить как evidence/diagnostic metric (диагностическую метрику), но не делать его единственным критерием.

Перед окончательной фиксацией числового threshold разработчик должен прогнать существующий набор Locus/Stage 05a fixtures и показать распределение метрик.

Если нормативный Stage 05a уже содержит конкретный порог — использовать нормативный.

Если нет — **не придумывать число до измерения fixture corpus**.

Это не блокирует начало разработки parser pipeline.

# OD-7 — можно ли использовать Locus

**Решение: да, можно и желательно переиспользовать проверенные части Locus.**

Но не делать runtime dependency (зависимость во время работы) Контур КП от отдельного приложения Locus.

Разрешено:

1. выявить в Locus чистые компоненты:
   - OCR adapter;
   - text extraction;
   - DOCX parser;
   - XLSX parser;
   - CSV parser;
   - нормализацию;
   - quality metrics;
2. вынести действительно общую часть в shared package (общий пакет) либо перенести с сохранением provenance (происхождения);
3. покрыть её тестами Контур КП.

Запрещено:

- тянуть UI Locus;
- тянуть его search/business logic;
- импортировать скрытое состояние его БД;
- делать сетевой вызов из Контур КП в Locus как обязательную внутреннюю интеграцию;
- считать поведение корректным только потому, что оно «так работает в Locus».

Контракт Контур КП остаётся источником требований.

# AD-05a-1 — страницы и structural anchors для DOCX/XLSX/CSV

**Решение: не придумывать фиктивные пиксельные страницы.**

Не задавать:

`width_px = 1`
`height_px = 1`

или аналогичные искусственные размеры.

Расширить существующую модель страницы до понятия **source unit (структурной единицы источника)** с минимальным изменением текущей схемы.

## PDF

Сохраняет физическую страницу:

- page number;
- width_px;
- height_px;
- bbox/coordinates.

## XLSX

Логическая единица:

`sheet`

Anchor (якорь) фрагмента:

- sheet identity/name;
- cell/range, например `B7:F12`;
- при необходимости row/column coordinates.

Пиксельный bbox не требуется.

## CSV

Логическая единица:

`table/file`

Anchor:

- row range;
- column range/header identity.

## DOCX

Логическая единица не должна называться физической страницей, поскольку DOCX не имеет стабильной пагинации без конкретного renderer (движка отображения).

Anchor:

- paragraph/block index;
- table index;
- row/cell при табличном содержимом;
- section при наличии.

## Схема

Предпочтительный минимальный путь:

расширить существующую page/unit-модель:

- `unit_kind`;
- pixel dimensions nullable;
- DB CHECK:
  - для физической PDF page размеры обязательны;
  - для logical unit размеры отсутствуют;
- structural locator фрагмента хранится типизированно/структурированно.

Не создавать параллельный полноценный документный pipeline.

Если существующая схема не позволяет это сделать без фундаментальной переделки Stage 04/05 — остановиться до миграции и вынести отдельный AD.

# AD-05a-2 — источник локального recognition_run

Источник локального прогона — **immutable document_revision**, а не путь к файлу.

Идентичность локального recognition run должна включать минимум:

- `document_revision_id`;
- SHA-256 исходного blob;
- recognizer/adapter id;
- recognizer version;
- configuration hash;
- input format;
- language configuration;
- способ обработки (`native_text`, `ocr`, `structured_parser` или эквивалент).

Путь Windows, временная папка и имя локального файла не являются identity.

Одинаковая document revision + одинаковая версия обработчика + одинаковая конфигурация должны давать идемпотентную постановку/результат согласно существующей модели jobs.

# AD-05a-3 — RDWeb должен выигрывать у local

**Решение: да, нужна защита сильнее порядка очереди.**

Порядок постановки jobs недостаточен.

Должно существовать детерминированное правило выбора active/preferred recognition (предпочтительного прогона):

при автоматическом выборе:

`valid RDWeb > local`

для документа, которому разрешён/назначен RDWeb route.

Это правило должно быть защищено второй линией — БД или централизованным selection invariant (инвариантом выбора), который нельзя обойти прямым прикладным вызовом.

## Разрешённая модель

Если существует таблица/указатель selected recognition:

- для `selection_mode = auto` БД не должна позволять выбрать local, когда существует допустимый RDWeb run с более высоким приоритетом;
- либо selected run вычисляется детерминированной DB-функцией/view.

Ручной override (ручное переопределение), если вообще предусмотрен спецификацией, должен:

- быть отдельным режимом;
- иметь capability;
- оставлять audit event;
- не притворяться automatic selection.

Не решать правило только:

- временем создания;
- номером job;
- `ORDER BY created_at`;
- очередностью worker.

# Настоящий XLSX fixture

Отсутствующий настоящий `.xlsx` не является блокером.

Для тестов создать **реальный синтетический XLSX binary fixture**, а не JSON, переименованный в `.xlsx`.

Он должен:

- открываться стандартным XLSX parser;
- содержать несколько sheets;
- текст;
- числа;
- пустые ячейки;
- формулу или формульную ячейку, если это требуется манифестом;
- merged cells, если они относятся к существующим случаям;
- Unicode/русский текст.

Фикстура должна быть детерминированной.

Если для Locus cases 10/14/15 нужны конкретные структуры — воспроизвести именно их.

# Обязательные security/regression tests

Особенно проверить:

1. RDWeb run не вытесняется local при auto-selection;
2. local job, завершившийся позже RDWeb, всё равно не становится preferred;
3. PDF ambiguous route не OCR-ится автоматически;
4. explicit local PDF обрабатывается;
5. повтор идентичной обработки идемпотентен;
6. изменение recognizer version создаёт новый run;
7. изменение configuration hash создаёт новый run;
8. DOCX anchors воспроизводимы;
9. XLSX sheet/cell anchors воспроизводимы;
10. CSV row/column anchors воспроизводимы;
11. historical search остаётся на нужном recognition run;
12. `contract.read` проверяется для договорных результатов;
13. отзыв `contract.read` после индексации немедленно закрывает выдачу;
14. локальное распознавание не расширяет evidence_scope само;
15. failed/needs_review результат не маскируется как полноценный successful run;
16. повреждённый DOCX/XLSX;
17. CSV с другой кодировкой;
18. очень большой файл — применяются установленные limits;
19. worker restart/retry;
20. duplicate job;
21. clean migration;
22. upgrade от принятой схемы Stage 06a;
23. регрессия Stage 04–06a.
