## 1. PortalCaptureStrategy

Механизм согласованности `portal_capture` принимается для режима `provisional`.

Проверено, что реализация сверяет не только `overview` до/после, но и:

- `cached_grand_total`;
- валютные курсы;
- количество позиций;
- количество BOQ-строк;
- наборы position ID между paginated positions и with-costs;
- общие поля позиции между этими маршрутами;
- дубли позиций при пагинации;
- `items_count` позиции против фактических BOQ-строк;
- принадлежность BOQ-строки известной позиции;
- `updated_at` строк относительно начала выгрузки по часам источника.

При обнаружении расхождения попытка становится `inconsistent`, нормализованное содержимое не создаётся и `calculation_revision` не появляется.

Это достаточная защита для принятой модели **provisional capture**, но не является и не должна называться доказательством атомарной ревизии TenderHub.

X-01 остаётся необходимым для настоящей `verified` source revision.

## 2. Неизменяемость содержимого

Модель `calculation_content` принимается.

БД самостоятельно обеспечивает:

- соответствие `content_hash` фактическому составу;
- соответствие заявленного числа позиций и строк;
- формирование содержимого в транзакции создания;
- запрет последующего INSERT в зафиксированный состав;
- запрет UPDATE/DELETE/TRUNCATE;
- повторное использование идентичного содержимого по hash.

Защита не полагается только на API приложения.

## 3. Линейность ревизий

Реализация принимается.

Перед созданием/выбором ревизии транзакция блокирует соответствующий `tender_stage`.

Под этой блокировкой выполняются:

- определение последней ревизии;
- решение о повторном использовании;
- создание следующей ревизии;
- событие `calculation_revision_added`;
- завершение capture.

Таким образом, последовательность ревизий защищена и от конкурентных capture одного этапа.

## 4. Provisional / verified

Граница соблюдена.

Подтверждено:

- portal capture создаёт только `provisional`;
- `verified` требует внешнюю ссылку на ревизию источника;
- запись ревизии immutable;
- source-status events допустимы только для `verified`;
- `provisional` не может получить `closed_at_source`;
- X-01 остаётся OPEN;
- `TenderHubRevisionReader` остаётся `BLOCKED_EXTERNAL`;
- `CALCULATION_PROVISIONAL` не снимается.

## 5. Деньги и точность

ADR-005 реализован приемлемо.

Числовые значения TenderHub сохраняются как десятичные строки и передаются PostgreSQL как `numeric`, без промежуточного бинарного `float`.

Исходные числовые лексемы сохраняются.

Есть отдельная регрессия прохождения значения с 21 значащей цифрой через:

`HTTP response → parser → domain → PostgreSQL → portal API`

без изменения значения.

## 7. RT-04 / A07

Покрытие принимается.

Проверяются:

- повтор одинаковой выгрузки;
- одинаковые строки при разных курсах;
- одинаковые строки при разном source total;
- одинаковый total при разных строках;
- A → B → A → повтор;
- новая ревизия после изменения;

- verified с содержимым прежней provisional в контрактном сценарии X-01;

Контрактное покрытие принимается:

- 401;
- 403;
- 404;
- 429;
- 5xx;
- `ENDPOINT_DISABLED`;
- non-JSON response;
- timeout;
- превышение размера ответа;
- gzip;
- обрыв после части пагинации;
- зацикленный cursor;
- изменение данных между маршрутами;
- изменение данных во время выгрузки.

Одна страница многостраничного результата не принимается за полный расчёт.
