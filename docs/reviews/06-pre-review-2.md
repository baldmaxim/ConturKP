## R06-01 — дублирующийся BOQ ID не определяется как несогласованность

**Severity: MEDIUM**  
**Статус: OPEN**  
**Блокирует U-04: да — исправить до живого прогона.**

### Сценарий

TenderHub возвращает для одной позиции, например:

ожидалось:

`A, B, C`

фактически:

`A, A, C`

При этом:

- общее количество BOQ-строк не изменилось;
- `items_count` позиции не изменился;
- строки относятся к существующей позиции;
- остальные контрольные признаки могут совпасть.

Текущая `PortalCaptureStrategy` считает количество строк по позиции, но не проверяет уникальность `boq.value[].id`.

В результате попытка может пройти consistency как `consistent`.

Позже БД отклоняет содержимое по UNIQUE с PostgreSQL `23505`.

Ложная `calculation_revision` при этом не создаётся — защита БД работает.

Однако worker распознаёт как DB invariant только:

- `23514`;
- `55000`.

`23505` превращается в `internal`, задача повторяется без смысла и завершается `failed/internal`.

### Требуемое исправление

Нужны две линии защиты.

#### 1. PortalCaptureStrategy

Добавить явную проверку уникальности BOQ row ID.

При повторе одного `boq item id` попытка должна стать:

`inconsistent`

с отдельной машинной причиной, например:

`item_duplicated`

или эквивалентным стабильным кодом в принятой модели.

Не создавать `content`.

Не доходить штатно до UNIQUE-ошибки БД.

Добавить регрессию минимум:

`A,B,C → A,A,C`

при неизменных:

- общем числе строк;
- `items_count`;
- position ID;
- overview markers.

Ожидание:

`consistency.outcome = inconsistent`

ревизия отсутствует.

#### 2. Defense in depth — worker

Отдельно обработать `23505` от записи calculation content/revision как отказ целостности данных, а не `internal`.

Не следует глобально объявлять **любой** `23505` во всём worker DB-invariant.

Ограничить обработку контекстом завершения calculation capture и, желательно, ожидаемыми constraint (ограничениями) calculation-схемы.

Если БД всё же обнаружила дубликат/нарушение уникальности содержимого, результат должен быть диагностируемым, например:

`content_rejected_by_db`

а не:

`internal`.

Не делать бессмысленные retry (повторы), если ошибка детерминированная.

### Тесты

Добавить минимум:

1. duplicate BOQ ID определяется стратегией до БД;
2. одинаковое число строк и совпадающий `items_count` не скрывают дубликат;
3. content/revision не создаются;
4. DB `23505` в calculation-completion fallback классифицируется как `content_rejected_by_db`, а не `internal`;
5. такой deterministic failure (детерминированный отказ) не выполняет бесполезные сетевые retry;
6. нормальный BOQ с уникальными ID остаётся PASS.
