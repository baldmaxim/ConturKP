# Контур КП — AD-06a-1

**Решение: вариант B.**

**Статус Stage 06a после фиксации решения: READY_TO_IMPLEMENT.**

## 1. Решение

Для договорного контура использовать **явный `contract_id` и контролируемые составные внешние ключи**, а не `tender_id = NULL` с восстановлением принадлежности триггерами.

Вариант A отклоняется.

## 2. Почему отклонён вариант A

Не использовать модель:

`document.tender_id = NULL → принадлежность договора определяется косвенно`

с последующей проверкой владельца через триггеры.

Причины:

- исчезает простой декларативный FK-инвариант существующей модели;
- одна и та же колонка начинает означать «тендер» для одного типа документа и «не применимо» для другого;
- downstream-таблицы получают nullable ownership (необязательное владение);
- для каждой операции приходится определять реального владельца условной логикой;
- права становятся труднее доказываемыми на уровне БД;
- возрастает риск утечки через search/evidence;
- индексы и JOIN становятся менее однозначными;
- будущие виды владельцев будут провоцировать дальнейшее расширение набора `NULL + trigger`;
- ошибка в одном guard-trigger способна нарушить весь ownership chain (контур принадлежности).

Экономия нескольких колонок не оправдывает такой архитектурный долг.

## 3. Принцип варианта B

Для договорных документов ввести явную идентичность договора:

`contract_id`

Договор является самостоятельным объектом доступа и жизненного цикла.

Но **не дублировать `contract_id` механически во все downstream-таблицы**, если принадлежность уже однозначно выводится через внешний ключ.

Принцип:

> Новая ownership-колонка добавляется только туда, где она необходима для декларативного инварианта, уникальности, FK или безопасного запроса.

Не добавлять её просто «для удобства JOIN».

## 4. Базовая модель

Минимально:

`contract`
→ `contract_document`
→ `document`
→ `document_revision`

или эквивалентная модель, если текущая спецификация D-017 уже задаёт конкретные имена сущностей.

Связь договор ↔ тендер хранить отдельно:

`contract_tender`

с many-to-many (многие-ко-многим), согласно D-022.

Не делать сам договор принадлежащим ровно одному тендеру.

## 5. Document ownership

На уровне документа должна существовать однозначная декларативная принадлежность:

- обычный тендерный документ — tender ownership;
- договорный документ — contract ownership.

Запрещено состояние:

- одновременно tender и contract owner;
- ни tender, ни contract owner для типов документов, которым owner обязателен.

Это обеспечить DB constraint (ограничением БД), а не только TypeScript.

Если существующая таблица `document` требует `tender_id NOT NULL`, миграция может расширить её до модели:

`owner_tender_id NULL`
`owner_contract_id NULL`

с `CHECK`, гарантирующим допустимую комбинацию в зависимости от типа документа,

**либо** использовать отдельную contract-document relation, если она позволяет сохранить существующий `document.tender_id NOT NULL` без фиктивного тендера.

Выбрать более узкий вариант после проверки фактической схемы.

**Фиктивный tender_id для договора запрещён.**

## 6. Downstream ownership

Для:

- `document_revision`;
- `recognition_run`;
- `evidence_fragment`;
- search/index;
- blob references;

сначала использовать существующие FK:

`row → document_revision → document → owner`

Если этот путь однозначный и БД гарантирует ссылочную целостность, отдельный `contract_id` в такую таблицу **не добавлять**.

### Когда `contract_id` добавлять

Только если таблица сейчас имеет собственный обязательный составной ключ вида:

`(document_revision_id, tender_id)`

и этот `tender_id` участвует именно в DB-инварианте, который невозможно сохранить ссылкой только на `document_revision`.

Тогда разрешено расширить ключ до альтернативной contract-ветки.

Но каждая такая колонка должна быть отдельно обоснована в migration report.

## 7. Запрет универсального owner_type

На Stage 06a **не вводить** универсальную полиморфную схему:

`owner_type + owner_id`

если она не требуется доказанно более чем двум типам владельца.

Сейчас существуют конкретные домены:

- tender;
- contract.

Использовать типизированные FK безопаснее универсального owner ID без обычного внешнего ключа.

Если разработчик считает, что нужен `owner_type`, остановиться и вынести отдельное архитектурное решение.

## 8. Evidence scope

`evidence_scope` должен фиксировать конкретный:

`document_revision_id`.

При этом принадлежность revision определяется через document.

Для договорной revision scope не должен требовать фиктивного `tender_id`.

Если текущий ключ:

`(document_revision_id, tender_id)`

делает это невозможным, схему scope необходимо расширить.

Новый инвариант:

- scope содержит конкретную immutable document revision (неизменяемую редакцию документа);
- revision имеет ровно одного нормативного владельца документа;
- inclusion in scope (включение в scope) не выдаёт право доступа.

## 9. Search

Search index (поисковый индекс) может хранить denormalized (денормализованный) `contract_id` **только если это требуется для безопасного и эффективного фильтра прав**.

Это допустимое исключение.

Если `contract_id` добавляется в index:

- значение должно выводиться из document/document_revision;
- клиент не может передать произвольный contract_id при индексировании;
- БД/worker должны проверять соответствие;
- нельзя изменить owner индексированной строки независимо от document revision.

## 10. Права

Сохраняется D-022:

для договорного evidence нужны одновременно:

- scope допускает конкретную revision;
- пользователь имеет `contract.read`.

`tender.read` не заменяет `contract.read`.

`contract.read` не заменяет membership (членство) конкретной revision в scope.

Администратор без `contract.read` не получает содержимое.

## 11. Допсоглашения и приложения

Не создавать отдельные ownership-модели.

Использовать тот же `contract_id`.

Тип/роль документа:

- contract;
- addendum;
- appendix.

Для addendum/appendix хранить явную связь с основным договором/документом согласно принятой доменной модели.

Они наследуют contract ownership, но не обязательно являются новой revision основного файла: самостоятельный файл допсоглашения должен оставаться самостоятельным document.

## 12. Миграция

До написания основной migration developer должен составить короткую migration matrix:

`таблица → почему сейчас нужен tender_id → можно ли вывести owner через FK → что меняется → новый DB-инвариант`

для всех десяти выявленных таблиц.

Правило:

- если owner можно безопасно вывести через уже существующий FK — колонку не добавлять;
- если колонка необходима для самостоятельного DB-инварианта — добавить contract-ветку;
- каждый nullable FK должен сопровождаться CHECK;
- не должно появиться состояния ambiguous owner (неоднозначный владелец).

## 13. Обязательные DB-тесты

Проверить минимум:

1. tender document не может одновременно принадлежать contract;
2. contract document не может одновременно принадлежать tender;
3. документ не может иметь недопустимо нулевого owner;
4. `contract_id` должен существовать;
5. удаление contract не должно осиротить revisions;
6. document revision не может сменить owner задним числом;
7. recognition не может сослаться на revision другого owner через поддельный ID;
8. evidence scope принимает contract revision;
9. historical scope сохраняет старую revision после появления новой;
10. search row нельзя привязать к чужому contract;
11. один contract может быть связан с двумя tenders;
12. один tender может быть связан с двумя contracts;
13. удаление `contract_tender` не меняет owner исторической document revision;
14. архивирование contract не удаляет evidence;
15. одновременная попытка создать конфликтующую ownership-связь завершается отказом БД.

## 14. Масштаб изменения

AD-06a-1 разрешает изменение схемы, необходимое для поддержки contract ownership.

Но это **не разрешение перепроектировать Stage 03–05**.

Разработчик обязан минимизировать diff.

Если после migration matrix выяснится, что действительно требуется менять все десять таблиц, это допустимо только если для каждой строки показана конкретная DB-причина.

Если часть из десяти таблиц может получать owner через `document_revision`, оставить её без новой ownership-колонки.
