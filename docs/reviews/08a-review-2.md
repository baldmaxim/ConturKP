## R08a-01 — P1, остаётся открытым: состояние всего фрагмента скрывает заменённый факт

Место: `packages/core/src/answers/packet.ts:44–54`, далее `claimChecks.ts`.

Исходный случай Review 08a-1 («30 дней» с цитатами старой и новой редакций) теперь отклоняется; штатные негативные тесты добавлены. Но новая пометка `superseded` ставится фрагменту только если **все** его факты перекрыты. Если в том же фрагменте есть другой действующий факт, старое значение теряет пометку, и числовой гейт снова принимает его как текущее.

Воспроизведение:

1. Один фрагмент основного договора: «3.1. Аванс в размере 20% от цены договора. Гарантийный срок составляет 5 лет.»
2. Явно связанное датированное допсоглашение меняет пункт 3.1: аванс 10%.
3. Граф корректно ставит факту аванса 20% `superseded`, факту гарантии — `active`.
4. Пакет считает весь старый фрагмент `current`. Черновик «Действующий аванс составляет 20% от цены договора» с одной ссылкой на него получает `passed: true`, renderer — `confirmed`.

Сценарий повторён через настоящий маршрут диалога и worker: GET графа показывает 20% как `superseded`, таблица `answer_evidence` для того же старого фрагмента — `current`, ответ API — `confirmed_by_citations`, текст содержит «Действующий аванс составляет 20%».

Это не ограничение полноты извлечения: оба факта успешно извлечены, замена уже вычислена графом. Дефект появляется при переносе статуса факта на общий фрагмент. Фрагменты распознавания могут содержать несколько условий; норматив не требует отдельного фрагмента на каждый тип факта.

Нужно проверять поддержку конкретного действующего значения/типа факта по графу либо передавать в пакет сведения о состояниях отдельных фактов. Действующая гарантия не должна легализовать заменённый аванс. Сохранить возможность отвечать о гарантии и об истории аванса. Добавить негативный тест фрагмента с одновременно действующим и заменённым фактом.

## R08a-03 — P1, новый: допсоглашения одной даты заменяют друг друга по кругу

Место: `packages/core/src/facts/graph.ts:179–213`, особенно фильтр семейных документов с `documentDate <= amendment.documentDate`.

Вход: основной договор с авансом 20%, два явно связанных допсоглашения от 01.03.2026, оба заменяют пункт 3.1, одно устанавливает 10%, другое — 15%. Временной порядок между ними неизвестен.

Результат: первое допсоглашение перекрывает в том числе факт второго (тот уже включён в кандидаты той же даты), затем второе перекрывает первое. Оба факта `superseded`; `10% → 15% → 10%`. Старый аванс тоже перекрыт. Действующего аванса нет, открытых замечаний нет. Сортировка по идентификатору документа не устанавливает реальный порядок подписания и не предотвращает цикл.

Подтверждено также на извлечённых из документов фактах через GET `/contracts/{id}/fact-graph`: статусы обоих значений `superseded`, ссылки `supersededByFactId` взаимные, число открытых замечаний — ноль.

Ожидается: неоднозначность порядка не разрешается автоматически. Различающиеся значения одной даты должны оставаться доступными как конфликт/неоднозначность с замечанием человеку; в графе перекрытий не должно быть цикла. Добавить тест одинаковой даты, включая результат API и отсутствие взаимного `supersededByFactId`.
