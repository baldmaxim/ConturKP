## R08a-04 — P2: состояние аванса применяется к НДС из-за совпадения процентов

Место: `packages/core/src/answers/claimChecks.ts:128–132`, использование в `usedFacts`, `stale` и `conflictFactTypes` (строки 158, 175, 185).

`usesValue` считает, что утверждение использует факт, если хотя бы одно число с той же единицей совпало с `rawValue`. Тип факта и название условия не проверяются. НДС 20% поэтому считается одновременно использованием аванса 20%. Состояния разных условий начинают влиять друг на друга даже при правильном графе.

Негативный сценарий:

1. Основной договор содержит один фрагмент: «3.1. Аванс в размере 20% от цены договора. НДС 20%.»
2. Явно связанное датированное допсоглашение меняет только аванс на 10%.
3. Факт `advance_percent=20%` становится `superseded`; `vat_rate=20%` остаётся `active`.
4. Корректный черновик «НДС 20%.» с цитатой этого фрагмента получает `superseded_evidence` по **авансу**, статус `contradicted`. Числовая опора для НДС существует; сама фраза «НДС 20%» не удаляется `currentText`. Отклонение создаёт именно ошибочное сопоставление типов.

Непосредственный вызов ядра и renderer подтверждает: `passed: false`, outcome `insufficient`, корректный НДС не показывается.

Независимый интеграционный тест подтвердил весь путь: штатная загрузка основного договора и допсоглашения, извлечение фактов worker, GET графа (`vat_rate` — `active`, старый `advance_percent` — `superseded`), создание диалога, вопрос «Какова ставка НДС?», черновик «НДС 20%.» с существующей читаемой цитатой. Ответ API не `confirmed_by_citations`, `droppedIssues.superseded_evidence = 1`, текст НДС удалён. Тем самым дефект не ограничен искусственными объектами модульной проверки.

Вторая форма того же дефекта: при `advance_percent=20%` в конфликте, действующем НДС 20% и второй стороне аванса 15% утверждение «НДС 20%» получает `conflictFactTypes: ['advance_percent']`; renderer ошибочно выдаёт outcome `conflict` с цитатами аванса. НДС при этом не конфликтует.

Ожидается: статус используется по тому **типу и значению** факта, который утверждение называет. Совпадение величин у разных типов не должно ни блокировать подтверждение НДС, ни переносить на него конфликт аванса. Исправить сопоставление, сохранив защиту заменённого аванса; добавить тесты одинаковых процентов разных типов при `superseded` и `conflict`, включая API/worker. Простое исключение совпавших чисел из проверки ослабит R08a-01 и не является исправлением.

Это воспроизводимый отказ проверки ядра, а не оценка качества живой модели и не недостаток извлечения: факты уже извлечены и имеют правильные состояния. Все вводимые в сценарий условия документальные, права на них есть.

## Повторная проверка прежних дефектов

**R08a-01 закрыт.** В пакет теперь передаются `facts` с `rawValue` и состоянием. Собственный сценарий Review 08a-2 повторён через API/worker: «старый аванс 20% + действующая гарантия 5 лет» больше не выдаёт текущий аванс 20%. Общая пометка основания остаётся `current`, но проверка отклоняет старое значение по состоянию факта. Штатные тесты сохранения гарантии, истории и нового аванса проходят в полном наборе. Новый R08a-04 записан отдельно как перенос статуса между **разными типами с одинаковой величиной**.

**R08a-03 закрыт.** Собственный сценарий Review 08a-2 через API показывает авансы 10% и 15% в `conflict`, взаимных ссылок `supersededByFactId` нет, открыто одно замечание. Штатный тест проверяет все три значения 20/10/15%. Датированные допсоглашения обрабатываются группами дат. Различные значения одной даты не перекрывают цель, отношения между допсоглашениями возможны только при строго более поздней дате; есть защита от циклических решений человека. Номера документов и UUID не превращаются в правило временного приоритета.

**R08a-02 остаётся закрытым.** Проверка текущих прав перед передачей истории сохранена и подтверждена отдельным независимым тестом отзыва `contract.read` между ходами: скрытый текст Д-СЕКРЕТ отсутствует в истории и пакете следующего запроса модели.
