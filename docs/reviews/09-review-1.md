## R09-01 — P1: событие, обработанное до результатов, не инвалидирует поздно записанное замечание и принятие риска

Места: `packages/db/src/invalidation.ts:150–224`, `packages/db/src/reviewRuns.ts:243–276`, `apps/server/src/routes/reviews.ts:140–176`.

Воспроизведение через API и настоящий worker:

1. Подтвердить требование «кладка 55 м3», покрыть строкой расчёта 50 м3.
2. Поставить проверку в очередь на прежнем снимке.
3. Штатным импортом зарегистрировать новую редакцию ТЗ. Обработать событие `document_revision_registered` до выполнения `review.run`.
4. Выполнить `review.run` и `review.model`, не выполняя пока распознавание новой редакции. Это допустимый порядок независимых заданий; прямого изменения таблиц продукта в тесте нет. Обработчик инвалидации вызван в транзакции для детерминированного порядка.
5. Открыть прогон и принять риск по найденному расхождению.

Получено: `freshness.outdated=true`, но замечание `open`; API принятия риска отвечает **200**, статус становится `accepted_risk`, у нового решения `invalidatedReason=null`.

Причина: обработанное событие больше не пересматривается; результаты и зависимости появились позже. При записи замечаний нет проверки уже обработанных событий. Команда принятия риска проверяет статус, права и вид замечания, но не актуальность основания. Позднейшее событие распознавания иногда маскирует дефект, однако его выполнение не гарантировано и не является защитой транзакции решения.

Ожидается: поздние результаты сопоставляются с событиями после закреплённого входа и соответствующее замечание сразу становится устаревшим; запись действующего решения/риска по затронутому прежнему основанию запрещена до перепроверки. Проверка актуальности должна удерживаться вместе с доменной блокировкой этапа. Нужен тест именно события до результатов, а не только изменения после готового отчёта.

## R09-02 — P1: содержимое реестра не закреплено при запуске, позднее изменение незаметно входит в старый прогон

Места: `packages/db/src/reviewRuns.ts:82–107`, `packages/db/src/reviewInputs.ts:107–165,318–325`, `apps/worker/src/handlers/review.ts:59–76`, `apps/server/src/reviewMappers.ts:95–110`.

Воспроизведение:

1. Поставить прогон в очередь при активном реестре без подтверждённых требований.
2. После ответа API запуска создать и подтвердить новое требование через обычные API кандидатов.
3. Выполнить очередь и открыть первоначальный прогон.

Получено: для того же `review_run` входы до изменения содержат 0 требований, после — 1. Программные проверки и модель проверяют позднее добавленное требование. Готовый прогон сообщает **`freshness.outdated=false`, `reasons=[]`**.

Причина: закреплён лишь `registry_id`; `requirementsOf` читает текущие подтверждённые требования, их `current_revision_id` и последнее покрытие. `contentFingerprint` вычисляется уже при выполнении задания, поэтому изменение между API запуска и исполнением становится исходной точкой проверки актуальности. Дополнительно модель читает требования отдельным заданием, что оставляет возможность различия её входов с программной частью.

Ожидается: при запуске закрепляется проверяемое содержимое входов, включая конкретные редакции требований, покрытие и влияющие записи. Программная часть и модель используют один неизменяемый набор. Изменение после запуска не должно незаметно подменять входы прежнего прогона; если архитектура отменяет такой прогон, это явно отражается, а новый запуск имеет собственный ID и снимок.

## R09-03 — P1: новое действующее решение разрешено по уже устаревшему разногласию

Место: `apps/server/src/routes/discrepancies.ts:130–178`.

Воспроизведение независимо от гонки R09-01:

1. Завершить проверку требования 55 м3 против строки 50 м3, создать разногласие у замечания.
2. Загрузить новую редакцию ТЗ, обработать инвалидацию. Убедиться, что замечание уже имеет статус **`stale`**.
3. Руководителем отправить `POST /discrepancies/:id/decisions` с новым решением.

Получено: **201**, в истории разногласия появляется `discrepancy_decision` с **`invalidatedReason=null`**, несмотря на устаревшее замечание. Здесь не требуется попадать в узкое окно выполнения worker.

Причина: маршрут проверяет права и видимость оснований, но не статус замечания и не актуальность основания. Событие, сделавшее его устаревшим, уже обработано и не инвалидирует последующее решение автоматически. Если обе стороны являются фактами, этот же маршрут также имеет ветку записи решения в граф; её последствия в данном воспроизведении отдельно не проверялись.

Ожидается: API отвергает запись действующего решения по устаревшему основанию (409 с причиной) до перепроверки/обновления разногласия. Проверка выполняется внутри транзакции после блокировки этапа и замечания. Аналогичные команды осей и графа следует проверить на такой же обход; этот отчёт не утверждает, что они независимо воспроизведены.
