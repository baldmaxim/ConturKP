## 3. Перепроверка исходных дефектов

**R10-01 — закрыт по исходным сценариям Review 10-1 (документ и OCR).** Новая причина по заменённой редакции документа и прежнему прогону распознавания получает 409 после обработки событий; авторские тесты проверяют также отказ до обработки, прямую запись в БД, сохранение истории и исключение/возврат в состав источников. Действующее основание разрешено. Новая миграция 0027 введена без изменения применённой 0026, что соответствует ADR-002. Дополнительный непокрытый тип основания — QA — описан отдельно как R10-03.

**R10-02 — закрыт в части вычисления.** При переходе `100 м2 × 10 RUB` → `1 000 000 см2 × 0,001 RUB` ложных вкладов объёма и цены больше нет. При неизменной сумме сохраняются нулевые `not_decomposable` с `reason=unit_changed`, `fromUnit=м2`, `toUnit=см2`; при изменённой сумме вся дельта пары отнесена к «без разложения». Неизменная единица по-прежнему даёт правильные объём +100 и цену +20, сумма вкладов совпадает с дельтой. Отдельная проблема видимости нулевого вклада — R10-04.

## 4. R10-03 — заменённый ответ заказчика подтверждает новую причину

**Критичность: P1. OPEN.** Это тот же механизм запоздалой записи после обработки события, что в R10-01, но для разрешённого типа основания `qa_answer`.

### Воспроизведение

1. Через `POST /tenders/{id}/qa-imports` импортировать вопрос «Изменена ли площадь штукатурки?» с ответом «Заказчик подтверждает увеличение площади штукатурки до 110 м2». Сохранить ID фрагмента ответа; включить обычный документ в состав и закрепить снимок области.
2. Создать сравнение ревизий расчёта. Импортировать новую редакцию того же QA-вопроса: «Предыдущее разъяснение отменено: площадь штукатурки остаётся 100 м2».
3. Убедиться, что новая `qa_item_revision.supersedes_revision_id` указывает на старую; закрепить новую область и обработать события инвалидации. В момент записи необработанных событий этапа **0**.
4. Контроль: подтвердить причину по новому ответу — **200**, `basisChanged=false`.
5. Записать следующую версию причины с `reasonKind=answer`, `reasonStatus=confirmed`, `fragmentIds=[старый ответ]`.

**Фактически:** API отвечает **200**, новая версия получает `reasonStatus=confirmed`, `basisChanged=false`, `invalidations=[]`. `change_basis_supersession(stage, oldFragment, NULL)` возвращает **NULL**, хотя редакция ответа уже заменена.

**В обход API:** транзакция вставляет `change_explanation` и `change_explanation_basis` по старому QA-фрагменту, затем делает COMMIT — **без ошибки**. Следующая версия сохраняется. Ожидалось отклонение с SQLSTATE `23514`.

### Причина и последствия

`docs/migrations/0027_change_basis_freshness.sql:16` проверяет типы `recognition_run`, `mail_message_revision`, `transcript_revision` и редакции документов, но не `qa_item_revision`. API и оба DB-триггера пользуются этой функцией, поэтому пропуск общий для обеих линий защиты.

При этом `packages/db/src/invalidation.ts:90` уже обрабатывает `qa_form_added` и адресно инвалидирует зависимости от прежней `qa_item_revision`. После обработки события новая причина появляется слишком поздно для этой инвалидации. Инженер получает ложное действующее подтверждение изменения стоимости по отменённому ответу заказчика.

### Требуемое исправление и приёмка

- Проверять замещение редакции QA-ответа при новой записи причины через API и в БД, независимо от состояния обработки событий. Уже применённую 0027 не переписывать: заменить функцию следующей миграцией по ADR-002.
- Старый ответ должен давать **409 `basis_superseded`**; прямой INSERT/COMMIT — отказ; новая действующая редакция — по-прежнему разрешена.
- Не создавать новую версию/основание при отказе; сохранять прежнюю историю и корректную инвалидацию существующих причин.
- Добавить регрессии до и после обработки события, через API и в обход API, с положительным контролем нового ответа.

Доказательство: первые три теста `reviewer10b.test.ts`, маркеры `REVIEW10B_STALE_QA_API` и `REVIEW10B_STALE_QA_DB`; компактные фактические данные — `independent-evidence.json`.

## 5. R10-04 — смена единицы исчезает из списка изменившихся позиций

**Критичность: P2. OPEN.** Вычисление исправлено, но специально сохранённая диагностика недоступна в стандартном представлении.

### Воспроизведение и результат

1. Две выгрузки той же версии TenderHub: у одной и той же строки/позиции меняются `м2`, количество 100, цена 10 → `см2`, количество 1 000 000, цена 0,001. Себестоимость 1000 RUB и коммерческая сумма 1200 RUB остаются прежними.
2. Подтвердить пару позиций; построить сравнение. Без фильтра API возвращает позицию «Штукатурка стен», оба нулевых вклада `not_decomposable` и причину `unit_changed` с единицами до/после.
3. Вызвать `GET /comparisons/{id}/units?changed=true&limit=200` — **эта позиция отсутствует**, `hasMore=false`; это не пагинация.
4. Открыть сравнение в настоящем браузере. Флажок «только изменившиеся» включён по умолчанию — позиции нет. Снять флажок — она появляется с текстом «Без разложения: смена единицы строки — пересчёт не подтверждён (м2 → см2)» и суммой 0.

В отдельном браузерном сценарии пара подтверждена системой по одному экземпляру/тендеру/версии/UUID; сценарий API проверяет также ручное подтверждение. Контроли выгрузки и готового сравнения проходят.

### Причина и требуемое исправление

`packages/db/src/economics.ts:532` считает изменившимися только unmatched/несопоставимые единицы и неравенство денежных сумм. Нулевые диагностические вклады не учитываются. `apps/web/src/pages/economics/UnitsList.tsx:72` включает этот фильтр по умолчанию.

Это расходится с `docs/stages/10-report.md:97` и проектом §13 п. 15: нулевой вклад специально сохраняется, чтобы смена единицы оставалась видимой. Пользователь стандартного списка пропускает изменение масштаба количества/цены, хотя пересчёт единиц не подтверждён.

Добавить признак диагностического изменения в фильтр изменившихся позиций (как минимум `unit_changed`); не возвращать фиктивное разложение и не менять исходные суммы. Приёмка: позиция есть в `changed=true` и в исходно открытом интерфейсе; обычные неизменённые строки остаются отфильтрованными. Проверить нулевую и ненулевую денежную дельту.

Доказательство: четвёртый тест `reviewer10b.test.ts`, `windows-reviewer-unit-ui.log`, снимки `reviewer-ui-shots/390-unit-change-filter-on.png` и `390-unit-change-filter-off.png`. Скрипт ревьюера — копия проектной UI-обвязки с дополнительным сценарием, отдельной БД и отдельным журналом; код продукта не менялся.
