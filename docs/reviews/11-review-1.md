## R11-01 — косвенное основание не наследует права источника — P1

**Сценарий.** Руководитель читает закрытый ящик и подтверждает требование с основанием-письмом. Он записывает текст этого требования в поле, указав основание `requirement_revision`. Инженер участвует в том же тендере, но не имеет `mail.read` на этот ящик.

**Ожидание.** Значение поля и история скрыты целиком, как само требование. Подтверждение такого значения инженером отвергается без раскрытия текста.

**Факт.** API требования возвращает `restricted: true, statement: null`. API приложения и история поля возвращают полный секретный текст с `restricted: false`; `confirm` отвечает 200 и создаёт ещё одну открытую версию. Два независимых теста падают.

**Причина.** Представление версии собирает права только по непосредственному `fragmentId` основания. У `requirement_revision` он `null`, поэтому проверка фактически проходит по пустому списку. Команда подтверждения аналогично проверяет только основания типа `fragment`.

Источник: [formsView.ts:149](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/apps/server/src/formsView.ts:149>), [formsView.ts:190](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/apps/server/src/formsView.ts:190>), [formDrafts.ts:55](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/apps/server/src/routes/formDrafts.ts:55>).

**Исправить.** Проверять полную цепочку источников каждого вида основания при чтении текущего значения, истории и при командах. Для требований сохранить правила R08-02: любые роли оснований и унаследованный текст. Аналогично проверить факты и решения; отсутствие непосредственного `fragmentId` не означает общедоступность. Это требование ADR-006, I13 и проекта этапа §1.1.

## R11-02 — «Обсудить» раскрывает скрытое значение — P1

**Сценарий.** Руководитель записывает поле по непосредственному фрагменту закрытого письма. Инженер без права на ящик получает `restricted: true, value: null`. Он вызывает `discuss`, передавая только комментарий и ответственного, без значения.

**Ожидание.** Команда не может прочитать, скопировать и открыть скрытый текст. Допустимо отказать либо хранить обсуждение отдельно, сохранив ограничения исходного значения.

**Факт.** Команда отвечает 200. Новая версия содержит секретный текст, `origin: manual`, `restricted: false`, `bases: []`. Пользователь получает текст, которого до команды не видел. Один независимый тест падает.

**Причина.** Ветка `discuss` копирует `latest.value`, не проверяя доступ к этой версии, затем удаляет все основания. Значение выглядит как общедоступный ручной ввод, хотя пользователь его не вводил.

Источник: [formDrafts.ts:157](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/apps/server/src/routes/formDrafts.ts:157>).

**Исправить.** Серверное обсуждение не должно снимать происхождение и ограничения автоматически скопированного значения. Добавить проверки для закрытого основания и отзыва доступа после создания версии. При переносе и других командах, копирующих прежнее значение, проверить тот же принцип.

## R11-03 — требование и факт обходят актуальность исходного документа — P1

**Сценарии.** После загрузки новой редакции ТЗ записать поле по подтверждённой ревизии требования, основанной на старом ТЗ. После новой редакции договора принять прежний факт гарантии, пока граф не перестроен. Затем записать первую из этих версий непосредственно через БД ролью `kontur_app`, в обход HTTP.

**Ожидание.** Заменённый исходный документ не подтверждает новую версию поля независимо от промежуточного статуса требования/факта и порядка фоновых заданий. API — `409 basis_superseded`, БД — отказ.

**Факт.** Обе команды API отвечают 200, новые версии имеют `stale: false`, основание — `problem: null`. Прямая запись в БД фиксируется без ошибки. Три независимых теста падают. Контрольные SQL-проверки доказывают, что непосредственные фрагменты уже дают `document_revision_superseded`, а старый факт всё ещё имеет статус `active`.

**Причина.** `field_basis_problem` проверяет у требования только `confirmed` и отсутствие следующей ревизии; у факта — только состояние `fact_state`. Актуальность исходных фрагментов этих сущностей не проверяется. Вторая линия БД вызывает ту же неполную функцию.

**Исправить.** Раскрывать зависимости косвенного основания и проверять их текущее состояние на запись, подтверждение и в конце транзакции. Обработать документ, повторное распознавание, письмо, ответ заказчика, исключение из состава и замену решения по применимым цепочкам. ## R11-04 — системное предложение суммы теряет единицу и валюту — P1

**Сценарии и факт.** `valueFromFactText` возвращает:

| Основание | Единица/валюта поля | Получено | Допустимое поведение |
|---|---|---|---|
| `25 000 000 руб.` | `млн руб.`, RUB | `25000000` | `25` при точном программном переводе либо отсутствие предложения |
| `25 млн руб.` | `руб.`, RUB | `25` | `25000000` при точном программном переводе либо отсутствие предложения |
| `100 руб.` | `USD`, USD | `100` | отсутствие предложения: конвертация валют не задана |

Через настоящий API факт цены из договора с исходной фразой `25 000 000 руб.` предлагается и принимается как `25000000` в поле `млн руб.`. В поле USD тот же факт также принимается; приложение получает `blocking: 0`, а команда завершения отвечает 200, `status: complete`. При этом `raw_value` извлечённого факта уже не содержит валюту: это дополнительная причина считать контекст неизвестным, а не приписывать ему валюту поля.

Три независимых теста падают: ядро и два сценария API. Это проверка детерминированного механизма; живая модель не нужна.

**Причина.** Для денежных единиц используется общий выбор `number/currency`, а из `q.raw` берётся первая числовая запись. Масштаб `млн` и `field.currency` не участвуют. Принятие факта использует тот же результат, сверка не запрещает такую подмену.

Источник: [suggest.ts:152](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/packages/core/src/forms/suggest.ts:152>), [formDrafts.ts:138](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-1/ConturKP/apps/server/src/routes/formDrafts.ts:138>).

**Исправить.** Сохранять и проверять единицу, масштаб и валюту источника. При неизвестном контексте или другой валюте предложение не формировать и не принимать; сверку показывать как «не сверено», а не совпадение. Возможный перевод масштаба выполнять только точным программным способом по принятой семантике, без расчёта моделью. Проверить обе стороны предложения: показ и команду принятия. Основание — D-031 В-11-6/В-11-10 и I10.
