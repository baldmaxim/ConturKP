## R11-03 — у решения не учитывается исходное основание требования-предмета — P1

**Воспроизведение.** Подтвердить требование по фрагменту ТЗ. Записать штатное `requirement_decision` по этому требованию, без собственных цитат: заявление «Принять условие о клинкерном фасаде», обоснование «По подтверждённому требованию». До замены ТЗ запись поля по этому решению проходит — положительный контроль. Загрузить новую редакцию ТЗ. Затем записать поле по прежнему решению через API и непосредственно через БД.

**Ожидание.** Решение, опирающееся на требование с заменённым исходным документом, не подтверждает новую версию поля. API — `409 basis_superseded`, роль `kontur_app` — отказ записи. Отсутствие повторной цитаты у решения не превращает его в независимое от требования основание.

**Факт.** Контрольная функция для фрагмента ТЗ уже возвращает `document_revision_superseded`. Но `field_basis_source_fragments` для решения возвращает **0 источников**, а `field_basis_problem` — `NULL`. API отвечает **200**, версия имеет `stale: false`, основание — `problem: null`. Прямая запись ролью `kontur_app` фиксируется без ошибки. Два новых независимых теста падают.

**Причина.** Ветка решения в функции источников читает только его собственные `evidence_link` и `basis_fragment_ids`; связь `decision.subject_id` с требованием не раскрывается. Проверка прав эту связь уже учитывает в графе закрытости, поэтому значение доступно только читающему исходный документ, но его актуальность проверяется по более короткой цепочке. Нет и зависимости поля от документа для инвалидации в этом сценарии.

Источник: [0030_forms_basis_sources.sql:34](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-2/ConturKP/docs/migrations/0030_forms_basis_sources.sql:34>).

**Исправить.** Учитывать реальные основания требования-предмета решения и применимые связи наследования в проверке актуальности и зависимостях инвалидации. Если решение фиксирует конкретную редакцию требования, сохранять и проверять эту редакцию; не подменять её произвольно текущей. Добавить регрессии для отсутствующих собственных цитат решения, через API и БД, до и после обработки события. Применённые 0029/0030 не переписывать — изменение оформить новой миграцией по ADR-002.

## R11-05 — скопированное значение теряет «устарело» и допускает завершение приложения — P1

**Сценарий A — обсуждение.** В приложении с одним обязательным текстовым полем записать значение по фрагменту документа. Пока источник действующий, нажать «Обсудить»: новая версия хранит то же значение и `value_from_version_id`. Загрузить новую редакцию документа. Прочитать историю и текущую версию; затем вызвать «Подтвердить» и «Отметить заполнено».

**Факт A.** В истории исходная версия имеет `stale: true`, обсуждаемая копия — **`stale: false`**. Подтверждение отвечает **200**, создаёт версию `accepted/manual` с `bases: []`, с сохранённой ссылкой на прежнюю версию, но снова `stale: false`. Завершение отвечает **200**, `status: complete`. Пользователь не вводил нового значения и не предоставлял действующего основания.

**Сценарий B — перенос.** Записать значение по документу, заменить документ, утвердить новую ревизию шаблона и перенести приложение. В отчёте переноса правильно записано `droppedBases: document_revision_superseded`.

**Факт B.** Перенесённое значение ссылается на исходную версию, но имеет **`stale: false`** и пустые основания. Его подтверждение и завершение приложения снова отвечают **200**. Два новых независимых теста падают.

**Ожидание.** Скопированное значение сохраняет не только права, но и актуальность своих оснований. Замена источника должна быть видна у действующей копии; простое подтверждение неизменённого текста по прежнему источнику не делает его текущим. Можно сохранить текст и обсуждение/перенос, но нельзя молча снять проблему основания и завершить приложение. Это следует из проекта этапа §5.6: повторное подтверждение — по действующему основанию.

**Причина.** Цепочка `value_from_version_id` используется для видимости. Однако `stale` вычисляется только по собственным основаниям/инвалидациям последней версии, `confirm` проверяет только `latest.bases`, а зависимости при добавлении версии строятся только из входных `bases`. Обсуждение записывает пустой список, перенос исключает устаревшие основания. Ссылка на источник остаётся, но в актуальности и инвалидации не участвует. Проверка завершения БД тоже рассматривает собственные основания текущих версий.

Источники: [formsView.ts:97](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-2/ConturKP/apps/server/src/formsView.ts:97>), [formDrafts.ts:164](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-2/ConturKP/apps/server/src/routes/formDrafts.ts:164>), [forms.ts:428](</C:/Users/odintsov.a.a/Documents/Codex/2026-10-06/review-11-2/ConturKP/packages/db/src/forms.ts:428>).

**Исправить.** Проверять актуальность оснований и инвалидации по цепочке источников скопированного значения, показывать причину у текущей версии и сохранять зависимости. Проверка записи/подтверждения и завершения, включая вторую линию БД, должна учитывать эту цепочку. Перенос или обсуждение не должны автоматически превращать значение по заменённому документу в ручное значение без проблемы основания. Добавить случаи замены источника как до копирования, так и после него, в том числе для нескольких последовательных копий.
