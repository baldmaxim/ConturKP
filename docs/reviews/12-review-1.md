## R12-01 — Windows: автоматически выбирается неработающий вход LibreOffice (P1)

`apps/worker/src/office/libreoffice.ts:17–25, 62–73`; `docs/runbooks/libreoffice.md:9–11`.

На Windows поиск предпочитает `soffice.exe`, стандартные пути и инструкция тоже указывают на него. На проверенном официальном пакете LibreOffice 26.8.0.3 вызов продуктового `LibreOfficeConverter.version()` через `.exe` заканчивается `converter_unavailable` по тайм-ауту. Это подтверждено и со штатным лимитом **120 секунд**: отказ через 120 025 мс. Через соседний `soffice.com` того же пакета версия успешно возвращается примерно за 2,5 секунды. Проверено повторным запуском `com → exe → com` и независимым тестом автоматического выбора из PATH. Шрифты на результат определения версии не влияют.

Результат: предусмотренная инструкцией конфигурация Windows не позволяет начать сборку. Для остальных проверок использован поддерживаемый явный параметр `SOFFICE_PATH` / `KONTUR_TEST_SOFFICE` со значением пути к `soffice.com`; это обход дефекта, а не исправление продукта.

Нужно обеспечить рабочий выбор и определение версии на Windows, согласовать с ним инструкцию и добавить регрессию автоматического выбора. Проверка версии и реальная конвертация должны пройти без ручной замены выбранного файла.

Доказательства: `outputs/windows-converter-launch-probe.log`, `outputs/windows-exe-default-timeout.log`, `outputs/windows-independent-tests-final.log`, тест `Windows default executable is usable for converter.version` в `reviewer12.test.ts`.

## R12-02 — Можно собрать актуальный комплект по уже устаревшему значению (P1)

`packages/db/src/releaseCandidates.ts:135–141`; `apps/worker/src/handlers/candidates.ts:177–186`; `docs/migrations/0032_release_candidates.sql:327–330`.

Воспроизведение через API и настоящий worker/LibreOffice:

1. Создать приложение с обязательным текстовым полем, записать значение с основанием — фрагментом документа, отметить приложение «заполнено».
2. Загрузить новую редакцию этого документа. GET приложения уже возвращает `latest.stale = true`, но его сохранённый статус остаётся `complete`.
3. Запросить сборку нового комплекта из этого приложения.

Ожидается **409** согласно `12-generation-design.md`, §6, строка `fields_complete`: «нет “устарело” по цепочке … на момент закрепления». Получено **201**, затем `ready_for_approval`, `current = true`, `failure = null`; все записанные проверки проходят. Событие замены произошло до базы кандидата, поэтому проверка событий после сборки его тоже не выявляет.

Причина: при создании проверяется сохранённый статус приложения, но не актуальность закрепляемых версий полей и цепочек оснований. Worker читает значение и состояние версии без проверки свежести; проверка входов в БД допускает такое закрепление.

Нужно проверять заполненность и свежесть именно закрепляемых версий под согласованной блокировкой/транзакцией. Учесть косвенные основания и копии из R11-03/R11-05, а также вторую линию БД. После замены источника новый кандидат по старому значению должен отклоняться; после обновления значения и нового подтверждения — собираться.

Доказательства: `outputs/reviewer12-observations.json`, объект `staleBasis`; независимый тест `fields_complete refuses an already completed draft whose source has since been replaced`.

## R12-03 — После 200 посторонних событий изменение входа теряется (P2)

`packages/db/src/releaseCandidates.ts:205–219`; потребители: `apps/server/src/routes/releaseCandidates.ts:87,133,224–225`.

Воспроизведение через API:

1. Собрать готовый кандидат из приложения A.
2. Сделать 200 правок поля другого приложения B того же этапа. Кандидат A обоснованно остаётся актуальным.
3. Изменить использованное поле приложения A — событие №201 после базы кандидата.

Ожидается `current = false`. Получено **`current = true` и в карточке, и в списке**. В БД есть 201 событие, API возвращает только первые 200, все с `affects = false`.

Причина: `LIMIT 200` применяется до определения влияния событий; признак актуальности вычисляется только из усечённого массива. Последующие события никогда не попадут в эту выборку при неизменной базе кандидата.

Нужно вычислять актуальность по всем событиям, независимо от ограничения списка для интерфейса. Допустим отдельный запрос существования влияющего события либо полное чтение с пагинацией. Сохранить контрольный случай: любые правки исключительно чужих приложений не делают кандидат устаревшим.

Доказательства: `outputs/reviewer12-observations.json`, объект `eventLimit` (`201 / 200 / 0 / current=true`); независимый тест `a relevant change after 200 unrelated field edits makes the existing candidate non-current`.
