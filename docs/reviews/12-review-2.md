## R12-04 — P2: противоположный порядок блокировок поля и комплекта

**Сценарий:** инженер меняет поле заполненного приложения, а другой запрос одновременно собирает комплект с этим приложением. Оба запроса используют штатный API и допустимые права. Последовательная правка проходит, переводит приложение в `in_progress`, и следующая сборка ожидаемо получает `409 drafts_not_complete` — контрольный тест проходит.

При наложении запросов:

1. `PUT /application-drafts/:id/fields/:key` получает блокировку строки `application_draft` через `loadDraft(..., true)` в `apps/server/src/routes/formDrafts.ts:122`.
2. `POST /stages/:id/release-candidates` получает блокировку `tender_stage` в `apps/server/src/routes/releaseCandidates.ts:184` и ждёт строку приложения при `getDraft(..., true)` в `packages/db/src/releaseCandidates.ts:150`.
3. Первый запрос дописывает версию поля и вызывает `emitStageEvents` в `packages/db/src/forms.ts:489`. Эта функция получает ту же блокировку этапа (`packages/db/src/stageEvents.ts:60`), уже занятую сборкой.
4. PostgreSQL обнаруживает цикл и прерывает транзакцию сборки с SQLSTATE `40P01`. `fromPgError` в `apps/server/src/http/errors.ts` не переводит этот код в управляемый конфликт, повтор транзакции не выполняется.

**Фактически на Windows:** правка поля — HTTP 200; сборка — HTTP 500 `INTERNAL`. В журнале приложения: `unhandled error`, `deadlock detected`. Диагностика PostgreSQL: процесс 59727 ждёт транзакцию 523308, занятую процессом 59725; процесс 59725 ждёт транзакцию 523309, занятую процессом 59727. Повторный независимый прогон воспроизвёл тот же результат. Потеря сохранённых данных или выпуск комплекта со старым значением в этом сценарии не обнаружены; дефект нарушает выполнение допустимых одновременных команд.

**Ожидается:** общий порядок доменных блокировок (этап прежде приложения) во взаимодействующих командах. При проигранной гонке допустим предусмотренный конфликт состояния с необходимостью перечитать приложение; внутренняя ошибка взаимной блокировки не должна доходить до пользователя. Одна замена ответа 500 на 409 не устраняет противоположный порядок блокировок.

**Регрессия:** `tests/reviewer12b.test.ts`, тест `concurrent field edit and assembly serialize without deadlock/HTTP 500`. Тест только приостанавливает реальный запрос сразу после уже полученной блокировки приложения; SQL, порядок запросов, транзакции и результаты не подменяет. Через `pg_stat_activity` подтверждается, что сборка действительно ждёт эту строку, затем первый запрос продолжает работу. Ожидания теста описывают исправное поведение: правка 200, сборка 201 либо 409. Сейчас тест падает на 500. Последовательный контроль проходит.

Доказательства: `outputs/windows-independent-tests.log`, `outputs/windows-concurrency-confirm.log`, `outputs/reviewer12b-observations.json`. Это впервые обнаруженное замечание; утверждение, что дефект появился именно в коммите исправлений, не делается.
