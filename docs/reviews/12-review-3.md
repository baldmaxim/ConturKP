## Разбор исправления R12-04

Изменены два продуктовых файла: `apps/server/src/routes/formDrafts.ts` и `apps/server/src/http/errors.ts`. В `loadDraft(..., lock=true)` сначала читается приложение для определения тендера и проверки прав, затем вызывается `lockTenderStages`, после этого — `getDraft(..., true)`. Этим общим путём пользуются правка поля, отметка «заполнено», перенос и принятие/отклонение предложения. Сборка комплекта уже брала этап прежде приложения. Отдельная проверка настоящей функции обработки ошибок подтверждает перевод `40P01` в 409.

Независимый конкурентный тест подтвердил именно устранение цикла блокировок: пока правка держит блокировки, сборка ожидает `SELECT id FROM tender_stage ... ORDER BY id FOR UPDATE`, что зафиксировано через `pg_stat_activity`. После продолжения правка получает HTTP 200, сборка — HTTP 409 `STATE_CONFLICT`, `current.reason=drafts_not_complete`, приложение остаётся `in_progress`. SQLSTATE `40P01` не возникает. Последовательный контроль также проходит. Доказательства: `outputs/windows-independent-tests.log` и `outputs/reviewer12b-observations.json`.

Файлы сборки и её проверки свежести, миграция 0033, поиск LibreOffice и расчёт актуальности относительно `f37a12c` не изменены. Признаков отката исправлений R12-01…R12-03 при просмотре diff не обнаружено; повторный исполняемый контроль на новой передаче прошёл.

## История восстановления среды

Прежний тестовый PostgreSQL с pgvector находился в Docker, порт `127.0.0.1:55432`. В начале этой проверки порт не слушал, Docker Desktop не работал. Установленная служба PostgreSQL 16 не использовалась и не менялась.

Запуск Docker сначала завершался на оставшихся файловых сокетах: `Docker/run/sailor-ingest.sock`, `docker-secrets-engine/engine.sock`, затем `Docker/vm-data/00000002.000007cf`. Каталоги сокетов сохранены переименованием; `vm-data` перед переименованием проверен: в нём был ровно один файл длиной 0 с атрибутом ReparsePoint, указанный в диагностике. Виртуальные диски и данные контейнеров не переносились и не удалялись. Настройки Docker не менялись. Останавливались только процессы Docker, запущенные в ходе восстановления; процессы других проектов не завершались.

После этого Docker смог запустить виртуальную машину `linux/sailor`, но соединение гостя с Windows продолжило отказывать: `virtio_vsock::muxer`, `failed to connect`, `os error 10022`; Docker API и порт БД остались недоступны. Сохранены краткая диагностика и состояние среды. Это отказ среды выполнения, не найденный дефект ConturKP.

После команды владельца «подключи докер» Docker API стал доступен. Список контейнеров, образов и томов в текущем daemon был пуст; контейнера `kontur-pg` не оказалось. Для ревью создан новый изолированный `kontur-review-pg`: PostgreSQL 18.6 (Debian), pgvector 0.8.7; адрес `127.0.0.1:55432`, отдельный том `kontur-review-12-3-pgdata`, политика перезапуска `unless-stopped`. Тестовые роли подготовлены, соединение и расширение проверены. PostgreSQL 16 и хранилища основного проекта не использовались. Новая тестовая БД не является восстановлением прежних данных портала.

Образ взят из [репозитория pgvector](https://github.com/pgvector/pgvector#docker) и закреплён digest: `pgvector/pgvector@sha256:2358fcba361ed2233a5ed81b5fe4ca779ccb304120ce531a3bf51c0ed7e2bc11`. Фактическое состояние и версии — `outputs/windows-docker-connected.json`. БД работает на Linux внутри Docker; код, Node, LibreOffice и Chrome — на Windows. Нативная служба PostgreSQL на Windows этим прогоном не проверена.
