## R13-01 — P1: устаревший прогон не блокирует согласование и выпуск

**Код:** `packages/db/src/approvals.ts:243`, `:306`; `docs/migrations/0034_approval_release.sql`, функция `candidate_gate_problem`; выбор последнего завершённого прогона — `packages/db/src/releaseCandidates.ts`.

Воспроизведение через штатные API:

1. Выполнить проверку этапа по двум подтверждённым требованиям.
2. В тот же реестр добавить и подтвердить третье требование по уже обработанному фрагменту ТЗ. Новый документ, снимок и расчёт не создаются.
3. Старый `/review-runs/{id}` правильно возвращает `freshness.outdated=true`: после проверки изменился реестр. Его закреплённый вход нового требования не содержит.
4. Собрать комплект и принять текущие бизнес-пункты риска.
5. Карточка комплекта возвращает `current=true`, открытых блокеров нет. Согласование получает **200**, выпуск — **201**.

Проверка свежести матрицы сравнивает только ID снимка и ревизии расчёта и наличие завершённого прогона. Закреплённый отпечаток содержимого `review_run_input.content_fingerprint` не сверяется. Вторая линия 0034 повторяет это ограничение: отдельная проба прямой вставки `approval`, перехода кандидата и `SET CONSTRAINTS ALL IMMEDIATE` прошла без отказа; транзакция всегда откатывается. Изменение реестра не становится событием источника, поэтому удержание S13-01 этот случай не ловит.

**Требуется:** перед согласованием и выпуском проверять актуальность входов обязательного прогона относительно зависимых от него требований, покрытия и решений. Старый вход сохранять; требовать новый прогон по изменённым данным. Это техническая неполнота, а не снимаемый риск покрытия. Проверка нужна также при прямой записи в БД. Правки полей приложения, которые не влияют на проверки, не должны возвращать S12-01.

**Доказательство:** сценарий `a review which omits…` в `tests/reviewer13.test.ts`; `outputs/independent-observations.json`, ключ `staleReview`; лог независимого прогона и дополнительный `windows-independent-stale-db.log`. Ожидаемый отказ согласования — 409, фактически 200 и последующий выпуск 201. Дополнительный запуск этого сценария после добавления пробы БД снова дал тот же отказ теста; остальные четыре сценария в нём специально не запускались.

## R13-02 — P1: причина принятого риска раскрывает закрытое письмо

**Код:** `apps/server/src/releaseViews.ts:132`; `apps/server/src/releaseRecord.ts:76`, `:134`; доступ к манифесту и журналу — `apps/server/src/routes/approvals.ts`.

Руководитель и инженер 1 имеют доступ к ящику; инженер 2 никогда его не имел. По фрагменту письма создано критическое замечание. Руководитель принимает риск с содержательной причиной, повторяющей условие письма: `SECRET-REVIEW13: заказчик требует скидку 27 процентов`. Поля комплекта не основаны на этом письме.

У инженера 2 текст самого замечания корректно скрыт. Однако он получает условие письма:

- в карточке комплекта: пункт имеет `restricted=true`, заголовок скрыт, но `acceptance.reason` содержит секретный текст;
- в `/release-candidates/{id}/history`, поле `basis`;
- в неизменяемом `/releases/{id}/manifest`, поле `acceptedRisks[].reason`.

Все три запроса успешны. Независимый тест проверяет фактические ответы. Удаление заголовка замечания из манифеста не защищает обоснование риска, которое относится к тому же закрытому предмету.

**Требуется:** замкнуть права на производные тексты решения по основаниям его предмета, включая текущие права. В карточке и журнале закрывать текст причины; при чтении точного манифеста/архива учитывать права на все включённые основания рисков, а не только версии полей. Не переписывать исторический манифест при отзыве прав. Проверить аналогичные причины по вопросам, рискам этапа 09 и решениям по удержаниям; их утечка настоящим тестом отдельно не утверждается.

**Доказательство:** сценарий `risk justification…`; ключ `riskVisibility`: `findingLeaks=false`, `cardLeaks=true`, `manifestLeaks=true`, `historyLeaks=true`. В тесте только вымышленные данные.

## R13-03 — P2: решение «влияет» перестаёт исключать выпуск

**Код:** `packages/db/src/approvals.ts:447–455`, `releaseSendReadiness`; функции `candidate_uncovered_events` и `import_item_covered` миграции 0034.

1. Согласовать и выпустить тестовый комплект.
2. Загрузить повреждённый PDF в ZIP. После обработки остаётся отклонённый элемент без исхода; событие `import_accepted` ставит удержание.
3. Руководитель решает удержание как `requires_new_candidate` («влияет»). Готовность выпуска становится **`excluded`**.
4. Затем руководитель задаёт элементу партии исход `not_applicable` через штатный `/import-items/{id}/resolve`.
5. То же выпущенное содержимое теперь получает **`state=ready`**. Запись решения «влияет» сохраняется, но предикат её больше не видит.

Причина: исключение ищется только среди *сейчас непокрытых* событий. После разрешения элемента событие становится покрытым и исчезает из выборки вместе с исключающим решением. D-033 В-13-5 и §4.3 проекта требуют исключения отправки этого выпуска **навсегда**; исправление — новым комплектом.

**Требуется:** проверять наличие любого действующего исторического решения `resolved_requires_new_candidate` по этому выпуску независимо от текущего покрытия события. `excluded` должен иметь приоритет перед вычислением текущих удержаний.

Воспроизведён тестовый выпуск, поэтому `sendable=false` в обоих состояниях. Реальная отправка и боевой выпуск не выполнялись. Ошибка находится в общей функции готовности, которую должен использовать этап 15.

**Доказательство:** сценарий `a release excluded…`; ключ `permanentExclusion`: `excluded → ready` без нового комплекта или выпуска.

## R13-04 — P2: старое подтверждение согласует новый риск

**Код:** `apps/server/src/routes/approvals.ts:204–214`; изменение риска не меняет `release_candidate.row_version`; диалог — `apps/web/src/pages/release/ApprovalActions.tsx`.

1. Руководитель открывает готовый к согласованию комплект: все три показанных бизнес-пункта риска уже приняты, матрица разрешает согласование. Сохранить показанные `etag`, `contentHash` и перечень рисков.
2. После этого инженер добавляет новое критическое замечание, руководитель в другой вкладке принимает по нему новый риск.
3. `etag` и `contentHash` прежнего комплекта остаются теми же. Запрос согласования со **старым показанным составом** получает **200**.
4. Новая запись `approval.accepted_risk_ids` включает четыре риска: добавлен риск, которого не было в диалоге подтверждения.

Проверяется хэш неизменяемых файлов, но не показанное состояние рисков и решений. Это нарушает D-033 В-13-8: сервер принимает согласование только того содержимого, которое было показано; I13 запрещает молчаливую потерю проверки при одновременных изменениях.

**Требуется:** закреплять и сверять под блокировкой версию/отпечаток подтверждаемого состава, включающий актуальные риски с версиями предметов и соответствующие решения по удержаниям. При изменении после открытия диалога — 409 и повторное ознакомление. Одной повторной оценки «все блокеры сняты» недостаточно. Не менять хэш самих файлов ради изменяемых метаданных согласования.

**Доказательство:** сценарий `approval must reject…`; ключ `confirmationChanged`: одинаковые ETag и contentHash, показано 3 риска, согласовано 4, HTTP 200 вместо 409.
