## R13-05 (P1) — изменение второго вопроса не инвалидирует прогон, согласование и выпуск разрешены

### Причина и места кода

`packages/db/src/reviewRuns.ts:416` строит часть отпечатка вопросов как количество записей и `max(row_version + extract(epoch FROM updated_at))`. Миграция `docs/migrations/0035_review_outdated_gate.sql:24` повторяет тот же расчёт. Изменение записи, которая не стала максимумом, не меняет отпечаток. Это потеря информации при агрегации до хэширования, не коллизия SHA-256.

Одинаково ошибочный результат используется карточкой прогона (`apps/server/src/reviewMappers.ts:109`), матрицей (`packages/db/src/approvals.ts:249`) и второй линией `candidate_gate_problem` (0035). Тест совпадения SQL и JS проходит, потому что обе реализации повторяют один пропуск.

### Независимое воспроизведение на Windows

Сценарий `changing a nonmaximum customer question must invalidate the pinned review and block approval`, `tests/reviewer13.test.ts`. Все изменения через обычный API, без изменения БД или часов:

1. Создать два черновика вопросов. Первый изменить 32 раза успешными PATCH с актуальным ETag: его `row_version = 33`.
2. Запустить обязательную проверку и дождаться её завершения. Оба вопроса на момент закрепления входа — черновики.
3. Второй вопрос перевести в `sent` после прогона: `row_version = 2`. Первый вопрос не изменять. Затем собрать комплект.
4. Принять предусмотренные бизнес-риски по свежей карточке, включая отправленный вопрос без ответа. Это не должно разрешать использование устаревшего обязательного прогона (технический блокер R13-01).
5. Согласовать и выпустить с актуальными ETag, contentHash и compositionHash.

Фактически:

| Наблюдение | Результат |
|---|---|
| Вопрос 1 | `draft`, ревизия 33, `updated_at = 2026-10-08T08:28:12.065Z` |
| Вопрос 2 после запуска проверки | `sent`, ревизия 2, `updated_at = 2026-10-08T08:28:12.190Z` |
| Закреплённый и текущий отпечатки | одинаковые: `868247231f13f43ece80b192e1175aa99172d4f545be5e35dc7937c137b513d9` |
| Свежесть прогона | `outdated: false`, причин нет |
| Открытые блокеры карточки | нет |
| `candidate_gate_problem` | `NULL` |
| Согласование | HTTP 200 |
| Выпуск | HTTP 201 |

Контроль в том же сценарии: после изменения **первого**, максимального вопроса прогон становится `outdated: true` с причиной изменения записей этапа. Значит, проблема именно в выборе максимума: статус второго вопроса изменён, но не попал в признак свежести.

Тест падает на утверждении `freshness.outdated === true`; остальные наблюдения сохранены **до** этого утверждения. Полная запись — `outputs/independent-observations.json`, объект `nonmaximumQuestion`. Выпуск тестовый, фактической отправки не было.

### Требуемое исправление

Изменение любого вопроса, от которого зависит проверка, должно менять признак свежести; оно не должно маскироваться версией другого вопроса. Нужен отпечаток полного упорядоченного набора идентификаторов/версий значимых записей либо надёжный счётчик изменений, обновляемый каждой соответствующей командой. Сервер и SQL должны одинаково замечать изменение каждой записи, а не только совпадать друг с другом.

Устаревший обязательный прогон должен давать неснимаемый `REVIEW_OUTDATED` в API и во второй линии БД; бизнес-риск по вопросу его не снимает. Принятую 0035 не переписывать: исправление SQL — новой миграцией. Проверить обновление со схемы 0035, поведение старых закреплённых отпечатков и путь «новый прогон → новый комплект → согласование/выпуск». Сохранить S12-01: изменение полей приложения само по себе проверку источников не устаревает.

## Два уточнения реализации из передачи

1. Обязательный `compositionHash` — обоснованная реализация D-033 В-13-8 и R13-04. Хэш файлов остаётся хэшем файлов; отдельный отпечаток фиксирует показанные риски и решения. Изменение контракта документировано; независимый тест отправляет отпечаток именно сохранённой карточки, а не перечитывает его перед командой. Отказ 400 без отпечатка — ожидаемое поведение нового контракта.
2. Руководитель без доступа к предмету удержания не должен принимать решение о его применимости. `409 restricted_event` соответствует D-033 ут. 4 о сохранении проверки прав. Это заключение ревьюера о совместимости реализации с записанным решением, а не новая запись от имени владельца. Проверяются и одиночная, и групповая команды, отсутствие частичного изменения и успешное выполнение после восстановления доступа.
