## R13-06 (P1) — смена типа документа не устаревает обязательную проверку

### Причина

Часть `document` нового отпечатка в `packages/db/src/reviewRuns.ts:436` и `docs/migrations/0036_stage_content_fingerprint_v2.sql:42` содержит ID документа, `contract_role`, `main_document_id`, `main_document_role`, но не **`doc_type`**.

В то же время `packages/db/src/reviewInputs.ts:45` читает `d.doc_type`. `sourceKindOf` (`packages/core/src/review/types.ts:130`) превращает `docType = contract` в вид источника «договор», а `reviewInputs.ts:177` по нему определяет `fromContract`. Проверка C07 (`packages/core/src/review/checksCalc.ts:220`) выполняется именно для таких требований. Тип влияет также на приоритет сторон конфликта.

Тип меняется обычным `PATCH /documents/:id` с ETag (`apps/server/src/routes/documents.ts:69`), через `updateDocument` (`packages/db/src/sources.ts:324`). У документа увеличивается `row_version`, но ни этот номер версии, ни изменённый тип не входят в отпечаток. Событие барьера не записывается: в воспроизведении `tender_stage.input_version` остаётся **24 → 24**. Совпадение SQL и JS не спасает: обе реализации одинаково пропускают значимое поле.

### Независимое воспроизведение

Тест `changing document type after a completed review must invalidate its contract-obligation check and block approval`, файл `tests/reviewer13b.test.ts`. Значимые изменения идут только через штатный API. Данные синтетические, модель поддельная, сборка на настоящем worker и LibreOffice.

1. Подготовить этап с двумя подтверждёнными требованиями из одного документа: первое покрыто расчётом, для второго оценки нет. Тип документа — `other`.
2. Завершить обязательную проверку. В её закреплённом входе оба требования имеют `sourceKind: other`, `fromContract: false`; C07 — `not_applicable`, договорных требований 0, замечаний 0.
3. После прогона изменить тип этого документа на `contract` успешным PATCH с актуальным ETag. Больше входы не менять.
4. Собрать комплект, принять предусмотренные бизнес-риски по свежей карточке. Это не должно разрешать использование устаревшего обязательного прогона.
5. Проверить свежесть, SQL-защиту, согласовать и выпустить с актуальными ETag, contentHash и compositionHash.
6. В конце запустить новую проверку. Она служит контролем, что изменилось содержимое C07, а не только подпись документа.

### Требуемое исправление

Смена классификации источника, влияющей на вход программных проверок, должна менять признак свежести либо порождать надёжно учитываемое событие. Учесть `doc_type` и проверить остальные изменяемые поля, которые действительно читает вход; одинаково реализовать расчёт в сервере и БД. Применённую 0036 не переписывать: новая миграция.

После смены типа старый прогон должен показываться устаревшим, согласование и выпуск — получать неснимаемый `REVIEW_OUTDATED`, включая прямую запись в БД. Добавить регрессию этого API-сценария и проверку обновления 0036 → новой схемы. Путь «новый прогон → новый комплект → согласование/выпуск» должен оставаться рабочим. Сохранить контроль S12-01: правка поля приложения сама по себе проверку источников не устаревает.
