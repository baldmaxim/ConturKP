## R14-01 — экспорт внутреннего манифеста без права на его основания (P1)

**Место:** `apps/server/src/routes/deliveries.ts:416–434` (команда размещения), `packages/db/src/deliveries.ts:379–384`, `apps/worker/src/handlers/delivery.ts:81–122`. Существующая защита: `apps/server/src/releaseViews.ts:118–130`, `apps/server/src/routes/approvals.ts:495,512`.

**Сценарий.** В выпуске есть принятый риск по закрытому письму. Инженер 2 видит закреплённые документы комплекта, но не видит письмо и причину риска. Администратор добавляет назначение `includeInternal=true`. Тот же инженер вызывает «Разместить».

**Фактически:** `GET /releases/{id}/manifest` получает **409**; `POST /releases/{id}/deliveries` получает **201**; worker заканчивает `delivered`. В назначении оказывается `release-manifest.json` с синтетической закрытой причиной. Проверены именно записанные байты файла, а не только состояние БД.

`loadVisibleRelease` проверяет входы кандидата, но не предметы решений внутреннего манифеста. Команда размещения не вызывает `requireManifestReadable`, которое уже защищает скачивание манифеста и ZIP всех файлов. Отметка назначения не должна давать человеку возможность обойти ограничения основания через другой канал экспорта (I13/I17, принятый R13-02).

**Требуется:** распространить проверку прав внутреннего набора на размещение, повтор и перенаправление; проверить также автоматическое создание и выполнение отложенных доставок с учётом текущих прав. Не заменять закреплённые файлы текущими и не ослаблять ограничения скачивания. Пользователь без доступа должен получить отказ или документированное ограничение набора, без записи закрытого манифеста.

**Регрессия:** `reviewer14.test.ts`, сценарий `a user denied the internal release manifest...`. Наблюдение: `outputs/independent-observations.json`, ключ `restrictedInternal`: `manifestGet=409`, `place=201`, `delivery=delivered`, `containsSecret=true`. Положительный контроль локальной доставки/неподтверждённого облака проходит.

## R14-02 — запасной перенос заменяет чужой признак готовности (P1)

**Место:** `packages/storage/src/deliveryFs.ts:81–89`.

После отказа `link` из списка `LINK_UNSUPPORTED` выполняются отдельные `exists(to)` и `renameSafe(from,to)`. Чужой файл может появиться между ними. Настоящий Windows `rename` заменяет этот файл.

**Независимый сценарий:** только невозможность жёсткой ссылки имитируется `ENOTSUP`; конкурентный файл создаётся на границе переноса. Само переименование выполняет настоящая файловая система Windows. `moveNoReplace` возвращает успех, содержимое назначения становится **OWN-MARKER** вместо **COMPETING-MARKER**. Это нарушает A30/I13; ограничение «конфликт никогда не разрешается перезаписью» заявлено и в D-034. Это проверка ветки отказа возможностей файловой системы, не утверждение, что проверенный реальный SMB не поддерживает ссылки.

**Требуется:** безопасный атомарный перенос без замены. Если назначение не поддерживает доступный механизм, отказывать с понятной причиной, а не использовать связку проверки существования и заменяющего `rename`. Чужие bytes должны сохраняться. Обычный путь с уже существующим файлом в независимом контроле проходит.

**Регрессия:** `reviewer14Fs.test.ts`, первый сценарий. `outputs/independent-fs-observations.json`: `markerRace.code=ok`, `actual=OWN-MARKER`; контроль `hardLinkControl`: `EEXIST`, `FOREIGN` сохранён.

## R14-03 — junction обходит запрет стадирования внутри синхронизации (P1)

**Место:** `apps/worker/src/handlers/delivery.ts:41–47,175–176`, `packages/adapters/src/delivery/fsTarget.ts:74–84`; сервер проверяет те же текстовые пути в `routes/deliveries.ts:54–79`.

Проверяется только лексическая вложенность путей. Служебная папка задана через junction с именем вне корня, но физически её цель находится внутри корня Яндекс Диска. Проверка строки считает пути раздельными; `checkBases` проверяет наличие каталогов, не их физическую вложенность.

**Фактически на Windows:** в физической папке синхронизации выполняется запись незавершённого файла (`syncWrites=1`). В регрессии заранее создана собственная служебная папка операции — допустимое состояние после предыдущей попытки; это также исключает отдельную особенность `mkdir` через junction. Поздний отказ создания другой папки не отменяет уже выполненную запись. Клиент синхронизации может начать загрузку до признака готовности. Самого клиента в этой проверке нет: подтверждён факт записи внутри синхронизируемого дерева, а не облачная передача.

Тот же тест отдельно выполнен в новом процессе без имитации `link`/`rename`: результат повторился.

**Требуется:** до изменяющих операций сверять разрешённые физические пути корня и служебной папки, включая junction/алиасы существующих родителей; отвергать пересечение. Не создавать и не записывать внутри синхронизации служебные данные. Добавить проверку через штатный probe/worker/API, а не только строковые утилиты.

**Регрессия:** третий сценарий `reviewer14Fs.test.ts`. `independent-junction-isolated.json`: `lexicallyInside=false`, `physicallyInside=true`, `syncWrites=1`.

## R14-04 — штатный тест конфликта не проверяет фактическое удаление папки (P2, обвязка Windows)

**Место:** `tests/deliveryFlow.test.ts:313–318`.

Полный набор и отдельная диагностическая копия получают `conflict` вместо ожидаемого `delivered`. Дополнительная проверка сразу после `rmSync(folder,{recursive:true})` показала: папка и чужой файл **остались на месте**. Поэтому текущий код размещения правильно продолжает сообщать конфликт. Причина такого поведения `rmSync` на этой Windows-машине не установлена; отказ нельзя выдавать за доказанный дефект повтора в продукте.

**Контроль:** в отдельной копии изменена только очистка собственного тестового файла: `unlinkSync` известного файла, затем `rmdirSync` пустой папки, с проверкой отсутствия. Тот же сценарий прошёл: команда 200, итог `delivered`, правильные bytes и журнал. Ожидания сценария не ослаблялись; исходный файл автора сохранён.

**Требуется:** обеспечить действительную очистку собственного тестового каталога на Windows, проверять её результат перед повтором. Вернуть зелёный штатный `deliveryFlow` и полный набор. Проверить, что cleanup не удаляет чужие файлы и не маскирует отказ операции.

**Доказательства:** `windows-full-tests.log`, `windows-independent-and-flow.log`, `windows-conflict-isolated.log`, `windows-conflict-explicit-cleanup.log`. Финальная диагностическая копия — `reviewer14FlowDiagnostic.test.ts`; её отличие от автора только в диагностике и явной очистке.
