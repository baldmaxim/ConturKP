## R16-01 — P1: принятие вопроса снимает закрытость его почтового основания

**Воспроизведение штатными командами.**

1. Инженер 1 читает ящик A; инженер 2 — участник того же тендера без `mail.read`. Руководитель читает ящик.
2. Инженер 1 через MCP `propose_question` создаёт текст с маркером `REVIEW-16-MAIL-PRIVATE-66231`, цитируя фрагмент письма. Инженер 2 видит предложение закрытым: `restricted: true`, `body: null`, цитат нет. Прямое чтение цитаты ему запрещено.
3. Руководитель штатно принимает предложение через `/mcp-proposals/{id}/accept`. Создаётся `customer_question`.
4. Инженер 2 читает `/stages/{id}/customer-questions`: **200, `visible: true`, полный закрытый текст**. MCP `list_questions` этого пользователя также возвращает текст.
5. У инженера 1 отзывают `mail.read`, сохраняя участие и инженерную роль: созданный вопрос всё равно возвращает тот же текст. Само предложение остаётся закрытым правильно.

В независимом прогоне вопрос: `fa0f1d5e-2a3d-4ec2-920e-7fc0c636f3cc`. Полные ответы — `outputs/independent-observations.json`, ключи `acceptedQuestionApi`, `acceptedQuestionMcp`, `acceptedQuestionAuthorAfterRevoke`. Это утечка первого чтения, а не повтор сохранённого ответа: исправление 15a здесь не помогает.

**Причина.** `apps/server/src/routes/mcpProposals.ts:172` создаёт вопрос с `requirementId: null`, копируя `p.body`, но не передавая происхождение и ограничения цитат. `packages/db/src/requirementTaint.ts:109` наследует закрытость вопроса только от требования; связи с принятым предложением и его фрагментами нет. У самого предложения `viewOf` учитывает цитаты, поэтому родитель закрыт, а автоматически созданный потомок открыт.

**Требуется.** Сохранить происхождение и замыкание ограничений чтения у созданного вопроса. Принятие человеком не является снятием прав на источник. Проверять ограничения при чтении через API и MCP, после отзыва доступа, а также при изменении/отметке отправки такого вопроса. Обычные вопросы без закрытого основания должны работать как прежде. Переход к новому виду основания должен быть явным; ограничение нельзя потерять копированием текста. Если нужна миграция, добавить новую, не переписывая принятую 0040.

Основания ревью: I13, правила унаследованного текста R08-02, уроки R11-02, проект 16 §6. Контроль с принятым `propose_finding` прошёл: созданное замечание сохраняет ограничения письма. Поэтому принятие само по себе не трактуется как разрешение публикации закрытого текста.

**Регрессии должны проходить с теми же ожиданиями после исправления:**

- `an accepted question retains the privacy of its original cited mail through the portal API`;
- `an accepted private question is also hidden from the MCP list_questions tool`;
- `after revoking the proposer mail access, its accepted question does not disclose the inherited text`.

Четыре контроля проверяют скрытие предложения/цитаты, отсутствие дубля, закрытость принятого замечания и 401 после отзыва токена. Их ожидания тоже не менять.

## Живое подключение клиентов

Проверены **Codex CLI 0.162.0-alpha.2** и официальный **Cursor CLI 2026.10.01-e373342**. Установленный Cursor IDE — 3.22.7; его графический чат отдельно не проверялся. Конфигурация Codex использовала URL и `bearer_token_env_var`, настройки только на время запуска. Cursor использовал отдельный тестовый проект и переменную окружения в заголовке. Настройки сверены с [официальной документацией Codex](https://learn.chatgpt.com/docs/extend/mcp?surface=cli) и [Cursor MCP CLI](https://cursor.com/docs/cli/mcp). Для Cursor допуск MCP задан флагом `--approve-mcps`; посторонний глобальный сервер `codex` отключён только в тестовом профиле. Локальные файловые/оболочечные действия клиента запрещены. MCP мог создавать только предложения на синтетическом деле.

CLI не использовал системный прокси при первом входе. Вход удалось выполнить с прокси, указанным только для процесса; `NO_PROXY` исключал loopback портала. Это соответствует [документированной настройке прокси Cursor](https://cursor.com/docs/cli/reference/configuration). Пароли и токены в чат или отчёт не переносились. Глобальные настройки рабочих проектов не менялись.
