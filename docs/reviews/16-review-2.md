## R16-01 — закрыт

Три прежних сценария утечки и четыре контроля проходят с теми же ожиданиями. Принятый вопрос хранит неизменный `source_proposal_id`, наследует права цитат предложения и скрывается через API/MCP после отзыва доступа к письму.

Дополнительно подтверждено:

- участник без доступа к источнику не может изменить, закрыть или отметить такой вопрос отправленным: **409 restricted_fragments**;
- прямое удаление `source_proposal_id` получает **55000**;
- принятие другого предложения с указанием обычного вопроса без нужного происхождения получает **23514**;
- новая отвязка и замена требования открытым не снимают закрытость вопроса через API/MCP;
- попытка стереть `basis_requirement_ids` прямой записью не стирает накопленные связи;
- вопрос по открытому требованию после отвязки читается и меняет статус как прежде.

Таким образом, **S16-12 исправлен для отвязок после 0041**. Результаты — `outputs/independent-additional-observations.json`. Существующий тест продукта обновления 0040 → 0041 по принятым предложениям также вошёл в зелёный полный набор.

## R16-02 — P1: старый отвязанный вопрос остаётся открытым после обновления

**Сценарий с двумя настоящими версиями продукта, без подмены данных ревьюером.**

1. Код **054cff4**, схема **0040**: руководитель создаёт требование с закрытым договорным основанием. Инженер 1 участвует в тендере, но договор не читает.
2. Руководитель создаёт вопрос с текстом `Подтвердите REVIEW-16-2-LEGACY-PRIVATE-45328`, связанный с этим требованием. Инженер получает **200, visible: false, text: null**.
3. Прежний штатный API отвязывает требование (`requirementId: null`).
4. На той же базе запускается текущий мигратор: применена ровно **0041**. Старых колонок происхождения до обновления нет — проверено.
5. Текущий сервер **745c5b7** с тем же сеансом инженера возвращает вопрос **200, visible: true, полный закрытый текст**. Само требование по-прежнему **visible: false**, закрытая цитата и его текст не выдаются.
6. Тот же инженер, не получая доступ к договору, отмечает вопрос отправленным: **200, status: sent**. Это запись статуса в тестовой базе; настоящего письма не отправляли.

Вопрос: `6f5f6284-199b-4ddc-aeb5-3181be1228ca`; требование: `fb569e36-9dc8-4ea4-b43f-00b74cb87816`.
После миграции у вопроса `requirement_id = null`, `basis_requirement_ids = []`, `source_proposal_id = null`.

**Доказательства:** `reviewer16Legacy.test.ts`, `outputs/windows-independent-additional.log`, `outputs/independent-legacy-observations.json` (`before`, `after`, `stillClosedRequirement`, `sendWithoutSource`, `basis`). Отказ дошёл до проверки отсутствия маркера в ответе нового сервера. Тест использует отдельную прежнюю копию с подтверждённым HEAD 054cff4. Обвязка не отключает триггеры и не пишет фиктивные версии; временное отключение охранника внутри штатной 0041 — её собственная операция заполнения.

**Причина:** `docs/migrations/0041_question_origin.sql:19` заполняет историю только текущим `requirement_id`. Уже снятая связь отсутствует, поэтому новый расчёт закрытости (`packages/db/src/requirementTaint.ts:112`) не находит основания. Признак неизвестного прежнего происхождения отсутствует; пустой список трактуется как открытый вопрос.

Граница прямо описана в проекте **§17.7**: отвязки до 0041 не восстанавливаются. Это не устраняет подтверждённую утечку существующих данных и противоречит I13/R08-02 и принятому правилу сохранения закрытости производного текста. Источник остаётся закрытым; снятие ссылки не является разрешением раскрыть его текст. Исключение для таких старых данных владельцем не утверждалось.

**Требуется:** безопасно обработать существующие вопросы с потерянной историей. Восстановить достоверные основания из сохранённого происхождения/аудита; если их определить нельзя, вопрос должен сохранять ограничение до явного разбора, а не автоматически считаться открытым. После обновления участник без доступа к прежнему основанию не должен получать текст, менять вопрос или отмечать его отправленным. Обычные открытые вопросы нужно сохранить отдельными контролями. Ожидание приватности независимого теста не менять.

Исправление оформить новой миграцией по ADR-002, не переписывая уже применённую 0041. Не откатывать рабочую защиту новых вопросов и исправление R16-01.
