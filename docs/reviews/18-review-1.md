## R18-01 — P1: несуществующие идентификаторы дают PASS по G1, М1 и М3

**Место:** `scripts/ops/pilot.ts:176–219`; `scripts/ops/pilot-gates.ts:8–38,63–76`; контракт идентификаторов — `scripts/ops/pilot-schema.ts:118–130`.

`matching.items[].found` по контракту содержит идентификаторы выводов портала, а `matching.citations[].ref` — замечания или прогона ответа, цитату которого проверили. Однако перед вычислением G1/М1/М3 отчёт не сверяет эти идентификаторы с БД. G1 и М1 проверяют лишь `result === 'found'` и непустой массив; М3 считает строки с `verdict === 'supports'`. Проверки существования, допустимого типа объекта, принадлежности тендеру и допустимого статуса вывода нет. Соседние М2 и М4 уже сверяют свои идентификаторы с БД.

**Воспроизведение настоящим CLI на синтетической БД:**

1. Созданы тендер, источники и два замечания штатным API; замечания разрешены человеком.
2. Эталон содержит один критический конфликт и одно некритическое изменение, соответствует схеме, его SHA-256 закреплён.
3. В обоих пунктах сопоставления указан `result: found` с одним случайным UUID. В БД подтверждено отсутствие замечания с этим UUID. Тот же UUID указан в единственной строке выборки цитат с `supports`. Разметка существующих замечаний для М2 заполнена корректно.
4. Запущен `scripts/ops/pilot.ts report` с настоящими файлами эталона и сопоставления.

**Фактически:** G1 — PASS (1/1), М1 — PASS (100%), М3 — PASS (100%). Сам CLI завершился кодом 1 из-за других разделов неполной фикстуры; это не отказ на неизвестный UUID и не исправляет ложные положительные результаты этих трёх показателей. Утверждения независимых тестов, запрещающие такой PASS, падают.

**Ожидается:** неизвестный или относящийся к чужому тендеру объект не подтверждает найденный пункт и не попадает в выборку принятых выводов. До расчёта показателей нужно проверить существование, допустимый вид, принадлежность выбранному тендеру, а для М3 — состояние принятого вывода. Ошибки идентификаторов должны быть явно указаны, без PASS по затронутым показателям. Проверки человеческой оценки содержания остаются за человеком.

**Влияние:** опечатка или устаревшая/чужая ссылка способна дать успешные пороговые показатели для несуществующего результата. Такой отчёт нельзя использовать для приёмки пилота.

**Доказательства:** `outputs/reviewer18-nonexistent-links.json`, `outputs/reviewer-tests.log`, `tests/reviewer18.test.ts` — два сценария R18-01. Необходимы также отрицательные проверки чужого тендера и непринятого вывода и положительный контроль настоящих допустимых ссылок.

## R18-02 — P2: допустимое основание из EML ошибочно считается чужим

**Место:** `scripts/ops/pilot-db.ts:90–96`; использование в G2 — строки 109,118; в G3 — строки 160,172.

Предикат `owned()` признаёт только фрагмент с `tender_id` выбранного тендера либо фрагмент активно связанного договора. У фрагмента тела письма `source_unit_type = mail_message_revision`, а `tender_id` и `contract_id` равны NULL по принятой модели хранения. Принадлежность письма определяется связями и составом источников; этот путь в предикате отсутствует. Аналогичный предикат применяется к основаниям ответов; отдельный прогон ответа в независимом сценарии не создавался.

**Воспроизведение штатным API:**

1. Импортирован EML, письмо связано с тендером и включено в закреплённый состав источников этапа (`buildStage09`).
2. Создано замечание с фрагментом письма; API создания — 201. Человек перевёл замечание в `resolved`; API — 200. Триггеры не отключались.
3. В БД проверено: `source_unit_type = mail_message_revision`, `tender_id = NULL`, `contract_id = NULL`, `fragment_in_stage(fragment, stage) = true`.
4. Вызваны настоящие `collectG2`/`collectG3` и вычисление ворот.

**Фактически:** G2 — FAIL, фрагмент попал в `foreignOrOutOfScope`; G3 — FAIL, «фрагмент основания замечания не из источников тендера — 1». Положительный контроль с обычным документом этого же тендера проходит. Независимый сценарий письма падает на ожидаемом PASS.

**Ожидается:** корректно связанное письмо в допустимом входе этапа проходит проверку принадлежности; письмо другого тендера или вне области по-прежнему отвергается. Нужно учесть владельцев источников из принятой модели, включая тело письма и распознанные вложения, с сохранением проверки области и межтендерной изоляции.

**Влияние:** пилот с обязательной реальной перепиской получает ложные сообщения о выдуманном источнике и утечке. Удалять допустимую переписку из проверки ради обхода этого отказа нельзя.

**Доказательства:** `outputs/reviewer18-valid-mail.json`, `outputs/reviewer-tests.log`, `tests/reviewer18.test.ts` — сценарий R18-02 и контроль документа.
