## R18-01 — CLOSED_BY_REVIEW

`collectPortalObjects` читает объекты по всем идентификаторам `found` и `citations` в той же транзакции READ ONLY / REPEATABLE READ, что и остальные данные отчёта. `checkLinks` проверяет существование, тендер, допустимый вид и статус. Ссылка на разногласие проверяется со статусом его замечания; для `price_reason` требуется версия причины. Для М3 допустимы замечания `resolved`/`accepted_risk` и завершённые ответы `confirmed_by_citations`.

Ошибочная ссылка исключается из зачёта; затронутый показатель получает FAIL, причина записывается в JSON `data.linkErrors`. Непрочитанный раздел ссылок даёт NOT_AVAILABLE вместо PASS. Неизвестный UUID, чужой тендер, неверный вид и недопустимый статус покрыты регрессиями. Проверки содержания по-прежнему выполняет человек.

Повторён настоящий CLI `report`: авторские сценарии неизвестного UUID, чужого тендера и открытого замечания в выборке цитат проходят на исправлении. Дополнительно проверены настоящие ответы, созданные API: G1/М1/М3 проходят, включая UUID в верхнем регистре. UUID редакций документов в `found` и `citations` дают FAIL всех трёх показателей.

## R18-02 — CLOSED_BY_REVIEW

`owned()` учитывает тело письма через `mail_message_revision` → `mail_message_tender` и распознанное вложение через `document_revision_mail_message`. Правило соответствует проверке принадлежности в миграции 0018. G3 учитывает тот же путь для основания типа `document_revision`. Проверка входа этапа и `allowed_source_unit_ids` остаётся отдельной. Наличие связи и допустимость исторического источника не подменяются проверкой текущего статуса связи.

Независимые положительные сценарии используют импорт EML штатным API, настоящее локальное распознавание CSV-вложения, создание и разрешение замечаний через API, а также ответы API с управляемой поддельной моделью. Основания тела письма и вложения проходят G2/G3. В положительных сценариях триггеры не отключались.

Письмо, связанное после закрепления снимка, остаётся источником тендера, но не становится входом прежнего этапа: API отвергает основание; при искусственной порче данных G2/G3 обнаруживают выход за область. Аналогично ответ с основанием вне `allowed_source_unit_ids` отвергается проверками отчёта. Для этих двух проверок испорченных данных использована отдельная superuser-транзакция с отключением триггеров только в тестовой БД; изменения затем восстановлены. Авторские отрицательные сценарии чужого и несвязанного письма также проходят.
