# Резервные копии и восстановление

Этап 17, ADR-011 §7–12, проект `docs/architecture/17-operations-design.md` §4. Отчёт о проверке — `docs/stages/17-backup-restore-report.md`.

## 1. Что в копии

Каталог `<BACKUP_ROOT>\kontur-<время UTC>\`:

| Файл | Содержимое |
|---|---|
| `db.dump` | `pg_dump` в формате custom ролью `kontur_backup` (только чтение); данных таблиц векторов `search_chunk_vector`, кеша эмбеддингов `embedding_cache` и `process_heartbeat` нет — они пересобираются, схема сохраняется |
| `files\sha256\…` | файлы хранилища по перечню `blob` из того же снимка БД; каждый сверен по SHA-256 |
| `manifest.json` | формат `kontur.backup.v1`: время, хост, сборка, роль, версия схемы, SHA-256 и размер дампа, число, объём и SHA-256 перечня файлов, сам перечень |

- Дамп и перечень файлов — один снимок (`pg_export_snapshot`): каждый файл, на который ссылается база, в копии есть.
- Неизменный файл прошлой копии связывается жёсткой ссылкой после сверки хэша, иначе копируется: добавляются только новые файлы.
- Манифест пишется последним. Каталог без манифеста — незавершённая копия, восстанавливать из него нельзя (команда откажет).
- Ничего не удаляется: срок хранения — решение В-17-3 (U-07).
- Зеркала Яндекс Диска и сетевой папки резервной копией не считаются (спецификация §9).

## 2. Снять копию

```powershell
npm run ops:backup
```

Окружение: `BACKUP_DATABASE_URL` (роль `kontur_backup`), `STORAGE_ROOT`, `BACKUP_ROOT`. Инструменты PostgreSQL (`pg_dump`, `pg_restore`, `psql`): сначала каталог `PG_BIN_DIR`, затем контейнер `PG_DOCKER_CONTAINER` (`docker exec`), затем `PATH` — явная настройка важнее `PATH`. В режиме контейнера инструмент подключается к серверу **внутри своего контейнера**, а не к адресу из URL. Поэтому команда сверяет идентификатор кластера через `psql` того же маршрута и отказывает, если это не кластер из `BACKUP_DATABASE_URL` (Review 17-1, R17-03). Перед снятием команда проверяет:

- каталог копий не совпадает с хранилищем и не внутри него;
- роль копии читает все таблицы и ничего не пишет;
- функции ограничений базы восстановимы (S17-20, миграция 0043);
- версия `pg_dump` не ниже сервера;
- места в каталоге копий хватает на новые файлы с запасом 512 МБ.

Код выхода: 0 — копия завершена; 1 — отказ (причина в выводе); 2 — не заданы ключи. Расписание — `docs/runbooks/release.md` §13.

Перед первым обновлением установки этапов 14–16 на этап 17: `npm run ops:backup -- --pre-update` — копию снимает владелец схемы (`DATABASE_MIGRATOR_URL`), роль записывается в манифест.

## 3. Проверить восстановление (учебно)

Только на чистом окружении — никогда поверх рабочей системы. Чистое окружение — отдельный кластер PostgreSQL (второй экземпляр службы, контейнер или другой ПК) и пустой каталог.

```powershell
$env:RESTORE_ADMIN_URL = '<суперпользователь кластера проверки>'
$env:RESTORE_STORAGE_ROOT = 'E:\KonturRestoreCheck'
npm run ops:restore-check -- --backup E:\KonturBackups\kontur-20261014T020000Z --login <логин руководителя или инженера> --out D:\Kontur\restore-check.log
```

Пароль `--login` вводится скрыто (или `--password-stdin`). Охранники — до любой записи, ключа обхода нет:

- база проверки — новая, имя `kontur_restore_…`, не совпадает с рабочей;
- каталог проверки пуст и не пересекается с рабочим хранилищем, каталогом копий и самой копией;
- `RESTORE_ADMIN_URL` — суперпользователь (создаёт базу, роли и расширения);
- `pg_restore` пойдёт в тот же кластер, что из `RESTORE_ADMIN_URL` (R17-03). Через `psql` того же маршрута сверяются идентификатор кластера и отсутствие базы проверки — до создания базы. После создания на базе ставится метка, и инструмент должен её увидеть — до `pg_restore`.

Кластер проверки в контейнере: `PG_DOCKER_CONTAINER` — **контейнер этого кластера**, а не рабочего (`$env:PG_DOCKER_CONTAINER = 'kontur-restore-pg'`). Указан чужой контейнер — отказ до записи с обоими идентификаторами кластера. Нативный кластер проверки: `PG_BIN_DIR` — каталог `bin` PostgreSQL той же или более новой версии; `psql` должен лежать рядом с `pg_restore`.

Шаги и вывод `PASS`/`FAIL`:

1. Манифест; SHA-256 и размер дампа совпадают.
2. Сверка маршрута `pg_restore` (кластер и отсутствие базы) → новая база (`db:setup`: роли, локаль `builtin`, `vector`, `pg_trgm`) → метка базы видна инструменту → `pg_restore` тремя секциями одной транзакцией каждая; дампу, снятому до миграции 0043, функции ограничений исправляются перед загрузкой данных.
3. Версия схемы = манифест.
4. Файлы восстановлены; SHA-256 каждого = манифест; перечень `blob` базы = перечень манифеста.
5. Ссылки на файлы выпусков, кандидатов, размещений и отправок — на сверенные строки `blob`.
6. Выпуски, согласования, фрагменты на месте; векторов нет.
7. Сначала только server на копии (`/health` — 200).
8. От имени `--login`: последний выпуск открывается, его манифест совпадает по SHA-256, цитата открывается. Поиск по документу из рабочего состава этапа: точный и полнотекстовый находят текст, смысловой — `unavailable` (`index_vectors_missing`): векторы не копируются, worker ещё не запущен.
9. Затем worker в режиме `restore_check` (без размещений, сканов папок и выгрузок TenderHub — пути в копии настоящие); `/ready` — 200.
10. При настроенной модели эмбеддингов — достройка векторов (`--vectors-timeout`, по умолчанию 1800 с) и повторный поиск: смысловая ветка `complete`, признака неполноты нет. Без модели — `NOT_RUN` с причиной.
11. Штатная остановка процессов по IPC — коды 0.

Код выхода: 0 — PASS, 1 — FAIL, 2 — неверный запуск, 3 — NOT_RUN (нет `pg_restore` нужной версии). `--drop-after` удаляет созданную базу и восстановленные файлы.

## 4. Аварийное восстановление

Когда рабочей системы нет (диск, ПК). Порядок:

1. Новый или очищенный ПК: §1–§8 `docs/runbooks/release.md`, без §9 (база будет из копии).
2. Проверка восстановления §3 этого документа в кластер нового ПК и в каталог будущего хранилища, без `--drop-after`. Все шаги — `PASS`.
3. В файле окружения: `DATABASE_URL` и `DATABASE_MIGRATOR_URL` — на базу `kontur_restore_…`, `STORAGE_ROOT` — на восстановленный каталог.
4. `db:migrate` (если сборка новее копии), службы (§10), `/ready`.
5. Живые проверки интеграций заново (§15 release runbook): статусы `VERIFIED_LIVE` из копии относятся к прежней установке.

Поверх существующей рабочей базы восстановление не выполняется ни этой командой, ни вручную.
