# Чистый старт (разработка, Windows)

Этап 02. Службы Windows, резервные копии и целевой ПК — этап 17 (ADR-011).

## Требования

- Node.js 24 LTS (проверено на 24.14.1), npm 11.
- PostgreSQL ≥ 17 в `PATH` (`initdb`, `pg_ctl`, `psql`); проверено на 18.3. Нижняя граница 17 — из-за провайдера локали `builtin` (ADR-002 §1, AR05-01).

## Шаги

```powershell
npm ci

# 1. Локальный кластер PostgreSQL в runtime/pg (только 127.0.0.1:55432, trust — только для разработки)
npm run pg:init
npm run pg:start

# 2. Конфигурация: скопировать образец и при необходимости поправить пути
Copy-Item .env.example .env
npm run config:check          # показывает «задано / не задано», значения не выводит

# 3. Роли kontur_migrator / kontur_app / kontur_backup и база
npm run db:setup
npm run db:migrate            # повторный запуск: «новых миграций нет»

# 4. Первый администратор-руководитель (пароль вводится скрыто, ≥ 12 символов)
npm run bootstrap -- --login <логин> --name "<Имя Фамилия>"
# повторный bootstrap при наличии активного администратора отклоняется (код 4)

# 5. Демо-данные (необязательно; только development/test; пароль вводится скрыто)
npm run db:seed-demo

# 6. Сборка интерфейса и запуск двух процессов (в разных терминалах)
npm run build
npm run start:server          # http://127.0.0.1:3200 (не 3000 — там Quantor)
npm run start:worker

# 7. Проверка готовности
curl http://127.0.0.1:3200/api/v1/ready   # 200 и ready=true: БД, схема, хранилище, heartbeat worker
```

Разработка интерфейса с горячей перезагрузкой: `npm run dev:server`, `npm run start:worker`, `npm run dev:web` → http://127.0.0.1:5273 (Vite проксирует `/api` на 3200; origin 5273 указан в `ALLOWED_ORIGINS`).

## Источники и наблюдаемые папки (этап 03)

- Загрузка файлов и ZIP — на странице этапа; обработку выполняет `worker` (без него партия остаётся «Обрабатывается», задания не теряются и выполнятся после запуска).
- Наблюдаемая папка: задайте `INTAKE_ROOTS` (корни через «;»), администратор создаёт канал на вкладке тендера «Каналы поступления». Папка синхронизации Яндекс Диска или подключённая сетевая папка — это `origin` канала. Файл импортируется, когда не меняется `INTAKE_STABILITY_SECONDS`; удаление из папки ничего не удаляет в портале.
- Хранилище (`STORAGE_ROOT`) не должно лежать внутри наблюдаемой папки и наоборот — такой канал не сканируется (`overlaps_storage`). Сравниваются физические пути: `STORAGE_ROOT` через junction, ссылку или короткое имя Windows считается тем же каталогом; каталоги хранилища создаются по физическому пути. Если хранилище не удаётся подготовить к записи, канал получает `storage_unavailable`, задание повторяется.

## Поиск (этап 05)

- В той же PostgreSQL нужно расширение **pgvector ≥ 0.8** (`vector`) и `pg_trgm`; их создаёт `npm run db:setup` суперпользователем. На Windows pgvector ставится отдельно (сборка под версию PostgreSQL); без него `db:setup` отказывает с внятной причиной. Альтернатива для разработки — контейнер: `docker run -d --name kontur-pg -p 127.0.0.1:55432:5432 -e POSTGRES_HOST_AUTH_METHOD=trust -e POSTGRES_INITDB_ARGS="--locale=C -E UTF8" -v kontur-pg-data:/var/lib/postgresql pgvector/pgvector:pg18 -c timezone=UTC` (так проверялся этап 05 на Linux).
- База разработки, созданная до этапа 05, имеет провайдер локали libc `C`: `db:setup` откажет, её нужно пересоздать (данные разработки).
- Индекс строит `worker`: при запуске он создаёт версию индекса и индексирует завершённые прогоны распознавания; поиск доступен на вкладке «Поиск» этапа после активации версии. Состояние — `npm run search:index -- status`, новая версия — `npm run search:index -- rebuild`.
- Модель эмбеддингов необязательна: без неё (`EMBEDDING_PROVIDER=none`) работают точный и полнотекстовый поиск, смысловой честно недоступен. Локальный сервер модели с OpenAI-совместимым `/v1/embeddings` (loopback или LAN): `EMBEDDING_PROVIDER=openai_compatible`, `EMBEDDING_BASE_URL`, `EMBEDDING_MODEL`, `EMBEDDING_MODEL_REVISION`; для моделей E5 — `EMBEDDING_INPUT_TEMPLATE=e5`. Смена модели или ревизии — новая версия индекса, её создаёт worker сам.
- Проверка интерфейса этапа: `node artifacts/stage-05/ui-check.mjs` — нужен Chromium (`CHROME_PATH` или `EDGE_PATH`); на Ubuntu 23.10+ без песочницы: `CHROME_NO_SANDBOX=1`.

## Требования и модель (этап 08)

- Реестр требований создаёт руководитель тендера на вкладке «Требования» этапа — на зафиксированном снимке области (вкладка «Поиск»). Переход на новый снимок — кнопка «Перенести на новый снимок»: прежний реестр не меняется.
- Генеративная модель необязательна: без неё (`MODEL_PROVIDER=none`) кандидатов предлагают люди, прогон анализа честно отказывает. Локальный сервер с OpenAI-совместимым `/v1/chat/completions` (loopback или LAN): `MODEL_PROVIDER=openai_compatible`, `MODEL_BASE_URL`, `MODEL_NAME`, `MODEL_REVISION`; при необходимости `MODEL_API_KEY` (только окружение worker), `MODEL_JSON_MODE=json_object`, `MODEL_MAX_INPUT_CHARS`. `MODEL_PROVIDER=fake` — только для разработки и проверок, в production запрещён.
- Ответное ядро (этап 08a) использует ту же генеративную модель. Без модели ход ответа завершается `incomplete_processing` (`model_disabled`) со списком найденных фрагментов — непроверенного текста нет. Необязательные ключи worker: `ANSWER_VERIFIER` (`off` по умолчанию; `same_model` — проверка черновика той же моделью), `ANSWER_MAX_REPAIRS` (0 или 1, по умолчанию 1 — повторный черновик, если ни одно утверждение не прошло правила; AD-08a-6), `ANSWER_PACKET_LIMIT` (1–30, по умолчанию 12 — оснований в пакете хода). Задание `answer.generate` — класс `gpu`: на одном GPU оно ждёт текущую пачку индексации или анализа (U-05).
- Проверка интерфейса этапа: `CHROME_NO_SANDBOX=1 node artifacts/stage-08/ui-check.mjs` (поддельная модель, настоящие `server` + `worker`).

## Расчёт TenderHub (этап 06)

- Адрес и ключ задаются только в окружении `worker` (`.env` пишет пользователь вручную): `TENDERHUB_URL` (`https://…`; `http` — только loopback) и `TENDERHUB_API_KEY` (ключ `thk_…` с областью «Чтение тендеров и смет», ограниченный разрешёнными тендерами). Ключ уходит только заголовком `X-API-Key`; `config:check` показывает лишь «задано / не задано». Без них выгрузка завершается `failed` с причиной `integration_not_configured`, остальной портал работает.
- Связь этапа с тендером TenderHub задаёт администратор, назначенный на тендер: вкладка «Расчёт» → uuid тендера TenderHub (версии тендера там — разные uuid). Выгрузку запрашивает участник; её выполняет `worker` в фоне. Результат — ревизия `provisional`: боевой выпуск с ней заблокирован (X-01), итог КП не выводится (Q-05).
- **Live-smoke (U-04)** — только после выдачи ключа и разрешённого тендера владельцем, только чтение: `npm run tenderhub:live-smoke -- --tender <uuid разрешённого тендера>`. Скрипт сверяет живую спецификацию `GET /api/v1/archive/openapi.yaml` с маршрутами адаптера, выполняет выгрузку тем же адаптером без БД портала (при одной странице позиций — ещё пробный обход малыми страницами) и пишет `artifacts/stage-06/live-smoke.log` по разделам 1–10: доступ, только GET, пагинация, with-costs, BOQ, согласованность, числовой контракт, поля Q-05, расхождения с контрактом, безопасность журнала. В журнале — коды, счётчики, имена полей и SHA-256 ответов; ключа, значений тендера и полных uuid нет. Код 0 — PASS, 1 — FAIL, 3 — не настроено (NOT_RUN). Журнал перед передачей просматривается человеком; статус интеграции скрипт не меняет, `VERIFIED_LIVE` ставится только по журналу после ревью.
- Проверка интерфейса этапа: `node artifacts/stage-06/ui-check.mjs` (поддельный TenderHub, настоящие `server` + `worker`; Chromium — как для этапа 05).

## Экономика (этап 10)

- `TENDERHUB_INSTANCE_ID` (окружение `worker`, `.env` пишет пользователь): стабильный идентификатор экземпляра TenderHub — латиница, цифры, «.», «_», «-», до 64 символов; задаётся один раз и не меняется. Записывается в каждую завершённую выгрузку. Без него пары позиций между ревизиями одной версии тендера система не подтверждает — они остаются предложениями (D-030). Адрес `TENDERHUB_URL` идентификатором экземпляра не считается.
- Вкладка этапа «Экономика»: отчёт ревизии (пишется при первом открытии и далее неизменен), сравнение двух ревизий тендера, сопоставление позиций (предложения подтверждает инженер, в том числе пакетом), причины изменений вручную и гипотезы модели (кнопка «Найти причины в источниках»: нужны снимок области этапа и активный индекс поиска; задание `economics.reasons` класса `gpu`).
- Проверка интерфейса этапа: `CHROME_NO_SANDBOX=1 node artifacts/stage-10/ui-check.mjs` (поддельный TenderHub с двумя версиями, настоящие `server` + `worker`).
- Живая проба семантики TenderHub (только GET, без БД портала): `node --env-file-if-exists=.env artifacts/stage-10/semantics-probe.ts` → `artifacts/stage-10/semantics-probe.log` (вердикты и счётчики, без сумм и названий).

## Доступ из LAN/VPN

Без TLS сервер отказывается слушать не-loopback адрес (`config:check` покажет ошибку). Для LAN задайте `HTTP_HOST`, `TLS_CERT_FILE`, `TLS_KEY_FILE` и `ALLOWED_ORIGINS=https://<имя>`. Выпуск сертификата и сетевое имя — U-02. LocalAI остаётся внутренним сервисом: портал не проксирует его наружу, адрес и токен — только в окружении worker/server.
