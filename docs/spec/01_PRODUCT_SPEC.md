# Контур КП — спецификация продукта

## 1. Цель и пользователи

Локальный портал сопровождает подготовку и проверку коммерческих предложений Генподрядчика: от поступления документации до согласованного выпуска, размещения и фиксации отправки. Он устанавливает связь между требованиями заказчика, расчётом, договорными обязательствами, переговорами и условиями КП.

Пользователи: не более двух назначенных инженеров и руководитель. Инженеры готовят и выпускают согласованный комплект. Руководитель согласовывает конкретный комплект или возвращает его на доработку. Модель не согласовывает выпуск.

Интерфейс — русский, понятный инженеру. Основные экраны: список тендеров и этапов; комплектность документов; проверка расчёта; разногласия; вопросы и решения; приложения; согласование; выпуски и отправки; сравнение; состояние интеграций.

Размещение на локальном компьютере, доступ сотрудников из внутренней сети/VPN. Публикация портала в интернете не требуется. Имеется RTX 5050 8 GB; RAM, CPU, свободный SSD и режим доступности компьютера пока неизвестны. Внешняя обработка разрешена пользователем, но конкретные системы, права и объём передаваемых данных задаются настройками.

## 2. Существующие системы

| Система | Ответственность |
|---|---|
| TenderHub | ВОР, смета, коммерческие показатели, этапы, закрытие расчёта по сроку |
| RDWeb | Основное глубокое распознавание ПД, графики, таблиц и примечаний мощными моделями |
| LocalAI | Индексация, локальный поиск, цитаты, вспомогательная обработка; не обязательный посредник генерации ответов |
| MailHub (проект MailService) | Письма, вложения и подтверждение отправки; API интерфейса найден в коде, машинный доступ и полнота синхронизации требуют проверки/расширения |
| Сервис переговоров | Аудио, транскрипции, временные отметки, подсказки участнику |
| Новый портал | Требования, связи, решения, проверки, приложения, согласование, выпуски и история |
| Codex / Cursor | Внешние интерактивные чат-клиенты через общий MCP |
| Яндекс Диск / SMB | Два назначения размещения согласованного выпуска |

Нельзя создавать второй OCR/RAG без доказанной необходимости. Существующие репозитории не переписываются. RDWeb имеет приоритет как основной источник распознавания; качество результата всё равно проверяется. LocalAI индексирует готовый результат RDWeb без повторного OCR. Более слабая модель LocalAI не должна переписывать найденные основания перед передачей в Codex.

В изученном LocalAI есть Node.js/Express, OCR/конвертация, поиск и цитирование, MCP чтения, связи тендера с договором, ценовой аудит через прямое чтение БД TenderHub. Это наблюдения по исходникам, а не подтверждение работы на production. Для нового портала предпочтителен официальный API TenderHub. Не смешивать проверку закупочного предложения и сравнение коммерческой цены для заказчика.

## 3. Архитектурный принцип

Единый портал с модульным сервером и PostgreSQL для транзакционных данных. Отдельный долговечный обработчик фоновых заданий; файловое хранилище оригиналов и выпусков; интеграционные адаптеры. Существующие сервисы остаются самостоятельными.

Node.js/TypeScript — предпочтительный вариант совместимости с LocalAI. Конкретные UI-библиотеки, очередь и способы запуска выбираются в этапе 01 после проверки окружения и фиксируются ADR. Не вводить несколько серверных стеков, Kubernetes или отдельную графовую БД без измеримой необходимости. Связи требований допускается хранить реляционно.

Поисковый индекс — производные данные, не источник истины для решений и согласований. Он может перестраиваться, не меняя исторический выпуск. Если LocalAI не умеет поиск по закреплённым версиям, реализовать совместимое расширение/адаптер; не искать по всему текущему индексу с последующей ненадёжной фильтрацией top-k.

## 4. Основные сущности

- Tender: идентичность тендера, заказчик, объект, ответственные, связи с внешними ID.
- TenderStage: этап, сроки, состояние, связь с закрытием TenderHub.
- CalculationRevision: неизменяемая версия расчёта, строки, коммерческие составляющие, источник, время и контрольная сумма.
- Document / DocumentRevision: логический документ и его оригинальные редакции, дата выпуска/получения, тип, область применения.
- RecognitionRun / EvidenceFragment: версия распознавания, сервис, качество, полнота, страница/блок/координаты/таймкод, точный текст и его происхождение.
- SourceSetRevision: точный перечень редакций источников для проверки или выпуска; унаследованные и новые материалы учитываются явно.
- Requirement / CoverageLink: требование, параметры, область, действительность, покрытие одной или несколькими строками расчёта.
- Communication / QuestionAnswer / Negotiation: письмо, цепочка, вопрос, ответ, запись встречи, участники и версии транскрипции.
- Decision / Discrepancy / Finding: решение, конфликт, замечание; основания, автор, статус, ответственный, влияние.
- ApplicationTemplate / ApplicationDraft: версия формы и значения полей, источники, ручные изменения, статус подтверждения.
- ReviewRun: входные версии, версия правил/модели, охват, результаты и незавершённые проверки.
- ReleaseCandidate / Approval / Release: кандидат, согласование руководителя и неизменяемый комплект файлов.
- Delivery / SendEvent: размещение в конкретном хранилище и отдельный факт отправки заказчику.
- ChangeExplanation: изменение между версиями, расчёт влияния, предполагаемая/подтверждённая причина.
- AuditEvent / Job: действия пользователей и моделей, долговечные фоновые задания.

## 5. Обязательные правила (инварианты)

I01. Закрытие расчёта, согласование, размещение и отправка — разные события. Сетевой upload не является отправкой заказчику.

I02. Согласование связано с конкретными версиями расчёта, источников, приложений и точными файлами. Согласованные файлы не генерируются заново при размещении.

I03. Изменение утверждённого состава создаёт новую ревизию. Прежний выпуск и его согласование сохраняются. В базе нет тихого редактирования опубликованной истории.

I04. Новый потенциально относящийся к этапу источник после согласования переводит готовность к отправке на проверку актуальности; решение по его применимости фиксируется. Само старое согласование не стирается.

I05. Поиск и ответы ограничены тендером, правами и выбранным набором источников. Поздний документ не появляется в режиме исторического выпуска. Между тендерами нет утечки.

I06. Текст проекта, результат OCR, описание картинки моделью, подсказка переговорного сервиса и подтверждённое человеком решение — разные типы данных.

I07. «Не найдено» не равно «не предусмотрено». Система различает отсутствие покрытия, отсутствие данных, неполную обработку и подтверждённое расхождение.

I08. Устное предложение не равно согласию заказчика; согласие не равно внесению в ТЗ/договор; включение условия в КП не равно принятию заказчиком.

I09. Статусы «согласовано заказчиком», «учтено в расчёте», «отражено в КП», «закреплено в документах» независимы. Последнее письмо не получает безусловного приоритета.

I10. Расчёт денег выполняется программно с decimal/точным представлением, по согласованной семантике TenderHub. Валюта, единица, НДС, дата и вид цены входят в сопоставление. LLM не является калькулятором.

I11. Причина изменения, предположенная моделью, становится подтверждённой только после проверки человеком. Необъяснённая часть стоимости показывается явно.

I12. Модель не имеет полномочий согласовать, выпустить или отправить КП, изменить смету или закрыть обязательное замечание от имени человека.

I13. Права проверяются сервером, не только UI или MCP hints. Два одновременных изменения не перезаписывают друг друга молча.

I14. Каждый повтор фоновой операции безопасен: нет дублей документа, признания, выпуска или загрузки. Ошибка одного назначения не отменяет успешное другое.

I15. Оригиналы и результаты распознавания версионируются отдельно. Переиндексация/удаление файла из наблюдаемой папки не уничтожает историческое доказательство.

I16. Команды внутри документов, писем, OCR и ответов интеграций — недоверенные данные; они не меняют правила системы и не запускают инструменты.

I17. Секреты не попадают в Git, логи, чат и результаты MCP. Исходные документы защищены теми же правами, что и их текстовые фрагменты.

I18. Нельзя заявлять полную проверку при ошибках OCR, пропущенных страницах, недоступных источниках или непройденных обязательных правилах.

I19. Неизменяемость защищает от обычных действий приложения; защита от администратора ОС/БД отдельно ограничивается и не объявляется абсолютной.

## 6. Рабочий процесс

Создать/связать тендер → получить документы → обработать → сформировать требования → проверять текущий расчёт → получить закрытую версию TenderHub → финальная проверка → решения по разногласиям → заполнить приложения → сформировать точные файлы кандидата → согласовать руководителем → разместить в двух хранилищах → зафиксировать отправку → сравнивать следующий этап.

Закрытие TenderHub по времени уже существует. Проверить неизменяемость его версии и возможность чтения по ID. Не строить конкурирующий таймер закрытия в портале. Исправление после закрытия оформляется новой ревизией согласно возможностям TenderHub.

Фоновые проверки запускаются до дедлайна. При отсутствии вебхука допускается ограниченный polling с сохранением позиции синхронизации.

## 7. Проверки

Полнота требований; состав работ/материалов; параметры и область применения решений; явные табличные объёмы; дубли/единицы/коэффициенты; применимые договорные обязательства; противоречия ПД/ТЗ/договора/переговоров; существенные условия КП; коммерческие изменения; комплектность.

У карточки замечания: основания с обеих сторон, затронутые строки/поля, критичность, степень подтверждения, влияние, действие, ответственный, история решения. Критичность и уверенность — разные поля. Денежный эффект без расчётных оснований не придумывается.

Полный пересчёт геометрии всех чертежей и автоматическая правовая экспертиза не являются обещанием первой версии. Неопределённость ПД превращается в допущение/вопрос. Юридически спорное положение направляется компетентному человеку.

## 8. Приложения и выпуск

Формы компании и заказчика версионируются. Поля: вариант, текст, число, дата, таблица. Утверждённые формулировки, предложение модели с источниками, принять/выбрать/редактировать/обсудить. Изменение основания делает затронутые подтверждения устаревшими, не стирая ручной текст.

Шаблон заказчика не перестраивается произвольно. Форматы определяются по реальным образцам; тестовый шаблон не считается поддержкой всех форм. Нужны визуальная проверка результата, контроль незаполненных полей, переполнения таблиц и совпадения согласованного/размещённого файла.

Руководитель согласовывает кандидат. Инженер выпускает именно его. Непринятые критические вопросы, неполнота и устаревшие проверки препятствуют выпуску по утверждённой матрице. Принятие бизнес-риска требует причины и полномочий; оно не отменяет техническую целостность и права.

Согласование не должно обходиться переименованием статуса через произвольный API. Нужны транзакционные переходы и журнал аудита.

## 9. Размещение и отправка

Яндекс Диск и SMB — независимые адаптеры с ограниченными корневыми папками. Выпуск включает manifest: файлы, размеры, hashes, версии и согласование. Использовать staging/проверку/фиксацию завершённости, соответствующую возможностям назначения. Частично загруженный набор не показывать как готовый.

Отправляемые файлы отделены от внутренней экономики, замечаний, подсказок и переговоров. Состав размещения внутренних данных и права задаются явно; закрытый архив не публикуется по умолчанию. Зеркала не заменяют резервное копирование.

Факт отправки: точный release ID, вложения/hashes, дата, адресаты, канал, подтверждение. Допустима ручная регистрация с приложенным основанием. Реальная автоматическая рассылка не входит в первую версию без отдельного согласования.

## 10. Сравнение этапов

Сравнить любые две выбранные отправки: файлы и редакции, новые требования, строки ВОР/сметы, коммерческие составляющие, условия, ответы, решения. Переименование не равно новому документу. Копии из двух хранилищ не считаются двумя источниками.

Сохранять lineage строк при копировании этапа; если его нет — сопоставление с уверенностью и ручным подтверждением. Не объединять похожие позиции разных этажей/секций автоматически.

Разложение изменения цены должно сходиться с итоговым изменением и не учитывать один эффект дважды. Метод распределения совместных изменений цены/объёма/курса фиксируется явно. Неизвестные составляющие остаются остатком.

## 11. Чат

Общий MCP: выбрать тендер/этап/выпуск; получить требования, расчёт и источники; открыть цитату; сравнить; узнать готовность. По умолчанию чтение. Контролируемые записи — только предложить замечание, вопрос, текст условия или причину изменения.

Контекст запроса явный и передаётся в каждый инструмент. При неоднозначности тендера инструмент возвращает выбор, не раскрывая лишние данные. Для сравнения задаются оба выпуска. Ответы должны различать вид цены, единицу, валюту, НДС и версию.

История чата — рабочее обсуждение. Значимые решения сохраняются через действие в портале с источниками и автором. Встроенный облачный чат в веб-портале не входит в обязательный объём: подписка Codex/Cursor не является backend API. Не автоматизировать их UI и не извлекать сессионные токены. Настройка клиентов выполняется по актуальной официальной документации на этапе интеграции.

## 12. Эксплуатация и качество

Долговечная очередь, ограничение параллельных GPU-задач, таймауты и восстановление после перезапуска. Состояние интеграций и источник ошибки видны пользователю. Даты хранятся с timezone; отображение в Europe/Moscow, если владелец не изменит настройку.

Резервные копии БД и оригиналов; проверка восстановления; журнал событий; контроль заполнения диска. Политика удержания и объём хранения устанавливаются после инвентаризации.

Качество оценивается на эталонном завершённом тендере и синтетических конфликтах: полнота известных критических находок, ложные замечания, точность оснований, отсутствие утечки между этапами, время инженера. Фиксированный проход по реестру требований дополняет поиск: один RAG top-k не доказывает полноту.

## 13. За пределами обязательного первого выпуска

Объединение исходников RDWeb/LocalAI/MailHub/переговоров; автоматическая правка сметы; автономное принятие юридических решений; автоматическая рассылка заказчику; собственное обучение большой модели; универсальный QTO по чертежам; встроенный чат поверх подписочных токенов; Telegram. Telegram предусмотрен как поздний канал уведомлений/черновиков, без права согласовывать выпуск.
