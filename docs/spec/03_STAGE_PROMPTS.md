# Поэтапные задания для Claude Code

Каждый раздел — самостоятельный промпт. Перед ним можно вставить универсальный промпт продолжения. Спецификация и инварианты обязательны на каждом этапе.

Во всех этапах: реализация → проверки → отчёт `docs/stages/XX-report.md` → независимое ревью Codex → исправления → повторная проверка. «Готово» означает выполненные критерии, а не только наличие файлов. Порядок можно менять лишь для независимых задач с зафиксированным основанием; зависимости и блокировки не исчезают.

## 00. Инвентаризация и границы

Изучи спецификацию и существующие системы read-only. Не запускай тяжёлую индексацию и production-операции. Проверь фактические исходники LocalAI и MailService, предоставленный архив API TenderHub и формат экспорта RDWeb. Репозитории/доступы RDWeb и переговоров не выдумывай. Составь список внешних доработок и вопросов, которые действительно влияют на реализацию.

Раздели функции на: переиспользовать; написать в портале; добавить в соседней системе; проверить доступность. Зафиксируй аппаратные и эксплуатационные неизвестные, формы приложений, правила согласования и эталонный тендер.

Особое внимание: поиск LocalAI по историческим версиям; текущий прямой DB-adapter TenderHub; коммерческие показатели vs закупочные цены; MailHub с cookie-auth и фильтрацией отправленных писем; отсутствие подтверждённого машинного API RDWeb.

Результат: `docs/discovery.md`, карта требований и возможностей с ссылками на исходники/документы, реестр неизвестных и интеграций, начальный tracker.

Проверка: каждое утверждение «уже есть» подтверждено кодом/контрактом, запуск не приписан исходнику. Нет утечек секретов. Обязательные пожелания пользователя присутствуют в карте.

Выход: обзор готов для архитектурного решения. Отсутствие внешних доступов перечислено, не замаскировано.

## 01. Архитектура, модель данных и контракты

На основании 00 спроектируй модульное приложение, долговечную очередь, PostgreSQL, файловое хранилище, LocalAI/RDWeb/TenderHub/MailHub/переговорные адаптеры и MCP. Выбери один основной web/backend стек, мотивируй совместимость с Windows и LocalAI. Не превращай портал в набор лишних микросервисов.

Опиши ER-модель, владельцев данных, контракты портала, таблицы переходов состояний и границы транзакций. Включи source-set revision, calculation revision, release candidate, approval, release, delivery и send event отдельно. Укажи идемпотентные ключи, optimistic concurrency, часовые пояса и точное представление денег.

Опиши область поиска как явные IDs разрешённых редакций; место модели и программных правил; способ миграций, запуска и восстановления. Определи роли и изоляцию по тендерам/почтовым ящикам. Согласование и выпуск не доступны сервисной учётной записи модели.

Результат: ADR, ER-схема, API/adapter contracts, таблицы состояний, перечень инвариантов с механизмом исполнения, сквозной план тестирования. Содержательные неизвестные должны иметь владельца и влияние.

Проверка: пройти на бумаге кейсы лампы, нового документа после согласования, изменения после закрытия, двух параллельных правок и повторной доставки. Проверить, что модель поддерживает каждый кейс без перезаписи истории.

Выход: нет неизвестного, которое требует переделать ядро; внешние форматы могут быть изолированы адаптерами. Код продукта ещё не считается реализованным.

## 02. Рабочий каркас, БД и права

Реализуй запускаемый локальный портал, миграции PostgreSQL, серверную авторизацию, роли инженера/руководителя, назначения на тендер, базовый интерфейс тендера/этапа и журнал действий. Bootstrap руководителя должен быть защищён, не открытая первая регистрация в LAN. Интеграционные credentials отделены от пользовательских сессий.

Добавь health/readiness, проверку конфигурации без вывода секретов, isolated test DB, демо-данные и инструкцию чистого старта. LAN-доступ должен учитывать origin, cookie/CSRF или эквивалентную модель и выбранный защищённый транспорт. LocalAI остаётся внутренним сервисом.

Проверки: миграция пустой БД; перезапуск; отказ неаутентифицированному пользователю; инженер не получает право руководителя подменой запроса; чужой тендер недоступен; stale edit возвращает конфликт; аудит фиксирует автора и объект.

Выход: функциональный каркас с реальными API/БД, без фиктивных экранов готовности остальных модулей.

## 03. Источники, редакции и очередь обработки

Реализуй регистрацию оригиналов, безопасный импорт файлов/архивов, document revisions, hashes, долговечные задания, retry/backoff и наблюдение за выделенной папкой. Дождись завершения копирования, не импортируй частичный файл. Проверяй выход за разрешённый корень, zip traversal, лимиты распаковки и типы файлов.

Поддержи дубликаты одного содержимого с несколькими местами получения; различай редакцию оригинала и распознавания. Удаление из входной папки не удаляет архив. Каталоги производных результатов не сканируются повторно. История исходного пути сохраняется без использования пути как единственного ID.

Реализуй состав источников этапа, статусы обработки и явные ошибки. Изображения и HTML открывай без исполнения активного содержимого/внешних скриптов.

Проверки: повторное обнаружение; одинаковое имя с другим содержимым; переименование; сбой во время импорта; restart worker; архив с `../`; большой архив; недоступная шара; двойное получение из Яндекс/SMB.

Выход: источник воспроизводим, задания не теряются, статусы соответствуют фактам.

## 04. RDWeb как основное распознавание

Реализуй адаптер RDWeb по подтверждённому контракту. Первый полезный вертикальный результат — импорт предоставленного экспортного формата PDF + results.md/html + blocks.json. Если API ещё отсутствует, импорт экспорта работает полноценно, автоматическая отправка/получение остаются явно заблокированными внешней доработкой.

Сохрани страницы, block ID, координаты, rotation, тип блока, текст, описания и служебные рекомендации раздельно. Не путай page_index с номером страницы и номером листа в штампе. По ссылке на доказательство открывай локальный PDF и нужный участок; crop URL не является единственным доказательством.

При доступном API добавь постановку задачи, status, получение частичного/полного результата, retry и корреляцию с hash оригинала. Нельзя принимать результат другого файла или старого задания как новый. Внешние crop URLs не скачивай произвольно без allowlist и защиты от SSRF.

Проверки: обезличенная fixture формата архива; повёрнутая страница; отсутствующий crop; несовпадающее число страниц; неизвестный block; повторная версия OCR; частичный ответ; timeout. Затем отдельный разрешённый live-smoke без автоматического повторного счёта/платежей.

Выход: воспроизводимое доказательство и явная полнота. Условие автоматического pipeline отмечено отдельно от загрузчика архивов.

## 05. Собственный индекс и поиск по версиям

Этап переопределён решением D-013: Locus (LocalAI) закрывается, его поисковое ядро переносится в портал. Внешнего адаптера `LocalAiIndex` нет, X-04 и Q-13 закрыты как неприменимые. Решения D-013, D-014, D-015 и D-020 приняты; спецификация, ADR-002/007/008, новый ADR-012, контракты и трассировка приведены в соответствие. Основной источник по индексу — ADR-012.

Построй индекс портала поверх неизменяемых `evidence_fragment`. Единица чанка — страница прогона, длинная режется с перекрытием, шапка повторяется в каждой части и получает больший вес. Связь чанка с фрагментами — упорядоченная, со смещениями: цитата сводится к существующему `evidence_fragment.id` со страницей и координатами. Принадлежность чанка единице источника и тендеру гарантируй составными внешними ключами, а не проверкой в коде.

Реализуй точный поиск обозначений, полнотекстовый с конфигурацией `russian` и смысловой на эмбеддингах, слияние рангов RRF. Фильтр по разрешённым единицам стоит в `WHERE` каждой ветки, до `ORDER BY … LIMIT`; постфильтрация top-k запрещена. Проверка ответа по БД портала остаётся второй линией: фрагмент вне области отклоняет ответ целиком с записью в аудит. Связь договора с тендером область не расширяет. Реестр документов и требований доступен отдельно от поиска.

Векторы — pgvector в той же PostgreSQL, `halfvec`, `SET STORAGE PLAIN`, отдельная узкая таблица, исключаемая из резервной копии по данным. ANN-индекс не создаётся намеренно: с ним `WHERE` применился бы после обхода индекса, то есть после отбора. Причина фиксируется в комментарии миграции, в ADR-012 и тестом на `EXPLAIN`; возврат к вопросу — только по замерам.

Смысловой поиск асинхронный: точный и полнотекстовый результат возвращаются синхронно, смысловой приходит заданием класса `gpu`. Индексация берёт ограниченную пачку и ставит себя заново, чтобы не выдавливать интерактивный поиск из единственного GPU-слота. Реранкер не заводится: переносится только интерфейс шлюза и поведение при недоступности.

Корпус этапа — существующие прогоны RDWeb. Договоры приходят этапом 06a, форматы вне охвата RDWeb — этапом 05a; охват не выдаётся за полный.

Гейт до начала работ: кластер создан с `--locale=C`, из-за чего `lower()` и `to_tsvector('russian', …)` не приводят регистр кириллицы. Равенство `to_tsvector('russian','Договор')` и `to_tsvector('russian','договор')` обязано быть истинным.

Проверки: два тендера с одинаковой фразой; два этапа с противоположными ответами; два прогона одного PDF — поздний первым при limit = 1, исторический режим поздний не видит; перепривязка договора не расширяет область; новая индексация не ломает старую цитату; удаление индекса не уничтожает оригинал; письмо из недоступного ящика отсутствует в выдаче; отсутствие результатов не становится утверждением отсутствия требования.

Выход: поиск на закреплённом комплекте, точные источники, честный охват. Индекс — производные данные: его потеря не трогает доказательства и выпуски.

## 05a. Локальное распознавание форматов вне охвата RDWeb

Заведи движок `local_ocr` рядом с `rdweb_export`, не подменяя его. `recognition_run.engine` это значение уже допускает. Покрой текстовый слой PDF, `.docx`, `.xlsx`, `.csv` и сканы без текстового слоя. Происхождение фрагмента различай: извлечённый текст документа и распознанный текст — разные значения `origin` (I06).

Задание локального распознавания не ставится на редакцию, у которой есть или ожидается завершённый прогон RDWeb; пришедший позже прогон RDWeb перекрывает локальный через существующий `supersedes_run_id`. При автоподборе прогона в снимок области локальный никогда не выигрывает у RDWeb.

Координат у этих форматов нет: интерфейс показывает текст и якорь страницы и прямо пишет, что координаты недоступны, а не рисует рамку наугад. Признаки неполноты и непригодного текста пишутся в качество прогона; страница, не прошедшая порог, не даёт статус «полностью».

Проверки: A43 — явная маркировка качества и происхождения без тихой подмены основной обработки; скан без текстового слоя; повреждённый файл; внешний конвертер упал или вернул пусто; повторный прогон того же файла.

Выход: корпус расширен договорами, письмами и таблицами; RDWeb остаётся основным распознаванием проектной документации.

## 06a. Договорной контур

Заведи `contract` рядом с `tender` — не надсущностью «проект» и не статусом «выигран» у тендера. Договор живёт годами после закрытия тендера и обрастает допсоглашениями; как статус тендера он переоткрывал бы готовность давно выпущенных этапов.

Доступ строится по образцу `mailbox_access`: общий внешний корпус и явная выдача, администратор ведёт строки. Возможности `contract.read`, `contract.write`, `admin.contract` — вторым типом рядом с возможностями тендера, вторая линия в БД обязательна.

Документы, редакции, прогоны распознавания и фрагменты получают необязательную принадлежность договору при обязательном ровно одном владельце — тендер или договор. Составные внешние ключи дублируются по договору. Это самая опасная миграция плана: ошибка даёт молчаливую утечку между тендером и договором, поэтому нужен отдельный регрессионный набор.

Связь договора с тендером подтверждает человек, и она не расширяет область поиска: единицы договора лишь предлагаются кандидатами в состав источников этапа, а ищутся только после явного включения в снимок.

Проверки: инженер без выданного доступа не видит договор ни списком, ни по прямому идентификатору; документ договора не попадает в поиск по тендеру без включения в снимок; подтверждение связи не меняет исторический выпуск.

Выход: корпус действующих договоров внутри портала с правами и аудитом.

## 06. TenderHub: этапы и закрытые расчёты

Подключи официальный API read-only по X-API-Key. Не используй Bearer для API-ключа. Импортируй тендеры, этапы/версии, ВОР, состав строк, примечания, hierarchy, коммерческие значения и внешние IDs. Учитывай pagination, лимиты, gzip и кэш with-costs согласно контракту.

Используй закрытие TenderHub как источник события закрытия, не создавай второй механизм. Получай согласованную неизменяемую ревизию. Если API её не отдаёт, документируй доработку; собственная выгрузка нескольких изменяемых маршрутов не доказывает атомарный снимок. Временная выгрузка может иметь статус provisional и не проходить production gate.

Сохраняй исходный ответ и нормализованные данные с версиями контракта. Не трактуй заголовок раздела как работу, большинство категорий позиции — как категорию каждой строки, manual_volume — без подтверждённой семантики. Храни lineage позиций между этапами.

Проверки: пустая/дополнительная позиция; комплексная строка; много страниц; 401/403/429; сбой после части загрузки; изменение в ходе импорта; повторное событие закрытия; новая ревизия после открытия; расхождение агрегатов. Отдельно live-smoke на разрешённом тендере.

Выход: историческая смета воспроизводима, итог/числа строк сверены, источник истины и недоступные поля обозначены.

## 07. MailHub, вопросы–ответы и переговоры

Используй фактический MailService (MailHub), не создавай почтовый клиент заново. Прочитай discovery: API писем/вложений уже существует, однако машинная авторизация и change-feed требуют подтверждения/расширения. Не используй украденную браузерную cookie или классификационный агент как универсальный доступ к почте.

Реализуй импорт писем, thread/message IDs, дат, участников, вложений, источника ящика, корреляцию тендера с ручным подтверждением. Отдельно получай отправленные: общий feed может исключать их. Не помечай письма прочитанными, не перемещай и не создавай черновики как побочный эффект чтения. Дедупликация должна сохранять происхождение нескольких копий.

Импортируй формы вопрос–ответ с устойчивыми номерами/редакциями, пустыми и заменёнными ответами. Подключи сервис переговоров по API или manifest-файлам: speakers, timestamps, transcript revisions, original audio reference. Подсказки участнику — отдельный тип, не речь заказчика.

Проверки: одинаковая тема разных тендеров; общий почтовый thread на несколько тем; письмо в нескольких ящиках; недоступный ящик; вложение по чужому ID; цитируемый старый ответ; устное «рассмотрим»; исправление транскрипции; повтор sync без дублей. Проверить разрешённое чтение реального примера отдельно.

Выход: сообщения и переговоры доступны как доказательства, кандидаты в договорённости не подтверждены автоматически. Если API переговоров отсутствует, полноценный файловый импорт + BLOCKED_EXTERNAL для автоматизации.

## 08. Требования, покрытие и решения

Реализуй реестр требований и связи many-to-many с расчётом. Извлекай кандидаты из ТЗ, ПД, договора, примечаний, Q&A и переговоров. Сохраняй объект/секцию/этаж/помещение, параметры, source revisions и статус человеческого подтверждения.

Добавь принятие/отклонение/редактирование кандидата, связь с комплексной расценкой, допущение ПД, вопрос заказчику и историю решений. Не теряй исходную цитату при редактировании формулировки. Нужен последовательный обход реестра для полноты, а не только произвольный чат.

Доступные модели вызываются через заменяемый ограниченный интерфейс со структурированной схемой ответа. Валидация JSON и проверка существования evidence IDs обязательны. Гипотеза без основания не превращается в подтверждённый факт.

Проверки: несколько работ на требование; несколько требований в позиции; одинаковый материал разных этажей; неверная единица; ложная цитата модели; конфликтующие требования; повтор извлечения; ручная правка не затирается.

Выход: инженер может пройти полный цикл от источника до подтверждённого покрытия/вопроса с историей.

## 08a. Ответное ядро и диалоги

Перенеси ответное ядро Locus, разложив его по ADR-009. Программными правилами остаются разбор вопроса, сбор пакета доказательств, числовые гейты и отрисовка ответа. Модели отдаются только черновик ответа и необязательная проверка — через шлюз, с JSON-схемой и валидацией до записи. Каждый процитированный идентификатор фрагмента обязан существовать и входить в область.

Числовой гейт переноси дословно: каждое число черновика обязано присутствовать в процитированном фрагменте с той же единицей, проценты не путаются с днями и годами, а коды вроде `B30`, `КС-2` и `п. 3.1` числами не считаются. Утверждение, не прошедшее гейт, в ответ не попадает. Перекрытый допсоглашением пункт не выдаётся за текущий.

Словарь статусов ответа — объединение двух наборов: к состояниям портала добавляется «нужно уточнить». Он остаётся отдельным от словаря результатов проверки и никогда не красит проверку: «подтверждено цитатами» не означает «проверено по регламенту». Недостаток оснований и отказ модели дают неполноту, а не «проверено» (I18).

Диалоги, сообщения и состояние хода живут в PostgreSQL. Стриминг черновика запрещён: непроверенный текст не показывается, поэтому интерфейс опрашивает готовый прогон, а не поток. Выполнение — заданием класса `gpu`, как и смысловой поиск.

Проверки: ложная цитата модели; число, которого нет в основании; ответ по перекрытому пункту; конфликт двух оснований показан, а не разрешён; отказ модели; выключенная модель не даёт неверифицированный текст; инструкция «игнорируй правила» внутри документа не исполняется.

Выход: ответ с основаниями, который человек может проверить по оригиналу, и который ничего не решает сам.

## 09. Правила проверки и договорные разногласия

Реализуй проверочный запуск с закреплёнными входами, версиями правил/модели и показателями покрытия. Раздели программные проверки и LLM-гипотезы. Добавь completeness, параметры, единицы, применимые арифметические правила, договорные обязательства, неопределённость ПД и конфликты источников.

Создай экран разногласий с двумя основаниями, затронутыми позициями, критичностью, действием и ответственным. Реализуй независимые статусы согласования заказчика, учёта в смете, отражения в КП и закрепления в ТЗ/договоре. Приоритет источников конфигурируется по тендеру; не выводится только из даты.

Изменение источника инвалидирует затронутые проверки/решения через зависимости. При ненадёжном определении затронутой области выбирай консервативную повторную проверку и показывай причину. Старые отчёты сохраняются.

Проверки: светильник №1/№2; электроэнергия в договоре против расчёта; конфликт двух ответов; молчание заказчика; принятый риск; отказ модели; нераспознанная страница; новая редакция после закрытия замечания.

Выход: нельзя получить «всё проверено» из пустого результата поиска или незавершённого job. Критические эталонные конфликты обнаруживаются и объясняются.

## 10. Коммерческая экономика и сравнение расчётов

После подтверждения семантики TenderHub реализуй точные суммы и сравнение выбранных calculation revisions. Раздели цену поставщика, себестоимость, коммерческую цену, суммы/единичные цены, доставку, валюту, НДС, наценку/скидку и общие затраты, если они есть в модели источника.

Расширь adapter contract для отсутствующих коммерческих затрат. Не вычисляй их из догадок. Покажи неизвестные составляющие и статус сверки с итогом TenderHub. Зафиксируй метод разложения совместных изменений количества/цены/курса и распределения общих затрат.

Построй lineage-сопоставление и ручную проверку неоднозначных пар. Причины: документ, ответ, поставщик, внутреннее решение, неизвестно. LLM предлагает причины, инженер подтверждает.

Проверки: decimal и округления; валюта; цены с/без НДС; единичная цена vs итог; quantity=0; отрицательная согласованная корректировка; замена/разделение позиции; цена+объём одновременно; общий discount; сумма вкладов равна итоговой разнице; повторный импорт не меняет результат.

Выход: экономический отчёт сходится с источником либо явно показывает неподтверждённый остаток; закупочная цена не сравнивается с продажной как ошибка без учёта состава.

## 11. Формы приложений и библиотека условий

Реализуй версии шаблонов компании/заказчика и веб-мастер заполнения. Поля: варианты, текст, числа, даты, таблицы; правила обязательности и применимости. Для каждого предложения — основание, состояние и история ручных правок.

Поддержи быстрые кнопки принять/выбрать/изменить/обсудить и повторно используемые утверждённые формулировки. Сопоставь решения с полями разных приложений и выявляй противоречия между ними. Обновление решения помечает поля stale, не перезаписывая подтверждённый текст.

Используй реальные предоставленные формы. При их отсутствии создай явно демонстрационную форму, сохрани блокировку приёмки генерации production-приложений. Не меняй структуру обязательного шаблона заказчика без основания.

Проверки: обязательное поле; условно применимое поле; длинная формулировка; несовместимые варианты; два редактора; смена template revision; предложение с ложной цитатой; ручная правка после предложения LLM.

Выход: заполнение через интерфейс, сохранение происхождения и понятный список незавершённых пунктов.

## 12. Формирование документов и кандидата выпуска

Реализуй генерацию согласованных форматов по образцам (точный набор фиксируется в ADR). Создай неизменяемого кандидата с calculation revision, source-set revision, review runs, decision set, template versions и точными файлами.

Сформируй manifest с hashes/размерами и разделением отправляемого/внутреннего. Включи проверку плейсхолдеров, заполненности и согласованности цифр с расчётом. Отображай пользователю превью именно того файла, который будет согласован.

Проверки: визуальная проверка всех типов страниц/таблиц образца; кириллица; переносы; длинные тексты; отсутствие placeholders; DOCX/PDF/XLSX только если заявлена поддержка формата; одинаковый candidate не генерируется заново при чтении. Файлы доступны по правам, не по угадываемому пути.

Выход: руководителю можно показать конкретный комплект. Наличие JSON с полями не является готовым приложением к КП.

## 13. Согласование и выпуск

Реализуй серверные переходы подготовки, готовности, согласования, возврата и выпуска. Руководитель подписывает candidate revision; только назначенный инженер выпускает её. Вызов API/MCP не обходит роли. Два concurrent запроса не создают двойной выпуск.

Реализуй матрицу blockers и принятия бизнес-рисков с обоснованием. Технические нарушения целостности и полномочий не обходятся risk acceptance. Новая применимая информация после согласования ставит hold на отправку до решения о применимости/нового согласования. Старое approval остаётся в истории.

Проверки: инженер напрямую вызывает approve; модель вызывает release; изменение файла после согласования; источник поступает между проверкой готовности и выпуском; повтор approve/release; отзыв/возврат; попытка выдать старое approval за новое; принятый риск не скрывает вопрос.

Выход: воспроизводимый согласованный выпуск, неизменяемые файлы, журнал автора/времени/основания, права проверены интеграционными тестами.

## 14. Яндекс Диск и сетевая папка

Реализуй два адаптера размещения на ограниченных тестовых корнях. Изучи актуальный API Яндекс Диска перед реализацией; не используй секреты в URL/логах. Выгружаются точные согласованные bytes, а не вновь сгенерированный документ.

Используй manifest, проверку содержимого доступным способом, стадирование и признак завершённости. Состояния по каждому назначению независимы. Повторные операции идемпотентны. Коллизия существующего файла другого hash — конфликт, не молчаливая перезапись. Отдельная политика для внутренних материалов; публичные ссылки по умолчанию не создаются.

Проверки: обрыв сети/SMB; потеря доступа; частичная запись; перезапуск; timeout с неизвестным результатом; существующий файл; несовпадение hash; успех одного направления и ошибка другого; вредоносный сегмент пути; заполненный диск.

Выход: VERIFIED_FIXTURE отдельно от VERIFIED_LIVE. Для окончательной приёмки нужны оба реальных тестовых назначения. Если разрешения/учётные данные отсутствуют, адаптер остаётся BLOCKED_EXTERNAL.

## 15. Отправки и полное сравнение выпусков

Реализуй ручную регистрацию отправки с подтверждением и импорт подтверждения из MailHub, если доступен нужный контракт. Сопоставляй точные вложения с manifest; несовпадение не считается отправкой утверждённого комплекта. Черновик и размещение — не отправка. Письмо об отправке не доказывает получение/принятие заказчиком.

Реализуй сравнение двух любых выпусков: источники, требования, смета/коммерческая разница, вопросы, договорные условия, решения и приложения. Отдельно покажи полученные между этапами документы, включая поздно распознанные. Для каждого вывода есть доказательство и статус причины.

Проверки: повторная отправка тех же файлов; исправленный выпуск; старый комплект в новом письме; дополнительное вложение; несколько отправленных папок; отсутствие sent-письма в общем feed; сравнение после переиндексации; новое имя того же документа; новые файлы вне области работ.

Выход: пользователь может восстановить точное состояние каждой отправки и объяснить разницу, не опираясь на текущую изменённую папку.

## 16. Чат через Codex и Cursor

Расширь/подключи общий MCP для портала, переиспользуя собственный поиск портала (этап 05). Второго MCP-сервера нет: семь инструментов Locus сливаются с инструментами ADR-010, вопрос к ответному ядру наружу не выставляется — клиент сам является моделью. Реализуй явный scope: tender, stage/release или два releases для сравнения. Ограничивай объём ответа, pagination, права и аудит инструментов. Суммы вычисляются сервером, источники имеют стабильные ссылки.

Инструменты чтения: выбрать дело, документы/цитата, смета/экономика, вопросы/решения, готовность, сравнение. Инструменты записи: только создать предложенное замечание, вопрос, условие или причину с идемпотентным request ID. Нет approve/release/send/admin или произвольного SQL/shell/filesystem.

Подготовь настройку Codex и Cursor по актуальной официальной документации; не объявляй прочитанный пример конфигурации успешным подключением. Включи сценарии проверки обоих клиентов. Если Cursor пока не установлен/недоступен, отдели проверенный протокол от live client gate. Встроенный чат из подписки не реализуй.

Проверки: неоднозначный тендер; исторический вопрос; отсутствие цены; неверный вид цены; citation не существует; инструкция «игнорируй правила» в PDF; запрос чужого тендера; запись от модели не становится решением; повторный request не дублирует замечание; секреты не уходят в result.

Выход: чат отвечает с основаниями на контрольные вопросы и может сохранять только предложения. Новая сессия не теряет историю продукта.

## 17. Сквозная надёжность и эксплуатация

Пройди сценарии `05_ACCEPTANCE_CASES.md` на сборке с согласованными интеграциями. Проверь серверные роли, конкурентность, восстановление заданий, метрики, дедлайны, временные зоны и деградацию зависимостей. Ограничь параллельные GPU-задачи; проверь взаимодействие с LM Studio/агентом MailHub без навязывания чужим приложениям управления моделью.

Подготовь установку на Windows, запуск служб без видимых лишних окон, restart/shutdown, миграцию и обновление. Выбери фактически доступный способ размещения PostgreSQL/зависимостей. Нужны backup БД+файлов, восстановление на чистом тестовом окружении и сверка manifest. Не выполняй destructive restore поверх рабочей системы.

Измерь время импорта, поиска, проверки и генерации на согласованном размере тендера. Согласуй SLO по фактам, не обещай скорость по объёму VRAM. Проверь ограничение хранилища, сбой DNS/сети, потерю токена и обработку больших ответов.

Результат: release runbook, backup/restore report, matrix passed/failed/blocked, остаточные риски. Все обязательные live-интеграции проверены или явно блокируют ввод в эксплуатацию.

Выход: техническая готовность подтверждена воспроизводимыми тестами, а не только успешной сборкой UI.

## 18. Пилот, приёмка и передача

Выбери с владельцем завершённый тендер с минимум двумя отправками, договором, ТЗ, изменённой документацией и известными решениями. Используй согласованный объём реальных данных. Не отправляй КП заказчику и не меняй исторические исходники.

До запуска составь независимый эталон известных критических конфликтов и изменений. Выполни весь цикл двумя ролями инженеров и руководителем. Зафиксируй найденное/пропущенное, ложные замечания, точность цитат, подтверждение причин цены и фактическое время ручной работы. Не подгоняй эталон под результат модели.

Минимальные ворота: все критические случаи согласованного эталона выявлены; нет выдуманных источников в принятых выводах; нет утечек между тендерами/этапами; денежная сверка проходит; одобренные файлы совпадают с размещёнными; восстановление подтверждено; нет открытых блокирующих дефектов. Другие пороги качества устанавливаются до пилота и фиксируются.

Подготовь руководства инженера/руководителя/администратора, ограничения первой версии, список внешних доработок, схему обновления и итоговую матрицу требований. Telegram и прочие необязательные расширения вынеси в backlog, не позволяй им задерживать исправление ядра.

Выход: Codex выполняет финальное независимое ревью; владелец принимает продукт либо возвращает с конкретными условиями. При блокировке интеграции, отсутствии форм или пилота итог — не «готово к эксплуатации».


## 19. Вывод Locus из эксплуатации

Заключительный этап слияния. Перенеси оставшийся корпус, прогони контрольный набор вопросов по договорам в обеих системах и сравни ответы. Без этого сравнения выключать нельзя: деградация обнаружится тогда, когда возвращаться будет уже некуда.

Зафиксируй дату, после которой новые договоры кладутся только в портал, иначе корпус разъедется между двумя работающими системами. После отключения — архив репозитория Locus, снятие автозапуска, освобождение портов и GPU.

Проверки: контрольные вопросы отвечены не хуже, чем в Locus; ни один документ не остался только в Locus; выключение Locus не ломает портал.

Выход: один сервис вместо двух.
