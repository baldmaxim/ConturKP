# Промпты независимой проверки

Codex работает в проекте портала. По умолчанию ревью read-only: не исправлять код, не менять статусы бизнес-данных, не писать в живые интеграции. Разрешены изолированные локальные тесты с фикстурами. Проверки не должны использовать production БД или реальные почтовые ящики.

## A. Независимое ревью этапа

Скопируйте и заполните параметры:

```text
Выполни независимое ревью этапа XX — НАЗВАНИЕ проекта «Контур КП».
Базовый коммит: BASE_SHA.
Проверяемый коммит: HEAD_SHA.
Отчёт Claude: docs/stages/XX-report.md.
Предыдущее ревью/принятые отклонения: ПУТЬ или «нет».

Изучи docs/spec/01_PRODUCT_SPEC.md, соответствующий раздел
docs/spec/03_STAGE_PROMPTS.md, docs/spec/05_ACCEPTANCE_CASES.md,
принятые ADR и актуальный журнал решений. Отчёт Claude является
утверждением, которое нужно проверить, а не доказательством успеха.

Сначала проверь текущий Git HEAD/status. Если дерево не соответствует
указанному коммиту, явно определи область ревью; не приписывай незакоммиченные
изменения проверяемой версии. Не откатывай и не исправляй файлы.

Проверь diff и контекст вызовов/схем/прав за пределами diff, если это нужно
для оценки поведения. Для этапов 00–01 проверяй документы и контракты,
не требуй ещё не запланированную реализацию. Для последующих — фактическое
поведение и интеграции. Найди нарушение критериев и инвариантов,
а не косметические предпочтения стиля.

Запусти необходимые безопасные проверки на изолированных данных.
Не повторяй всю дорогую матрицу без причины. Отдельно проверь негативные
сценарии и конкурентность там, где они относятся к этапу. Не используй
реальные секреты, не посылай письма и не загружай файлы в рабочие хранилища.

Особенно проверь:
- закрытый расчёт, approval, release, delivery и send не смешаны;
- фильтрация тендера/редакций/прав выполнена до поиска;
- новые данные не меняют исторические доказательства;
- цены сопоставимы по виду/единице/валюте/НДС;
- модель не подтверждает решения и не принимает полномочия;
- повтор операций не создаёт дубли, неизвестный сетевой исход обработан;
- fixtures/mocks не объявлены live-интеграцией;
- неполная обработка не даёт ложного зелёного статуса.

Для каждого дефекта дай: ID, приоритет, файл и точную строку, конкретный
триггер, фактическое и ожидаемое поведение, влияние, связанный инвариант,
минимальный способ воспроизведения. Не выдумывай дефекты ради списка.
Неизвестные и неисполненные проверки запиши отдельно от доказанных дефектов.

Заверши:
1. Вердикт PASS / PASS_WITH_LIMITATIONS / CHANGES_REQUIRED / BLOCKED.
2. Проверенные требования и критерии.
3. Дефекты по убыванию серьёзности.
4. Выполненные проверки с результатами.
5. Непроверенное и ограничения.
6. Разрешён ли следующий зависимый этап и почему.

Сохрани отчёт docs/reviews/XX-review-N.md, если запись только отчёта
разрешена в этой задаче; иначе верни полный отчёт в чат. Код не изменяй.
```

Приоритеты: P0 — немедленная опасность потери/утечки или разрушения данных; P1 — нарушение обязательного инварианта/критического сценария; P2 — существенный дефект с ограниченной областью/обходом; P3 — малая ошибка. Сам по себе номер приоритета не заменяет проверку acceptance criteria.

PASS_WITH_LIMITATIONS допустим, только если все обязательные критерии этапа выполнены, а ограничения действительно вне его обязательного объёма. Отсутствующий обязательный API — BLOCKED, а не «PASS, протестировано на mock». Любое невыполненное обязательное правило запрещает приёмку независимо от приоритета.

## B. Исправление замечаний — передать Claude

```text
Исправь подтверждённые замечания независимого ревью этапа XX:
ОТЧЁТ/СПИСОК ID. Работай в текущем этапе, следующий не начинай.

Для каждого ID сначала проверь воспроизведение. Исправь первопричину,
сохрани согласованный объём и инварианты. Добавь регрессионную проверку,
которая обнаруживает описанный дефект, где это уместно. Не ослабляй
ожидания теста и не подменяй ошибку молчаливым fallback.

Если не согласен с замечанием, приведи проверяемое основание и минимальное
воспроизведение; не помечай его закрытым единолично. Обнови отчёт этапа,
журнал дефектов и проверяемый коммит. Укажи ID → изменение → проверка.
Передай результат на повторное ревью.
```

## C. Повторное ревью — передать Codex

```text
Повторно проверь этап XX после исправлений.
Исходное ревью: ПУТЬ.
Проверенный ранее коммит: OLD_SHA.
Новый коммит: NEW_SHA.
Отчёт исправлений: ПУТЬ.

Проверь закрытие каждого замечания по поведению, не по комментарию Claude.
Изучи весь новый diff на регрессии, затронутые инварианты и критерии этапа.
Не перезапускай без причины уже подтверждённые независимые проверки.
Не исправляй код. Дай статусы CLOSED / STILL_OPEN / DISPUTED по ID,
новые дефекты, результаты проверок и итоговый вердикт. Проверь, что
доказательства относятся к NEW_SHA и что обязательные блокировки не скрыты.
```

## D. Архитектурная контрольная точка после 01

```text
Проверь архитектуру «Контур КП» до реализации. Пройди путь от новой редакции
ТЗ до закрытого расчёта, изменения светильника по письму, приложения,
согласования, размещения, отправки и сравнения следующего этапа.

Найди места, где отсутствует устойчивая идентичность, точная версия,
источник истины, транзакционная граница или полномочие. Проверь, что
LocalAI не становится второй базой решений, RDWeb не подменён локальным OCR,
MailHub read-feed не используется как полный sent-архив и чат не требует
неподдерживаемого API подписки. Сформулируй только исправимые замечания,
подкреплённые конкретным сценарием. Не выбирай другой стек из предпочтения.
```

## E. Финальная независимая приёмка после 18

```text
Проверь готовность «Контур КП» к эксплуатации по всему пакету требований.
Коммит/сборка: RELEASE_SHA. Отчёт пилота: ПУТЬ.

Сопоставь каждое обязательное требование с реализацией, тестом и результатом
пилота. Проверь существующие отчёты ревью и незакрытые дефекты. Самостоятельно
воспроизведи критический путь на изолированном наборе: новый документ →
RDWeb/import → поиск версий → закрытый расчёт → конфликт → приложение →
approval → release → два назначения → send evidence → сравнение.

Особенно проверь гонку новой информации перед выпуском, невозможность
подменить одобренный файл, отказ неуполномоченному пользователю и восстановление
из backup. Для реальных интеграций используй уже согласованные тестовые цели
и не выполняй внешних действий сверх разрешённого объёма.

Не принимай продукт по screenshots, числу тестов или словам «все этапы done».
Отдели код, fixture-проверки, live-проверки и бизнес-пилот. Итог:
READY / READY_WITH_EXPLICIT_LIMITATIONS / NOT_READY, список обязательных
условий перед эксплуатацией и фактически подтверждённый объём.
Если обязательный сценарий не проверен, не ставь READY.
```
