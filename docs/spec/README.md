# Контур КП — пакет разработки портала

Версия пакета: 1.0. Дата: 2026-09-17.

Рабочее название: **Контур КП**. Описание: «От исходных данных до согласованного предложения». Техническое имя проекта: `kontur-kp`. Название рабочее, без проверки уникальности бренда.

Пакет подготовлен по обсуждению с владельцем процесса. Разработчик — Claude Code с выбранной пользователем моделью Opus 5; независимая проверка — Codex в отдельном проекте. Пакет не утверждает доступность конкретной модели и не требует API облачной модели для работы портала.

## Как начать

1. Создайте отдельную папку и Git-репозиторий портала. Поместите туда содержимое этого пакета в `docs/spec/`. Не создавайте портал внутри репозитория LocalAI.
2. Добавьте этот же репозиторий как проект Codex для независимых проверок. Claude и Codex должны видеть один и тот же код или идентичный зафиксированный коммит. Одновременно изменяет код только один исполнитель.
3. Передайте Claude целиком `02_CLAUDE_START.md`. Он должен прочитать `01_PRODUCT_SPEC.md` и выполнить только этап 00 из `03_STAGE_PROMPTS.md`.
4. После этапа проверьте отчёт и передайте Codex шаблон независимого ревью из `04_CODEX_REVIEW.md`, указав номер этапа и точные Git-ревизии.
5. Замечания передавайте Claude через шаблон исправлений. После исправлений повторите независимую проверку затронутой области.
6. Переходите к следующему этапу после выполнения его критериев. Весь пакет не является командой выполнить все этапы за один запуск.

Пользователь остаётся владельцем требований. Подтверждённые изменения требований записываются в журнал решений и спецификацию, а не остаются только в чатах.

## Состав

| Файл | Назначение |
|---|---|
| `01_PRODUCT_SPEC.md` | Полное описание продукта и обязательных правил |
| `02_CLAUDE_START.md` | Начальный промпт, порядок работы и отчётности |
| `03_STAGE_PROMPTS.md` | Задания этапов 00–18 с проверками и условиями завершения |
| `04_CODEX_REVIEW.md` | Независимая проверка, исправления, повторная проверка и финальная приёмка |
| `05_ACCEPTANCE_CASES.md` | Сквозные приёмочные сценарии и оценка качества ИИ |
| `06_TRACKER_AND_TEMPLATES.md` | Шаблоны отчётов, статусов, решений и дефектов |
| `07_INTEGRATION_DISCOVERY.md` | Что проверить у существующих систем, доработки API и открытые вопросы |
| `prompts/stage-00.md` … `prompts/stage-18.md` | Отдельные готовые к копированию задания этапов; соответствуют разделам общего файла |

## Передача между исполнителями

После каждого этапа нужны: базовый коммит, проверяемый коммит, чистота рабочего дерева, отчёт, фактические результаты проверок, перечень ограничений. Если Git-коммит недоступен, требуется сохранённый патч и точный перечень изменённых файлов; для итогового ревью предпочтителен коммит.

Codex получает задание на чтение и проверку. По умолчанию он не исправляет код, не запускает живые интеграции и не отправляет сообщения заказчику. Claude исправляет подтверждённые замечания. Рабочие документы и секреты не включаются в Git и в архивы отчётов.

## Правила перехода

- Нет перехода через дефект, нарушающий обязательное правило продукта, изоляцию тендеров, расчёт денег, неизменяемость выпуска или полномочия согласования.
- Успешный тест на фикстурах не означает рабочую интеграцию. Используйте отдельные статусы `VERIFIED_FIXTURE`, `VERIFIED_LIVE`, `BLOCKED_EXTERNAL`, `NOT_IMPLEMENTED`.
- При недоступности внешней системы разрешено продолжить независимые этапы. Интеграция и финальная приёмка остаются незавершёнными; не переименовывайте блокировку в успех.
- Не нужны повторные разрешения на обычные локальные правки и тесты в репозитории портала. Производственные записи, рассылки и изменение соседних систем выполняются только в согласованном объёме.
- Реальные КП не отправляются в ходе разработки. Испытания размещения выполняются в специально согласованных тестовых папках.

## Рекомендуемые контрольные точки

После 01 — согласована архитектура и контракты. После 06 — воспроизводимый комплект источников. После 10 — содержательная проверка расчёта. После 13 — полный цикл подготовки и согласования. После 15 — размещение и история. После 17 — сквозная техническая готовность. После 18 — проверенный пилот и решение о вводе в эксплуатацию.

Конечный результат разработки: локальный портал для двух инженеров и руководителя, рабочие интеграции в согласованном объёме, инструкции запуска и восстановления, проверенный контрольный тендер. Промпты и отчёты сами по себе результатом разработки не являются.

## Проверка самого пакета

Пакет содержит 19 этапов (00–18), 19 обязательных инвариантов и 46 сквозных приёмочных случаев. При подготовке проверены наличие файлов, последовательность этапов и UTF-8. Это проверка структуры пакета, а не тестирование будущего портала или живых интеграций.

Интеграционные наблюдения по LocalAI и MailHub основаны на чтении документации и выбранных исходников. Секреты и живые пользовательские данные не читались, соседние проекты не изменялись. Полный независимый аудит этих приложений в подготовку пакета не входит.
