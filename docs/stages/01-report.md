## Результат для пользователя

Есть проект портала, по которому можно начинать реализацию: выбран стек и состав процессов, спроектированы схема данных, переходы состояний, контракты API, адаптеров и MCP, расписаны механизмы всех девятнадцати обязательных правил, план тестирования на 46 сценариев и реестр неизвестных с владельцами. Пять сквозных случаев пройдены на бумаге и не потребовали изменения ядра. Кода портала ещё нет — это решение этапа 01.

## Непроверенное

- Код не написан: ни одно проектное решение не подтверждено работающей реализацией.
- Внешние API не вызывались; контракты X-01…X-05 — проект, не согласованный с владельцами соседних систем.
- Конкретные версии библиотек (Express, React, схемы, десятичная арифметика, MCP SDK) не зафиксированы и не проверены на совместимость.
- Способ разбора чисел JSON без промежуточного `float` выбран как требование, но не проверен тестом (этап 06).
- Транспорт и версия спецификации MCP не сверялись с официальной документацией (этап 16).
- API Яндекс Диска, способ сверки содержимого и служебная учётная запись SMB не изучались (этап 14).
- Производительность, SLO, размер хранилища и восстановление не измерялись (этап 17); на машине разработки нет GPU и мало свободного места (U-08).
- Матрица блокеров, набор уровней критичности и правило итога КП — предложения до ответов Q-09, Q-05.

## Решения и отклонения

- ADR-001…ADR-011 со статусом `proposed`: принимаются вместе с этапом после независимого ревью.
- D-004: ответы владельца (валюты `RUB`, `USD`, `EUR`, `CNY`; рабочее название на время разработки; обязательное согласование со смартфона) внесены в модель денег и план тестирования.
- D-005 (proposed): ветка `stage-01` создана от принятого `stage-00`, так как слияние в `main` не выполнялось.
- **Требует внимания ревью:** ADR-008 §4 размещает точный и полнотекстовый поиск по фрагментам в PostgreSQL портала, а не в LocalAI. Обоснование — отсутствие в LocalAI фильтра по редакциям и стабильных ID (`docs/discovery.md` §5.2) и требование полноты прохода (спецификация §12). Второй OCR и векторный индекс не создаются (C01); смысловой поиск остаётся за LocalAI после X-04.
- Изменён артефакт принятого этапа 00: `artifacts/stage-00/verify_discovery.py` теперь считает ID определёнными и в реестре этапа 01. Логика проверок не менялась, 8 сценариев по-прежнему проходят.
- Бренд и визуальная система (`BRAND.md`, логотипы) живут в ветке `design/brand` и в область этого ревью не входят.

## Передача в Codex

Область ревью: diff `cbe5bf5..stage-01` — документы проекта и скрипты проверки. Реализации ещё нет, поэтому проверяются документы и контракты (04, шаблон A, плюс архитектурная контрольная точка D).

Команды воспроизведения (из корня портала):

```bash
git diff --stat cbe5bf5 stage-01
python artifacts/stage-01/verify_architecture.py
python artifacts/stage-01/test_verify_architecture.py -v
python artifacts/stage-00/verify_discovery.py --materials <manifest.json>
```

На что обратить внимание при ревью:
1. Проходит ли путь «новая редакция ТЗ → закрытый расчёт → замена светильника по письму → приложение → согласование → размещение → отправка → сравнение» по модели без перезаписи истории.
2. Достаточно ли `content_hash` кандидата и `approval.candidate_content_hash`, чтобы согласованный комплект нельзя было подменить.
3. Не стал ли портальный поиск вторым RAG (ADR-008 §4) и не нарушает ли он C01.
4. Не требует ли какое-либо неизвестное переделки ядра вопреки `unknowns.md` §4.
5. Нет ли в контрактах адаптеров выдуманных полей внешних API: всё, что не подтверждено инвентаризацией, помечено как «проект».
