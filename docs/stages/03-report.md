## Результат для пользователя

Инженер загружает на странице этапа файлы и ZIP-архивы. Портал сохраняет каждый оригинал один раз по SHA-256 и регистрирует редакции документов:
- то же содержимое под другим именем или из другой папки — дубликат с новым происхождением;
- то же имя с новым содержимым — новая редакция, прежняя остаётся доступной.

Опасные и неподдерживаемые элементы архива отклоняются по одному, с причиной:
- `../` и абсолютные пути;
- ссылки;
- zip-бомбы и превышение лимитов;
- запрещённые типы и вложенные архивы.

Отклонённый элемент остаётся в истории, пока ему не зададут исход: повторный импорт (инженер) или решение руководителя о неприменимости.

Администратор подключает наблюдаемые папки: локальную, синхронизированную папку Яндекс Диска или сетевую SMB. Worker забирает файл только после того, как копирование закончилось. Удаление файла из папки ничего не удаляет в портале.

Задания обработки не теряются при остановке или падении worker. Статусы партий, элементов и каналов соответствуют фактам. Состав источников этапа ведётся черновиком: включение или исключение с причиной.

Каждое значимое изменение входов пишет событие барьера актуальности этапа. Данные в проверках — синтетические.

## Исправления по ревью 03-4

Ревью 03-4 закрыло R03-10, R03-11 и R03-12 и нашло R03-13: завершения задания освобождали слот GPU изменяющим CTE **до** подтверждения владения заданием. После `recoverExpiredJobs` задание уже возвращено в очередь без токена, а слот намеренно остаётся за прежним владельцем до конца защитного интервала — устаревший обработчик очищал слот и тем обходил интервал перехвата. Дефект сначала воспроизведён пятью падающими тестами (`tests/regressions-r03d.test.ts`).

| ID | Первопричина | Изменение | Регрессия (`tests/regressions-r03d.test.ts`) |
|---|---|---|---|
| R03-13 | `succeedJob`, `confirmCancel`, `failJob` (повтор), `requeueJob` использовали общий изменяющий CTE, который очищал слот независимо от результата проверки задания | владение подтверждается до любой записи: короткая транзакция в порядке `resource_slot` → `job`, блокировка и проверка обеих строк, затем освобождение слота и перевод задания; при неудаче любой проверки не меняется ничего. Операция работает и как самостоятельная транзакция (дан пул), и внутри уже открытой транзакции вызывающего (`inTransaction` в `packages/db/src/pool.ts`) | устаревшие `succeedJob`, `confirmCancel`, `failJob`, `requeueJob` — каждый возвращает отказ и не меняет слот; после всех четырёх вызовов новый GPU-захват невозможен до конца защитного интервала и возможен после; обработчик, потерявший аренду, не освобождает слот и не пишет доменный отказ через `onError` |

Наблюдение по среде: за день дважды аварийно завершались фоновые процессы PostgreSQL 18.3 на Windows (autovacuum launcher, затем launcher логической репликации) — кластер уходил в восстановление и прерывал прогон. В локальном тестовом кластере логическая репликация отключена (`scripts/pg-local.mjs`, `max_logical_replication_workers = 0`); это настройка среды разработки, кода продукта она не касается. На целевом ПК причину нужно проверить отдельно (этап 17).

## Найдено и исправлено в ходе этапа

- Сбой записи в хранилище при скане папки (ENOENT временного файла) принимался за «файл ещё копируется» — импорт молча откладывался навсегда. Теперь «нестабильным» считается только ошибка чтения исходного файла; остальное — ошибка задания. Регрессия: `intake.test.ts` «сбой хранилища при скане…».
- Повреждённый каталог ZIP прерывал разбор без следа — теперь элемент `(архив)` с отказом `corrupt` и указанием, после скольких элементов разбор прервался.

## Замечания по прогону и артефакту

- Во время одного из полных прогонов процесс autovacuum PostgreSQL 18.3 на Windows аварийно завершился (`autovacuum launcher process ... was terminated by exception 0xFFFFFFFF`), сервер ушёл в восстановление и прервал тесты. Это сбой среды, а не кода: после перезапуска кластера (`npm run pg:stop && npm run pg:start`) полный набор проходит целиком. Сохранённый лог — от успешного прогона.
- Ревью 03-2 отметило расхождение SHA-256 ZIP: локально посчитанная сумма не совпала с суммой загруженного файла (состав, размер и метка коммита совпали). В этой передаче SHA-256 считается с того же файла, который передаётся, и после расчёта архив не пересобирается; рядом с архивом кладётся файл `.sha256` с той же суммой.

## Непроверенное

- Реальная сетевая шара SMB и папка клиента Яндекс Диска; копирование Проводником Windows большого файла (блокировка на запись) — проверены изменение размера и времени и исчезновение файла, но не блокировка чужим процессом.
- Архивы объёмом в гигабайты: на машине разработки 12 ГБ свободно (U-08); проверены 1500 элементов и лимиты на малых данных.
- Реальная GPU-нагрузка: слот GPU проверен только протоколом очереди (U-05).
- Отмена загрузки большого файла из интерфейса и 413 вживую в браузере.

## Решения и отклонения

- D-008: загрузка по одному файлу на запрос; только ZIP; группировка редакций по имени файла и уникальность содержимого в тендере; наблюдаемые папки внутри `INTAKE_ROOTS`; скан папки порождает `import_accepted` (строже §1.1); удержания и инвалидация — с кандидатами; заморозка набора — этап 04; `decision` с одним видом.
- D-009: ветка `stage-03` от `7457833` по указанию владельца.
- Контракт: вместо `POST /source-sets/{id}/revisions` — `POST /stages/{id}/source-set-revisions` (набора до первого обращения нет); списки партий и документов этапа отдаются по тендеру (источники относятся к тендеру, применимость к этапу — через состав источников).
