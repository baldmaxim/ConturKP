## Результат для пользователя

На странице этапа появилась вкладка «Поиск». Инженер вводит вопрос или обозначение («АР-01», «B30», «неустойка за просрочку») и получает цитаты из распознанных документов этапа: документ, редакция, страница и лист, происхождение текста, какой поиск нашёл фрагмент, и ссылку «Открыть доказательство» на участок оригинала. Искать можно по текущему составу этапа или по зафиксированному снимку области — историческому составу, в который поздние документы и новые прогоны распознавания не входят. Если смысловой поиск недоступен (модель не подключена, не ответила, подменена), это написано прямо, а результат даёт точный и полнотекстовый поиск. Пустой результат формулируется охватом — «не найдено в области: N единиц, M страниц распознано из K», — а не «требования нет». ## Ревью 05-1: исправление R05-01

**Дефект.** Миграция 0009 запрещала `UPDATE`/`DELETE` единиц снимка области, но не вставку. У `kontur_app` есть `INSERT` на `evidence_scope_item`, а охранник 0009 пропускал любую включённую в основу редакцию с завершённым прогоном. Поэтому снимок состава A можно было прямым SQL расширить до A+B при прежнем `content_hash`, и исторический поиск по снимку тоже расширялся. На схеме 0009 дефект воспроизведён (см. «Проверка чувствительности» ниже).

**Как БД теперь гарантирует неизменность состава.** Правила заданы миграцией `docs/migrations/0010_evidence_scope_sealed.sql` в триггерах, а не только в правах роли, поэтому действуют для любой роли, включая владельца таблиц:

| # | Правило | Механизм | Что закрывает |
|---|---|---|---|
| 1 | Печать транзакции создания | `BEFORE INSERT` на `evidence_scope` ставит `created_xact = pg_current_xact_id()` (новая колонка `xid8`) и `created_at = now()`, значения из запроса игнорируются. `BEFORE INSERT` на `evidence_scope_item` (`evidence_scope_item_creation_guard`, срабатывает раньше охранника 0009) пропускает единицу, только если печать снимка совпадает с текущей транзакцией. Иначе — `55000` «снимок … зафиксирован — единицы добавляются только в транзакции его создания» | вставку в созданный снимок из любой другой транзакции: после `COMMIT` состав закрыт. Время начала транзакции входит в печать, потому что после восстановления из `pg_dump` номера транзакций могут совпасть. У снимков, созданных до 0010, печати нет — они закрыты для вставки |
| 2 | Сверка после каждой команды вставки единиц | `AFTER INSERT … FOR EACH STATEMENT` с таблицей переходов вызывает `evidence_scope_verify` для каждого затронутого снимка. Проверяется, что каждая включённая редакция основы представлена единицей (state-machines §5.1) и что `evidence_scope_composition_hash(id)` равен `content_hash`. Эта функция считает хэш фактического состава по формуле data-model §5 | неполный состав и хэш не того состава отклоняются сразу, состав пишется одной командой. Досрочная проверка через `SET CONSTRAINTS … IMMEDIATE` снимок не открывает |
| 3 | Сверка при `COMMIT` | отложенный constraint-триггер `evidence_scope_commit_check` (`DEFERRABLE INITIALLY DEFERRED`) на вставку снимка вызывает ту же `evidence_scope_verify` | снимок без единиц или с неполным составом не фиксируется, транзакция откатывается целиком |
| 4 | Без правки и удаления (как в 0009) | у `kontur_app` нет `UPDATE`/`DELETE`; на обеих таблицах — `forbid_mutation('immutable')` | правку и удаление строк |
| 5 | Идемпотентность и новый состав | уникальность (`stage_id`, `content_hash`) и `ON CONFLICT DO NOTHING` в `createEvidenceScope` | повтор того же состава возвращает зафиксированную строку. У другого состава другой хэш — создаётся новая строка, старая не меняется |

Уже созданные снимки миграция 0010 проверяет тем же правилом; при расхождении она не применяется.

**Код.** `createEvidenceScope` (`packages/db/src/searchScope.ts`) пишет снимок и весь состав в одной транзакции; при вызове с пулом открывает свою. Единицы вставляются одной командой `INSERT … SELECT … FROM unnest(…)`. Формула хэша в БД повторяет `evidenceScopeContentHash` из `packages/core/src/search.ts`. Их совпадение проверяет каждый тест, который создаёт снимок штатным путём: `content_hash` равен пересчёту БД.

**Параллельное создание.** До `COMMIT` снимок и его единицы другим транзакциям не видны. Вторая транзакция с тем же составом ждёт первую на уникальности (`stage_id`, `content_hash`). Если первая зафиксировалась, вторая получает её снимок (`created: false`); если откатилась — создаёт снимок целиком сама. Команда `POST /stages/{id}/evidence-scopes` вдобавок сериализована блокировкой этапа.

**Регрессии** — `tests/regressions-r05.test.ts`, 8 тестов, все PASS (`artifacts/stage-05/vitest.log`):

**Результат теста прямого INSERT в зафиксированный снимок.** Снимок создаётся штатно, в нём три единицы. Затем роль `kontur_app` прямым `INSERT INTO evidence_scope_item` добавляет две единицы, допустимые по правилам 0009: новый завершённый прогон R1b включённой редакции и новую редакцию этапа с завершённым прогоном.

- Обе вставки БД отклоняет: `SQLSTATE 55000`, «evidence_scope_item: снимок <id> зафиксирован — единицы добавляются только в транзакции его создания».
- Та же вставка от владельца таблиц (`kontur_migrator`) отклоняется так же.
- `UPDATE` и `DELETE` единиц: от владельца — «операция … запрещена», от `kontur_app` — `permission denied`.
- После всех попыток состав (три единицы) и `content_hash` совпадают с исходными, пересчёт БД равен `content_hash`.

**Проверка чувствительности.** Разовые прогоны на этой машине, временные файлы не коммитились:

| Сценарий | Результат |
|---|---|
| сценарий ревью прямым SQL на схеме 0001–0009: снимок из одной единицы при основе из двух, `COMMIT`, затем `INSERT` второй | дефект воспроизведён: вставка прошла, единиц стало две, `content_hash` прежний |
| тот же сценарий на схеме с 0010 | снимок состава A не фиксируется: `COMMIT` отклонён с `23514` «состав неполон» |
| мутация: без `evidence_scope_item_creation_guard` | падают 2 из 8 регрессий (прямой INSERT и вставка в новый снимок) |
| мутация: без сверки после команды | падает 1 из 8 (транзакция создания) |
| мутация: без проверки при `COMMIT` | падают 2 из 8: снимок без единиц фиксируется, и следующая команда получает его как «тот же состав» |

## Регрессионный контракт Locus: как получены пороги

Правила ранжирования `r1` уточнялись по результатам прогона донорского корпуса — это видно по истории, и честнее назвать каждый шаг, чем показать только итог. Пороги не менялись; манифест (9/8) не менялся.

| Шаг | Что изменено | Recall@5 | MRR |
|---|---|---|---|
| 1 | исходная проекция: до 2 фрагментов на чанк, расширение обзорного вопроса (правило донора) | 0,571 | 0,520 |
| 2 | `search_prepare` (кавычки-ёлочки, тире, `№`, неразрывный пробел отделяются от слов) и префикс для основ от 5 символов | 0,643 | 0,704 |
| 3 | шапка листа цитируется, только если нет совпадения в теле | 0,786 | 0,741 |
| 4 | обзорный вопрос: по одному фрагменту на чанк — ведущий пункт раздела, не нумерованный заголовок | 0,929 | 0,759 |

Шаг 2 — исправление дефекта, а не настройка: парсер `to_tsvector` при `LC_CTYPE = C` считает любой не-ASCII символ буквой, и «ООО «Стромынка»» не находило «Стромынка» (находка записана в ADR-002 и ADR-012). Шаг 3 устраняет вытеснение: повторяющаяся шапка («Дополнительное соглашение…») забирала проекцию каждого чанка допсоглашения. Шаг 4 — эвристика обзорного намерения (ведущий пункт раздела); она срабатывает только при обзорном вопросе по договору и не влияет на конкретные вопросы. Непойманное основание — «гарантийный срок» обзорного вопроса.

## Непроверенное

- **Живая модель эмбеддингов.** Смысловая ветка проверена на поддельной модели и контрактных тестах; качество с настоящей моделью, задержка и p95 векторной ветки (порог возврата к ANN, ADR-012 §8) — на целевом ПК.
- **pgvector на Windows целевого ПК.** Расширение ставится отдельно под версию PostgreSQL; проверка — этап 17 (U-03).
- **Большой корпус.** Проверено на синтетических данных до десятков документов; производительность точного перебора и полнотекстовой ветки на сотнях тысяч чанков не мерялась.
- **Настоящий экспорт RDWeb** — как и на этапе 04, только фикстура формата.
- **Смартфоны.** Headless Chromium на 390 и 360 px; реальные iOS Safari и Android Chrome — этап 17.

## Решения и отклонения

- **`evidence_scope` заведён на этапе 05.** Он спроектирован на этапе 01 (R01-01), но не был создан; без него исторический режим (A10, A11, RT-01) проверить нельзя. API фиксации снимка — `portal-api.md` §2.3.
- **Режимы поиска** — `working` и `review` (снимок области); `release`/`comparison` — с выпусками.
- **Дополнительные таблицы против эскиза §4.13:** `search_index_unit` (полнота по единицам) и `integration_status` (из §4.12; сервер узнаёт доступность модели от worker, ADR-007). `fragment_index_state` ведётся для полнотекстовой системы.
- **Подготовка текста `search_prepare`** вместо смены `LC_CTYPE` базы: на Windows целевого ПК libc-локали `C.UTF-8` нет, а провайдер `builtin` классы символов парсеру не передаёт (ADR-002, «Реализация»).
- **Правила ранжирования `r1`** — см. раздел о регрессии Locus; расширение обзорного вопроса перенесено из донора (`chat-intent.js`).
- **Приоритет заданий по умолчанию 50** (ADR-004 §7a): без этого импорт стоял бы ниже пачек индексации.
- **R05-01: печать транзакции создания, а не функция `SECURITY DEFINER`.** У `kontur_app` остаётся `INSERT` на обе таблицы, но расширить или рассогласовать снимок она не может. Правило задано в триггерах, как все прочие правила неизменяемости проекта (ADR-002 §3), и действует даже для владельца таблиц — это показывает тест. Отдельная функция создания с отзывом прав ввела бы в проект новый приём, а вторую линию для владельца всё равно пришлось бы делать триггерами (ADR-002, «Реализация (этап 05)»).
- **Смена среды разработки** (Linux, PostgreSQL в контейнере, Chromium без песочницы) — описана в шапке; поведение приложения от неё не зависит, требования к целевому ПК прежние.
