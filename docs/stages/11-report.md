## Результат для пользователя

**Шаблоны и ревизии.** Руководитель ведёт шаблоны компании, руководитель тендера — шаблоны заказчика. Схема полей — файл JSON forms/1: разделы, поля «вариант», «текст», «число», «дата», «таблица», обязательность, применимость, условия несовместимости. Схема проверяется до утверждения, утверждённая ревизия неизменна. Ревизия шаблона заказчика утверждается только с основанием, отличия от прежней ревизии видны.

**Мастер заполнения.** На вкладке этапа «Приложения» приложение создаётся по утверждённой ревизии. Разделы — шаги, у каждого поля видны значение, происхождение, основание с цитатами, состояние и история правок. Быстрые действия: «Принять» (предложение системы из факта или модели), «Выбрать» (вариант или утверждённая формулировка), «Изменить», «Подтвердить», «Обсудить» (комментарий и черновик вопроса заказчику). Список незавершённых пунктов ведёт к полю; «заполнено» — только без блокирующих пунктов.

**Библиотека условий.** Участник предлагает формулировку, руководитель утверждает. Выбранная формулировка закрепляется версией; новая редакция в библиотеке видна пометкой и подтверждённый текст не меняет.

**Противоречия и устаревание.** Поля одного смысла (аванс, гарантийное удержание, сроки, гарантия…) сверяются во всех приложениях этапа и с действующими фактами документов — в одном контексте. Разные значения — противоречие у обоих полей; неизвестное — «не сверено», а не совпадение. Новое решение, редакция документа или распознавание помечают значение «устарело», текст не меняется; подтвердить значение по заменённому основанию нельзя.

**Смена ревизии шаблона.** Приложение остаётся на своей ревизии. Перенос — новый черновик: значения переносятся с пометкой «перенесено — подтвердите», отчёт показывает изменения подписи, единицы, вариантов, применимости, удалённые и новые поля.

Данные: демонстрационные формы (вымышленный текст в структуре реальных форм компании, `docs/forms/`); реальные формы компании переданы владельцем и хранятся вне Git. Модель — поддельная: проверяется механизм, а не качество.

### R11-03 — решение по требованию без собственных цитат

- Причина — неполнота исправления 0030: источники решения ограничивались его собственными основаниями, связь с требованием-предметом не раскрывалась.
- Решение закрепляет ревизию требования, на которую опирается (`decision_requirement_revision`, миграция 0031; запись решения API — текущая ревизия требования; для решений до 0031 — ревизия на момент решения). Источники решения — его основания и основания закреплённой ревизии и её кандидата; закреплённая ревизия, заменённая следующей, — `requirement_revision_superseded`. Текущей ревизией закреплённая не подменяется.
- Новая редакция ТЗ: запись по решению — `409 basis_superseded` до и после обработки события, прямая запись — `23514`; значение по решению получает отметку инвалидации (зависимость от исходных фрагментов требования и от закреплённой ревизии). После изменения требования прежнее решение значение не подтверждает, новое — подтверждает.

### R11-05 — актуальность по цепочке скопированного значения

- Основания значения версии — её собственные и всех версий-источников копии (`field_version_basis_problem`, 0031). Копия «устарела», если заменено основание любой версии цепочки или у источников копии без подтверждения есть отметка инвалидации; причина — у текущей версии (`inheritedProblem`, в интерфейсе «Основание исходного значения заменено»).
- «Подтвердить» повторяет действующие основания всей цепочки (основания исходного значения восстанавливаются); заменённое основание — `409 basis_superseded`. Вторая линия: подтверждённая копия по заменённому основанию — `23514` при вставке и в конце транзакции; «заполнено» проверяет цепочку текущих версий.
- Покрыты: обсуждение до замены документа, несколько обсуждений подряд, замена до обсуждения, перенос значения по заменённому документу; «заполнено» во всех случаях — `409`. Сохранить текст без действующего основания можно только новым вводом.

### R11-01 — косвенное основание наследует права источника

- Видимость значения считается по источникам каждого основания, а не по непосредственному фрагменту: факт графа — фрагменты, из которых он прочитан; ревизия требования и решение по требованию — замыкание закрытости этапа 08 (основания любой роли и унаследованный текст, R08-02). Основание с неопределённым источником закрыто (`packages/db/src/fieldBasisAccess.ts`).
- Те же правила — в приложении, истории поля, списке незавершённых (комментарий обсуждения) и в командах: запись по невидимому основанию и «Подтвердить» невидимого значения — `409 restricted_fragments` без текста; версия не создаётся.
- Основанием поля служит только решение по требованию: для решений других видов закрытость по графу этапа не определена (`409 decision_basis_unsupported`, вторая линия — 0030).

### R11-02 — «обсудить» не раскрывает скрытое значение

- «Обсудить» повторяет текущее значение только видимое пользователю целиком; иначе `409 restricted_fragments`, ничего не копируется и не возвращается.
- Версия, повторяющая значение другой версии (обсуждение, «Подтвердить», перенос), ссылается на неё (`value_from_version_id`, 0030): права и происхождение наследуются по цепочке. Обсуждение руководителя скрыто для инженера без доступа и после отзыва права у самого автора; перенесённые на новую ревизию значения сохраняют ограничения исходных версий. В интерфейсе — «значение прежней версии», кнопки «Обсудить» у скрытого значения нет.
- Вторая линия: обсуждение со значением и перенос без ссылки на источник или с другим значением — `23514`.

### R11-03 — актуальность исходного документа требования, решения и факта

- Миграция 0030 заменяет `field_basis_problem`: сначала сама сущность (заменённое решение, изменённое требование, состояние факта), затем каждый исходный фрагмент основания (`field_basis_source_fragments`) функцией актуальности 0027–0028 — редакция документа, письма, транскрипции, ответа заказчика, повторное распознавание, исключение из состава источников. API и оба триггера 0029, «заполнено» и признак «устарело» пользуются этой функцией.
- Новая редакция ТЗ: запись по ревизии требования и по решению на старом ТЗ — `409 basis_superseded` до и после обработки события; прямая запись — `23514`. Новая редакция договора до перестроения графа: прежний факт не предлагается, принять его нельзя, прямая запись — `23514`. Новая редакция письма — `409` по требованию из письма. Тест проверяет на всех основаниях тендера: заменённый источник всегда даёт проблему основания.
- Зависимости версии для инвалидации — от исходных фрагментов каждого основания (требование и решение раньше зависели только от себя).

### R11-04 — сумма из факта сохраняет единицу, масштаб и валюту

- Величина читается вместе с классом единицы, масштабом, валютой и видом дней (`packages/core/src/forms/quantity.ts`); в единицы поля переводится только точным сдвигом запятой внутри одной валюты: «25 000 000 руб.» → 25 для «млн руб.», «25 млн руб.» → 25 000 000 для «руб.». Другая валюта, сумма без валюты, рабочие дни против календарных, годы против месяцев — предложения нет.
- Фраза правила D-018 не содержит валюты и масштаба («Цена договора составляет 25 000 000»): они берутся из фрагмента источника сразу после фразы; не найдено — контекст неизвестен, валюта поля не приписывается.
- Показ предложения и «Принять» пользуются одним правилом: факт для поля USD не предлагается и не принимается (`409 fact_value_unavailable`). Сверка с фактом — в единицах поля: неизвестное или другая валюта — «не сверено», расхождение — противоречие. Гейт модели и принятие её предложения проверяют число в цитате тем же правилом.

## Инварианты БД (миграции 0029–0031)

1. Шаблон компании создаёт и ведёт роль «руководитель», шаблон заказчика — руководитель тендера; владелец и демо-признак неизменны.
2. Ревизия: создаётся черновиком со следующим номером; содержание неизменно; утверждает тот, кто ведёт шаблон; заказчика — только с основанием тендера.
3. Формулировка: предлагает участник с содержательной ролью; утверждает тот, кто ведёт шаблоны владельца; текст версии неизменен.
4. Приложение: по утверждённой ревизии своего тендера; «заполнено» — без пустых безусловно обязательных, перенесённых, обсуждаемых значений и заменённых оснований; «заменено» — только переносом; заменённое неизменно.
5. Поля приложения создаются вместе с ним по ключам ревизии.
6. Версия значения: следующая по полю со ссылкой на текущую; автор — участник с `application.fill`; приложение в работе; перенос — только в транзакции переноса из того же поля; формулировка — утверждённая; предложение модели — открытое этого поля.
7. Основание версии: в этапе и тендере; действующее — при вставке и в конце транзакции; принятое предложение системы и модели — с основанием.
8. Прогон предложений: создаёт участник с `application.fill` по приложению и снимку этапа; вход закрепляется в транзакции запуска; предложение пишет только выполняющийся прогон; цитата — фрагмент входа поля; принятие — с версией поля по предложению.
9. Права `kontur_app`: неизменяемые таблицы — `SELECT, INSERT`; шаблон, ревизия, версия формулировки, приложение, прогон, предложение — плюс `UPDATE`; `DELETE` и `TRUNCATE` запрещены.
10. Действующее основание (0030, R11-03): сама сущность и каждый исходный фрагмент — основания ревизии требования в любой роли и её кандидата, основания решения, фрагменты факта — по функции актуальности 0027–0028.
11. Основание-решение — решение по требованию (0030, R11-01).
12. Скопированное значение (0030, R11-02): обсуждение со значением ссылается на текущую версию поля, перенос — на версию, с которой перенесено; значение совпадает со значением источника.
13. Решение по требованию закрепляет текущую ревизию требования-предмета; закреплённая ревизия неизменна (0031, R11-03).
14. Действующее основание-решение — не заменено, закреплённая ревизия требования не заменена и подтверждена, исходные фрагменты решения и ревизии действуют (0031).
15. Подтверждённая копия значения — только по действующим основаниям всей цепочки источников; «заполнено» — без проблемы основания в цепочке текущих версий (0031, R11-05).

- Полнота кандидатов-оснований для предложений на реальных документах не измерялась.
