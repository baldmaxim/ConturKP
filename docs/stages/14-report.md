## Результат для пользователя

**Размещение после выпуска.** Выпуск комплекта сам создаёт доставки во все включённые назначения своей среды: тестовый выпуск — только в тестовые назначения, боевой — только в боевые. Размещает worker. На вкладке «Комплект», под каждым выпуском, — блок «Размещение»:
- сводка «Размещение: N из M» и, если есть Яндекс Диск, «облако подтверждено k из m»;
- подпись: «Размещено» не означает «отправлено заказчику»;
- по строке на назначение: статус («Ожидает», «Загружается», «Переносится», «Проверяется», «Размещено», «Ошибка», «Конфликт», «Исход неизвестен — сверяется», «Заменено»), папка выпуска относительно корня, набор файлов, версия путей, число попыток, последняя ошибка;
- раскрытие «Файлы и журнал»: каждый файл с размером, коротким SHA-256 и состоянием сверки; события и попытки.

**Яндекс Диск — через локальную папку синхронизации (D-034).** Портал пишет в папку внутри папки синхронизации клиента Яндекс Диска; в облако выгружает клиент. Поэтому у Яндекс Диска две отдельные отметки:
- «Проверено в локальной папке» — файлы сверены по SHA-256 и размеру;
- «Облако: не подтверждено / подтверждено». Подтверждает человек — «Подтвердить облако…» с примечанием, как проверено. Помощь — `npm run delivery:compare` для папки, скачанной из веб-интерфейса Диска.

**Действия — с причиной, только у своей доставки.**
- «Повторить…» — после ошибки, в ту же закреплённую версию путей; уже записанное сверяется, дублей нет.
- «Повторить после проверки…» — после конфликта. Портал не перезаписывает и не дописывает папку выпуска: человек убирает её или посторонние файлы, портал снова сверяет.
- «Перенаправить…» — на новую версию путей назначения; прежняя доставка и её попытки сохраняются.
- «Разместить в новые назначения (N)» — для выпуска, сделанного раньше, или после добавления назначения.

**Администрирование → «Назначения размещения».** Только администратор:
- создание назначения: тип, среда, корень, служебная папка, состав (только файлы для заказчика или все с манифестами), причина;
- «Новая версия путей…» — существующие доставки остаются на своей версии;
- «Выключить / Включить»;
- «Проверить назначение» — выполняет worker под своей учётной записью: пробная папка записывается, читается, переносится в корень и обратно, удаляется. Результат и ошибка — на карточке.

Паролей и токенов в портале нет: доступ к папкам — права учётной записи службы worker.

Смартфон 360–430 px — без горизонтальной прокрутки, длинные пути переносятся; обе темы.

## Инварианты БД (миграция 0038)

1. Доставка — для выпуска со средой, равной среде назначения; назначение активно; версия — текущая; создатель — `null` (выпуск) или участник с `delivery.manage`.
2. Набор файлов, признак готовности и папка выпуска в конце транзакции создания соответствуют выпуску и политике версии назначения (`delivery_set_check`); набор закрепляется только в этой транзакции.
3. Закреплённые поля неизменны; `row_version` растёт на 1.
4. Переходы — по §16; человеческие — только с `delivery_event` этой транзакции от участника с `delivery.manage` и с причиной.
5. `delivered` — только при всех файлах «сверен»; `delivered` и `superseded` — конечные; заменённая ссылается на заменяющую того же выпуска и назначения.
6. Облако: у сетевой папки — `not_applicable`; `confirmed` — только у `delivered` Яндекс Диска, с автором, временем и примечанием, один раз.
7. Назначение: заводит и меняет администратор; `kind` и `environment` неизменны; номер версии — следующий; указатель версии — только вперёд.
8. Версии назначения, проверки доступа, попытки, события неизменны; `DELETE` и `TRUNCATE` запрещены у всех таблиц этапа.

## Непроверенное

- Живая приёмка обоих назначений и проверка облака Яндекс Диска — **NOT_RUN** (нет доступа). Окончательная приёмка этапа — только после неё.
- Прогон на Windows — `NOT_RUN` на машине разработки. Этап добавляет работу с путями Windows: UNC и буквы дисков в проверке путей (модульные тесты ядра), `moveNoReplace` (жёсткие ссылки NTFS; на ресурсе без ссылок — запасной путь), перенос папки на занятое имя (на Windows — отказ), короткие повторы `rename` при `EPERM`/`EACCES`/`EBUSY` от антивируса и индексатора (логика повторов проверена на Linux с внедрённой платформой `win32`). Эти места — в просьбе к ревьюеру.
- Учётная запись **службы** worker: на машине разработки проверка доступа выполнялась под учётной записью разработчика. На машине проверки сценарий нужно запускать под той же учётной записью, что и служба worker.
- Реальная установка PWA и Safari — не проверялись; мобильные ширины — эмуляцией Chromium.

## Решения и отклонения

- D-034 — все решения владельца; толкование исполнителя записано в D-034: облако подтверждает человек с `delivery.manage` и примечанием. Отмены подтверждения нет: ошибочное подтверждение исправляется новой доставкой (проект §3.1).
- Уточнения реализации — проект §15.1 (общий алгоритм `placeFolder`, перенос признака без замены, «ровно файлы набора», служебная папка по умолчанию, закрепление набора в транзакции создания, `admin.delivery`).
- Боевые назначения заводятся, но доставок в них нет: боевой выпуск невозможен (Q-01/X-01, Q-05, Q-08).
- Полный путь «выпуск → размещение» в общем smoke не проходит: комплект демо-этапа до выпуска не доходит (неснимаемые блокеры этапа 13). Он проверяется интеграционными тестами и ui-check на настоящих server + worker; smoke проверяет назначения, проверку доступа worker и алгоритм размещения сценарием живой проверки в режиме `--fixture`.
