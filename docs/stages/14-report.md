## Результат для пользователя

**Размещение после выпуска.** Выпуск комплекта сам создаёт доставки во все включённые назначения своей среды: тестовый выпуск — только в тестовые назначения, боевой — только в боевые. Размещает worker. На вкладке «Комплект», под каждым выпуском, — блок «Размещение»:
- сводка «Размещение: N из M» и, если есть Яндекс Диск, «облако подтверждено k из m»;
- подпись: «Размещено» не означает «отправлено заказчику»;
- по строке на назначение: статус («Ожидает», «Загружается», «Переносится», «Проверяется», «Размещено», «Ошибка», «Конфликт», «Исход неизвестен — сверяется», «Заменено»), папка выпуска относительно корня, набор файлов, версия путей, число попыток, последняя ошибка;
- раскрытие «Файлы и журнал»: каждый файл с размером, коротким SHA-256 и состоянием сверки; события и попытки.

**Яндекс Диск — через локальную папку синхронизации (D-034).** Портал пишет в папку внутри папки синхронизации клиента Яндекс Диска; в облако выгружает клиент. Поэтому у Яндекс Диска две отдельные отметки:
- «Проверено в локальной папке» — файлы сверены по SHA-256 и размеру;
- «Облако: не подтверждено / подтверждено». Подтверждает человек — «Подтвердить облако…» с примечанием, как проверено. Помощь — `npm run delivery:compare` для папки, скачанной из веб-интерфейса Диска.

**Действия — с причиной, только у своей доставки.**
- «Повторить…» — после ошибки, в ту же закреплённую версию путей; уже записанное сверяется, дублей нет.
- «Повторить после проверки…» — после конфликта. Портал не перезаписывает и не дописывает папку выпуска: человек убирает её или посторонние файлы, портал снова сверяет.
- «Перенаправить…» — на новую версию путей назначения; прежняя доставка и её попытки сохраняются.
- «Разместить в новые назначения (N)» — для выпуска, сделанного раньше, или после добавления назначения.

**Администрирование → «Назначения размещения».** Только администратор:
- создание назначения: тип, среда, корень, служебная папка, состав (только файлы для заказчика или все с манифестами), причина;
- «Новая версия путей…» — существующие доставки остаются на своей версии;
- «Выключить / Включить»;
- «Проверить назначение» — выполняет worker под своей учётной записью: пробная папка записывается, читается, переносится в корень и обратно, удаляется. Результат и ошибка — на карточке.

Паролей и токенов в портале нет: доступ к папкам — права учётной записи службы worker.

Смартфон 360–430 px — без горизонтальной прокрутки, длинные пути переносятся; обе темы.

## Исправление Review 14-1

Регрессии написаны по сценариям ревью до правки продукта: на `8c6cb90` 9 сценариев падали на утверждениях дефектов, 3 контроля проходили (`artifacts/stage-14/regressions-14-before.log`). Подробно — проект §15.2.

### R14-01 — внутренний манифест выпуска выгружался в обход права на его основания

- Сценарий ревью: принят риск по замечанию с основанием из закрытого письма; инженер 2 видит комплект, но не письмо — манифест выпуска ему закрыт (409), а «Разместить» во внутреннее назначение давало 201, worker записывал `release-manifest.json` с закрытой причиной.
- Исправление: внутренний набор — только тому, кто сейчас читает манифест выпуска. При выпуске внутренние назначения пропускаются, если выпускающий манифест не читает (аудит — `deliveriesSkipped`); «Разместить» их пропускает, пропущено всё — `409 restricted_basis`; повтор и перенаправление на внутреннюю версию — `409 restricted_basis`; worker перед записью перепроверяет текущее право того, кто запросил размещение, иначе `RESTRICTED_BASIS` без записи.
- Регрессии (`reviewRegressions14`): выпуск инженером без права, «Разместить», отзыв права между заказом и выполнением, повтор без права и с правом, перенаправление на внутреннюю версию.

### R14-02 — запасной перенос заменял чужой признак готовности

- Исправление: перенос без замены — только жёсткой ссылкой; без неё — `NO_ATOMIC_MOVE` без повторов, признак не записан, чужие байты целы. «Проверить назначение» переносит пробный файл жёсткой ссылкой и сообщает то же заранее.
- Регрессии (`reviewRegressions14Fs`): сценарий ревью (ссылки недоступны, чужой признак на границе переноса), размещение и проверка доступа без ссылок; контроль `EEXIST`.

### R14-03 — junction обходил запрет служебной папки внутри синхронизации

- Исправление: до любой записи сверяются разрешённые пути и идентичность (dev + ino) каждого родителя; служебная папка Яндекс Диска физически внутри корня, корень внутри служебной папки — `INVALID_PATH`.
- Регрессии: адаптер (`reviewRegressions14Fs`: размещение, проверка доступа, корень внутри служебной у сетевой папки, контроль) и API с worker (`reviewRegressions14`: «Проверить назначение» и размещение). На Linux вместо junction — символическая ссылка на каталог; на Windows тест создаёт junction.

### R14-04 — очистка в тесте конфликта на Windows

- Исправление: удаляется только известный файл и пустая папка, результат проверяется. На Linux поведение не воспроизводится — проверка на Windows за ревьюером.
